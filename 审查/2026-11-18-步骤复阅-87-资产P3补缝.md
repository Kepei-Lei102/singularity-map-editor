## P2：start 窗口 allow 撤掉会停整批，而不是跳过这个 key

`assets.ts:111-115`：

```ts
if (!started) {
  if (startRevoked) await fail(key, 'forbidden');
  if (startAborted) continue;
  return;
}
```

`startRevoked` 分支发完 forbidden 后**没有 `continue`**，直接落到 `return`。同批 32 个 key 里，只要当前 key 在 start 的 `paced` 等待期间 allow 被撤掉，后续仍允许的 key 一个都不会发，玩家只能等 30/120 s 超时。

**复现（probe）**：先用一个 key 把全局 `nextAssetAt` 推到未来，再 `serve(['a','b'])`；`a` 的 `load` 里 5 ms 后撤掉 `a` 的 allow，`meta` 仍允许 `b`；结果只发：

```
asset-fail:a
```

`b` 没有 start/chunk/end。把 `startRevoked` 后补 `continue` 后，`b` 正常 start/chunk/end。

**为什么测试没抓到：**新 test 26“load 后 allow 被撤掉”是在 `load` 里就撤 allow，`assets.ts:102` 的 load 后检查先 `fail + continue`，**根本走不到 `startRevoked`**。它只覆盖 load 后、start 前的静态检查，不覆盖 start 的 paced 回调窗口。

**修复：**

```ts
if (!started) {
  if (startRevoked) { await fail(key, 'forbidden'); continue; }
  if (startAborted) continue;
  return;
}
```

并加多 key 测试：把 `nextAssetAt` 先推远，`a` 在 paced 等待里撤 allow，断言 `b` 仍有 start/end。

## 焦点 1：start 窗口

- `startAborted`（cancel）只 `continue`，正确：正常 reset/timeout 的 pending 已清；同批后续 key 继续。
- `startRevoked`（allow 撤掉）应 `fail forbidden` 后 **continue**；现在是 `return`，**P2**。
- `send(start)` 本身返回 false 才 `return`，正确（peer 没了）。
- `paced` 回调里查 `isCancelled`/`meta` 与外部检查有冗余但无冲突；检查到 `send` 之间是同步，不加 await，窗口已收窄到一次同步调用。取消/allow 恰在同步 `send` 前后到达的极端窗口仍可能发一条 start，但不会再无界扩大，属 P3。
- `startRevoked` 的 `fail` 用 `opts.meta(key)` 判 liveReason；allow 已撤时为 forbidden，符合。

## 焦点 2：end 单 key cancel

- `endCanceled` 单独标记，回调 false 时 `continue` 跳过这个 key；`send` false 才 `return`。代码语义正确。
- test 20 覆盖单 key end 窗口 cancel；去掉回调检查 1 红（20）。
- **测试缺口：**test 27 的 a/b 是在 `send(chunk a)` 里同步 `canceled.add('a')`，`assets.ts:137` 的 end 前静态检查先 `continue`，**没走到 `endCanceled` 回调**；因此 `end_return_all` 突变 0 红。需要 a chunk 后 `setTimeout` 5 ms 再 cancel、pace 20，才能让静态检查先过、回调再看到 cancel，并断言 b 有 end。
- 取消 key 时 blob 已在内存、不发；没有字节问题；跳过这个 key 后同批继续，符合预期。

## 焦点 3：reset 三处 fence

- `contentKey` 后先 `if (p.gen !== generation) return;`，再进 hash 不符分支：旧 finish 不会再 `pending.delete` 新请求的 pending。
- save catch 里先查 gen 再 `pending.delete/failed/onFail`：reset 后旧 save 抛错不会清新 pending、不会写 failed/onFail。
- `request` 的 `load` 返回后先查 gen，再 `requesting.delete`：旧 load 不会删 reset 后新请求的去重标记。
- 三处全去掉后 test 22/23 红；说明测试能咬住整体 fence。单处去掉大多 0 红，因为其他处/测试路径兜住；代码本身这三处都在。
- **save 已开始时 reset 仍写 IDB、但不再 onReady/known**：文档已写明；文件按内容哈希命名，可被后续 load 复用，P3 接受残留。

## 焦点 4：严格 start

- `chunk`/`end` 都要求 `p.started`；start 前 chunk/end 忽略，queue watchdog 继续；重复 start 直接 return，不续 inactivity。
- test 17 改成：start 前 chunk 被忽略后，start + end 必须因缺块 `read-failed`，再 reset 重新请求拼回。`chunk_no_start` 突变 1 红（17），现在咬住了。
- **测试缺口：**`end_no_start` 突变 0 红。原因是 start 前 end 若被接收，会因缺块走同一条 `read-failed` 路径，最终 `saved=0`、`fails=[['k','read-failed']]`，和“被忽略”结果一样；test 17 无法区分。若要咬住，需在 start 前发 chunk+end，断言 start 前 `fails` 为空，start 后才 fail。
- 迟到/乱序 start 找不到 pending 直接忽略；没有新问题。
