## 2. 逐项回答

### Q1：override 层挂条件是否满足作者「动作级」需求？

**是，结构上满足。** `Precondition` 移到 `src/core/types.ts:96-102`；`ObjectInteractionOverride` 新增 `range`/`preconditions`（`:105-114`）；`physicalActionError()` 按 `input.actionId` 找 override（`src/rules/physicalAction.ts:68-72`），编辑器和 RunPanel 都按动作 id 取。每个动作卡单独配，符合作者拍板的「动作 × 本物件」，不是全局 action-rules。

- `targetHasProp` 用 `object.interaction.tags` + 锁具自动属性（`physicalAction.ts:74-76`）；锁具物理/电子都能命中，思路合理。
- `actorHas` 用 `PC.tags`（`physicalAction.ts:82`）。`PC.tags` 的注释是「途径/职业」（`core/types.ts:382`），PartyPanel 的标签栏也写「途径」（`src/components/PartyPanel.tsx:63`）。**机制能跑，但语义是「角色途径」不是「物品拥有」**；`打火机` 这类标签只能先硬塞进途径栏，UI 输入框写「角色途径标签，如 打火机」本身也矛盾。文档 `docs/物理互动-动作条件-v0.3.md:36` 已承认没有物品栏、先临时写这里。列 P3，不阻断。
- `targetEnabled` 数据层支持，但公共闸门 `physicalAction.ts:66` 已先拦禁用，`checkCtx.targetEnabled` 在 `:80` 固定 `true`，所以这个条件实际不可达；属于兼容项，P3。
- `withinRange` 数据层支持，但外层 `override.range` 先于条件检查（`physicalAction.ts:71,116`）；如果 override.range 没配而默认 1 格，`withinRange: 5` 永远走不到。想要 5 格应配「距离」字段，文档 `:31` 也这么写；两套距离口径容易混淆，P3。

### Q2：无试玩时开始查非位置条件，是否违背 A 的边界？

**不违背。** A 的边界理由是「试玩外没有棋子，算不了位置/朝向」；目标状态、目标标签、发起者标签都不需要棋子。代码在无试玩时只过滤 `withinRange`（`physicalAction.ts:91-96`），仍查 `targetHasProp`/`targetStateIn`/`actorHas`；`targetEnabled` 由闸门兜底。`docs/物理互动-基座-v0.2.md` 已把口径改成「v0.2 只查启用；v0.3 起再查非位置条件」，测试 `physical-base.test.mjs:248-263` 覆盖「备团也查标签，不查距离」。

测试标题在这轮已改成「不在试玩里且不传动作 id：只查物件启用…」（`physical-base.test.mjs:81`），与当前口径一致；无试玩传 actionId 时查条件的覆盖在 `physical-base.test.mjs:248-263`。Q2 的旧 P3 文案问题也关闭。

### Q3：状态迁移「条件全丢删整条 override」是否过激？

**作为安全口径可以接受，不算过激。** `setObjectStates()` 在 `src/runtime/actions.ts:552-569` 把 `targetStateIn` 的序号随状态列表迁移；某条件所有目标状态都消失时，`:563-566` 删整条 override，而不是删条件后让动作无条件可用。作者已明确这个选择；当前模型没有「动作暂时禁用」字段，删整条是唯一稳妥做法。

P3 三点：

- 部分状态丢失时（例如 `[0,1]` 删掉 0）只把条件收窄成 `[1]`，**没有 toast 说明**；条件变严但作者可能不知道。
- 删整条会连带丢掉其他有效条件/outcomes；作者接受，但可在 toast 里说清楚「整条映射已删」。
- **与 repairWorld 现在同口径**：坏条件也删整条（见第 1 节），不再出现“正常迁移删整条、repair 只删条件”的不一致。

### Q4：schema/repair 是否漏掉坏条件、重复条件、range 边界？

**坏条件已按安全口径修复；重复条件仍未覆盖。**

- `checkWorld()` 校验：`range` 是 0..200 的 safe integer（`schema.js:622`）；`preconditions` 是列表；kind 是五种之一；`targetHasProp`/`actorHas` 非空；`targetStateIn` 非空且每个状态在 `o.states` 范围内；`withinRange.cells` 是 0..200 整数（`:623-642`）。这些边界都对。
- `repairWorld()` 对 `range` 坏值只清空（`:83-88`）；对 conditions 坏值返回 `droppedCondition`，调用方 `:202-205` 删整条 override；坏 kind、空 prop/tag、越界状态、坏 withinRange、非数组都走这条。原 P2 已关闭（见第 1 节）。
- **重复条件没处理**：`checkWorld()` 不拒绝同 kind 同值的多条条件，`repairOverrideConditions()` 也不合并重复条件；UI `splitTags`（`src/components/ObjectInteraction.tsx:54`）同样允许重复输入。`targetStateIn` 的重复状态值 repair 会去重（`w1` 测试），但重复的条件对象不会。运行时重复条件只会多报一次，不改变真假，属 P3；若以后要严格，建议 schema 对同 kind 同值的条件去重或拒绝。
- **`preconditions: []`**：`checkWorld` 接受空列表，`repairWorld` 会删掉空列表；不一致但不影响功能，P3。
- **range 边界**：0..200 在 schema、repair、UI clamp（`ObjectInteraction.tsx:87`）三处一致；`range 200` 可用，`201` repair 清空，`checkWorld` 拒绝 1.5，均正确。
- **range 坏值清理的边角**：`range=-1` / `0.5` 这类坏值在运行时本来没有合法语义，但清成默认 1 格时相对“运行时夹到 0/0.5”并不是严格收紧；正常数据不会出现，列 P3。
- 文档 `docs/物理互动-动作条件-v0.3.md:45` 已改成“坏条件删整条”，与代码一致；`:31` 仍把 `withinRange` 指向“距离”字段，容易误用，P3。

### Q5：UI 写入会把未展示的 `targetEnabled`/`withinRange` 冲掉吗？

**不会。** `setConditions()`（`ObjectInteraction.tsx:90-97`）只过滤掉**同 kind** 的条件：

```ts
const rest = (ov.preconditions ?? []).filter((p) => p.kind !== kind);
const list = [...rest, ...next];
```

`setRange()`（`:80-89`）只改 `ov.range`。我用 jsdom 探针预置了 `targetEnabled` + `withinRange:3` + `targetStateIn:[0]` + `actorHas`，再依次改目标标签、发动者标签、距离：

- 改目标标签后，`targetEnabled`、`withinRange`、`targetStateIn`、原 `actorHas` 都还在；
- 改发动者标签后，前三者仍在；
- 改距离后，所有条件仍在。

所以焦点 5 的答案是安全的。P3 有两个边界：

- UI 的 `preconditionStates()`（`:60-63`）只取**第一条** `targetStateIn`；`toggleState()` 用 `setConditions(...,'targetStateIn')` 会过滤掉**所有** `targetStateIn`。我另跑探针：预置两条 `targetStateIn`（`[0]` 和 `[1]`），UI 只显示 `[0]`；取消勾选 `[0]` 后，两条都被删，只剩 `targetEnabled`。这是「未展示的 targetStateIn 被冲掉」，与 targetEnabled/withinRange 不同，列 P3。
- 目标标签/发动者标签输入不去重，重复值会写成重复条件；schema 目前也接受，P3。

UI 不展示 `targetEnabled`/`withinRange`，所以作者无法在编辑器里删除它们；这是作者明确约定「数据层支持、UI 不另开」的结果，P3 文档提示即可。

### Q6：commit 复核是否覆盖 range/conditions 变化？

**覆盖。** `commitObjectInteraction()` 在 `src/runtime/objectInteraction.ts:33` 调 `physicalActionError({ ..., actionId: input.actionId, ... })`；`physicalActionError` 每次都会重新取 override（`physicalAction.ts:68-72`），重新算 range（`:71`）、重新查 conditions（`:130-133`）。所以预览后改范围、改条件、改目标标签/状态、改发起者标签，落账都会被拦；现有测试 `physical-base.test.mjs:265-277` 覆盖「缺目标标签不落账」，并断言 state/events 不动。

P3：没有单独测试「预览后 range 变化 / actorHas 变化」；代码路径和距离/状态测试相同，但最好补一条。另外 `actionId` 是 commit 必填（TS 类型），生产调用 `ObjectInteraction.tsx:264` 已传；若 JS 外部调用漏传，会退化成无条件默认 1 格，属 P3 防御性校验。

## 4. P3 清单（均不阻断；P2 已清零）

1. **两套距离口径**：`withinRange` 条件在默认 range 1 下无法放宽；想要更远必须在「距离」字段配。文档已提示，但容易误用。
2. **actorHas 的语义**：`PC.tags` 现在只是途径/职业，`打火机` 等物品标签临时塞进途径栏；UI placeholder「角色途径标签，如 打火机」应改成更诚实的文案，未来接物品栏。
3. **重复条件/重复标签**：schema/repair/UI 不合并重复条件对象；`targetStateIn` 的重复状态值 repair 会去重。运行时只会重复提示，不改变真假；可后续 dedupe 或拒绝。
4. **UI 多条 targetStateIn 被状态勾选冲掉**：`preconditionStates` 只看第一条，`toggleState` 过滤全部；未展示的额外状态条件会丢（我探针复现）。
5. **状态条件部分丢失无 toast**：只收窄不提示；删整条时也没说明丢掉的其他条件/outcomes。
6. **`withinRange` 文档口径**：`:31` 说“用距离字段配”，但 UI 实际写的是 `range` 不是 `withinRange`；容易误以为 UI 会写入条件。
7. **repair 提示在浏览器被丢弃**：`parseWorld()` 只 `repairWorld(w)` 不展示 notes；现在坏条件会静默删整条映射，建议把 notes 提示给作者。
8. **range 坏值清理边角**：负数/小数 < 1 的坏 range 清成默认 1 格，相对运行时夹到 0/0.5 不是严格收紧；坏值无合法语义，P3。
