## 测试夹具

- `heldIDBKeys/heldIDBRequests` 是全局的，host/player 两套 fake IDB 共享；但 watchdog 测试只 hold `k1`，host 侧 `getRaw(k1)` 被 hold，player 侧 receiver 的 `load` 是 `async () => undefined`，不会碰 IDB；`save` 在 release 后才跑。当前用例不会串到玩家侧。
- `__releaseIDB` 删除 held key、取 run、删除 map、执行 run；释放后 fake IDB 请求继续并触发 transaction complete。hold set 在成功路径会清；**失败路径没有 `finally` 清理**，若测试在 release 前失败，held key 会留到进程结束（本文件只有一个大 test，影响有限）。
- `setTimeout` 包装只改 `ms===60_000`/`ms===120_000`，其它毫秒原样；fake IDB 的 0ms、waitFor 的 20ms、pacer 的 20/45ms 不受影响。server 的 60s 是 `setInterval`，不会被替换。测试成功后会恢复；**失败路径没有 `try/finally` 恢复**，会污染同一进程后续用例（本文件只有一个 test，但仍是测试卫生问题）。
- `heldIDBRequests` 以 key 为键，同一 key 多个 hold 请求会互相覆盖；当前只有一个 host get。

## watchdog 测试

- `__holdIDB('k1')` 后发 r-flow-hang；`players===1` 证明 flow 创建；`players===0` 只能来自25ms watchdog（load 被 hold 不 resolve）。release 后断言该 requestId 无任何消息；serve 的 `flowAborted` 使 load resolve 后直接收尾，**测试能咬住**“watchdog 后还发 start/chunk/end/fail”。
- **但没有断言 `AssetSession` active 已 release**：测试只看 players；若 finally 漏 release，本测试仍过，后续 cap 测试也不一定触发64上限。`session.release` 目前靠 deployment 源码守卫兜底。
- **没有覆盖 fail 路径**：release 后 load 返回 Blob（不是 reject），只验证 abort 后成功 load 静默；load reject 后 abort 静默未测。
- **断言“完全无消息”锁定当前“watchdog 不发 fail/cancel”的实现**；如果以后想给玩家发 cancel，这个测试会红，需要同步改。
