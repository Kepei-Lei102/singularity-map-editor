## 51 P2 复检

### 攻击面：三类都堵住

- `consent.ts:5-10`：`handlePlayerDecision(m, actorPcId)` 先认 castId/step，再
  `if (!actorPcId || actorPcId !== c.actorPcId) return false;`。
- `consent.ts:15-19`：`listenPlayerDecisions` 不再只传 `m`，而是
  `listen((m, _source, from) => handlePlayerDecision(m, from ? pcIdForBinding(from) : null))`。
  `from` 是 transport 认出来的 binding，不是消息里的 `m.from`。
- `sync.ts:322-324`：`pcIdForBinding` 只查 host 的 `players` 映射：
  `players.get(binding)?.pcId ?? null`；不读消息自报字段。
- `transportLocal.ts:47-50`：`bindingFor` 只按 `peers` 里的 Window 身份反查；
  未知 source / cross-origin window / BroadcastChannel 的 `source=null` 都返回 null。
  `:117` host 的 `CROSS_ORIGIN_FROM_PLAYER` 只是放行传输层，不改变来源。
- 实测（host bundle，pc/other 两个真实玩家窗口，`listenPlayerDecisions`）：
  - `source={}`、origin=player、`m.from='pc'` 的 attacker → cast 仍 `approval`；
  - `source=null`、`m.from='pc'` 的 BroadcastChannel 式消息 → 仍 `approval`；
  - 绑了 `other` 的真实窗口、`m.from='pc'` → 仍 `approval`；
  - 真实 `pc` 窗口、故意把 `m.from` 写成 `'other'` → cast `confirm`（传输层身份优先，
    消息自报无效）。
- 正常 pc 仍为 `true`：`consent.test.mjs:71-72` 和 `skills.test.mjs:136` 都覆盖。
- 结论：51 的 P2 主路径关闭；`source=null` 的 skill-decision 现在是 null → false，
  不会再冒充 host。

### `bindPeer` closed 接管是 P3 边界，不是 52 的 P2 回归

- `transportLocal.ts:39-44` 仍允许旧 window 已关后，新 source 接管同一 binding；
  `sync.ts:542-544` 的 hello 路径会 `bindPeer`。
- 实测：host 开 pc 窗口，关掉；attacker 带 pc binding 发 hello，`bindPeer` 返回 true；
  随后 attacker 发 skill-decision，cast 仍能被推到 `confirm`。
- 这要求 attacker 知道一个已关闭 binding，且 binding 本身就是 URL 里的 bearer 凭据；
  没有绑定凭据的未知窗口仍是 null → false。按 P3，归到 51 P3.4 的同一边界：
  “关窗是否等于撤销”没有定义。若产品把关闭窗口当撤销，应升 P2；当前不阻塞。
- 不是 52 引入的：52 只把 `from` 接到 consent，`bindPeer` 行为未改。

### P3-2 `bindPeer` closed 接管（51 P3.4 延续）

- 见上：旧窗口关闭后，新 source 只要知道 binding 就能接管，`from` 会变成该
  binding，`pcIdForBinding` 返回对应 pc，consent 会通过。
- 这是 bearer 凭据的接管，不是未知 source 绕过；没有绑定凭据的 attacker/other/null
  仍被拒。建议：关闭即撤销 binding，或 closed 替换只允许同一 WindowProxy / 明确
  主持端重连，并在 docs 说明。按 P3，不阻塞。

### P3-3 `pcIdForBinding` 只到 pc，不到 context / peer

- `pcIdForBinding` 只返回 `players` 里的 pcId，不检查 `sameContextWindow`；
  同一个 pc 的 trial 窗口和 real 窗口都能通过 actor 检查。若 trial/real 的 cast
  必须隔离，这会让 trial 窗口替 real 的 approval 点头（同一玩家，影响有限）。
- `bindingFor` 是 peers 线性扫描，若同一个 source 被绑到多个 binding，返回第一个；
  `pcIdForBinding` 随之取第一个 pc。当前只由 hello/refresh 产生，未观察到误认，
  但多绑定边界没有测试。
- `pcIdForBinding` 不检查 `hasPeer`；`from` 只可能来自 `bindingFor`，所以当前
  saved binding 不会成为 from；WsTransport 接入后应保证 `meta.from` 也只来自
  房间连接。按 P3。
