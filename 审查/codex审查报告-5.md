## 第二部分：新发现

以下既包括本次回归，也包括本轮新确认的残留问题。

### 1. P1 — 会话最终换号，仍不能阻止裁决前的信息串场

**`src/sync.ts:149`、`src/sync.ts:190`、`src/sync.ts:222`**

编辑器等待 250ms 后即可发送数据，而玩家只比较 `from`，不检查新增的 `inst / born`。

**具体触发：** A 与玩家窗口已经绑定会话 S；复制编辑器得到 B，在 B 使用另一份世界后，让冲突消息处理延迟超过 250ms。B 开始用 S 推送，玩家立即接受 B；之后冲突处理才使 B 换号。

**后果：** 内存消息调度复现了玩家收到 **A → B → A**。重新推送 A 无法撤回已经展示的 B 内容；错误播放也不会因重推世界自动停止。

**建议：** 玩家绑定已确认的编辑器实例，并提供明确的刷新交接机制；所有权尚未确认的实例不能仅凭短超时开始发布。

### 2. P2 — 媒体读取失败时提示“导入失败”，实际上世界已经替换

**`src/actions.ts:623`、`src/actions.ts:625`**

检查缺失媒体的读取被移到了 `commitImport()` 之后。

**具体触发：** 导入带媒体引用的 JSON，或部分媒体缺失的 ZIP；让提交后的某次 `getRaw()` 因存储异常失败。

**后果：** 已复现当前世界变成 B、撤销历史被清空，却显示“导入失败”；后续 `setUI()` 没执行，界面状态也没有完成切换。用户若据此重试，还可能用 B 覆盖原先保存 A 的导入前备份。

**建议：** 提交前完成媒体可读性检查并算好缺失清单；提交后只执行不会失败的状态切换，不能把已成功提交报告为导入失败。

### 3. P2 — 新增的目标存在检查使玩家窗口无法平移新地图

**`src/components/MapCanvas.tsx:249`**

平移处理之前，代码要求地图存在于模块级 `getWorld()` 中；玩家实际显示的是通过消息收到的 `world` 属性。

**具体触发：** 先打开玩家窗口，再在主持人端新建／导入地图并推送；玩家窗口本地 store 没有该地图 ID，此时拖动画面。

**后果：** 每次移动都会进入 `gone()`，平移被取消。使用实际组件事件处理器的内存验证得到视图未移动、拖动已取消。

**建议：** 先处理不依赖编辑器世界的平移分支；只有编辑物件、棋子等操作才查询 `getWorld()`。

### 4. P2 — 未完成的导入会覆盖用户后来明确切换的新世界

**`src/actions.ts:596`、`src/App.tsx:143`**

`exclusive` 没有覆盖“新建空白世界／载入示例”，提交时也不检查操作是否仍属于当前世界。

**具体触发：** 开始导入 B，在读取或哈希尚未结束时新建 C 并编辑；随后 B 的导入完成。

**后果：** 已复现当前世界从编辑后的 C 跳回 B，C 的历史被清空。C 尚能通过导入前备份找回，但用户后作出的世界切换被较早操作覆盖。

**建议：** 为世界替换维护操作代号；主动新建或载入示例时使旧导入失效，或者在导入期间明确禁止这些入口。

### 5. P2 — 试玩中的异步上传能在退出后写入正式工程

**`src/components/MediaPanel.tsx:19`**

上传完成后直接调用 `update()`，没有核对开始上传时的世界或试玩身份。

**具体触发：** 试玩中上传较大媒体，在哈希／存储完成前退出试玩；随后上传完成。上传期间切换工程也有同类问题。

**后果：** 使用实际上传回调和延迟存储替身，复现了试玩已退出、正式世界却新增媒体记录。该记录还会正常进入自动保存。

**建议：** 上传绑定世界及沙盒操作代号；完成时上下文已经变化就取消挂接，不能将结果写入当时恰好处于活动状态的世界。

### 6. P2 — 导入换世界不会取消旧世界尚未完成的同步播放

**`src/actions.ts:97`、`src/actions.ts:603`**

播放序号在停止及试玩切换时失效，在工程替换时没有失效。

**具体触发：** A 中开始同步播放媒体 m，延迟其读取；导入同 ID、不同内容的 B；最后让 A 的读取完成。

**后果：** 已复现主持人当前世界及媒体预览指向 B，玩家却收到 A 的存储名和 Blob。新存储设计保证读到了准确的旧版本，但缺少上下文检查使它在错误时机发出。

**建议：** 世界替换时取消待发播放，并明确停止／清空原播放；异步回调同时校验播放序号和世界操作代号。

### 7. P2 — 补齐缺失媒体后，已经打开的预览仍永久显示“载入中”

**`src/media.ts:119`、`src/media.ts:121`、`src/actions.ts:587`**

新增文件后没有通知媒体订阅；预览只依赖媒体 ID、存储名、传入 Blob 和版本号。

**具体触发：** 导入带 `key`、但本地缺少文件的 JSON，并打开该媒体；随后导入包含相同媒体及相同 `key` 的完整 ZIP。

**后果：** 文件已经存在，但上述依赖都没变化，读取不会重试。内存 hooks 验证中补齐后 URL 仍为 `null`；显式触发 `mediaChanged()` 后才正常取得 URL。

**建议：** 新文件成功提交后通知相应存储名的订阅者；保留按存储名缓存，同时处理“原先不存在，现在存在”的变化。

### 8. P2 — 旧数值修复遗漏玩家记忆，仍拒绝编辑器旧版生成的工程

**`src/schema.js:94`、`src/schema.js:120`**

`repairWorld()` 只修实时物件，没有修 `map.seen.objects` 和 `map.views[*].seen.objects`。

**具体触发：** 旧版将物件高度设成 1001，玩家看见过它，存档中因此同时有实时物件及记忆快照；用新版导入。

**后果：** 已复现实物高度被夹到 1000，随后校验仍因 `seen.objects[0].height === 1001` 拒绝工程。宽高越界／小数快照也有同类缺口；浏览器导入和命令行读取均受影响。

**建议：** 对实时物件、共享记忆及个人记忆复用同一套数值修复，保留其各自的历史内容并报告修复项。

### 9. P2 — NPC 明确提供的新子项 ID 仍可能被旧 ID 覆盖，错误继承进度

**`src/npc.ts:142`、`src/npc.ts:145`**

显式 ID 找不到旧项后，仍继续按结果名称或近况文字匹配，与“有 ID 按 ID”的规则不一致。

**具体触发：** NPC 已完成近况 `{id:"old", text:"来访"}`；导入同名 NPC，其中换成新的近况 `{id:"new", text:"来访"}`。结果项使用同名标签时也一样。

**后果：** 新项被改回 `old`，旧完成记录被错误沿用，新近况直接视为已经讲过。内存验证也确认新结果 ID 被改回旧 ID，保留原判定且没有警告。

**建议：** 只让没有显式 ID 的项按文字匹配；显式新 ID 应保留为新项，失去对应项的旧进度按现有警告机制处理。
