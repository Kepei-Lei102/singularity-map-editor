### P1（2 条）

#### P1-1 单次地形/小格编辑仍全量重算：非批量 152.5–222ms；一次单击的批量收尾 133.5–208ms

修复后的实测（200×200，30×30 fixture 与 200×200 浏览器页各一组）：

- **非批量单次**：`store.update` 地形一格 **152.5ms**（本轮无队伍 fixture；lead 的有队伍基准为 **222ms**）。
- **批量 50 格**：`store.update` 平均 **2ms**（lead 有队伍基准平均 **11ms**，max 20.3ms）；`endBatch` **133.5ms**（lead **208ms**）；总账 **234ms**（lead **约 0.75s**）。这部分确实明显改善。
- **一次单击**：`MapCanvas` 在 pointerdown 就 `beginBatch()`（`src/components/MapCanvas.tsx:267/325/329/341/349`），松手 `endBatch()`；单格单击的收尾仍是 **133.5–208ms** 的整图补算。也就是说，**“拖动 50 格”通过，“单次编辑 <100ms”没有通过**。
- 这说明批量方案只是把 N 次全量摊成 1 次全量；**单次操作的成本没有下降**，只是拖动时不再每格卡。

判定口径建议：

- 如果验收标准是“连续画一笔不逐格卡”，**通过**。
- 如果验收标准是原审阅里的“单格编辑 0.23–0.27s 要降下来”，**未通过**；单次依旧 0.13–0.22s。

不是本轮新引入的错算：单元测试覆盖了拖动中 `observationSeq`/`fog` 不变、松手 `seq+1`、fog 重写、仍一步撤销；这些行为实测成立。问题只是**验收目标只覆盖了“批量”**。

#### P1-2 批量延后只认 `plan.full`：材质/贴图组画笔仍每格扫全图记忆

实测（200×200，浏览器 dev 页）：

- `paintMaterialCells` 连续 5 格：**129.2 / 124.8 / 124.5 / 125.2 / 125.0ms**，`endBatch` 0ms，总 **628.7ms**；按这个量级 50 格约 6.2s。
- `paintCellGroup` 走同一条 `structure`/`memoryDirty` 路径：`mapStructureChanged` 为真，但 `visionStructure` 为假，`plan.full` 为假；因此同样不会进入批量欠账，仍每格 `syncMemory`。
- 对照：`nudgeHeight` 一格 **2ms**（高度不在 `memoryDirty` 里）；雾笔第一格 135ms 后，因为地图被标记为手动雾，后续 `plan.full` 变真而进入欠账，5 格连 `endBatch` 约 271ms。

原因：

- `update` 只在 `plan.full` 时设 `batchVisionDeferred`（`src/core/store.ts:167-169`）。
- 材质/贴图组只触发 `memoryFullMaps`，不触发 `visionFull`（`src/scene/visionPlan.ts:37-39`；`src/scene/dirty.ts:84-91` 的 `mapStructureChanged` 包含材质/组，但 `mapVisionChanged` 不包含）。
- 每次 update 仍执行 `syncMemory(d, plan)`（`src/core/store.ts:164-172`），`syncMemory` 在 `memoryFullMaps` 命中时走无 scope 的全量扫描（`src/scene/memory.ts:223-234`、`:130-131`）。

推荐修法：

- 把欠账条件从 `plan.full` 扩展到 **`plan.full || plan.memoryFullMaps?.size`**；`endBatch` 不要无条件 `withVision(..., { full: true })`，而是先算 `finalPlan = planVision(world, diffWorld(base, world))`，再 `withVision(world, base, { plan: finalPlan })` + `syncMemory(d, finalPlan)`。这样材质/组只补记忆、不额外跑视野，也不会因为 `full:true` 强行套自动迷雾。工作量约 **0.5–1 天**，风险中等（要保证手动雾/autoFog 语义不被改变）。
- 材质/组画笔在 `MapCanvas` 里也有批量入口，修好 store 的欠账条件即可覆盖主要路径。
- 这不是 P1-1 原句里的“地形”，但严重度同级；如果只验收地形，可作为独立 P2 排期，但不能说“画笔都不卡了”。

### P2（3 条）

#### P2-1 “改画笔值不再触发 fillRect”未达标：仍 40,004 次 `fillRect` / 一次重绘

浏览器实测（200×200，806×857，编辑模式）：

| 操作 | `fillRect` 次数 | 结果 |
|---|---:|---|
| 改 `world.name` | **0** | 通过 |
| 改无关 UI（`tab`） | **0** | 通过 |
| 改 `ui.brush`（无 hover/preview） | **40,004** | **未通过** |
| 改地图一格地形 | **40,004** | 通过（应重绘） |
| 改 `ui.selection` | **40,004** | 通过（选择框应重绘） |
| 初始加载绘制 | **40,011** | rAF 初次绘制正常 |

原因：

- 绘制 effect 依赖里仍有 `ui.brush`（`src/components/MapCanvas.tsx:153`）；`ui.brush` 只在实际有 hover/preview 时才影响画面（`src/scene/render.ts:894-898`），无 hover 时改画笔值不应重画。
- `MapCanvasImpl` 自己 `useUI()`（`:66`），所以即便父组件被 memo 跳过，改 `ui.brush` 仍会让它重渲染并让 effect 重跑；memo 不能解决这条依赖。
- rAF 合并是有效的：同一 task 里连改 10 次 `ui.brush`，实测只有 **54,811 次 `fillRect`（一次绘制）**，而不是 10 次 40k；问题不是“没合并”，是“本来不该画”。

推荐修法：

- 把画笔依赖改成条件依赖：只有 `hover || preview` 存在时才把 `ui.brush` 放进依赖；或在 effect 内用 `hover/preview` 判断是否重画。工作量 **10–20 分钟**，风险低。
- 如果担心“拖动前没有 hover、第一次 hover 才用到 brush”，保留 `ui.tool`（画笔工具仍可能影响 cursor/zone 选择框），只把 `ui.brush` 条件化即可。

memo/依赖其余部分复核通过：

- `sameCanvasInputs` 覆盖的 world 字段（terrains/materials/party/labels/connections/npcs/marks/viewerId/visionMode/visionGroups）和 map/mode/viewer/follow/cursor/onCellClick 都是画面相关字段（`src/components/MapCanvas.tsx:53-61`）；未覆盖 `world.flows`/`log` 等非画面字段，可接受。
- 选择、预览、悬停、雾、编号、坐标尺、小格、贴图 tick、标记 tick、尺寸、view、viewer/playerNumbers 都在依赖里（`:151-157`）；选择/地图/编号/坐标尺实测会重绘，世界名/无关 tab 实测不重绘。
- `view` 的 `useMemo` 稳定了无 stored view 时的 fallback（`:73-75`）；rAF cleanup `cancelAnimationFrame`（`:150`）正确；初始绘制实测 40,011 次，非空白。
- 未发现 memo 挡住必须的重绘或 stale 闭包；`onCellClick`/`cursor` 等非绘制字段只影响事件/样式。

#### P2-2 批量中 undo/redo 会重算出与撤销快照不一致的记忆

实测（30×30 autoFog + token）：

1. 先做两次普通更新，得到 W-1 和 W0；保存 W-1 的 `fog`/`seen`。
2. `beginBatch()`；改一格地形（进入欠账）；`undo()` 两次（回到 W-1）；此时 world 的确回到 W-1，fog 与 W-1 相同。
3. `endBatch()`：`fog` 仍与 W-1 相同，但 **`observationSeq` 从 2 变成 3**，`seen.cellRevs`、`seen.observed` 与 W-1 快照不一致。

原因：

- `undo()` 只把 `batchStart` 改成当前 world（`src/core/store.ts:242`），**没有重基 `batchVisionBase`，也没有清 `batchVisionDeferred`**。
- `endBatch()` 仍以 batch 开始时的 W0 为 base，对撤销后的 W-1 调 `withVision(world, base, { full: true }) + syncMemory(d)`（`:222-230`），于是多跑一次全量，把 W-1 的 `seen` 内存改成 rev=3。
- 这不是“视觉上立刻错”，但 **撤销后的记忆状态不再是原快照**；对依赖 `observationSeq`/`seen.cellRevs`/`seen.observed` 的后续逻辑（例如陈旧记忆判定）是潜在错算。

推荐修法：

- 在 `undo()`/`redo()` 里，如果 `batching`，在设置 `world` 之后把 `batchVisionBase = world`、`batchVisionDeferred = false`，再 `emit()`；或先 `endBatch()` 再撤销，然后按需要重新开 batch。工作量约 **10–20 分钟**，风险低；必须补测试“批量中 undo/redo 后 endBatch 仍等于撤销快照”。
- 同类问题：`endSandbox()` 只清 `batching/batchStart`，不清 `batchVisionBase/batchVisionDeferred`（`src/core/store.ts:464-475`）；如果试玩结束恰好落在批量中，会留下旧 base 引用。建议一并清理。

#### P2-3 地形 + 手动雾在同一个批量里：手动雾会被自动雾覆盖

实测（30×30 autoFog，隐藏格）：

- 非批量顺序 `update(terrain)` → `paintFog(reveal)`：fog = **1**（手动雾保留，等待下一次真正视野脏动才被自动接管）。
- 同一 batch 里做同样两步：batch 中 fog = 1，`endBatch()` 后 fog = **2**（自动雾把它改写成记忆）。

原因：

- 地形先让 `batchVisionDeferred = true`；随后 `paintFog` 的 update 因为 `deferred` 为真被整体跳过，手动雾的 `manualPending` 没有机会落。
- `endBatch()` 用 `withVision(..., { full: true })`；`withVision` 里 `manualApply = manual && (otherDirty || full)` 在 full 时为真，自动雾直接覆盖；`manualPending` 只会是空集（见下）。

概率：正常 `MapCanvas` 一次拖动只有一种工具，**普通 UI 碰不到**；但 store API、组合操作、后续自动化会踩。建议在修 P1-2 时一并处理：把欠账期间的 `manualPending` 累积到 endBatch，或让 endBatch 重放手动雾的意图；并补测试。风险中等，工作量 **0.5–1 天**。

### P3（4 条）

1. **`endBatch` 的 `manualPending` 循环是死代码（静态）**：`withVision` 在 `opts.full=true` 时，`manualApply` 对 manual 位为真，`manualPending` 的两个条件都不成立（`src/scene/perception.ts:125-128`），所以 `src/core/store.ts:223-228` 永远空转。它不是性能问题，但会误导以后维护者以为 pending 已处理；建议删掉或改成真正的 pending 累积。
2. **`endSandbox` 未清 `batchVisionBase/batchVisionDeferred`**（`src/core/store.ts:464-475`）：可能留下旧世界引用和错误 base；建议在 `endSandbox` 里一起清，或在 `beginSandbox` 的 `endBatch()` 后确保清空。
3. **测试覆盖不足**：
   - `scripts/ui.test.mjs:461-506` 只测了 comparator、地形批量、一步撤销、批量棋子移动；没有测批量中 undo/redo、autoFog 开关、材质/组/高度笔、`replaceWorld` 期间、`endBatch` 无欠账、手动雾 pending。
   - `MapCanvasImpl` 是直接调用（`scripts/ui.test.mjs:67/232`），React mock 的 `useEffect` 是空函数（`:27`），所以 **rAF、依赖数组、memo 真实行为全没有被单测覆盖**；画笔依赖的 bug 正是这类空档。建议至少加一个浏览器/jsdom 真实 React 渲染测试，或在 e2e 里断言 `fillRect` 次数。
4. **批量期间的自动保存/广播是 raw world（lead 已允许短暂滞后）**：`broadcastWorld`/`saveNow` 看到的是未补视野的中间世界；正常松手会补，但如果拖拽中崩溃/关页，自动保存槽里是 raw world。作为 P3 记一笔：可以接受，但最好在 `beforeunload` 或 `endBatch` 时强制补齐保存。
