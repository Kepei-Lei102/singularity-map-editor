## 焦点 1：协议形状与边界

- 四种消息形状完整；`asset-request` 的 `requestId/keys`，`asset-chunk` 的 `index/count/data`，`asset-end` 的 `bytes`，`asset-fail` 的 reason 都有类型；`isSyncMsg` 不按 type 白名单，asset 消息能过 relay。
- 请求 key：receiver 过滤空串/去重/32 一批；host 侧同样过滤、去重、`.slice(0,32)`；`assetKeyOf` 用 `key ?? id`。
- 单块 256 KiB 原文，base64 约 350 KB；64 MB 文件 256 块 + end；单条远低于服务器 8 MB，`maxPayload` 不会打掉。
- **rate 会打掉**：`ASSET_PACE_MS = 25` → 约 40 条 asset 消息/s；`broadcastWorld` 是 60 ms → 约 16.7 条 world/s；`alive` 每 2 s 一条 0.5/s。稳定叠加约 **57.2/s**，离服务器 60/s 只剩约 2.8/s 余量。玩家移动时 host 还要发 `move-result`（约 1/s），再碰一次 `pushFocus`/判定请求就到 60；`asset-fail` 还是**不经过 paced**，32 个 key 的 forbidden 会瞬间发 32 条。超限后服务器只回 `error`，`WsTransport` 不处理这个 error，chunk 被静默丢弃，玩家端没有 ack/timeout。这是 P2（见下）。
- `asset-fail` 的 fail 也走 `opts.send`，未节流；`serveAssetRequest` 只对 chunk/end 节流。
- 服务器仍只转发：server 不解析 `room.relay` 的 payload，只看到 base64，没有文件名/路径；成立。
- 服务器/客户端均无 backpressure：host 以 14 MB/s 推 chunk，server 直接 `ws.send`，慢玩家会让 Node ws 缓冲增长；属于 P3 运维风险。

## 焦点 2：主持端允许集合

- `assetAllow` 每个 binding 一份 `Map<key,{mime}>`；`setPlayerAssets` 在每次 `world` 发送前用该 binding 的 `pw.media` 重建；trial/real、focus-only 都走 `body.type === 'world'`，正确。
- 未知 key：`serveAssetRequest` 一开始 `if (!opts.meta(key)) fail(forbidden)` 且不 `load`；当前代码正确。
- 清理路径：
  - `send` invalid → clear + `players.delete` + `dropPlayerAssets`；正确。
  - `clearTrialWindows` → drop；`onProjectReplaced` → `assetAllow.clear()`；正确。
  - **`resetPlayerBindings` 只清 players，不清 assetAllow**；`peer.left` 不清；`registerOnlinePlayer` 重连不清。旧 binding 的 allow 会留在 Map 里，当前没有玩家能访问（`players.has` 先拦），但属于泄漏/旧权限残留。P3。
  - `onAssetRequest` 在 `!binding`/`!players.has`/`!allowed` 时**静默 return，不发 asset-fail**；玩家 pending 可能一直等。P3。
- **旧 allow 闭包**：`serveAssetRequest` 的 `opts.meta` 捕获请求时的 `allowed` Map。世界推送换 allow 后，旧闭包仍按旧 Map 继续发 chunk；注释写的“发到一半权限没了就停”不成立。
  - 是否越权：当前 binding/pcId 没变，旧文件本来就是该玩家旧 world 的媒体，且请求发生在允许时；**不算越权**。
  - 但新 world 已收走 key 后仍继续发旧字节，违反文档“换图/换视角后旧 key 收走”；如果以后 binding 被复用到另一个 pc，就会变成越权。P3，建议每块用 `assetAllow.get(binding)` 实时查或带 generation。
- 绑定重连后：players 保留，allow 保留旧 world；同一 pc 重连，旧 allow 在下一份 world 到来前仍可用。P3。
- `assetAllow` 只存 key/mime，不存 size；host `load` 拿到完整 Blob 后才检查 64 MB；allowed 的 64 MB+ 文件会先读进内存。P3。

## 焦点 3：玩家端 receiver

- `request`：去重、查 `known`、查 pending、查 `failed` 15 秒冷却、查本地 `load`；分批 32；正确。
- 拼块：`index/count` 整数、count 范围、count 一致、重复 index 忽略、`parts.filter(Boolean)` 数量、`bytes` 合计、chunk 长度上限、maxBytes；保存前 `asset-end` 校验 bytes；正确。
- 空文件：host count 至少 1，空 chunk 也能拼；可用。
- 哈希：`v:`+40 hex 才校验，`contentKey` 失败回随机名不校验；不符重试一次，第二次 `read-failed`；不会死循环。
- `failed` 15 秒：挡住每帧重问；`reset` 清掉后可立即重试；测试覆盖。
- **没有 timeout**：end/chunk 丢失、host `sendToPeer` 返回 false、`onAssetRequest` 静默 return 时，pending 永远在，`request` 以后都跳过这个 key。只有 `clear`/`close`/unmount 的 `reset` 能解。P2（见下）。
- **reset 与在途 finish 竞态**：`reset` 清 pending/known/retried，但已在 `save`/`contentKey` 的 `finish` 仍可能 `known.add`/`onReady`；清空后旧文件仍落地。P3。
- **`request` 并发竞态**：多个 world 推送同时调用时，都要先 `await load`，`pending` 在 await 后才 set，两个请求可能同时把同一 key 当 missing，发两份 asset-request；host 重复传。P3。
- **`putRaw` 配额失败**：catch 后 failed + `onFail(read-failed)`，但 15 秒后每次 world 都会再试；没有用户反馈/退避上限。P3。
- 测试没覆盖：bytes 不符（有完整 chunk 但 end bytes 错）、count 中途变化、稀疏 holes、重复块、空文件、chunk 超 256 KiB、receiver maxBytes；见焦点 6。

## 焦点 5：安全边界

- 玩家只能请求 `assetAllow` 中当前 binding 的 key；`serveAssetRequest` 初始 `meta` 和每块 `meta` 都检查，host 不会因玩家 key 直接读任意 IndexedDB key。
- 服务器只看到 base64，不解析 payload；失败只回 reason，不带 host 路径/文件名/错误栈。
- 清理缺口：`resetPlayerBindings`/`peer.left`/`registerOnlinePlayer` 不清 allow；旧 allow 对当前无玩家时不可达，但残留。
- **没有每 binding 的 asset-request 配额**：恶意玩家可 60 次/s 发 32 key 请求，host 为每个请求 `load` 并串行/并发发；`paced` 只限出带宽，不限并发 load/内存。P3（DoS）。
- **导入世界可把 media.key 指向别的 `v:` 内容**：schema 只校验 `^v:[A-Za-z0-9]{1,80}$`，若攻击者知道 host 本机另一个文件的 content hash，可通过贴图组让 host 把该文件发给玩家。属于已导入不可信世界的边界，P3。
- host 的 `getRaw` 只在 allow 后调用，未发现玩家直接诱导任意 key 的现成路径。

## 焦点 7：P0/P1/P2

### P2

1. **asset 节流预算打穿服务器 60 条/s**
   - 40 asset/s + 16.7 world/s + 0.5 alive/s ≈ 57.2/s；再加 move-result/judge/pushFocus 就超 60。
   - 服务器超限只回 `error`，host 的 `WsTransport` 不处理，chunk/end 静默丢；receiver 没有 ack/timeout，贴图传输会失败或 pending 卡死。
   - 单文件 64 MB 要 6.4 s，期间只要玩家在动就会叠加 world；这是正常使用路径，不是极端刷屏。
   - 修法：`ASSET_PACE_MS` 降到 40–50 ms（20–25/s），或服务器把每连接上限提到 120，或把 asset 预算和 world 分开计；`asset-fail` 也节流。
2. **没有超时/取消/ack，失败不可恢复**
   - end 丢失、`sendToPeer` false、`onAssetRequest` 静默 return，都会让 pending 永久保留；后续 world 的 `request` 因 `pending.has` 跳过。
   - `clear` 只 reset receiver，host 仍把在传文件发完；没有 `asset-cancel`。
   - 4-C 前至少补：每 key 30 s 超时→`asset-fail(timeout)`、host 端 cancel token、`sendToPeer` 失败→fail、`asset-fail` 后有限重试；再加进度/失败 UI。

### P3（10）

1. 旧 allow 闭包不实时收权限：world 换 allow 后仍继续发旧 key；“发到一半权限没了就停”不成立；同 binding 旧 world 不算越权，但 binding 复用会变越权。P3。
2. `resetPlayerBindings`/`peer.left`/`registerOnlinePlayer` 不清 `assetAllow`；旧 allow 残留。P3。
3. `onAssetRequest` 无 binding/allow 时静默 return，不发 fail；玩家 pending 无反馈。P3。
4. 没有每 binding 的 asset-request 配额；恶意玩家 60 次/s × 32 key 可让 host 反复 load/并发传。P3。
5. 服务器/客户端无 outbound backpressure；慢玩家会让 server 的 ws 缓冲增长。P3。
6. host 先 `load` 完整 Blob 再查 64 MB；allowed 的超大文件先占内存；并发请求可叠多份。P3。
7. 测试缺 bytes 不符、count 中途变化、稀疏 holes、重复块、空文件、超 256 KiB chunk、receiver maxBytes。P3。
8. 测试缺 initial allow 不读 IDB 的断言（`serve_no_allow` 0 红）、`onAssetRequest`/allow 清理/PlayerView 无自动化。P3。
9. `asset-fail` 的 `read-failed` 同时覆盖配额写失败/坏 chunk/哈希失败；4-C 要区分需拆 reason；无失败 UI。P3。
10. 导入世界的 `media.key` 只校验 `v:` 前缀，不校验是否本工程内容；知道本机其他 content hash 可跨工程取文件。P3。

## 4-C 前必须补

1. **降速/预算**：asset pace 至少降到 20–25/s，或服务器上限提高，保证 asset+world+alive+交互留余量；`asset-fail` 也 paced。
2. **超时/取消/ack**：per-key timeout、host cancel、send 失败回 fail、`asset-fail` 后有限重试；否则 rate-limit 丢包会永久卡住。
3. **backpressure**：server 检查 `ws.bufferedAmount`，或 host 等 ack/窗口再发；慢玩家不能把 server 缓冲撑爆。
4. **allow 生命周期**：每块实时查 `assetAllow.get(binding)` 或带 generation；`resetPlayerBindings`/`peer.left`/重连清理；无 allow 时回 `forbidden`。
5. **请求配额**：每 binding 同时最多 1 个 request/32 key，防 DoS。
6. **测试**：完整块 + 错 bytes、count 变化、稀疏/重复/空文件、超 chunk、initial allow 不读 IDB、onAssetRequest allow 命中/拒绝/替换、PlayerView call site、rate/backpressure。
7. **UI**：失败/进度（4-C）；`play` 线上仍禁用，播放留 4-C。

## 结论

协议形状、单条大小、服务器只转发、allow 按 binding、玩家端拼块/哈希/冷却、PlayerView 顺序都成立；但 **40 asset/s + 16.7 world/s 已贴近服务器 60/s**，且 **没有超时/取消/ack**，超限丢包会让贴图传输失败或 pending 永久卡住。这两条是 P2，不能推。其余 allow 闭包、清理、DoS、backpressure、测试缺口为 P3。修掉 P2 并补 4-C 前三项后可再推。
