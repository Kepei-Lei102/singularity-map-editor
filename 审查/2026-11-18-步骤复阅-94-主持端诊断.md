## 统计语义

- `players` 按 binding 计：每个 `assetSessions` 值若 `activeCount>0` 计 1；`requests` 累加 `activeCount`（同一 requestId 的多个 ref 也算）。这个语义正确：一个玩家多个请求仍是 1 名玩家，几个 ref 就是几条在途 serve。
- `rejectAssetRequest`（active cap 超限）不占 active，所以不显示，符合“拒绝不是传文件”。
- 玩家 reset/cancel 只标记 cancel，不立刻减 active；要等 serve 下一次检查/`finally`，dock 会延迟一小段才降，可接受。
- `registerOnlinePlayer` 用 fresh 替换旧 session 并立即 refresh；旧 serve 若还在跑，不计入新 session，dock 会先掉到 0。正常重连旧连接已被 drop，问题不大；但“旧 serve 还在发、dock 说 0”是 P3 口径问题。
- **P3 语义**：`players` 是**所有在途 asset 请求**，不是“正在传这个广播文件”。广播时 3 个玩家若只是在下载地图图片，dock 也会说「正在传给 3 名玩家」；配额拒绝路径走 `beginAssetServe` 也会占 active，于是只发 forbidden 的请求也会被计成“在传”。文案应改成「有 N 名玩家正在下载素材」，或按 broadcast key 统计。
- **P3 语义**：`requests` 当前 UI 没用；没有 per-binding 已发字节、队列深度、速率，主持人只能看到人数，不能诊断 12 人 138s 的瓶颈。

## 订阅

- `refreshAssetTransferStats` 覆盖了：`beginAssetServe` 的 `tryAcquire` 成功后、serve `finally` release 后、`register`、`unregister`、`dropPlayerAssets`、`resetPlayerBindings`、`onProjectReplaced`。没有漏掉的 active 增减路径。
- `assetSessions.set(binding, fresh)` 后旧 session 的引用不再计入；旧 serve 的 finally 只释放旧实例，正确。
- snapshot 只在 `players/requests` 变化时换成新对象；`useSyncExternalStore` 的 getSnapshot 身份稳定，subscribe 返回退订函数，组件卸载会退订。
- **P3 覆盖**：`register/unregister/drop/reset/onProject` 的 refresh 全部 0 红（只有 begin/finally 被 online 咬住）；`requests` 按 refs、snapshot 身份、listener 退订都没有直接测试。`refresh` 里某个 listener 抛错会中断其余 listener，未包 try，属于低概率健壮性问题。

## UI

- `MediaDock` 在 `broadcast && transfer.players>0` 时加 `<span className="muted">正在传给 N 名玩家</span>`；本地 `broadcast=false` 不显示，`np` 为空时 dock 不渲染。
- `useSyncExternalStore` 放在 `if (!np)` 之前，hook 顺序稳定；无媒体时也订阅，但返回 null，开销很小。
- **P3 布局风险**：`.dock` 固定 340px，`.dock-head` 是 `display:flex; justify-content:space-between`，原来只有标题+按钮两个子项，现在变成三个。标题本身可能很长（「📡 玩家也在看/听　label」），再加「正在传给 12 名玩家」和按钮，窄屏/长标题会挤压、换行，甚至把按钮挤出去；没有 `flex-wrap`/`white-space:nowrap` 或窄屏隐藏规则。没有浏览器检查，按 CSS 判断是 P3 UI，不是 P2 功能错误。
- 玩家 bundle 会包含 `assetTransferStats`/listener（约 +0.25 KB），但 PlayerView 不挂 MediaDock，没有 UI，属可接受的小冗余；真要去掉需要把统计只放在 host 入口。

## 测试

- online 的 `hostTransferDuring` 在 receiver `onProgress` 里采样 host 当前 `players`；5 字节文件虽然小，但 start/chunk/end 各走 45 ms 节流，start 的 onProgress 到来时 host 已 `tryAcquire` 并 refresh，所以 `some(n===1)` 真在 serve 期间采样，不是碰巧其他刷新。
- `statEvents>=2` 来自 begin 与 finally 两次 refresh；register 在订阅前，reset/close 在断言后，所以不靠无关刷新凑数。
- `await waitFor(players===0)` 咬住 finally 降回 0。
- **P3 测试缺口**：没有直接渲染 MediaDock 验证文案/布局；没有多玩家、多个 request、`requests` 数值、register/drop 后旧 serve、配额 forbidden 被计数的用例；5 字节单 key 不能覆盖 12 人/32 key 的调度。

## 下一包调度

- 94 只做了计数，没有 per-binding 字节/队列/速率；12 人 64 MB、全局 45 ms 仍约 138 s，超过 receiver 120 s queue timeout，最后几个玩家会排队超时失败，这点未改。
- **更简单的第一步不是 round-robin，而是队列 watchdog 从 key 开始**：receiver 现在从发 `asset-request` 起就 arm 120 s 排队超时；host 串行 12 人时后面的玩家还没轮到就超时。把“等 start”改成较长的总请求上限（例如 10 分钟）或从收到 `asset-start` 才开始 key 的 inactivity watchdog，能直接消掉 120 s 假超时，不改调度器。缺点是 host 永不回时玩家会等更久，所以总上限要保留。
- **不建议“先 start 所有 key 再传”**：`asset-start` 会立即换成 30 s inactivity timer，排在后面的 key 还没发块就会 idle 超时；除非 receiver 区分“已 start 但未开始收块”的状态。
- **不建议先加大 chunk**：旧 receiver 用 `ASSET_CHUNK_BYTES=256 KiB` 校验，512 KiB 会破坏旧客户端；需要协议协商。
- **推荐顺序**：
  1. queue watchdog 从 key start 起算 + 一个宽松的总等待上限；先消除 120 s 假超时。
  2. host per-binding 统计加 `sentBytes/totalBytes/queued/rate`；MediaDock 显示“N 名玩家正在下载素材”，不要声称都在收广播。
  3. `paced` 改每 binding 一条钟 + 全局 token bucket/预算，round-robin 公平出块；同一玩家 64 MB 不阻塞其他玩家。
  4. 每 binding 队列/在途上限，超限回 forbidden 或让玩家显示“排队中”；再按文件大小调 queue timeout。
- 目前 94 的计数可以作为第 2 步的 UI 骨架；先做第 1 步的 watchdog 改动收益最大、风险最小。
