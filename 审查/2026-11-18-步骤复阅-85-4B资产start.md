## 焦点 1：120 s 排队上限

- **4×64 MB 安全**：每文件 start + 256 chunk + end = 258 条；4 个 = 1032 条 /22.2/s ≈ **46.5 s**；第 4 个约 **35.0 s** 收到 start，<120 s。
- **200×1 MiB 单人也安全**：每文件 start + 4 chunk + end = 6 条；200 个 = 1200 条 /22.2/s ≈ **54.1 s**；最后一个 key 约 53.8 s 收到 start，<120 s。
- **32×64 MB（约 371 s，2 GB）会超 120 s**；32×24 MB（768 MB，约 141 s）也会超；3 个玩家各拉 200×1 MiB（600 MB，约 162 s）同样超。**32×64 MB 是极端上限，v0.1 的 120 s 可接受；但“多人 + 大世界”会碰到，文档里应写明 120 s 是单请求/全局节流下的上限，不是无限。**
- 120 s 目前是单值常量，没有按 size/并发动态计算；正常 4×64/200×1 MiB 单人留有余量。若 4-B 要承诺 3 人以上大世界，建议把排队 watchdog 改成“host 每发一个 key 的进度 + 全局队列估算”或串行批次；否则 P3 已知上限。
- 45 ms 每块仍成立：22 条 asset 消息/s（start/end/fail 都算），world 16.7 + alive 0.5 ≈ 39.2，服务器 60/s 有约 20/s 余量。

## 焦点 2：asset-start 顺序

- host **先 load 完整 Blob、查 size/mime，再发 start**；load 失败/missing/too-large 都只发 fail，不发 start；玩家 pending 由 fail 直接清；**没有“先 start 后失败”的正常路径**。
- 队列 watchdog 覆盖 load 时间：120 s 从 request 到 start，load 计入；如果 load 本身 >120 s，玩家会先 cancel，host load 完再发 start 已经没人接（见 P3）。
- **缺口：load 后、start 前不再查 `isCancelled`/live allow。** 玩家在 load 期间 queue timeout/reset 时，host 仍会发一条 start；allow 在 load 期间撤掉时也会先 start，随后第一个 chunk 才 fail forbidden。没有字节泄露，但会多一条 start，并让“start 表示文件确实存在且马上发”的语义短暂失真。P3。
- start 发送本身走 `paced`，失败返回 false 时直接 return；玩家靠 120 s watchdog 收尾。

## 焦点 3：active 引用计数

- `assetActive` 改成 `Map<binding, Map<requestId, number>>`；同 requestId 第二次 serve 会加引用；`finally` 减到 0 才删；每 binding active 上限 64，新的 requestId 超限走 `serve`+`meta:undefined` 回 forbidden；register / resetPlayerBindings / peer.left / project / clearTrial / send invalid 都清或 drop。
- **缺口：** `finally` 里 `assetCancels.delete(requestId)` 不看引用计数。同一 requestId 有两个 serve 时，第一个 serve 结束就删掉 cancel entry，第二个 serve 的合法 cancel 会丢。正常 receiver 每次新 requestId 不会重复，属恶意/异常路径，P3。
- active 上限拒绝路径不写 active；玩家 reset 的 cancel 会被 active 拦截丢掉，host 仍把 32 个 forbidden 发完（约 1.44 s），P3。
- 同 requestId 的 count 没有额外上限，恶意可把 count 抬高；request 配额 30/10 s 限制了短期量，P3。
- **active 清理本身完整**：register 清、peer.left drop、reset/project 清、finally 减引用。

## 焦点 4：watchdog 与 start

- **start 前收到 chunk（协议外）**：`handle('asset-chunk')` 不要求 start，只要 pending/requestId 对就收，并 `armKeyTimeout(timeoutMs)`，等于把排队 watchdog 提前换成 inactivity；不会崩，但协议不严。P3。
- **start 重复**：再次 `armKeyTimeout(timeoutMs)`，只是把 inactivity 重新计时；重复 start 可延长等待，P3。
- **start 后 30 s 无块**：inactivity 到点，pending 删、key cancel、read-failed；正常。
- **reset 后 start 迟到**：pending 已清，requestId/key 不匹配，直接忽略；正常。
- **host 先 start 后 allow 撤掉**：start 已发，第一个 chunk 前 `live` 查不到 → fail forbidden；玩家 pending 被 fail 清；没有 end。
- **host 先 start 后 player cancel**：start 可能已发；chunk 循环第一块前 `isCancelled` 停；玩家 reset/timeout 已清 pending，start/chunk 被忽略；正常。

## 焦点 5：end 前 cancel

- `serve` 最后一块后先查 live，再查 `isCancelled(key)`，cancel 时不发 end；这条代码在。
- **玩家已收完 chunks、cancel 到达时，不会“pending 保留到 30 s”**：receiver 的 cancel 只有两个来源——`reset()`（先清 pending）和 timeout（先清 pending）；host 端 `continue` 不补 fail 也不会留下 pending。**正常路径不需要主动发 fail。**
- 如果是协议外的裸 `asset-cancel`（玩家自己发、不经过 receiver），receiver pending 会留到 inactivity 30 s；此时 host 应补一条 fail 才更快。属 P3/健壮性。
- **`serve` 在 `isCancelled` 检查之后、end send 之前仍有窗口**：cancel 恰在此刻到达仍会发 end；P3。
- **测试只覆盖“第一块后 cancel”，没有“最后一块后 cancel/end 前 cancel”用例**；`end_no_cancel_check` 突变 **0 红**。
