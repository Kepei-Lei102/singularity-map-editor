## P2（阻塞协议 v1 验收）

### P2-1 hostToken 与 inviteToken/playerToken 没有隔离

- 位置：`src/protocol.ts:126-131`（`addInvite`）、`:134-145`（`consumeInvite`）。
- `addInvite` 只查 `room.invites[inviteId]` 和 `room.inviteTokens[inviteToken]`，不查
  `inviteToken === room.hostToken`。实测：
  `addInvite(room, 'i1', 'HOST') === true`。
  一旦服务器生成/碰撞出 inviteToken 等于 hostToken，邀请链接就会把 hostToken
  发给玩家，直接违反 `docs:77`、`:120`、`:122` 的“hostToken 不发给玩家端”。
- `consumeInvite` 的 collision 检查只查 `room.players[binding]` 与
  `room.playerTokens[playerToken]`，不查 hostToken。实测：
  `consumeInvite(room, 'HOST', 'b1', 'HOST')` 返回
  `{ ok: true, inviteId: 'i1', binding: 'b1' }`，
  随后 `room.playerTokens['HOST'] === 'b1'`，
  `relayRoute(room, 'player', 'HOST')` 返回 `{ from: 'player', to: 'host' }`。
  即 hostToken 可以作为 playerToken 通过玩家路由；如果服务器把 token 当凭据而不是
  只看连接角色，这就是跨角色 token 混用。
- 同一函数还接受空 binding/空 playerToken：实测
  `consumeInvite(room, 'inv1', '', '')` 返回 `ok: true, binding: ''`；随后
  `playerReconnect(room, '')` 返回 `null`，邀请已经被用掉，绑定却不可路由。
  服务器应在生成后校验，但纯函数既然承担 collision 语义，应在协议层拒绝空串。
- `createRoomState`（`:118-123`）也不拒绝空 `hostToken`；`addInvite` 不拒绝空
  `inviteId`/`inviteToken`（信封校验能挡空 token，但状态机 API 自身没有不变量）。
- 影响：token 域边界不清；“hostToken 不发给玩家”“token 不串”的安全不变量在协议层
  无法保证，只能靠服务器生成器永远不碰撞。对协议 v1 这是实质安全缺口。
- 是否阻塞：**阻塞**。修法：`addInvite` 拒绝 `inviteToken === hostToken` 与空串；
  `consumeInvite` 拒绝 `playerToken === hostToken`、空 `binding`/`playerToken`；
  `createRoomState` 拒绝空 `hostToken`；补对应测试。

### P2-2 closeRoom 只置 closed，不清 token/邀请/绑定

- 位置：`src/protocol.ts:175-179`；文档 `docs/三端分离-v0.1.md:86`
  “房间关闭时内存清空”，`:21` 房间数据在服务器内存。
- `closeRoom` 只做 `closed = true`、`hostOnline = false`、玩家 `online = false`；
  实测关房后：
  `hostToken: 'H'`、`invites: ['i1']`、`players: ['b1']`、`playerTokens: ['pt1']`
  全部还在。路由会因 `closed` 拒绝，但 token 和绑定仍留在 room 对象里。
- 影响：若服务器保留 room tombstone 以便回 `room.closed`，hostToken/playerToken
  会继续驻留内存；文档的“内存清空”不成立。要么清空凭据/绑定，要么明确
  “closeRoom 只是标记，服务器必须删除 room 对象”，不能两可。
- 是否阻塞：**阻塞协议 v1 文档**（安全不变量与实现不一致）。

### P2-3 Envelope 类型与文档的握手字段不一致

- 位置：`docs:48-66` 的 Envelope、`:70-75` 的流程；`src/protocol.ts:26-38`。
- 具体不一致：
  - 文档信封没有 `from`；`protocol.ts:35` 有 `from?: string`，文档 `:74` 又使用
    `from: binding`，测试 `scripts/protocol.test.mjs:30` 还断言 `from` 合法。
  - 文档 `room.created { roomId, hostToken }`、`room.invited { inviteId, inviteToken,
    joinUrl }`、`room.joined { binding, playerToken }`、`peer.joined { inviteId,
    binding }` 里的字段，在 `Envelope` 中只有 `roomId`/`token`/`to`/`payload`；
    `hostToken`/`inviteId`/`joinUrl`/`binding`/`playerToken` 没有落位。
  - 文档 `:46` 说 payload 是“现有 `SyncBody`”，但上面的握手字段不是 `SyncBody`；
    没有定义 handshake payload 类型，也没有说 `hostToken` 放 `token` 还是 `payload`。

- 影响：Server MVP 要猜：`room.created` 的 hostToken 是 `token` 还是 `payload`？
  `room.joined` 的 `binding` 放哪里？实现和文档会再次漂移；测试也只测信封，不测
  这些消息形状。
- 是否阻塞：**阻塞**。补 `from`；为每种消息定义 payload 形状或明确字段落位；
  在文档里把 `room.created`/`invited`/`joined` 的字段写成 Envelope 的实际字段。
