### P1（1 条）

#### P1-1 批量拖动收尾：`endBatch` 拿“未同步记忆的世界”做 `narrowTerrainMemoryPlan`，新看见的物件/格记忆丢失

**位置**

- `src/core/store.ts:314`：`const memoryPlan = narrowTerrainMemoryPlan(base, world, plan, dirty);`
- 对照非批量路径 `src/core/store.ts:197-199`：先把 `withVision` 的结果 `visioned` 算出来，再 `narrowTerrainMemoryPlan(world, visioned, plan, dirty)`，最后 `syncMemory`。
- `flushBatchVision` 同样问题：`src/core/store.ts:167` 用 `base, world`，而下一行才 `withVision(world, base, {plan})`。

**为什么错**

`narrowTerrainMemoryPlan`（`src/scene/memory.ts:230-253`）用 `compareFog(pm.fog, nm.fog)` 找“圆盘内雾变了的格”，前提是 `nm` 已经是**套用本次视野后的世界**。批量路径把 `world`（`base` 上直接改地形的原始世界，`fog` 还没被 `withVision` 改）传进去：

- 地形改动造成“原来被墙挡住、现在看见”的格，其 `fog` 在 `world` 里仍是 0，和 `base` 一样，`compareFog` 看不到变化；
- 于是记忆 scope 只含 `changedTerrainCells`，不含新看见格；`syncMemory` 只同步这批格，物件/observed/cellRevs 漏掉。

`visioned` 的雾数组才是 `withVision` 算过的新雾；这是非批量路径能对、批量路径不对的原因。

**复现（当前工作区）**

- `/tmp/batch-memory-object.mjs`：60×40，墙列 `x=26, y=15..25`，墙后 `(30,20)` 放物件；`beginBatch` + 批量擦墙 + `endBatch`。结果：
  - `fogObjCell: 1`（屏幕上物件已经可见）
  - `seenObjects: []`
  - `fullObjects: [<id>]`
  - `objectsSame: false`
- `/tmp/batch-memory.mjs`：同一场景不变量对比，`seenDiff: true`，`cellRevsDiffCount: 673`，`observedDiffCount: 6057`，而 `fogEqualsFullVision: true`——视野雾本身对，错在记忆。
- 对照 `/tmp/single-memory-object.mjs`：同样场景用 11 次非批量 `paintTerrainCells`，物件正确进入 `seen.objects`，说明不是快速路径本身的问题，而是 `endBatch` 的收尾参数。

**影响**

用户拖地形笔松手后，画面已经能看见的物件不会进入记忆；`seen.cells/observed/cellRevs` 与全量重算不一致，后续移动、存档、玩家侧记忆都基于这份漏项状态。默认 `shared` 也中招，所以是 P1，不是模式专属。

**建议修法**

- `endBatch` 和 `flushBatchVision` 都改成：先 `withVision` 得到 `visioned`，再用 `narrowTerrainMemoryPlan(base, visioned, plan, dirty)`；即 `src/core/store.ts:197-199` 的同一顺序抽成公共 helper，避免两处再次分叉。
- 增加测试：批量擦墙/刷墙后，`seen.objects`、`seen.observed`、`seen.cellRevs` 与 `produce(withVision(world,base,{full:true}), syncMemory)` 归一化相等；现有“地形-only 收窄===全量”用例是单次 `update` 路径，覆盖不到 `endBatch`。

## 逐项回答本轮重点

1. **`viewerScope` 的“视野半径是硬上限”是否对所有结构/物件/建筑/D100/朝向前提成立？**
   - 地形-only 的“观察者半径内才可能变”成立，且 `r=17` 兜小格 eye offset；随机 480 组 fog/views 相等。
   - `!added`、手动雾、autoFogOn、尺寸不同都退回整图；这些条件本身对。
   - **例外**：同一次更新里的 `pcId` 变化没有被 `viewerScope` 排除，配合 P2-1 的组快路径会漏旧组清雾；`manualChanged` 同 update 也没有排除（P2-2）。
   - 跨图/首次同步/换世界走 `full`；`replaceWorld` 重置批量状态，未发现漏项。
   - **无 PC / token 增删**：`added` 为真直接整图；无 PC 时 scope 为空或按 moved，随机测试未发现 fog 差异。

2. **建筑记忆整层重排是否 field-identical 于 full？**
   - 就建筑**内容不变、只是地形变**的场景：当前 scoped merge 保留 base 建筑，`arch-modes`/`batch-arch-store` 三模式建筑条目数均为 2（与 full 同量；raw rev 仍按增量不同）；随机 480 组归一化 `seen` 失败 0，说明现有场景没有 field 级分叉。
   - `architectureChanged` 为真时 `architectureFullMaps` 驱动整层重排；`/tmp/arch-plan.mjs` 单点、`/tmp/arch-scoped.mjs` 可见片段与 full 同。
   - **但** `architectureChanged` 的 `objects !==` 过宽，会把非建筑物件改动也整层重排（P3-2）；且 `mergeLayersScoped` 不合并 layers 新增建筑片段（P3-6，未复现）。
   - 结论：**不是“完全没有问题”，但当前没有可复现的 field-identical 失败**；先不要拿“建筑记忆已完全等价”做宣传，补新看见建筑用例。

3. **快速路径 store 不变量**
   - `updateTerrainFast`（`store.ts:268-292`）只浅拷贝 `cells/fineCells`；no-op 检查也只比这两数组，与它实际能改的字段一致。地形画笔不会新建 NPC hp，跳过 `normalizeNpcHp` 对现有已归一世界安全；`architectureTransitionError` 也不涉及，因为只改地形。
   - 非批量 `freeze(next,true)` 在 commit 前安全；批量中世界不冻结，但只被后续浅拷贝/数组写入，`endBatch` 在管线前免费 `freeze(world,true)`；undo/redo/replaceWorld/endSandbox 都重置 batch 标记（`store.ts:326-353`、`:563-575`）。
   - **真正的问题不在快路径本身，而在收尾参数**（P1-1）；`commitWorld` 的 history/coalesce/evicted 仍在，未发现抽取等价性回归。
   - `update` 的 architecture transition 循环和手动雾 replay 仍在 `update()` 里，非批量语义保持；批量首笔手动雾的 `markManualFog` 时序是 P2-2。

4. **`commitWorld` 与旧 `update` 等价性**
   - 非批量单次 update：`planVision` + `withVision` + `narrow(visioned)` + `syncMemory`，等价；测试 1033 绿。

5. **性能数字可信度**
   - **69ms 可信**：独立 Node 4PC 200×200 当前代码中位 **65.0ms**；浏览器 1PC warm 52–74ms；量级一致。

6. **上一轮 P1-1/P2 是否真关闭**
   - P1-1 单次地形：**shared 口径可闭合**（65–69ms）；individual/grouped 未闭合（P2-3）。

   - P2-2 批量撤销重基：**闭合**（测试 + 探针通过）。
   - P2-3 手动雾顺序：**部分闭合**（地形→雾通过；雾→地形、同 update 混合仍错，P2-2）。
   - 剩余 P3 大体可接受，但 P3-1 的测试缺口必须补，否则下一轮同类 P1 还会漏。

- 独立随机复验 `/tmp/scope-random.mjs`（当前代码）：3 模式 × 0–3 PC × 40 次随机地形/小格/D100/物件移动/建筑移动，`viewerScope` + `visionStructure` 的 480 组，`fails: 0`；比较包含 `seen.architecture`、`seen.objects`、`seen.groups`、`cellRevs/observed` 等归一化字段，不只看 fog。
- 手工检查：scope 外的 `fog/cells/cellRevs/materialCells/architectureRevs` 原地保留；`objects/groups` 由所有 layers 全局重建（不是保留旧聚合），因此不会漏掉旧聚合，但也不会把 layer 里没有的旧物件“凭空”补回来——这与 `mergeLayers` 语义一致，随机 480 组没有分叉。
- 结论：**outside-scope 旧聚合没有发现漏项；原地写回与 clone 版在现有覆盖下等价。** 唯一性能观察是 `mergeLayersScoped`（clone 版）还没有像 `mergeLayersScopedInto`/`mergeLayers` 那样去重重复层引用（P3-2）。

### 3. undo/redo flush 是否覆盖 `undo→endBatch→redo`（覆盖）

- 代码：`src/core/store.ts:354-358` 的 `undo` 与 `:371-374` 的 `redo` 都在 `batching && batchVisionDeferred` 时先 `flushBatchVision()`；`flushBatchVision` 用 `visioned` + `narrow` 补齐后把 `batchVisionBase` 更新为补完世界。`undo` 之后 `future.push(world)` 推入的是补完视野的世界，不是 raw world。
- 测试：`scripts/ui.test.mjs:528-548` 的 `undo-redo` 与 `undo-end-redo` 两序，断言 redo 后 fog 等于非批量结果；当前 1038 全绿。
- 手工路径推演：
  - batch 内第一次改 → `pushHistory(batchStart)`；
  - undo（欠视野）→ flush → pop `batchStart` → `future` 收到补完世界；
  - redo 在 batch 内 → 取回补完世界；或 `undo→endBatch→redo` → `endBatch` 清 batch 标记，redo 从 `future` 取回同一补完世界；
  - 两条路径都不会把未补视野的快照写进 redo 栈。
- 未发现新的 history/redo 回归。理论上 `redo()` 在 deferred 为 true、future 为空的罕见顺序会先 flush 再返回（副作用是补算一次视野，但不改变历史），本期没有用户路径复现，列 P3-3 观察项。
