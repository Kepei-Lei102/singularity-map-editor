## P2-1：广播后改「▶ 仅主持人」，再关，玩家还停不下来

`playMedia(..., false)` 只把 `nowPlaying` 换成 local，不发 `stop`，也不清 `broadcastAsset`。随后 `stopMedia` 看的是 `np.broadcast === false`：

```ts
if (np?.broadcast) send({ type: 'stop' });
setUI({ nowPlaying: null });
```

于是没有 stop，`broadcastAsset` 仍指向旧 key，`assetAllow` 也仍允许它；玩家一直播旧的，主持端已经显示 null。

**探针（线上房间实测）：** host 广播 `k1`，玩家收到 play；host `playMedia('m2', false)`；host `stopMedia()`；120 ms 内玩家没有收到 `stop`；再请求 `k1` 得到 `read-failed` 而不是 `forbidden`（说明广播 key 仍在 allow）。`host.getUI().nowPlaying` 已是 null。

**修复：**广播状态不能只靠 `nowPlaying.broadcast` 判断。要么 `playMedia` 非广播分支在已有广播时先发 `stop`，要么 sync 暴露 `hasBroadcastAsset()`/`clearBroadcast()`，让 `stopMedia` 无条件清广播再停。并补线上测试：广播 → 本地 ▶ → 关闭，断言玩家收到 stop、`k1` 变 forbidden。

## P2-2：失败后的同一媒体再播，卡在「载入中…」且没有重试按钮

`PlayerView` 收到 play 时走 `assets.current.request([m.mediaId])`。失败后 `failed` 有 15 秒冷却；再次 play 同一 key 时：

1. `setMedia({ failed: false })`，错误 UI 消失；
2. `request` 看到 `failed` 冷却，**静默跳过**，不发 `asset-request`；
3. 没有 fail 事件，`MediaView` 一直 `载入中…`，重试按钮也不会出现。

assets 的 retry 测试正好证明这一点：冷却期内普通 `request` 只发 1 次，`retry` 才发第 2 次。

**触发：** 玩家收到 `asset-fail` 后主持端 15 秒内重播同一媒体（或 stop 后很快重播），Host 端正常，玩家永久 loading 到刷新。

**修复：** play 是明确的新播放动作，应走 `assets.current.retry([m.mediaId])`（或给 `request` 加 force 参数），不能走普通冷却 `request`。补 PlayerView 级测试：fail → 再 play → 应发第二次 asset-request。

## allow 边界

- trial：`send('world')` 传 `!p.trialContext`，`refreshPlayerAssets` 跳过 `p.trialContext`；trial 窗口拿不到真实广播 key，**没有发现 trial 泄漏**。
- `stop`/`clear`/`onProjectReplaced`/`resetPlayerBindings`/`openOnlineHostRoom`/`closeOnlineHostRoom` 都会清 `broadcastAsset`；`stop` 会 refresh 收 allow，online 测试的 stop→forbidden 断言通过。
- **缺口是 P2-1：本地 ▶ 替换 `nowPlaying` 后，这些清理路径都不会被触发。**
- `send('play')` 先设 `broadcastAsset` 再 `refreshPlayerAssets`，然后才逐 binding 发 play；玩家收到 play 前 allow 已就绪，顺序正确。
- 新玩家 join 时 `registerOnlinePlayer` 清 allow，随后 hello 触发的 world 推送会带上广播 key；如果没收到 play，至少不会因为 allow 缺失而 forbidden。
- `setPlayerAssets` 的广播 key 以 `size: 0` 覆盖同 key 的世界媒体，只影响预检，load 后仍按真实 size 判，P3。

## PlayerView

- `onlineNow && assets.current && !m.blob` 才请求；本地窗口 blob 在，不发请求，`MediaView` 直接用 blob。
- `onReady`：`mediaChanged()` + 当前 key 才清 `failed`；`onFail` 只对当前媒体标记失败；旧 key 的 fail/ready 不会串到新 media。
- `MediaView` 无 URL 显示「载入中…」；`retry` 按钮只在 `failed` 时出现；卸载/clear/online close 都 `assets.current.reset()`，没有卸载后 setState（receiver 的 gen/pending 已清）。
- **P2-2 是这里的主要 call site 问题：play 用 `request`，没有绕过失败冷却。**
- **P3：**`stop` 只 `setMedia(null)`，不取消当前 asset 请求；stop 后很快重播同一 key，旧的 fail 可能把新 play 标失败（用户还能点重试，不是永久卡死）。

## retry

- `retry` 过滤空 key，清 `failed` 后调用 `request`；仍受 `pending`/`known`/`requesting` 限制，符合注释。
- 只由 PlayerView 的重试按钮调用，没有自动 retry；assets 测试掉 `failed.delete` 会红。
- **P3：**`retry` 不重新开始 `v:` 哈希重试（`retried` 没删），哈希不符第二次后再点重试仍直接 `read-failed`。
