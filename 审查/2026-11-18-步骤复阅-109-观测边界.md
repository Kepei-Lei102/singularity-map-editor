## ticker active flow

- 第二 test 在 `Blob.prototype.arrayBuffer` 上做切片闸门：第一块真读，第二块起挂起；请求后 `requests1 && bytes>0`，等 `rate0`，断言订阅器收到 `rate0` 刷新；释放后 flow 结束，再等700ms 断言不再通知。**删掉 `beginAssetFlow` 里的 `scheduleAssetRateTick()`，该 test 超时红（我实测）**，说明 ticker 刷新是必要的。
- **但测试缺了“第一块后 rate 必须为正”的锚点**：`noteFlowSample` 对同一毫秒的样本是合并（`last.at === now` 时只更新 `last.bytes`），如果 start 和第一块落在同一毫秒，flow 只有1个样本，`rateFromSamples` 直接返回0；此时“第一块刷新”就会以 rate0 通知订阅器，**即使没有 ticker，测试也能通过**。当前机器上 start/chunk 分在不同毫秒，突变才红；这是时序依赖的假过风险。建议先断言一次 `rate>0` 再等0。
- **“结束后700ms不再通知”不足以证明 timer 停了**：ticker 回调开头 `if (!assetFlows.size) return;`，flow 结束后即使 timer 还在，也不会 refresh/通知；所以测试只能证明“没有通知”，不能排除“timer 还在排”。要证明停排，需要计时器 spy/账本钩子。
- `Blob.prototype.arrayBuffer` 是全局替换，但本 test 是 raw `asset-request`，玩家没有 receiver/save，不会影响落盘；finally 先恢复原函数再释放 pending，后续块走真读。前一 online test 用的是另一个 host2，且替换只在本 test 内，未串场。
- `pending` 只放第二个块的 release；恢复后 serve 继续后续块并发 end，`requests0` 正常。若断言失败，finally 仍会恢复/释放，不会把全局 Blob 带走。

## +2000 语义

- 当前实现 `rateFromSamples` 在 `now - last.at === 2000` 时：`now-last.at` 不 `>` 窗口，cutoff 落到最后样本，base 取到最后样本，seconds=2，bytes差0，返回0；`now-last.at >2000` 走 stale 返回0。
- docs 改成“满 2 秒没有新块会回 0”，与测试 `+2000 -> 0` 一致；我**认可不改正向值**，只锁当前口径。边界从1900的500直接跳到2000的0，语义是“满2秒归0”，文档已说清，不必为这个包改实现。
- `+1900 -> 500`、`+2000 -> 0`、`+2001 -> 0` 三条现在锁住了；旧公式在1900会返回1000，能咬住。
