## 焦点 1：active / cancel 引用计数

- `beginAssetServe` 统一登记 active：正常请求与配额拒绝都加引用；`finally` 先减引用，只有归零才删 `assetCancels[requestId]`。**同 requestId 两个 serve 的正常顺序不再丢第二个 serve 的 cancel**。
- 每 requestId 最多 4 个 serve，超过 `return` 丢弃；`registerOnlinePlayer`、`resetPlayerBindings`、`peer.left`、project、clearTrial、send invalid 都清 active。
- **remaining P3：** active 总量上限删掉后，`assetCancels` 仍按 binding 限制 64 个 requestId；request 配额只限 10 秒 30 次，长请求可让 active 超过 64，第 65 个在途 request 的合法 cancel 会被丢。
- **remaining P3：** requestId 第 5 个 serve 直接 `return`，不发 fail；恶意重复 request 的玩家 pending 只能等 30/120 s。
- **remaining P3：** register/drop 清 active 后，旧 serve 的 `finally` 用新 active map 的同 requestId 计数时可能减到新 serve 的引用（旧请求迟到）；正常 reconnect 不复用 requestId，属异常路径。
- **配额拒绝登记 active 是对的：** `serve` 循环 32 个 forbidden，玩家 reset 的整批 cancel 可在每个 key 的 `isCancelled` 处 `continue`，引用归零后清理；未被 reset 时 fail 会逐条清 pending，1.44 s 可接受。
- **正常 `finally` 不会把另一个 serve 的 cancel 删掉**：引用 2→1 时不删，归零才删；只有 active 被 register/drop 清空或 requestId 复用才会出现上面的异常。

## 焦点 2：load → start 边界

- `serve` 在 load 后、start 前先查 `isCancelled`，再查 live allow：cancel 就 `continue`（不发 start），allow 撤掉就 `fail forbidden`；顺序符合“取消优先、allow 其次”。
- cancel 只 `continue` 不发 fail：receiver 的正常 cancel 来自 `reset`（先清 pending）和 timeout（先清 pending），所以玩家侧不会留 pending；裸 `asset-cancel`（不经过 receiver）会留到队列/inactivity 超时，P3。
- **remaining P3：** `isCancelled`/`meta` 检查与 `paced(send start)` 之间仍有窗口；cancel 或 allow 撤掉恰在窗口内到达时，仍会先发 start，再在第一个 chunk 前停/fail。没有字节，但 start 语义短暂失真。
- load 卡住时玩家 reset/timeout 走后，host load 完不会再发 start；不会再出现 85 的“load 完补一条 start”。

## 焦点 3：严格 start

- receiver 的 chunk/end 都要求 `p.started`；start 前收到 chunk/end 直接忽略，queue watchdog 继续跑，最终 120 s fail/cancel；start 后正常。
- `asset-start` 重复时 `if (p.started) return`，不再 `armKeyTimeout`，不会无限续 inactivity；测试覆盖。
- `asset-fail` 不要求 started，missing/forbidden/too-large 仍能直接清 pending；合理。
- start 迟到（queue 超时/ reset 后 pending 已清）找不到 pending，忽略；reset 后旧 start/chunk 不会污染新请求。
- **remaining P3：测试“start 前的 chunk/end 被忽略”只断言 `saved.length === 0`；chunk 在 start 前被接收但没保存时也满足，`chunk_no_start` 突变 0 红。代码是严格的，测试没咬住 chunk 分支；`end_no_start` 突变 1 红（test 17）。**

## 焦点 4：reset fence

- `reset` 先 `generation++`，再发整批 cancel，清 timers/pending/requests/known/failed/retried/requesting。
- `finish` 在入口、contentKey 后、save 后各有 `p.gen !== generation` 检查；`request` 在每次 `await load` 后和每个 batch 前检查。测试 22/23 覆盖 save/load；把三处 finish 检查全去掉会 2 红（22、23），把两处 request 检查全去掉会红 23。
- **save 已开始时 reset 仍会写文件，但之后不再 `onReady`**：文件内容按内容哈希命名，残留可接受；新请求可重新 load 到它，只是这次 reset 的 UI 不会收到 ready。P3，建议 4-C 文档写“reset 不撤销已开始的 IndexedDB put”。
- **remaining P3：** contentKey 后 hash 不符分支没有 generation 检查；reset 期间旧 finish 可能 `pending.delete` 掉 reset 后新请求的 pending，并 `request` 旧 generation。
- **remaining P3：** save 的 catch 没有 generation 检查；reset 后旧 save 抛错会清掉新 pending、写 failed、调 onFail。
- **remaining P3：** `requesting.delete` 在 generation 检查之前；reset 时旧 load 返回后会删掉 reset 后新 request 的 `requesting` 标记，削弱同 key 去重。
- 同一 key 并发 request 只发一次，测试覆盖；reset 后立即同 key 再 request 的交叉没有测试。

## 焦点 5：end 前 cancel

- `end` 的 `paced` 回调里再查 `isCancelled(key)`；测试 20 在最后一块后 5 ms cancel、pace 20，断言不发 end；去掉回调检查 1 红。
- **remaining P3：** 回调返回 false 既可能是 cancel，也可能是 `send` 返回 false；外层 `if (!ok) return` 一律停整个 `serve`。reset 的整批 cancel 停整批是对的；但**单个 key 的 cancel** 在 end 窗口也会停掉同批剩余 key，而不是 `continue`。正常 receiver 的单 key timeout 发生在最后一块后 30 s，而 end 仅隔 45 ms，所以正常情况够不到；协议外/恶意 key cancel 可触发。
- **是否发 fail：** 正常 reset/timeout 的 pending 已清，不需要 fail；裸 key cancel 才需要补 fail。当前 `continue` 不发 fail，属 P3。
- `send` 本身 false 说明 binding 没了，停整批是预期；不需要 fail。

6. **allow 撤掉**：决定是 fail 后等 15 s 冷却重试，还是保留已收字节；player 侧要有测试。
