## P1

### P1-1 `mergeLayers` 丢掉 `seen.materialCells`，材质记忆在独立/分组模式下系统性丢失

**位置**

- `src/scene/vision.ts:5`：`emptyVision` 的 `seen` 没有 `materialCells` 字段。
- `src/scene/vision.ts:43-99`：`mergeLayers` 重建了 cells、cellRevs、objects、groups、architecture、observed、objectRevs、groupRevs，但**没有写 `seen.materialCells`**。
- `src/scene/perception.ts:136`、`:140`：独立/分组模式每次 update 都 `mergeLayers` 一次组层/地图层；分组多成员组和多玩家地图都会走多 layer 分支。
- `src/scene/memory.ts:230`：`syncMemory` 最后又 `Object.assign(m, mergeLayers(...))`，地图层同样被清掉。
- 消费侧：`src/scene/material.ts:33-35` 的 `rememberedMaterialAtCell` 读 `seen.materialCells`；`src/runtime/hostSession.ts:229` 的 `playerMap` 也从 `L.seen.materialCells` 取灰区材质。

**触发条件**

- `visionMode` 为 `individual` 或 `grouped`，且**任意一次 update**；不需要视野脏动。分组模式下一个组有 ≥2 人时，连只改 `session`、改棋子名字/HP、扣队员 HP 都会触发 `withVision` 的 merge，然后材质被丢。
- 也可由 sharing 切 individual/grouped、individual 切 grouped 等模式切换触发（`perception.ts:127`、`:136`、`:140`）。
- 组内只有 1 人时 `cloneLayer` 会保留材质，但只要地图层还要 union（party > 1），地图层仍丢；组内 ≥2 人时玩家层也丢。

**复现证据（store 实际路径，非直接调函数）**

- 初始 `replaceWorld` 后：`individual`/`grouped` 的 `m.seen.materialCells` 已经是 `undefined`（merge 在地图初始化就丢了），玩家层还有材质。
- 60×40 分组图：甲 `(5,5)`、乙 `(50,30)` 同 `g1`；材质 `(5,5)=wood`、`(50,30)=tile`。初始 `m.views.a/b.seen.materialCells` 都有 tile/wood；把甲走一格后：
  - `m.views.a.seen.materialCells[(50,30)] === undefined`
  - `m.views.b.seen.materialCells[(50,30)] === undefined`
  - 地图层 `seen.materialCells` 始终为空对象/undefined（初始就是）。
- 后果：`(50,30)` 当前仍是 `fog=1` 时玩家端还能从实时 `materialCells` 看到 tile；一旦这一格转灰，`playerMap`/`rememberedMaterialAtCell` 取不到旧材质，玩家记忆里的地板材质变回默认空值。这是“看得见→看不见”后应保留的记忆，直接违反文档 `docs/视野增量计算-v0.1.md:64` 的“材质也按脏格同步”。

**影响**

- 增量记忆与全量真正独立计算不一致；是**数据丢失**，不是单纯显示抖动。
- 共享模式正常（不 merge）；独立模式玩家层多数情况下保留，地图层丢；分组模式玩家层和地图层都可能丢。模式切换后共享层也会丢。
- 该 bug 在本次 PR 前已经存在于 `mergeLayers`，本次 PR 把 `materialCells` 纳入增量记忆和测试口径后仍然保留；因为测试基线有缺陷（见 P2-4），绿灯没有暴露它。

**建议**

1. 在 `VisionLayer` 的 seen 初始化/merge 中正式携带材质：`emptyVision` 加 `materialCells: {}`；`mergeLayers` 对 `seen.materialCells` 按与 `seen.cells` 相同的 `cellRevs` 口径逐格选择（或对所有 fog>0 的 layer 取最近一次材质记忆），不要只 merge 地形。
2. `syncMemory` 的 `Object.assign(m, mergeLayers(...))` 必须保留 merge 后的材质；如果地图层材质暂时不用，也不要把它从 `m.seen` 清空。
3. 补独立全量基线测试：`full = produce(withVision(next, prev, {full:true}), d=>syncMemory(d))`，而不是拿同一个 `visioned` 再 sync；再加 grouped 多成员组、材质在脏区外、模式切换、save/replace 的断言。

**优先级：P1（正确性；上线前必须修）。**

### P1-2 独立/分组模式仍按“每图 × 每玩家”整层 clone/merge，且建筑记忆每层全量重剪

**位置**

- `src/scene/perception.ts:116-122` 的 `apply` 只在非空 scope 时计算视野，但 `:136-140` 无论 scope 是否为空都会：
  - `cloneLayer` 每个组的层（`:138`）；
  - `mergeLayers(src, d.party.map(...))` 合并整张地图（`:140`）；
  - 分组时先 `mergeLayers` 组内成员（`:136`）。
- `src/scene/vision.ts:6`：`cloneLayer` 是 `JSON.parse(JSON.stringify(...))` 深拷贝；`:43-99` 的 `mergeLayers` 逐格 `choose()`，比较器里对每个候选做 `JSON.stringify(...).localeCompare(...)`（`:47`），并逐 key `flatMap`（`:62`）。
- `src/scene/memory.ts:218-230`：独立/分组模式下每张图都逐玩家 `syncLayer` + `pruneMemory` + `cloneLayer` 给同组 peer，最后整图 merge。
- `src/scene/memory.ts:142-144`：`syncLayer` 里建筑记忆**每个 layer 每次全量**两次 `clipArchitecture`；`src/scene/vision.ts:144` 的 `pruneMemory` 又整层两次。scope 只作用于格/物件/贴图，建筑不受 scope 限制。文档说“建筑记忆按整层重算，跟格数无关”，但实际是“每层每次两次全量几何重剪”，9 个独立玩家就是 9×4 次全图建筑重剪。
- `src/scene/memory.ts:237-240`：每次 update 还对每个 layer 的每个 seen object 做 `JSON.stringify` 身份比较。

**实测（Node 24.11，100×80，3 张图，每图 454 段建筑，9 个角色；`api.update(fn,{history:false})`，单位 ms/次）**

| 模式 | 纯移动 move | 只改 session | 只改棋子名 | 只改队员 HP |
| --- | ---: | ---: | ---: | ---: |
| shared | 110 | 0.2 | 4.7 | 83 |
| individual | 1030 | 407 | 410 | 489 |
| grouped | 1984 | 1436 | 1441 | 1522 |

直接拆分（同一场景，3 张图）：

- individual：`withVision(move)` ≈ 195 ms，`syncMemory(move)` ≈ 596 ms；只改 session 的 `withVision` 仍 ≈ 176 ms；`syncMemory` 全量换 move ≈ 1401 ms。
- grouped：`withVision(move)` ≈ 330 ms，`syncMemory(move)` ≈ 475 ms；只改 session 的 `withVision` ≈ 317 ms；`syncMemory` 全量换 move ≈ 1128 ms。
- 1 张图 9 人时 individual 的 `syncMemory(move)` 仍 ≈ 598 ms；grouped ≈ 477 ms；shared ≈ 73 ms。说明成本主要不是格数，而是**按玩家/组复制整层 + 每层建筑全量重剪**。
- 文档 `docs/视野增量计算-v0.1.md:81-84` 的 100×80/454 墙/9 人/3 图口径是“整条链路 ~230 ms、视野 ~17 ms、记忆 ~100 ms”；在这台机器上按同尺寸复测，独立/分组明显不在这个量级。即使考虑 2 核 VPS 与 Mac 的绝对差异，session/改名这种非视野更新仍要 0.4–1.4 s，方向不对。
- `shared` 基本符合预期（只改 session 0.2 ms），说明问题集中在 non-shared 的 clone/merge/建筑重剪路径，而不是 dirty 本身。

**影响**

- 9 人 3 图是 PR 自己写明的目标规模；当前独立/分组模式下拖动棋子、打字、扣血都会让主持人主线程付出 0.4–1.5 s，直接影响拖动/输入体感，且比文档“改前 ~770 ms”还差。
- 纯改名/扣 HP 本不需要重算视野；`withVision` 仍未 early-return 空 scope，导致这些更新付整层 clone/merge。`store.update` 的 `needMemory` 能跳过 syncMemory，但跳不过 `withVision`。
- 建筑记忆全量化让 scope 优化只覆盖“格”，没有覆盖最大头之一。

**建议（按收益排序）**

1. `withVision` 对 `scope?.size === 0` 且无 membership/manual/opts.full 的图直接跳过整张图的 clone/merge（仍保留必要的先生成 `m.views`/清理失效 view 的逻辑）。这样 session、棋子改名/HP、队员 HP 在 non-shared 下接近 shared。
2. 把“每组先 merge 再 clone 给 peer、最后整图 merge”改成**只在 scope 非空时做**，并缓存 per-group 结果，不要每笔 update 重建整层。
3. 建筑记忆增量：scope 只覆盖与脏区相交的墙段/房间，或至少与 scope 外旧 architecture 合并而不是每次 `clipArchitecture` 重剪整层；`pruneMemory` 同理。
4. `cloneLayer` 改成结构化浅拷贝 + 只拷贝变化数组；`mergeLayers` 的 `choose()` 不要用 JSON 字符串比较器，改用稳定 id/版本比较。
5. 增加 Node 性能基准到 CI（至少非 shared 的 session/move 两档），否则文档数字无法防回归。

**优先级：P1（目标规模下不可用；与 P1-1 同为阻塞项）。**

### P2-1 `autoFog=true` 时，手动雾会被棋子/队员的普通元数据修改整图覆盖

**位置**

- `src/scene/perception.ts:106`：`otherDirty` 用整包引用比较 `before.tokens !== src.tokens`、`membershipChanged`（party 引用变化）；`:111` `manualApply = manual && (otherDirty || opts.full)`；`:113` 的 pending 条件。
- `src/core/store.ts:164` 的 `planVision` 已经把 `party` 引用变化视为 globalFull；`src/scene/dirty.ts:49` 同样。
- 与 `src/core/store.ts:124-132` 的 `partyVisionChanged` 口径不一致：store 认为 HP/名字/技能不影响视野，`withVision` 却按整包 party 引用判脏。

**复现（store 实际路径）**

- 40×30 图，`autoFog=true`；对视野外格 `(35,28)` 调 `paintFog(...,'fogReveal')`，三种模式都从 `fog=0` 变 `1`。
- 随后只改棋子名字：`api.update(d => { d.maps[0].tokens[0].name = '改名'; }, {history:false})`。
- 结果三种模式全部 `fog=1 → 2`，所有 `m.views[*].fog` 也变 2。
- 同类触发：改 token HP、队员 HP/名字、队伍数组任何字段变化；甚至分组模式下只改 `session` 不触发 `otherDirty`，但 `grouped` 的材质记忆仍会被 merge 丢掉（P1-1）。

**影响**

- 手动揭示/隐藏的格子在“改个名字/扣个血”后立刻被自动迷雾覆盖，主持人会认为手动工具失效；文档 `docs/视野增量计算-v0.1.md:59` 说只有“下一次有视野脏动”才覆盖，而改名/扣血不是视野脏动。
- 这也放大了 P1-2：这些普通编辑在 non-shared 下还付整层 clone/merge。

**建议**

- 把 `withVision` 的 `otherDirty` 改成**字段级**判断：token 只看 `x/y/subcell/facing/stance/pcId`（必要时还有会影响眼高的派生字段）；party 只看 `id/visionGroupId/sex/heightCm`（抽成与 `partyVisionChanged` 共享的谓词）；`materialCells/fineMaterials`、`heights/rooms/groups` 不应算视野脏动。
- `diffWorld` 的 `globalFull` 也改用同一个 `partyVisionChanged`，不要整包 party 引用。
- 增加断言：手动 reveal 后改 token name/HP/party HP，fog 必须保持 1，直到下一次真正的移动/结构变化。

**优先级：P2（正确性/UX，非数据丢失；但应在上线前一并修，否则手动雾不可靠）。**

### P2-2 dirty 信号过宽，`heights/rooms/groups/material` 改动也触发整图视野和全量记忆

**位置**

- `src/scene/dirty.ts:39-43`：`mapStructureChanged` 把 `heights`、`rooms`、`roomCells`、`groups`、`materialCells`、`fineMaterials` 都算结构变化；`:64` 任一结构变化 `full=true`；`planVision` 对 `full` 直接整图。
- `src/scene/dirty.ts:49-50`：`party` 整包引用变化触发所有地图 full。
- 这些字段中：`heights` 只影响渲染/跳跃（`src/scene/sight.ts` 的 `cellSightCost` 不读 heights）；`groups` 只是贴图记忆；`materialCells/fineMaterials` 只进材质记忆；`rooms/roomCells` 是房间归属。它们不应让 `withVision` 重算 fog，但当前会生成 full plan，`syncMemory` 也会因 `plan.full` 走全图。

**影响**

- 画一格高度/改一个房间/涂一块贴图/改一格材质，会让所有地图所有玩家走整图视野 + 全量记忆；9 人 3 图时是 P1-2 的最坏路径。
- 还会让手动雾按 P2-1 的路径被覆盖（因为 full plan + para dirty）。
- 这是“保守上界”的设计选择，不是漏算；但保守到与视野无关的字段，成本/收益不成立。

**建议**

- 把 dirty 拆成两个谓词：`visionStructureChanged`（cells/fineCells/d100/objects 中真正影响视线的状态/architecture/terrains）与 `memoryOnlyChanged`（groups/material/rooms/heights 等）。`planVision` 只接收前者；`syncMemory` 可以继续用后者触发，但不应把 `plan.full` 传给视野。
- `diffWorld` 对 token 新增/删除仍全图；对 `party` 用 `partyVisionChanged`。
- 增加“改高度/改贴图组不改变 fog”的测试，防止以后又把无关字段加回 full。

**优先级：P2（性能/架构；在 P1-2 修复时一起收）。**

## P3

1. **`plan` 是隐式契约，`MapScope`/`CellScope` 两套表示**
   - `src/scene/visionPlan.ts:13` 定义 `MapScope = Set<number> | null`；`src/scene/memory.ts:19-20` 定义 `CellScope = Set<number> | undefined`。
   - `withVision` 的 `scopeOf`（`perception.ts:92-95`）和 `syncMemory` 的 `scope`（`memory.ts:216`）对 `null/undefined` 的处理不同；`planVision` 实际从不返回 `null`，`Set|null` 分支是死类型。
   - `withVision` 与 `syncMemory` 都假设 `plan` 来自同一对 prev→next，但没有版本/校验；调用方传错 plan 时，缺失地图会静默退回全图（正确但慢），不会报错。
   - 建议：统一成一个 `PlanScope = Set<number> | 'all'`，由 `planVision` 生成、带 map id 校验；或至少抽 `scopeFor(plan, mapId)` 一处实现。

2. **三份脏白名单已经出现漂移**
   - `dirty.ts:37-50`（结构/全局）、`perception.ts:106`（`otherDirty`）、`store.ts:134-147`（`memoryDirty`）。
   - 例：`dirty.ts` 把 `heights/rooms/groups/material` 当结构；`otherDirty` 不含这些；`memoryDirty` 额外含 `architectureFragments`，而 `dirty.ts` 不含。三者对“同一次改动”的判断不一致，正是 P2-1/P2-2 的根源。
   - 建议：抽一个 `visionChanged(a,b)` + 一个 `memoryChanged(a,b)`，三个调用点共用；测试直接对谓词做真值表。

3. **模块级可变状态不可重置**
   - `src/scene/dirty.ts:22` 的 `manualFog = new WeakSet<object>()`；`src/scene/sightIndex.ts:22` 的 `entries = new WeakMap<GameMap, Entry>()`。
   - 手动标记依赖“调用历史”；测试只能靠新模块实例/新对象隔离，没有 `resetManualFog()` / `clearSightCache()` seam。`undo/redo/导入` 时标记跟对象走，行为正确性依赖注释而非显式状态机。
   - 建议：把 mark 变成 map 上的显式字段（例如 `manualFogRev`/`manualFogPending`，随 world 保存/恢复），或至少提供只在测试/诊断用的 reset API；sight cache 提供统计和 clear。

4. **`cloneLayer` 与 `mergeLayers` 的 JSON 分配**
   - `vision.ts:6` 整层 JSON 深拷贝；`vision.ts:47` 每次候选比较 `JSON.stringify`，`:62` 每 key `flatMap`。在 P1-2 的高频路径上会放大 GC/CPU。
   - 建议：结构化 clone + 按 rev 直接比较；`choose` 的 tie-break 用 id/稳定字段而不是 JSON 字符串。

5. **O(n²) 与小分配**
   - `dirty.ts:63` 对新增/删除 token 用 `before.tokens.some(t => !m.tokens.some(...))`；token 多时二次。
   - `memory.ts:158` 每个 live object 对 `L.seen.objects` 做 `findIndex`；objects 多时二次。
   - `memory.ts:145` 每层 `{ ...source, fog: layer.fog }` 复制整个 map 对象。
   - 建议：token 用 Set/Map diff；objects 建 id→index Map；`anyVisible` 只取 width/height/fog 的小对象。

6. **物件锚点在脏区过滤/空间键里不一致**
   - `src/scene/vision.ts:29-33` 的 `spatialKeys` 用 `r.x/r.y` 直接 ×3，忽略 `SeenObject.anchor`；`memory.ts:99-100 touchesRect`、`vision.ts:112-113 rectHits` 也不含 anchor；`hostSession.ts:225` 的 seen object 可见性同样只看 raw x/y/w/h。
   - 物件锚点会按 1/3 格偏移（`objectFootprintCells`，`core/grid.ts:78-88`），所以锚点物件在 scope 边界上可能被误判为“不相交”，scoped memory 漏同步；`pruneMemory` 也可能误删。当前测试基本没有带 anchor 的物料/记忆用例。
   - 建议：统一用 `objectRect`/`objectFootprintCells` 做矩形/空间键；补 anchor 在 scope 边界上的测试。

7. **文档与实现/实测不一致**
   - `docs/视野增量计算-v0.1.md:64` 声称 `syncLayer`“物件按脏区外接矩形过滤，贴图组只处理与脏区相交的”，但没有说建筑记忆每个 layer 全量重剪（`memory.ts:142-144`）；实际建筑是最大成本之一。

   - P2-1 的手动雾行为也与 `:59` 的“下一次视野脏动”措辞不完全一致（token 改名/扣血也被算作脏动）。

8. **`WallIndex.stamp/tick` 共享可变状态，且缺少可观测性**
   - `src/scene/sight.ts:175-230` 的 `WallIndex` 用共享 `stamp/tick` 去重；当前调用是单线程且没有递归回调，所以未发现错误，但一旦以后在 `wallSightSumIndexed` 内重入/并发复用同一 index，就会漏墙或重复计数。

   - 此外 schema 对 `token.x/y` 只做 `int` 校验、没有地图边界约束（`src/core/schema.js:662`），越界 token 的视野是未覆盖边界；本次没把它列为已确认 bug，但属于残余风险。
