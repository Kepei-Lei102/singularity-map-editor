## 2) 迁移判定安全性：只认明确名字，不误伤

探针矩阵（一扇门 `states=[关闭, X]`、`openStates=[]`、`blocksWhen=[0,1]`）：

| 状态名 X | 结果 |
|---|---|
| `打开`、`开门`、`开着`、`开启`、`open`、`OPEN`、`Opened`、`opened`、` 开门 `（前后空格） | 补成 `openStates=[1]`，`blocksWhen` 去掉 1 → `[0]`，提示「按状态名补成「X」」 |
| `关着`、`关闭`、`锁着`、`打开门`、`未打开`、`开`、`已打开` | **不动**，提示「状态名里也没有『打开/开门/open』，请手工设一个」 |

- 正则 `schema.js:156` 是 `^(打开|开门|开着|开启|open|opened)$/i`，锚定 + `trim()`，不会把「关着/锁着」「打开门/未打开」误判成打开；大小写和前后空格都正常。
- **多扇门**：逐扇处理，消息逐条列；无 `name` 时 label 回退到 `id`。
- **同一门多状态**：`findIndex` 取第一个打开名；`blocksWhen` 只去掉这一个下标，其余不动（不猜别的状态该不该挡）。
- **`blocksWhen` 同步**：`[0,1]→[0]`、`[0]→[0]`、`[1]→[]`、`[1,0]→[0]`；数组缺省/空数组保持原样（见 P3-2）。
- **幂等**：补完再跑第二次返回空消息、字段不变。**合法数据**（`openStates=[1]`、`blocksWhen=[0]`）跑 `repairWorld` 返回 `[]`，对象逐字节不变。
- 补完 `checkWorld` 能过（合法墙+门的探针世界）；两扇门一扇能猜一扇不能时，只有能猜的动，另一扇留空并给「请手工」提示。

## 3) `repairWorld` 顺序与“会不会改坏”

- `repairWorld` 里门迁移放在**函数最后**（`schema.js:146`），所有调用方都在它之后才 `checkWorld`（导入、导出、CLI、`migrateWorld`）✓。
- 只对 `opening.openStates` 是**空数组**的门动手；合法的、非门的对象、`openStates` 非空的门全部跳过 → 不会把好数据改坏；幂等。
- 例外：`openStates` **缺失/为 null** 时直接跳过（`schema.js:160` 的 `!Array.isArray`），随后 `checkWorld` 会在 `checkArchitecture` 里抛 **裸 TypeError** 而不是「工程文件有问题：…」——见 P3-1。
- `migrateWorld` 在 `load()` 路径里调用 `repairWorld`，能猜到的旧自动存档会被修好；猜不到的留在内存里（不 `checkWorld`），所以“能打开、但导出/保存失败”。

## 4) P2-2：`setObjectStates` 的 fallback 会把关闭态标成打开态（新问题）

`actions.ts:459-490`。删/改名导致 `openStates` 映射为空时：

```ts
const mapped = [...new Set(o.opening.openStates.map(to).filter(i => i >= 0))];
if (!mapped.length) {
  const named = o.states.findIndex((s) => /^(打开|开门|开着|开启|open|opened)$/i.test(s.trim()));
  if (named >= 0) mapped.push(named);
  else if (o.opening.openStates.length) mapped.push(Math.min(o.opening.openStates[0], o.states.length - 1)); // ← fallback
}
o.opening.openStates = mapped;
```

探针（合法门 `states=[关闭,打开]`、`openStates=[1]`、`blocksWhen=[0]`，经 Inspector 的状态列表文本框 `Inspector.tsx:475` 提交）：

| 用户提交的 states | 实得 | 后果 |
|---|---|---|
| `['关闭']`（删掉打开态） | `openStates=[0]`、`blocksWhen=[0]`、`state=0` | `openingIsOpen=true` **门立刻变成打开**；`architectureGeometry` 里门构件消失（门洞可通过）；`toggleArchitectureDoor` 返回「门缺少关闭或打开状态」，**再也关不上**；`checkWorld` 过；测同一把 `lock:{locked:true}` 的锁仍锁着，但门已可通过 |
| `['']` / `[]`（清空文本） | `states=['']`、`openStates=[0]`、`blocksWhen=[]` | 同上：门永久打开、不可关；`checkWorld` 过 |
| `['关闭','锁死']`（同长度换名） | `openStates=[1]`（位置保留） | 门“打开态”叫「锁死」，能开能关；语义误导但结构正常 |
| `['锁着','关着']`（同长度改名） | `openStates=[1]`（「关着」） | 门打开态叫「关着」；能开能关 |
| `['打开']`（只删关闭态） | `openStates=[0]`、永久打开、不可关 | 门只剩打开态，物理上正常但无法关闭 |
| `['打开','关闭']`（对调） | `openStates=[0]`、`blocksWhen=[1]` | 正常 |
| `['锁着','关着','打开']`（改名+加状态） | `openStates=[2]` ✓，但 `blocksWhen` 被映射成 **`[]`** | 关闭态「锁着」不再算挡路（`blocksWhen` 是门自己的语义字段，当前运行时移动/视线主要读 `openStates`/几何，影响小；见 P3-6） |

**判断**：这个 fallback 不合理。作者要的是「门至少能开」，但只剩非打开名状态时，fallback 把其中一个关闭态声明成打开态，效果是**门悄悄变成开着且关不上**，正是 docs `:271` 说的「别悄悄把某扇门当开着」的反面；而且 `checkWorld` 只查 `openStates` 非空、不查它与 `blocksWhen` 是否相交（`schema.js:417-419`），所以保存/导出都放行，问题到下一局才暴露。

建议修法（任选，优先前两条）：

1. 与 Inspector 复选框的既有口径对齐：`Inspector.tsx:456` 在取消最后一个打开态时会 `toast('门至少要留一个「打开」状态')` 并拒绝。`setObjectStates` 在“映射后为空且没有打开名状态”时也应**拒绝这次编辑**（toast 后不 `update`），不要凭空挑一个位置；用户要删打开态，必须先加一个打开名状态。
2. 若保留 fallback，选中的下标必须**不在 `blocksWhen` 里**、且不能等于当前 `state`（否则门立刻“打开”）；选中后同步把该下标从 `blocksWhen` 去掉。
3. `checkWorld` 增加不变量：`openStates` 与 `blocksWhen` 不得相交（或至少 door 的 `blocksWhen` 不应包含任何打开态），`repairDoorOpenStates` 对非空 `openStates` 也顺手去掉相交项。

## 5) P2-1：“猜不到”的旧门仍在门外，且提示被丢弃

- 探针等价 `parseWorld` 链路（`repairWorld` → `repairOrphanSubcells` → `checkWorld` → `migrateWorld` → `checkWorld(w,true)`）：
  - 能猜到：过；repair 返回「按状态名补成「打开」」。
  - 猜不到（旧门 `states=['关','开']`）：`repairDoorOpenStates` 返回「…请手工设一个」，但链路在第一次 `checkWorld` 就抛
    `工程文件有问题：地图「一楼」.objects[1]（门）.opening.openStates 门至少要有一个打开状态`。
- 浏览器三条路径都把 `fixed` 丢了：`parseWorld` 的 `repairWorld(w)`（`actions.ts:899`）不接返回值；`buildProjectZip` 的 `repairDoorOpenStates(w)`（`:828`）和 `exportWorldJson` 的（`:863`）同样不接。只有 CLI 的 `warnRepairs(repairWorld(world))`（`tsmap.mjs:66/77`）会打印「请手工设一个」。
- 实测 `exportWorldJson` 猜不到时 toast 是 `导出失败：工程文件有问题：…门至少要有一个打开状态`（没有 repair 提示）；`saveToDisk` 同样 toast `保存失败：…` 且没有发 `/__save`。也就是说 `docs:271` 写的「名字里找不到就不猜，直接提示手工设」在浏览器里只兑现了后半句的 schema 错误，没兑现「手工设」这个可操作提示。
- 影响：旧工程若门的打开态名字不在 6 个模式里（例如 `关/开`、`锁死/打开门`、`已开`），**从文件导入会直接失败**（备份恢复同样），用户拿不到工程；已在自动存档里的旧工程虽能打开（`load()` 不 check），但导出/保存磁盘会失败，需要先在 Inspector 里把某个状态改成打开名/勾选打开态。按作者「旧工程能继续用」的收口，这是 P2。
- 建议（按成本从低到高）：
  1. 至少把 `repairDoorOpenStates` 的返回值接到 UI：`parseWorld` 返回/抛出带「门『X』没有打开状态…请手工设一个」的错误；`buildProjectZip` / `exportWorldJson` 在 `checkWorld` 抛错时把 hint 拼进 toast。这样用户知道要改哪扇门。
  2. 导入时给显式修复选择：若 hint 里含「猜不到」，弹 confirm「门『X』没有打开状态，是否补一个『打开』状态后导入？」——用户同意后才补（不是静默猜），旧工程能直接继续用。
  3. 或允许导入后进入编辑器、在 Inspector 里修（需要把严格 `checkWorld` 放宽为警告一次）；但这会破坏「交给编辑器的一定是完整工程」的现有约定，不如 2。
  4. 名字表可加上明确无歧义的常见写法（如 `开`、`已开`、`已经打开`，仍锚定整串），减少挡在门外的旧工程；但“猜不到不猜”的原则下这只能算辅助。

## 8) 新问题清单

1. **P2-1（未关闭）— 猜不到的旧门仍把旧工程挡在导入/导出/保存之外，且 repair 提示在浏览器被丢弃**：`parseWorld`/`buildProjectZip`/`exportWorldJson` 均不接返回值；`docs:271` 承诺「直接提示手工设」未兑现。建议按 §5 接提示/给导入时显式修复选择。
2. **P2-2（新，需修）— `setObjectStates` fallback 把关闭态标成打开态**：只剩关闭态/清空状态列表时门立刻 `openingIsOpen=true`、锁着的门变成可通过门洞、`toggleArchitectureDoor` 永远报「门缺少关闭或打开状态」，`checkWorld` 放行。建议拒绝编辑或只在非挡路状态下标选择，并加 `openStates ∩ blocksWhen = ∅` 不变量。
3. **P3-1 — `openStates` 缺失/null 不迁移**：`schema.js:160` 的 `!Array.isArray` 跳过；随后 `checkArchitecture` 的 `openingIsOpen` 对 undefined/null 调 `.includes` 抛裸 TypeError（不是「工程文件有问题：…」）。旧编辑器门都写过这个字段，概率低；建议把缺失/null 当空数组迁移，并给 `openingIsOpen` 加防御。
4. **P3-2 — `blocksWhen` 缺失/空数组不补**：`schema.js:166` 只有数组才过滤；缺失时补完 `openStates` 后 `blocksWhen` 仍 undefined（语义上“每态都挡”），空数组则任何状态都不挡。当前运行时门移动/视线主要由 `openStates`+几何决定，影响小；但字段语义不完整，建议迁移时按“除打开态外都挡”补齐。
5. **P3-3 — 浏览器里成功迁移也是静默的**：`parseWorld`/`buildProjectZip`/`exportWorldJson` 都丢掉 `fixed`，用户不知道哪扇门被按名字补了；CLI 有 `warnRepairs`。可接受但和 docs 的“提示”口径不一致。
