## AssetSession 语义

- `activeCount` 把同一 requestId 的重复 refs 也算进总量；`tryAcquire` 先看 refs（≥4 拒绝），再看 activeCount（≥64 拒绝），拒绝时不占引用。
- `release`：不存在的 requestId 直接返回；refs 减到 0 才删 requestId；只要 refs 还 >0，cancel 保留。不存在 id 不会误删别人的账。
- `cancel`：只认 active 里 refs>0 的 requestId，迟到/木马 cancel 返回 false 且不建表；带 key 时最多 64 个 key，不带 key/空 key 设 `all`；`isCancelled` 对 all 或指定 key 生效。
- 引用归零时删 cancel；`cancel` 后再 `release` 的路径测试覆盖：两个 serve 共用一个 requestId，release 一次不丢 cancel，release 到 0 才丢。
- 旧实例：`register` 给新 fresh；旧 serve 的 `.finally` 捕获的是旧实例，`release` 只还旧账，不会减新连接的相同 requestId。旧实例本身仍可 release，不需要 epoch。
- 边界：`tryAcquire` 在 refs=4 或 total=64 时都拒绝；两者同时到达也走短路拒绝，不会先占后拒。`release` 不存在的 id 是 no-op；`cancel` 空字符串按 all 处理，和旧实现一致。
- **没有发现 P2 语义错误。**

## reject / active

- `tryAcquire` 失败走 `rejectAssetRequest`：用 `serveAssetRequest` + `load/meta undefined` 发 forbidden，最多 32 条 × 45ms ≈ 1.44s；不登记 active，玩家 reset 的 cancel 对它无效。
- 这可接受：拒绝流有界，不占 64 个在途名额，也不会把不该给的文件发出去；不建议改成 allow，allow 会放开媒体库，风险更大。
- **P3**：如果一定要让 reset 能立刻停掉拒绝流，需要给 reject 也登记一个轻量 active/cancel 标记；当前 1.44s 的尾巴对正常玩家无感，对恶意请求也只是浪费一点带宽。
- `rejectAssetRequest` 的 `send` 在 `players` 已删时返回 false，`serveAssetRequest` 的 start/chunk/end 都会提前结束，符合预期。
