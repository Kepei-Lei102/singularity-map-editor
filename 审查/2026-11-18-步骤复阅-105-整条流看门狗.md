## abort 路径

- timer 在 serve 开头 arm；每次 `opts.send` 返回 true 后重新 arm（start/chunk/end/fail 都算）。到点先 `flowAborted=true`，再 `onFlowTimeout`；所有发送点都检查：
  - key 循环顶、load await 后、load catch、fail 回调、start 回调、chunk 读取后、chunk 回调、end 回调；abort 后不再发任何 body。
  - `paced` 等待期间 abort：回调进入时检查 `flowAborted`，返回 false；已在执行中的同步 `send` 不会被 timer 打断（JS 单线程，timer 只能在该同步段之后触发）。
- load pending 的测试：watchdog20 触发，`onFlowTimeout` 收账本；load resolve 后 serve 只走到 abort 检查就收尾，`sent=[]`。行为正确。
- **abort 后 serve 仍持 session，直到 load resolve / serve finally**：`onFlowTimeout` 只 `session.cancel` + `endAssetFlow`，不 release、不 drain。因此：
  - **queued 请求不会在 watchdog 到点时立刻 drain**，要等这条 aborted serve 的 `.finally`；正常 load 30 秒超时会在60秒 watchdog 前结束，所以生产默认不会出现“60秒时 load 仍挂着”；只有自定义 `flowTimeoutMs < loadTimeout`（测试20<30）或 `loadTimeoutMs:0` 时会多等。
  - **flow 已被删，`assetFlowHasRoom` 会放新请求进来**，旧 aborted serve 还占一个 active ref；会出现“2 条 flow + 旧 abort serve”的瞬时 active>2，但旧 serve 不发任何块，受 `ASSET_MAX_ACTIVE=64` 约束；若队列里已有请求，新来的请求可能插到它们前面（drain 未跑），是公平性问题不是带宽问题。
- **watchdog 不向玩家发 fail/cancel**：玩家端的 pending 只能靠自己的 queue120/inactivity30 收口；若服务器在60秒中止且没有 start，玩家要等到120秒。这是 P3，不是永久 pending。

## 续命/误杀

- `fail` 成功后也 arm。32 个 key 全部 load 超时：每30秒一次 missing fail，send 后重置60秒 timer，不会在第一个60秒被误杀；整批会持续很久，但 watchdog 不会误杀。
- 每块 send 后 arm；`paced` 正常最多受全局约50块/s + 每条binding 45ms 限制，12人场景单块约240ms，远小于60秒。
- **每个 end 后也 arm**，然后 key loop 结束进 finally 立即清 timer，不会残留。
- **每个 chunk/start/end/fail 都 arm，测试2两块 pace30、总耗时>80ms，不会被80ms watchdog误杀。**

## sync 收尾

- `onFlowTimeout`：`session.cancel(m.requestId)` + `if (stats !== false) endAssetFlow(binding, m.requestId)`。
- serve 的 `.finally` 仍 `endAssetFlow + session.release + refresh + drain`。`endAssetFlow` 对不存在的 flow 是 no-op（Map.delete 不抛，空 Map 再 delete binding），所以双重调用幂等。
- `session.release` 在 cancel 后正常把 active 归零并删 cancels；不会把 `AssetSession` 弄坏。
- `refreshAssetTransferStats` 在 timeout 和 finally 各跑一次；flow 已删后 queued/inFlight 不会为负；ticker 看到无 flow 直接返回/后续重排正常。
- **`endAssetFlow` 删除 flow 后 serve 仍 active 的问题见上（active>2/queue drain延迟）**；不影响默认路径。
