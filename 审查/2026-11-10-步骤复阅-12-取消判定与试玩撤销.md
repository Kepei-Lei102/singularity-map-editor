## 9) 还有哪些路径会留下骰盘（重点）

先说根：PlayerView 的 `world` 分支只在一份**非空** `pendingJudgment` 时 `setPending`（`PlayerView.tsx:66-67`），`pendingJudgment:null` 的 world 推送**不会**清本地 pending；骰盘只能靠 `judge-cancel` 或 `clear` 收掉。所以任何「主持端清了 pending 但没发 cancel/clear」的路径都会留盘。

| 路径 | 骰盘会不会留下 | 实测/依据 |
|---|---|---|
| 取消判定（本笔修的） | 不会 ✓ | `judge-cancel` 到达 |
| 换判定（pending 已存在时再开） | 不会（开不出来） | `openJudgment` 拒绝：「已经有一个判定在等玩家掷骰，先结算或取消它」✓ |
| **代掷结算**（主持端点「代掷」，玩家窗口其实开着） | **会** | 主持端 `publishJudgment + setUI pendingJudgment:null`，只推 `world`（pendingJudgment:null）；玩家窗口收到 `world` 不清 pending，也**没有** `judge-cancel` → 骰盘一直挂着；玩家掷了会被主持端当 `p.judge==null` 丢掉 |
| **玩家自己掷完、主持端确认广播** | **会（面板残留）+ 这条路本身先失败** | `publishJudgment` 拒收 `persona:'player'`（见 P1）；即便用 witness 数据放行，也只推 world、无 cancel → 「轮到你了…已送到」面板常驻（骰盘在掷完后已隐藏） |
| **试玩结束 endTrial** | **部分会** | `clearTrialWindows()` 给试玩窗口发 `clear`（试玩窗口的盘会清 ✓）；但 **`pendingJudgment` 不清**（`endTrial` 只 `setUI({trial:null,…})`）→ 主持端 UI 卡在待掷面板、开不了新判定；之后随便开一个真实玩家窗口/推一次 world，旧试玩判定会通过 `pendingFor` 塞进新窗口 → 骰盘又出现（实测新窗口收到 `world.pendingJudgment={id:'jt1'}`） |
| **新建/载入工程 replaceWorld** | **会** | `replaceWorld` 只清窗口（`onProjectReplaced` 发 `clear`、清 players），**不清 `pendingJudgment`** → 跨工程残留；新工程里开窗口推 world 会把旧判定塞给玩家（实测收到 `旧工程判定`） |
| **开新窗口（pending 在）** | 正常 ✓ | hello→world 带 `pendingFor(pcId)`，该角色看到应掷的骰盘；别的角色看到 null |
| **切人 / 开窗口给别的角色** | 不会 ✓ | `pendingFor` 按 subjectId 过滤；world 只给该角色 pending |
| **主机关闭/刷新** | 约 10 秒后清 ✓ | `listenAsPlayer` 的 beat：10 秒没收到消息 → 自己 `fn({type:'clear'})`；玩家窗口刷新也会 hello→world 恢复 |
| **试玩请求/取消跨上下文** | 会发到「错的窗口」 | `pushJudgmentRequest`（旧）和 `pushJudgeCancel`（新）都不看 `trialContext`：试玩里 a 有真/试玩两个窗口时，**两个都收到** judge-request / judge-cancel（实测）。真实世界窗口会显示试玩的骰盘 |
| **直接调 `cancelJudgment()`（不经 wrapper）** | — | 仓库里没有别的调用点（grep 只有 wrapper 和定义），所以眼下不会漏 |

**建议**：①`standIn` 结算 / 正常结算也给 subject 窗口发一条 `judge-cancel`（或加 `judge-done`）；②`endTrial`、`replaceWorld`（以及 startFreshWorld/import 路径）在切换前把 `pendingJudgment` 清掉并给对应窗口发 cancel/clear；③`pushJudgmentRequest`/`pushJudgeCancel` 增加 trialContext 过滤；④ PlayerView 收到 `world.pendingJudgment === null` 时也可以顺手清掉本地 pending（一行，能兜住以后所有「只推 world」的路径）。

## P1（既有，非本笔引入）：`publishJudgment` 拒收玩家自己掷的骰子

- 实测：`publishJudgment({… roll:{persona:'witness', …}})` → **null（成功）**；同样数据改成 `persona:'player'` → **「骰子记录无效」**。
- 代码互斥：`rules/judgments.ts:18` 要求 `r.persona === 'witness'`；而 `JudgmentPanel.tsx:60` 的广播传的是 `persona: result.byStandIn ? 'witness' : 'player'`，玩家自己掷时 `onJudgeRoll` 把 `byStandIn` 设成 `false`（`sync.ts:399`）→ 传 `'player'` → 必然被拒。
- 影响：**玩家自己掷的正式判定**，主持端点「确认并广播给全队」会报「骰子记录无效」，判定卡在待掷面板；只有代掷（witness）能发出去。攻击走 `settleAttack` 不受影响。这与 `JudgmentForm` 的文案「见证者只宣告，不掷；骰子交给玩家」直接冲突。
- 历史：校验 `persona !== 'witness'` 是 `c1b913f`（10-31）就有；`result.byStandIn ? … : 'player'` 是 `18def62`（11-10 16:36）引入，两边一直没对上；仓库里没有测试覆盖 `publishJudgment`（`grep` 无命中）。不是 `d05530d` 引入，但这次审到真路径，建议优先修（允许 `player`，或广播时归一成 `witness`，并补一条测试）。
