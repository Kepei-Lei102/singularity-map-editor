## 一、试玩回合状态机（`src/runtime/trial.ts`）

### P1-1 战斗里第一个动作若是跳跃/攀爬，移动点直接清零 —— `trial.ts:556`

```ts
const left = Math.max(0, (t.movePoints?.[req.tokenId] ?? 0) - cost);
```

这是全场唯一一处**没有** `?? movePool(...)` 兜底的读法。回合开始时 `movePoints` 还没被写（要等第一次走格子才写），所以「本回合第一个动作是跳坑/攀爬」时 `t.movePoints` 是 `undefined`，`left` 变成 `max(0, 0 - cost) = 0`。

实测：战斗第 1 回合先跳跃成功落地，`movePoints = {t1: 0}`，之后再按方向键 → `这回合的移动点数用完了，按空格结束回合`。人要一直罚站到结束回合。

同一段逻辑还有个更隐蔽的面：`settleJump` 用的是**当前** `t.combat` 和**当前** `t.movePoints`，跟判定开出时不是同一份状态（见 P1-5）。

建议：这里也走 `t.movePoints?.[id] ?? movePool(budget, stored)`（跟 `trial.ts:243 / 345 / 1049` 统一成一个小函数 `leftFor(t, tokenId)`），顺手把「点池懒初始化」收成一个入口，别让 4 处各自读。

### P1-2 结束回合不重置跑法 / 拐弯计数 —— `trial.ts:666`

```ts
setTr({ moved: {}, turned: {}, turn: t.turn + 1, acted: false, opportunity: null, msg: '', charge, movePoints });
```

`runMode`、`runTurns` 没清。实测：`runMode:'run', runTurns:1` 过一回合后还是 `runMode:'run', runTurns:1`，`turn` 已到 2。

后果（跑法规则在 `trial.ts:215-231` / `992-1017`）：
- 「奔跑只准拐一次」变成**整场只准拐一次**，第二回合第一次拐弯就被拦。
- `runMode` 留着，下一回合第一格仍按奔跑单价 50 扣，但**不用再付 ME**（ME 只在 `trialRun` 时扣）——等于白送一个免费跑法。
- 界面上「本回合跑法」的高亮也会跨回合留着。

建议：`runMode: null, runTurns: 0` 加进这次 `setTr`。`turn` 归零的三处（`endTurn`、`toggleCombat`、`switchTrialPlayer`）都应共用同一个 `resetTurnLedger()`，别再各写一份——现在这三份清单各不相同（`toggleCombat` 还不清 `turned`/`charge`）。

### P1-3 行动点 / 跑法 / 锐器是「全队一份」，不是「每人一份」 —— `store.ts:253`、`trial.ts:670-673`、`trial.ts:762`

`acted?: boolean`、`runMode?: 'jog'|'run'|'sprint'|null`、`runTurns`、`sharpAttack` 都挂在 `Trial` 上（整个试玩共用一份），而 `moved` / `turned` / `movePoints` / `charge` 是按 `tokenId` 记的。

实测：A 攻击（`acted:true`）后按 Tab 切到 B，`actionsLeft(trial) = 0`——B 这一回合**也不能攻击**。要等 A 按空格结束回合，而结束回合是全队一起结束。

建议：按人分的字段全部改成 `Record<tokenId, …>`：
`acted?: Record<string, boolean>`、`runMode?: Record<string, 'jog'|'run'|'sprint'|null>`、`runTurns?: Record<string, number>`、`sharpAttack?: Record<string, boolean>`。
读的地方只有 `trialAttack:681`、`actionsLeft:670-673`、`trialRun:992-1017`、`trialRescue:897`、`trialSense:980` 和 TrialHud 的几处，改动面可控。

### P1-4 尸体和昏厥（`down`）还能走、能打 —— `trial.ts:205-207`、`trial.ts:688`、`trial.ts:681`

移动只拦 `tok.status`（`trial.ts:205-207`），攻击只拦 `stance === '躺'`（`trial.ts:688`）。`corpse` 和 `down` 是**另外两个字段**，没有任何一处拦。

实测：
- 棋子 `corpse = true`，连按两次方向键 → 走到 `4,2`，`msg` 为空。
- 棋子 `down = true`（钝器打到 0 血就是这个状态，见 `trial.ts:515` / `730`）→ 同样走掉。

好消息：`trialRescue:905`、`trialSense:973`、`trialStance:1035` 都查了 `corpse`；「濒死 / 晕厥」这种带 `status` 的也在 205-207 拦住了。所以只差 `trialMove` 和 `trialAttack` 两处，各加一行 `if (tok.corpse || tok.down) return setTr({msg:…})` 就补齐。`corpse` 在实战里会出现（`trialEndTurn:628` 濒死倒计时到了就把棋子设成尸体）。

### P2-1 关/开战斗不重建点池 —— `trial.ts:762`

实测：`movePoints {t1:264,t2:414}` → `toggleCombat()` 两次 → `turn` 回到 1，`movePoints` 还是 `{264,414}`。回合归零了、点池没归零，下一回合的额度是上一回合的残值。

### P2-2 `pendingGap` 跨回合、跨角色都不失效 —— `trial.ts:288-298`、`trial.ts:666`

### P2-3 打没有血条的目标，行动点照扣、判定照记命中 —— `trial.ts:713`、`trial.ts:730`

`update` 里 `if (!pool) { note = …; return; }` 提前退出，但外面 `setTr({ acted: true, event: { kind: r.hit ? 'hit' : 'miss', … } })` 照写。结果是：对一堵墙/一个没填 HP 的 NPC 挥一刀，算你打了一刀（行动点没了），卡片还写「命中」，底部小字才补一句「没有血条」。

### P2-4 借机攻击不结算 NPC 伤害，也不会让人濒死 —— `trial.ts:859`

```ts

```

只有带 `pcId` 的目标才扣血；但 `hits.push` 里照样写伤害数字，`msg` 也那么显示。同一套攻击规则，`trialAttack` 会扣 NPC 棋子上的 `hp/hpMax`、会挂 `downed`/`status`，借机攻击两样都不做。

### P2-5 反复点同一个跑法会白扣 ME —— `trial.ts:992-1017`

`mode === t.runMode` 时没有「已经是这个跑法」的短路：再点一次「奔跑」就再扣一次 ME、`runTurns` 归零，人可以靠反复点跑法绕开「只准拐一次」。

建议：`if (mode && mode === t.runMode && t.runMode !== null) return null;`（或者把 ME 扣费挪到「本回合第一次移动」时结算）。

### P2-6 状态栏还在按「细分格」显示 —— `TrialHud.tsx:89`

## 二、沙盒 / epoch

### P1-5 判定结果和当前判定没有绑定：取消一笔判定后，下一颗骰子会被当成新判定的结果 —— `judgments.ts:60-68`、`JudgmentPanel.tsx:47`、`JudgmentPanel.tsx:56`、`JudgmentPanel.tsx:91`、`JudgmentPanel.tsx:101`

链条：
1. `cancelJudgment`（`judgments.ts:60-68`）只 `setUI({ pendingJudgment: null })`，**不清 `judgmentResult`**；`openJudgment`（`judgments.ts:36-57`）也不清。
2. `PendingJudgmentPanel` 直接 `const result = getUI().judgmentResult`（`JudgmentPanel.tsx:47`），**没有 `result` 与 `p` 的 id / session 比对**。
3. 于是：开一笔判定 → 玩家掷了 → 见证者点「取消」→ 再开一笔新判定（或换角色、换工程后再开）→ 面板立刻显示「他掷出了：D20 = 17」，那是**上一笔**的骰子。
4. 此时点「确认并广播」（`JudgmentPanel.tsx:51-63`）会把旧 `result.rollId / sides / value` 原样包进新判定去 `publishJudgment`。`publishJudgment`（`judgments.ts:5-28`）只校验这颗骰子自身自洽 + 没被用过，不会校验它属于哪一笔 → **新判定得到旧骰子，而且写进了判定记录**。
5. 跳跃更直接：`按结果执行` 调 `settleJump(p.jump!, [result.value])`（`JudgmentPanel.tsx:91/101`），`p.jump` 是新的、`result.value` 是旧的 → 用上一颗骰子结算这一次跳。这里也**没有上下文检查**（没有 `ctx === worldContext()`、没有 `p.session` 对比），全靠 tokenId 碰巧不匹配来挡；同一次试玩里 id 是匹配的，挡不住。

实测（伪造注入那一半见 P1-6）：`onJudgeRoll` 把任意 `value` 写进 `judgmentResult`，面板原样显示 `D20 = 999`，不校验 `<= sides`。

后果：骰子是这个程序最核心的可信承诺，现在「哪颗骰子属于哪一笔判定」只靠一个全局槽。见证者点错一次，判定记录就是错的，而且不可撤销（判定一旦 publish 就进了 `w.judgments`）。

建议：
- `judgmentResult` 加 `judgmentId` 字段，`PendingJudgmentPanel` 只在 `result.judgmentId === p.id` 时才用；`broadcast` / `settleJump` 也走同一个判断。
- `cancelJudgment` / `openJudgment` 里把 `judgmentResult: null` 一起清掉。
- `settleJump` 开头加 `p.session === getWorld().session`（或 `pendingJudgment.at` 之后的上下文检查），失败就返回「判定已经过期，重新开一笔」。

### P2-7 工程替换不清试玩 / 判定的 UI 残留 —— `store.ts:171-181`

`replaceWorld` 只做「epoch++、清 history、通知 listeners」，`ui` 完全不动。所以导入新工程后：`pendingJudgment` 还指着旧工程的 party id（面板显示「等 角色 掷骰」、且 `openJudgment` 会一直回「已经有一个判定在等」），`judgmentResult`、`pendingGap` 也留着。

现在的兜底是 `onProjectReplaced` 清了玩家绑定、玩家窗口收 `clear`；但主持人自己的判定面板没人管。

建议：`replaceWorld` 里顺手 `setUI({ pendingJudgment: null, judgmentResult: null, pendingGap: null, selection: null, trial: null })`——它已经在 import 路径上了（`actions.ts:commitImport` 之前会 `endSandbox`）。

### P2-8 试玩里 ⌘Z / ⇧⌘Z 照样能用 —— `App.tsx:84-89`、`store.ts:152-169`

`onKey` 里 undo/redo 分支在 `if (getUI().trial)` **之前**，只有 ⌘S 做了试玩拦截（`App.tsx:91`）。试玩里 `undo()` 会去弹 `past`：一笔试玩改动都没有时，`past` 里全是**试玩前**的快照，undo 会把试玩世界退回到进试玩前的样子（`emit` 在 sandbox 里不存盘，玩家窗口会收到这个退回的世界）；`endSandbox` 之后世界和 history 又整体还原，所以不会污染正式工程——但现场会看到莫名其妙的一步回退，而且 `batchStart` 会被打断。

建议：`if (getUI().trial) return;`（放在 mod+z 之前）；真要在试玩里悔一步，应该是试玩自己的栈。

### P2-9 `replaceWorld` 不处理 sandbox（防御缺口，当前打不到）

`beginSandbox`（`store.ts:370-373`）在同一次试玩里是幂等的（`if (sandbox) return`），`endSandbox` 会**整体**把 `world / past / future` 换成快照。如果将来有路径在试玩中调用 `replaceWorld`，导入的新工程会被 `endSandbox` 静默换回旧世界——表现就是「导入了但没生效」。

现在所有调用点都先 `endSandbox` 或先检查 `getUI().trial`（`actions.ts:782/819/835/855/980`），所以打不到。建议在 `replaceWorld` 里加一句断言/自动 `endSandbox`，别让这个约束只活在调用方的记忆里。

### P2-10 `judge-cancel` 有协议、玩家端有处理，但**没有发送方** —— `sync.ts:26`、`PlayerView.tsx:65`、`judgments.ts:60-68`

`SyncBody` 里声明了 `judge-cancel`，`listenAsPlayer` 白名单里有它（`sync.ts:456`），`PlayerView.tsx:65` 收到会 `setPending(null)`；但 `src/` 里没有任何一处 `send({ type:'judge-cancel' })`。

后果：见证者点「取消整个判定」后玩家窗口的骰盘一直开着（要等下一次 `world` 推送把 `pendingJudgment` 刷成 null 才会关）。玩家在那儿掷完骰，主持人这边什么都不发生。

建议：`cancelJudgment` 里 `pushJudgmentRequest` 的反向消息（发给该 `subjectId` 的绑定）。

现状：`MediaPanel.tsx:14` 先抓 `ctx = worldContext()`，`storeBlob` 之后在 `:21` 再比一次，不一致就 toast 并丢弃；`commitImport`（`actions.ts:977-980`）、`restoreBackup`、`importAnyFile`、`playMedia:333-337` 都有 ctx 检查。**这条可以划掉。** 只剩两个小尾巴：

## 三、跨窗口安全（`src/runtime/sync.ts`）

先回答三个明确问题：

### 问 1：任何窗口能不能伪造 `world` / `judge-roll`？

- `world` **不能**。它只由主持人 `send()` 发出，玩家端 `listenAsPlayer:456` 白名单里有 `world`，`:458` 又要求 `source === window.opener`，别的窗口发不进来。
- `judge-roll` **能**。见 P1-6。

### P1-6 `judge-roll` 两条入口都不验来源、不验内容 —— `sync.ts:366-375`、`sync.ts:397`、`sync.ts:427`

```ts
function onJudgeRoll(m) {
  const p = getUI().pendingJudgment;
  if (!p || p.id !== m.id) return;
  setUI({ judgmentResult: { …结果原样抄过去… } });
}
```

只比了一个 `id`。没有 `m.from === SESSION`、没有「这个窗口是不是这一笔判定的当事人（`binding.pcId === p.subjectId`）」、没有校验 `sides/value/tens/units` 自洽。而 `listen` 的守卫 `:397` 是 `… && e.source`——`source === null` 的 BroadcastChannel 消息**整条跳过**来源检查，直接进 `listenAsEditor:427` → `onJudgeRoll`。

实测（两种都成）：
- 用一个**没有绑定**的陌生窗口对象 `postMessage` 一条 `judge-roll`，`value:999, sides:20` → `judgmentResult` 原样落进 UI。
- 用 BroadcastChannel（`source = null`）发同一条 → 一样落进 UI。

后果：
- 任何同源标签页（另一个玩家的窗口、另一个编辑器标签页、甚至控制台）都能往主持人的待掷判定里塞一颗骰子。玩家本来就能自己选点数（这是设计），但**塞进一个不可能的点数**（`> sides`）会让面板显示 `D20 = 999`，见证者点广播时 `publishJudgment` 报「骰子结果无效」，于是只能取消——这次跳跃/攻击就白做了。
- 和 `DiceTray.isRecord`（`DiceTray.tsx:55-72`）的校验口径完全不一致：组件这边查了协议、`sides`、整数、`randomSeed` 的 64 位十六进制、发射参数、TEN/UNIT 一致性；到了 wire 上（`SyncBody:27`）只带 `id/title/sides/value/tens/units/material/seed/rollId`，主持人侧**一项都不查**。

建议：`onJudgeRoll` 里补
```ts
if (!p) return;
if (m.from !== SESSION) return;                    // 主持人自己的会话
if (!Number.isInteger(m.value) || m.value < 1 || m.value > m.sides) return;
if (!Number.isInteger(m.sides) || m.sides !== p.sides) return;
if (m.tens !== null && !(Number.isInteger(m.tens) && m.tens >= 0 && m.tens <= 9)) return;
```
（`units` 同理；`material` 走 `MATERIALS` 白名单。）再加上「是否当事人」的检查：`players` 里反查出 `binding`，`entry.pcId === p.subjectId` 才认。

### P1-7 玩家点「同意 / 不同意」会被当成「复制出来的编辑器标签页」，可能让**所有**玩家窗口永久掉线 —— `sync.ts:420-424`、`consent.ts:13-15`

`listenAsEditor` 的撞号分支：

```ts
if (m.type !== 'hello' && m.type !== 'judge-roll' && m.type !== 'say' && m.type !== 'move'
    && m.from === SESSION && m.inst !== INST) {
  const iAmNewer = m.born < BORN || …;
  if (iAmNewer) renewSession();                       // ← 换掉自己的会话号
  else { send({type:'taken'}); onHello(); saveNow(); }
  return;
}
```

`skill-decision` **不在**这个排除名单里。玩家窗口用 BroadcastChannel 发这条（`consent.ts:14` 的 `listen` 收到），而**同源部署**下玩家窗口的 `sessionStorage` 是主持人的副本，所以 `m.from === SESSION`、`m.inst` 是玩家窗口自己的 → 命中撞号分支。

实测（在 node 里跑两个 bundle + 假 BroadcastChannel）：
- 玩家窗口的 `born` 比主持人页面**早**（= 主持人中途刷新过页面，这是带团时最常见的动作）：主持人执行了 `renewSession()`，`sessionStorage['ts-sync-session']` 从 `8st6…` 变成 `matq…`。
- 换号之后，玩家窗口再发 `hello`（URL 里还是旧 session）→ 主持人**一帧 world 都不推**。也就是：玩家点一次「同意」，此前开着的所有玩家窗口就全部变成「等待主持人推送地图……」，永久不会恢复，只能重新打开窗口。

`born` 更晚的情况（主持人没刷新过）：主持人会回 `taken`、重推一遍世界、再 `saveNow()`——每次点同意都白推一遍世界、白存一次盘。

「玩家窗口刷新收不到 world」的根因排查（都实测过，结论和直觉相反）：

| 场景 | 结果 |
|---|---|
| 玩家窗口自己 F5 | **能恢复**（hello → 主持人从 sessionStorage 恢复绑定 → 重推 world；`from` 与 URL 里的 session 一致）。**不是刷新本身的问题。** |
| 主持人页面刷新 | **能恢复**（绑定在 sessionStorage 里，`win:null` 重新绑定）。 |
| 主持人 `renewSession()` 之后（= 上面的 P1-7，或者真的复制了主持人标签页） | **永久收不到**。玩家 URL 里的 session 和主持人的新 session 对不上，`hello` 被 `m.to !== SESSION` 丢掉，之后只会 10s 超时收一个 `clear`。 |
| 工程被替换（导入/恢复/自动载入） | 永久收不到。`onProjectReplaced` 把 `players` 清了、`saveBindings` 也清了，玩家窗口的 hello 找不到绑定。 |
| 试玩窗口 + 主持人刷新 | 永久收不到。`saveBindings`（`sync.ts:54-56`）有意跳过 `trialContext` 的绑定，README:134 也写了「试玩绑定不跨主持人刷新保存」——这是设计，但玩家看到的是同一句「等待主持人推送地图……」，没有任何提示。 |
| 玩家窗口不是被主持人 `window.open` 打开的（手输地址、复制链接到新标签页） | 永久收不到。`window.opener` 是 null，`:458` 全拒，hello 也发不出去。`PlayerView.tsx:101` 有说明文案，这个算设计。 |

建议：
1. **把 `skill-decision` 加进 `:420` 的排除名单**（和 judge-roll/say/move 一样），这是最小修复。
2. 根本问题：**「哪些消息可能来自玩家窗口」有 4 份各写各的名单**（`send():289-293`、`listen():397`、`listenAsEditor():420`、`listenAsPlayer():456`）。现在这 4 份已经漂移了（`skill-decision` 只在第 4 份里）。建议收成一张表：`PLAYER_TO_HOST = new Set(['say','move','judge-roll','skill-decision'])`，四处都引用它。
3. 掉线要能说出来：玩家端心跳超时（`sync.ts:470`）现在只发 `clear`，`PlayerView` 收到后回到「等待主持人推送地图……」，但从没告诉人**为什么**。给 `clear` 带上 reason（`'session-changed' | 'project-replaced' | 'trial-ended' | 'opener-missing'`），玩家端显示对应文案 + 「重新连一下」按钮（重新 hello 一次，主持人侧允许 `p.win && source !== p.win` 时更新绑定——现在这条被 `:432` 挡住，玩家刷新后如果窗口对象变了就永远连不上）。

### P2-11 广播时把玩家掷的骰子标成 `persona: 'witness'` —— `JudgmentPanel.tsx:58`

玩家在玩家窗口掷完（`DiceTray persona="player"`），主持人点「确认并广播」时 `publishJudgment` 收到的 `roll.persona` 被硬写成 `'witness'`（`:58`）。`publishJudgment:5-28` 又恰好拿 `persona !== 'witness'` 当校验条件，所以这个改写是「为了让校验过」而做的。

后果：判定记录里分不出「玩家自己掷的」和「见证者代掷的」；`byStandIn` 也只记「代掷」，不记「实际是谁掷的」。审计口径没了，而这正好是这个功能存在的理由。

建议：`publishJudgment` 的入参里加 `rolledBy: 'player' | 'witness'`，`persona` 保留 DiceTray 的原值；校验条件改成「有 `rolledBy` 且与 `persona` 一致」。

### P2-12 跨域拆分部署下，`move` / `say` / `judge-roll` 会被主持人丢掉 —— `sync.ts:393`

`allowed = [location.origin, playerWindowOrigin()]`，而拆分部署时玩家窗口是 `5179`、主持人 `5178`。玩家窗口用 `opener.postMessage` 直发这三类（`send():289-292`），`e.origin` 是 5179 → 不在 `allowed` 里 → 丢。只有走 BroadcastChannel 的那条路能过（`source=null`），而 BroadcastChannel 又会把消息送给**所有**同源标签页。

之前已报，**现状：仍在**。建议 `allowed` 里把 `playerWindowOrigin()` 无条件放进去（现在非 hello 分支只放 `location.origin`，就是因为怕跨域玩家伪造；改成「origin 白名单 + 绑定反查」两件事分开做）。

### P2-13 玩家暂停只「半通」—— 传输有、输入没关

`trialFlagsFor`（`sync.ts:328-334`）确实把 `{paused, isCurrent}` 推给玩家（`sync.ts:271`），`PlayerView.tsx:122-125` 也画了覆盖层。但 `PlayerView` 的方向键监听没有按 `trialFlags.paused` 停发，靠主持人 `onMove` 回一句「见证者暂停了你的操作」。功能上没错，只是多一个来回；如果哪天 `onMove` 的检查被去掉，暂停就失效了。建议玩家端也自查一次。

## 四、静默失败

### P2-14 `actions.ts` 里 31 处「找不到就悄悄 return」

`update` 回调里 `if (!x) return;` 共 31 处（`grep -c "if (![A-Za-z].*) return;"`）；另有 18 个 `export function …: string | null` 的动作函数，`null` 表示成功、字符串表示原因。问题在**调用方把返回值丢了**，例如：
- `Inspector.tsx:432` `setObjectState(mapId, o.id, i)` —— 物件被碰撞规则挡住时返回原因字符串，这里直接丢，按钮看着没反应。
- `TrialHud.tsx:131` / `:150` `trialAttack(...)` / `trialRescue(...)` —— 返回 `string | null`（「这回合的行动点已经用掉了」「先打开战斗模式」…），也直接丢。攻击因为 `confirm()` 已经弹过一次，失败时**只**改 `msg`（有时改 `event`），不弹 toast。

实测：昏厥/尸体那条 `trialMove` 返回的 `msg` 是能看到的；但 `trialAttack` 的「已经濒死」「没血条」只进 `event.note` 或什么都没有。

建议：给这几处加一个 `const err = …; if (err) toast(err);`，或者让动作函数自己 `toast`（少一处就少一个漏洞）。

### P2-15 `update()` 本身可以「静默不生效」—— `store.ts:117-138`

immer 的 `produce` 如果回调没改出差别，`next === cur`，`emit` 照样跑、监听器收到同一个对象，React 不会重渲——动作执行了、UI 没有任何变化也没有提示。另外 `architectureTransitionError` 分支只 `toast` 一下就 `return`（不开历史、不 emit）。

后果：作者点了一个改了参数但值恰好没变的按钮，会以为「没点上」。建议 `update` 返回 `changed: boolean`（或 `null`），让调用方决定要不要 toast「没有变化」。

### P2-16 `catch` 吞掉原因

- `MediaPanel.tsx:25` `catch { toast('上传失败：' + f.name) }` —— 配额不足/格式不支持/写库失败全变成同一句话。
- `media.ts:145` `blobUrl(id).then(…).catch(() => setUrl(null))` —— 失败后 `url` 是 null，界面永远停在「载入中…」，没人知道是丢文件了。
- `actions.ts:337` `getRaw(key).catch(() => undefined)` —— 媒体读不出来时**照样**把 `play` 发出去（`blob` 是 undefined），玩家端拿到一个没有内容的播放请求；主持人这边没有任何提示。

建议：这三处把 `e` 的 message 带进 toast/文案（`上传失败：${f.name}（${msg}）`），`playMedia` 读不到 blob 时直接返回原因而不是发一个空播放。

### P2-17 `trialAttack` 的 `note` 只有卡片里一行小字

见 P2-3。行动点已经扣了，而说明藏在事件卡片底部。规则上「打了一个没有血条的东西算不算一次行动」应该先问清楚再扣。

## 九、口径空白（规则没写清、代码只能猜的地方）

1. **「一次行动」到底指什么**：`acted` 同时被攻击、救治、感知、跑法（`usesAction`）用，但结束回合是全队的。两个人同时在场时「谁的回合」没有定义——`switchTrialPlayer` 只是换视角，不是换回合。

3. **尸体能不能被借机攻击 / 能不能挡路**：`trialMove` 的占位判断只看 `x/y`，尸体照样挡路（实测 `B 在这里，不能停在同一个格子上` 对普通棋子；尸体没测到但同理）。这属于规则空白，不是代码错。
4. **「暂停」是暂停这个人的输入，还是暂停这个人的回合**：现在只拦 `onMove`（`sync.ts:360`），不拦攻击/技能（那些是主持人点的）。如果暂停的意思是「这个人完全不能动」，主持人端也得拦。
