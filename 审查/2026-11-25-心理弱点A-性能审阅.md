## 结论一句话

**无 P0 / P1 / P2 性能回归。** 唯一可测到的增量是：`playerToken` 对 300 个可见棋子**每次投影 +18.75µs**（占 `playerWorld` 约 0.17%），`endsWhenMePositive` 的 NPC 分支**每次 update +15µs**（占约 0.66%），都在噪声以下、不可感知；`migrateWorld` 不在帧循环里（只在载入/替换/导入跑，200×200 旧档一次 0.14ms）；`npm test` 1055 条实测 14.9–15.3s，新增的 17 条测试 244ms CPU，并行下墙钟上看不出来。另外顺手量到一处**与本提交无关的既有 O(n²)**（`diffWorld` 棋子段：300 棋子 1.64ms/次、1000 棋子 18.4ms/次，占 update 的 74%/93%），单列在 P3-3。

### P3（可优化/可记录，不阻断）

1. **`playerToken` 每个可见棋子约 0.07–0.09µs**：300 个可见棋子 +21–27µs，仪器化测到 24.96µs（基线 6.21µs）。绝对值可忽略；只有将来棋子到数千个、或广播频率从 60ms 防抖提到每帧，才值得把这份投影缓存到“弱点变化时”。当前不建议为它加缓存复杂度。
2. **`endsWhenMePositive` 的 NPC 分支 +15µs/次 update**（仅在存在“驱逐”状态且 ME 仍为 0 时）：来自 300 次 Immer draft 上的 `k.me` 代理读（约 50ns/次）。不是本次引入的主要成本——真正贵的是既有的整段 `produce` + 全地图走一遍（约 249µs），本次只把 NPC 也纳入收口。若要省，可把这段收口挂到“ME 有变”的脏标记上，而不是每次 update 都跑。
3. **既有 O(n²)：`diffWorld` 每次 update 都对棋子做嵌套比较（非本次引入，但本 feature 会让棋子变多，值得单独立项）**。300 个棋子时一次 `update()` p50 2.14ms，其中 **1.64ms 花在 `diffWorld` 的棋子段**（74%）；1000 个棋子时 20.2ms，其中 18.4ms（93%）。根因是 `src/scene/dirty.ts:162` 的 `before.tokens.some((t) => !m.tokens.some((x) => x.id === t.id))`——嵌套 `some` 是 O(n²)，而且 **棋子数组引用没变（这次 update 根本没动棋子）时也照样跑**。我按“`before.tokens === m.tokens` 就整段跳过”的语义不变改法量了一次：300 棋子 2.14 → **0.47ms**，1000 棋子 20.2 → **1.52ms**。`dirty.ts` 本次提交没改，所以不计入回归，只记录。
4. **收益（不是成本）**：载荷里剥掉了 `weaknessKnownBy`，同一夹具的投影 JSON 从 3,684,762 字节降到 3,645,162 字节（**−39.6KB，−1.07%**）。序列化略快，抵消了上面的投影增量。

## 实测一：玩家载荷（playerToken / playerMap / playerWorld）

夹具：`newMap('大图','现实',1,200,200)`（40,000 主格 / 360,000 小格），`fog` 全 1（全可见，**上界**），300 个棋子（4 个 PC + 296 个 NPC），每个棋子都带 `weakness {physical, psychological}` 与 4 人 `weaknessKnownBy`，队伍 4 个 PC。三种视野模式分别用 `shared` / `m.views[pcId]`（individual）/ `visionGroups`（grouped）构造。

`playerWorld(w, mapId, 'p1')` 与 `playerMap(m, L, 'p1')`，每次 60 次取 p50（3 个进程各一遍，表中为中位）：

| 模式 | HEAD playerWorld p50 | HEAD p90 | 基线 playerWorld p50 | 基线 p90 | HEAD playerMap p50 |
|---|---|---|---|---|---|
| shared | 11.19ms | 13.70ms | 11.64ms | 13.42ms | 6.00ms |
| individual | 12.49ms | 15.94ms | 12.34ms | 15.37ms | 5.93ms |
| grouped | 12.02ms | 15.54ms | 11.70ms | 15.03ms | 5.89ms |

整段 p50 上 HEAD 与基线互有高低（差 0.3–0.8ms），**这已经是跨进程噪声，分辨不出 19µs**。同进程交替配对（每轮先跑 HEAD 再跑基线，取逐对差中位）也是同一结论：shared −0.29ms（p90 1.71ms）、individual +0.006ms（p90 2.19ms）。所以增量只能用插桩看：

**仪器化 tokens 相位**（`m.tokens.filter(...).map(playerToken)` 这一段，120 次、3 个进程）：

| 副本 | token 段 p50 | p90 | 占 playerMap(5.91ms) |
|---|---|---|---|
| HEAD（filter+map） | **24.96µs** | 30.96µs | 0.42% |
| 基线（只 filter） | **6.21µs** | 7.75µs | 0.105% |
| 净增 | **+18.75µs** | — | **+0.32%** |

旁证（小图隔离，10×10 图、300 个可见棋子 vs 0 个棋子）：HEAD Δ = 21.3–26.8µs，基线 Δ = 4.5–4.9µs，即约 **0.071–0.089µs/棋子**（基线 filter 约 0.015µs/棋子）。

频率换算：`broadcastWorld` 是 60ms 防抖（`src/runtime/sync.ts:845-847`），最高约 16.7 次/秒；每次广播对每个已绑定玩家各做一次投影（`src/runtime/sync.ts:372`）。4 个玩家时投影增量 = 4 × 18.75µs ≈ **75µs/次广播 ≈ 1.25ms/秒**。同一次广播里既有的成本是 4 × 11.2ms 投影 + 序列化（同一载荷 `JSON.stringify` 实测 27.2ms，属既有 P2-3，本次未改），增量占其 **0.05%**。

结论：**不可感知**。一帧 16.7ms，19µs 是一帧的 0.11%。

## 实测二：`endsWhenMePositive` 收口（`src/core/store.ts:206-222`）

夹具：200×200、`update(d => { d.session += 1 })`（最小世界变化），100 次取 p50：

| 夹具 | HEAD p50 | HEAD p90 | 父提交 p50 | 父提交 p90 |
|---|---|---|---|---|
| D：0 个棋子 | 0.029ms | 0.037ms | 0.028ms | 0.038ms |
| A：300 个棋子、无状态 | 1.831ms | 2.026ms | 1.776ms | 1.957ms |
| B：300 个 NPC「驱逐」、ME=0（不会被清） | 2.271ms | 2.501ms | 2.239ms | 2.400ms |
| pc：300 个状态、1 个 PC 的 ME=1（只清 1 个） | 2.647ms | 2.857ms | 2.649ms | 2.808ms |

插桩这一段（6 个进程，各 p50 中位）：

| 夹具 | HEAD | 父提交 |
|---|---|---|
| A（无状态，只跑守卫扫描） | **2.17µs** | 2.21µs |
| B（有 300 个持续状态） | **252.8µs**（251.9–254.5） | **237.8µs**（236.9–239.7） |
| 净差 | **+15.0µs** | — |

拆开看：

- **守卫扫描**：`for (const m of next.maps) for (const k of m.tokens) …` 每次 update 都跑，300 个棋子 **2.17µs**，与父提交相同（父提交也有这段），不是新增成本。
- **有状态时的整段**：`produce(next, …)` 再全地图走一遍，300 个棋子 **约 238–253µs**，占 2.27ms 的 10–11%。这段父提交就有。
- **NPC 分支新增**：`const me = pc ? pc.me : k.me` 让每个“驱逐”NPC 多读一次 `k.me`；在 `k` 是 Immer draft 的情况下每次读都是 proxy trap，300 次 ≈ **15µs**（占该段 6%，占整次 update 0.66%）。
- 端到端交替配对测不出这 15µs（`Δ p50 +42µs`，`p90 214µs`，噪声底约 30–40µs），只能用插桩看到。

结论：**没有引入可感知成本**；“每次 update 扫全地图 token”本身是父提交就有的守卫扫描（2µs 级），真正贵的是有状态时的 `produce`（既有）。NPC 分支只多了 15µs。注：B 的 2.27ms 总耗时里约 1.6ms 来自实测五那条既有 `diffWorld` 棋子段，与状态收口无关。

## 实测三：`migrateWorld` 确认不在帧循环

调用点只有 3 处（全仓 grep）：

- `src/core/store.ts:29` —— `load()`，模块初始化时读自动存档，**启动一次**；
- `src/core/store.ts:398` —— `replaceWorld(w)`，换/新建工程时**一次**；
- `src/runtime/actions.ts:1026` —— `parseWorld` 导入工程文件时**一次**（导入校验）。

`update()` / `commitWorld()` / `withVision` / `syncMemory` / 渲染路径里**没有** `migrateWorld` 调用；玩家端和 `sync.ts` 也没有（`grep` 为空）。

实测（200×200、300 个棋子、队伍 4 人）：

| 夹具 | `migrateWorld` 总耗时 p50 | p90 | 新增弱点迁移相位 |
|---|---|---|---|
| v2 旧档（走 `weakness.psychological` → 全队 `knownBy`） | **0.142ms** | 1.09ms* | **96.7µs** |
| v3 新档（不进迁移分支） | 0.062ms | 0.123ms | 8.96µs |
| 净差 | +0.081ms | — | +87.7µs |

\* p90 1.09ms 是 8 次里的 1 次 GC 抖动，其余 7 次 0.13–0.14ms。

结论：**只在载入/替换/导入跑，不进帧循环**。新加的迁移循环在旧档上一次 **97µs**（创建 300 × 4 = 1200 个小对象），一次性的，可忽略。注：这里量的是“格式已完整”的 v2 档；真正 v1 稀疏档还要走 `buildFineCells` 重建 360k 小格，那是旧口径的既有成本，本次未改。

## 实测五（对照，非本次提交）：`diffWorld` 棋子段的既有 O(n²)

用来解释“为什么 300 棋子时 update 是 2ms 级，而 `endsWhenMePositive` 只占 15µs”。夹具同实测二，只是棋子数变化，`update(d => { d.session += 1 })`（不改任何棋子）：

| 棋子数 | HEAD `update` p50 | 其中 `diffWorld` 棋子段 | 加“引用没变就跳过”后 `update` p50 |
|---|---|---|---|
| 100 | 0.379ms | 197µs | 0.180ms |
| 300 | 2.138ms | **1,637µs** | **0.472ms** |
| 1000 | 20.21ms | **18.4ms** | **1.52ms** |

- `src/scene/dirty.ts:146-170`：每张图、每次 update 都 `new Map(before.tokens.map(...))` + 逐棋子 `tokenMoved`，再加 `before.tokens.some(t => !m.tokens.some(x => x.id === t.id))` 的嵌套 `some`（O(n²)）。
- 只有 `before.tokens !== m.tokens` 时棋子才可能真变；引用相同说明这次 update 根本没动棋子，整段可以跳过。上面第三列就是按这个语义不变的改法实测的效果（`dirty.ts` 本次未改，所以不算回归）。
- 这条对心理弱点 A 的意义：本 feature 会往场上加 NPC（每个 NPC 都可能有 `me`/`status`），棋子越多，每次 update 的固定成本按平方涨；它比 NPC 分支那 15µs 大两个数量级。

## 复现方法（关键锚点）

1. 打包：esbuild `bundle: true, platform: 'node', format: 'cjs'`，入口
   `export { playerWorld, playerMap } from './src/runtime/hostSession'` +
   `export { newMap, emptyWorld } from './src/core/defaults'` +
   `export { effectiveLayer } from './src/scene/vision'`；
   `react` / `react/jsx-runtime` 用空桩（同 `scripts/ui.test.mjs`），`localStorage`/`window`/`BroadcastChannel`/`Path2D` 在 require 前装好。
2. 基线副本：`onLoad({filter:/hostSession\.ts$/})` 里把
   ```
   tokens: m.tokens
     .filter(t => { const p = tokenPosition(t); return t.pcId === pcId || fogAt(m, L, p.x, p.y) === 1; })
     .map(t => playerToken(t, pcId)),
   ```
   换成只留 `.filter(...)`，其余一字不动。
3. 仪器化副本：把同一段包成 IIFE，前后各记一次 `process.hrtime.bigint()` 写进 `globalThis`；`store.ts` 则把 `let hasEndsStatus = false;` 到 `// syncMemory 在独立/分组模式会 clone fog 数组` 之间整段包起来计时。
4. 父提交副本：只替换三处——删 `const me = pc ? pc.me : k.me;`、`if (me !== undefined && me >= 1)` 换回 `if (pc && pc.me !== undefined && pc.me >= 1)`、`ME 恢复到 ${me}` 换回 `${pc.me}`。
5. 计时：`process.hrtime.bigint()` 差；每配置 warmup 后 40–300 次采样，报 p50/p90；3 个独立进程各跑一遍取中位；噪声底：`playerWorld` ±0.3ms、`update` ±0.04ms、相位段 ±1–2µs。
6. 测试计时：`/usr/bin/time -p npm test`；对照跑 `node --test $(ls scripts/*.test.mjs | grep -v psychology.test.mjs)`；再单跑 `node --test scripts/psychology.test.mjs`。
7. `diffWorld` 对照（实测五）：插桩用 `const byId = new Map(before.tokens.map((t) => [t.id, t]));` 前记时、`const autoFogOn = !before.autoFog && m.autoFog;` 前收时；快路径变体只改两处——`for (const t of m.tokens)` 前加 `if (!tokensSame)`、`const added = …` 整句外面套 `!tokensSame && ( … )`，`tokensSame = before.tokens === m.tokens`。这些都只在 `/tmp` 的打包副本里改。

## 局限与口径

- Node 微基准**不含 React 渲染和画布重绘**；绝对毫秒数（11–12ms 的 `playerWorld`）随机器变化，本次结论只用**HEAD 与基线的差**，不用绝对值下结论。
- 载荷夹具是“全图可见、小格全填”的**上界**（投影 JSON 3.6MB）；仓库里“玩家包 310KiB 闸门”是另一个场景，两者不要混用（3.6MB 也不是本次改动造成的）。
- 载荷大小对比只在同一夹具内有效：HEAD 比基线少 39.6KB（剥掉了 `weaknessKnownBy`），方向是变好。
- `endsWhenMePositive` 的 15µs 只出现在“有驱逐状态且 ME 仍为 0”的窗口里；ME 一恢复、状态清掉后，这段就恢复成 2µs 级守卫扫描。
- 本次提交触到的其他文件（`trial.ts`、`rules/psychology.ts`、`Inspector.tsx`、`TrialHud.tsx`、`schema.js`、`actions.ts`）都只在**事件/渲染/导入**路径上用到 `weakness*`，没有进入 `update`、`render`、视野循环（全仓 grep 确认）；`TrialHud` 新增的两组 chip 按钮只在试玩面板展开、且逐条 utterance 渲染，不在帧循环里。
