## P2：2 条在途上限和玩家端分批冲突

- 玩家端 `request()` 对超过 32 个 key 的世界会**同步把每一批都发出去**，不是一批一批等：
  - `src/runtime/assets.ts:403-410`：`for (let i=0;i<missing.length;i+=32) { ... opts.send({type:'asset-request',...}) }`，循环里没有 await 批次完成。
  - 探针：65 个 key、load 全 miss，实际发出 `[32,32,1]` 三个 requestId（3 条 asset-request）。
- 主持端 cap 是 `flows.size >= 2` 就拒；前两批64个 key 建2条 flow，第三批1个 key 直接 `rejectAssetRequest`，玩家端收到 forbidden，`onFail` 标失败，**不会自动重发**。
- 结果：**世界媒体超过64个时，第3批及以后永远加载不到**；33–64个媒体时第三批是广播/retry 的话同样会被拒。docs 还写着“200个1MiB（单人约54秒）都在120秒内”，与 cap64/2 flows 直接矛盾。
- 这不是“第三条65个排队 key 才拒”：只要已有2条 flow，第三条哪怕只有1个 key 也拒；所以正常大世界会被截断。
- **建议修复**：玩家端按批串行，发一批后等这一批的 key 全部 end/fail（或该 requestId 的 pending 清空）再发下一批；只保留最多2条在途。或者主持端把超额请求排队，而不是立刻 forbidden；单纯把 `ASSET_MAX_FLOWS` 调大不能解决200个key的7批问题。

## cap 口径

- `assetFlowHasRoom` 在 `tryAcquire` 前，stats 非 false 才检查；拒绝不占 active、不建 flow、发 forbidden 条目不占全局发送名额。方向正确。
- `flows.size>=2` 是严格“两条在途 request”，不是“两个文件”；一个请求32 key + 广播1 key=2，刚好；再 retry 第三条就 forbidden。
- 已 start 的 key 不计排队；failedFiles 已在 cancel/fail 扣；新 keys 先去重/slice32；计算本身正确。
- **但 queue64 实际不可达**：flows.size<2 时最多一条 flow32 key，加新32=64，`<=64` 恒真；flows.size>=2 时先被 flow cap 拒。`ASSET_MAX_QUEUED_KEYS` 永远不会单独触发（把 `ASSET_MAX_QUEUED_KEYS` 改成0、或去掉 queue 判断，测试都0红）。文档“64个排队 key”实际行为是“最多2条请求”。
- **误伤**：世界>32 media 已经占2条，广播/retry 第三条会被拒；retry 是玩家手动按钮，被 forbidden 后只显示失败，不会自动再试。cap2 对“世界32+broadcast”刚好，对分批世界太紧。

## 测试

- online cap：r-cap1/r-cap2/r-cap3 连续发，r3 在 r1/r2 结束前到达；5字节/45ms 窗口下稳定，连跑12次全过。去掉 cap 检查、把 `ASSET_MAX_FLOWS` 改成3、去掉 flow 上限检查都会红，确实咬住 flow cap。
- 但 online 只断言 r3 forbidden 和最终 players=0，**没有断言 r1/r2 各自 asset-end**；也没有65 key/queue 边界。queue 相关突变全0红。
- 公平测试新用例 `b1,a1,b2,a2`：先 b 发一次、再 a 发一次，之后 a2/b2 同时 ready，选 last 最小才会 b2 先；改成 FIFO 立刻红。**这条终于咬住选择逻辑**，连跑12次稳定；不写 `last` 也红。
- deployment 守卫删 source 的 `ASSET_MAX_FLOWS` 或 reject 调用会红；但只断言 flows cap，**没有断言 `ASSET_MAX_QUEUED_KEYS`**，queue 上限没有任何守卫。
- **P2 没有测试**：65 key 世界分批、33 media + broadcast/retry。

## 排队上限

- `Σ(total-started-failed)` 对新旧 flow 的排队数计算正确；两条 flow 各32 key 且都没 start 时合计64，第三条1 key 理论上65。
- **实际上第三条在 `flows.size>=2` 就被拒，不会走到65判断**；把 queue 上限设0也没有测试变化，说明该分支是死代码/文档承诺未实现。
- 如果想让64真正生效，需要允许超过2条 flow（或 host 侧挂起队列），同时用 queued 总数控制；这和“防止一个人占多份全局预算”的目标要一起重新设计。
