- 根因：`settlePendingJudgment` 在 `trial.ts:891` 传 `worldContext()`（当下值），`publishJudgment` 的守卫在 `judgments.ts:7` 是 `context !== worldContext()`；两边是同一个表达式，**永远通过**。
- `PendingJudgment` 里也没有存“开出这笔判定时的 context”。
- 实测（真实 `startTrial`，不是只调 `beginSandbox`；探针直接调 `settlePendingJudgment`，相当于玩家已掷、主持端已收到结果）：

```
before startTrial: pending id=8asu8hrr（真实世界，subject=a）
after  startTrial: trial=true，pending 仍是 8asu8hrr，subject=a
settlePendingJudgment(...) → null
settle 后：sandbox judgments=1、pending=null
endTrial 后：真实世界 judgments=0、log 里没有「正式判定」
```

  也就是：真实窗口还挂着这笔判定的骰盘，玩家掷完后主持端在试玩里结算成功；`endTrial` 一还原，正式判定在真实世界里**从未存在**。玩家窗口在这次 settle 也只因 `sameContextWindow` 过滤收不到 `judge-cancel`（最终靠后续 world 推送的 null 兜底收盘，但判定记录已经丢）。

- 建议改法（两处，都很小）：
  1. `PendingJudgment` 开判定时存 `context: worldContext()`（或不进类型的 `publishContext`），`settlePendingJudgment` 用 `p.context` 传给 `publishJudgment`，让原守卫重新生效；

## D11. **PlayerView 兜底的 FIFO 结论（明确回答）**

**是 send 时算的，不是 broadcast 捕捉的旧值；同一 host→玩家窗口的 FIFO 足够，不需要版本号。**

依据：

1. `send()` 的 world 分支（`sync.ts:253-283`）在发每个绑定窗口时，才构造
   `{ ...playerWorld(w, mapId, p.pcId), pendingJudgment: pendingFor(p.pcId), ... }`；
   `pendingFor`（`sync.ts:89-92`）读的是当下的 `getUI().pendingJudgment`。
2. `broadcastWorld(w)`（`sync.ts:530-533`）只是 `clearTimeout` + 60 ms 后 `send({type:'world', world: w})`；
   但 `send` 对玩家窗口的 world **并不使用传入的 `body.world`**，而是按绑定重新取 `getRealWorld()` / `getWorld()`，所以 payload 本身也是 send 时当前世界，`w` 只是节流触发器（探针 D11c 证实：传入旧 world 后两次 world 推送带回来的都是新名字）。
3. 探针（fake timer，手动 flush）：
   - D11a：先 `broadcastWorld` 排一笔 pending=j 的 world，然后**在 timer 触发前** `closePendingJudgment()`；flush 后消息顺序 `judge-cancel, world`，world 的 `pendingJudgment` 是 **null**。若 broadcast 捕捉旧值，这里会是 j，从而在 cancel 后把骰盘又设回来——没有发生。
   - D11b：先排一笔无 pending 的 world，再 `openJudgment` + `pushJudgmentRequest`；flush 后顺序 `judge-request, world`，world 带着**新 pending 的 id**（send 时算），不会把刚收到的 request 清掉。
   - D11c：捕旧 world 再更新世界名，排旧 `broadcastWorld` + 立刻 `send` 当前 world；两个消息都是当前名，证明 `send` 不拿 `body.world` 里的旧快照。
4. 消息都从**同一个 host 窗口** postMessage 到**同一个玩家窗口**，按调用顺序 FIFO；`judge-cancel` 是同步直发，晚到的 world 里 pending 已按 send 时算成 null，只会清、不会重新设。反过来，world 若在 request 之后才发，它带的是 request 后的当前 pending，也不会清掉。
5. PlayerView 代码（`PlayerView.tsx:66-73`）也一致：world 有 pending 就按 id 设/保留，没有就 `setPending(null); setRolled(null)`；`judge-request` / `judge-cancel` / `clear` 各自同步处理。

**结论：FIFO 够，不用版本号。** 唯一前提是以后别把 `pendingJudgment` 挪到 broadcast 捕获的 `body.world` 里；一旦那么改，才需要版本号/序号。另：world 推送本身是“send 时当前世界”，也没有旧 payload 覆盖新 payload 的问题（`body.world` 参数实际被忽略，这点代码注释容易误导，建议下一笔顺手清掉参数语义）。

- **P3（同一根）**：`startTrial` 不清 pending；这是 P2 的另一半，补 `closePendingJudgment()` 即可。
- 既有已知尾巴（`sharpAttack` 未读、sync 白名单漂移、`PlayerView` 无 jsdom 等）不再重复报，除非本笔弄坏——本笔没有。

## 结论

**先别推。** 主线 12 条和构建全绿，提交范围也干净；但 A3 的失败路径现在确实不报 context 错（`settlePendingJudgment` 自己取当下 `worldContext()`），叠加 `startTrial` 不清 pending，实测一笔真实判定会在试玩里结算、退出试玩后消失。改法很小：pending 存开出时的 context（或 settle 接收它）+ `startTrial` 先作废并通知，再补一条测试；改完这轮就能推。

**PlayerView 兜底的 FIFO 结论再明确一次：pendingJudgment 是 send 时算的（`send` 里 `pendingFor`，不是 broadcast 捕获的 `body.world`），同一 host→玩家窗口的 FIFO 足够，不需要版本号。** 探针 D11a/b/c 已证；只有以后把 pending 挪进 broadcast 快照时才需要版本号。
