## 1. 玩家入口：开发端生效，构建端没有生效

`src/player-main.tsx:1-7` 只 import `createRoot`、`PlayerView`、`styles.css`，没有 `App/Editor`；`vite.config.ts:14-19` 用 `transformIndexHtml` 把 `/src/main.tsx` 换成 `/src/player-main.tsx`。

- **开发端生效**：`npm run dev:player` 返回的 HTML 是 `<script type="module" src="/src/player-main.tsx"></script>`（实测）；`/src/runtime/sync.ts` 的 `skills` import 被解析成 `/src/rules/skills.player.ts`（实测）。
- **构建端没有生效**：用 `npx vite build --mode player --outDir /tmp/player-audit-dist --sourcemap` 复查，source map 的 62 个 `sources` 含 `src/main.tsx`、`src/App.tsx`、`src/rules/actionLibrary.ts`、`src/components/toolGroups.ts`、`jszip`，**不含 `src/player-main.tsx`**。
- 构建产物末尾的唯一入口仍是 `createRoot(document.getElementById('root')).render(<App/>)`（`main.tsx` 的入口）；`App.tsx:40-42` 的 `isPlayerEntry()` 分支被 `VITE_APP_ROLE='player'` 常量折叠成 `<PlayerView/>`，所以页面看起来正常，但**不是 `player-main` 在跑**。
- 这也解释了 `dist-player/index.html` 的 `<title>` 仍是“奇点之后 · 地图编辑器”；运行时标题由 `PlayerView.tsx:162` 写成“奇点之后 · 玩家视角”，而 `player-main.tsx:6` 的“玩家端”从未执行。页面能正常显示（见第 6 节），所以不是初始化缺失，而是**声称的独立入口没有进生产包**。
- 这不是“没 import App/Editor”的源码问题，而是入口选择问题：`transformIndexHtml` 改变了 dev HTML，但 build 仍按原 `index.html` 的 `/src/main.tsx` 建图。应显式为 player 构建提供独立 HTML/入口（例如单独的 `player.html`，或 `build.rollupOptions.input` 指向 `src/player-main.tsx`），并在闸门里断言产物入口不是 `main.tsx`。

## 2. 技能投影桩：正常玩家路径安全，但不能代替入口约束

`sync.ts:4` 从 `../rules/skills` 取 `publicSkillsOf`、`currentPathwayOf`；真正用到它们的是主持端 `send(world)` 的投影分支 `sync.ts:375-376`。玩家构建把这一处 import 换到 `skills.player.ts:5-11`（`publicSkillsOf → []`、`currentPathwayOf → null`）。

- 玩家 UI 的发送点只有：`PlayerView.tsx:193`（move）、`:338`（say）、`:407-408`（code-submit）、`:431-432`（skill-decision）；`:336-337` 明确写“玩家窗口不自己写 world”。**PlayerView 没有 `send({type:'world'})`**。
- `sync.ts:325-327` 的 `selectTrialViewer`、`:840-842` 的 `pushFocus`、`:845-847` 的 `broadcastWorld` 会发 world，但它们是主持端导出（`pushFocus` 只由 `skillCast.ts:47` 调），PlayerView 不调用。
- 开发端实测 `sync.ts` 解析到 `skills.player.ts`；构建 source map 也含 `skills.player.ts`，实际玩家 JS 的技能库 id 命中 0。**正常玩家路径不会走到空投影**。
- **会坏的地方**：如果以后从玩家构建里调用到 `sync.send({type:'world'})`（例如误把 Editor/试玩主持逻辑挂进玩家页），投影会变成 `skills: []`、`pathway: null`，玩家技能树/当前途径为空。当前没有这种调用；但由于生产入口仍是 `App/Editor` 图（第 1 节），这个风险不能靠“源码只 import PlayerView”来保证。建议加一条构建期/运行期断言：玩家图里除 `sync.ts` 外不得出现 `rules/skills`，也不得执行 world 广播路径。

## 3. 构建闸门：正则取到 0 个 token，等于没检查

`scripts/check-player-bundle.mjs:8-10`：

```js
const skills = await readFile(join(root, 'src/rules/skills-data.ts'), 'utf8');
const ids = [...skills.matchAll(/id:\s*'([^']+)'/g)].map((m) => m[1]);
const names = [...skills.matchAll(/name:\s*'([^']+)'/g)].map((m) => m[1]);
```

- 但 `src/rules/skills-data.ts:7` 是 `{"id": "001-9-001", ...}`，**双引号**。实测这两条正则在该文件上得到 **ids = 0、names = 0**；`:24-28` 的 `for (const token of [...ids, ...names])` 因此循环体一次都不执行。
- 所以当前闸门输出“没命中技能库 id/名字”并不代表检查过；即使有人把完整的 `SKILL_LIBRARY` 原样塞进 `dist-player`，它仍然会通过。**这是漏报**。
- 若把正则改成匹配双引号并**按名字**检查，当前干净产物会 **误报**：`skills-data.ts` 实际有 194 个 id/194 个 name，而 `dist-player` 目前 id 命中 0、name 命中 7——`威吓`、`愚弄`、`群嘲`、`淬火`、`酿酒`、`改图`、`私聊`。这 7 个都是 `src/rules/actions.json` 里的公开动作名/描述（例如 `actions.json:615` 的“愚弄”、`:2037` 的“群嘲”、`:305` 的“威吓”描述），不是技能库对象；只按名字做子串匹配必然误报。若只按 id 检查，当前产物通过。
- 覆盖也不完整：闸门只读 `skills-data.ts` 的 194 条，**漏掉 `skills.ts:44-48` 的 Ian 4 条**（`037-9-101` / `037-9-102` / `037-9-003` / `037-9-201`），技能库总数是 **198**。当前若只泄漏 Ian 4 条，闸门也看不见。
- 路径和产物类型本身没问题：`new URL('..')` 指向仓库根，`dist-player/assets` 存在，JS 为 1 个；`build:split` 末尾执行闸门，`assets.length===0` 会抛错。问题是 token 集为空、没有数量断言，也没有闸门自测/变异用例。
- 建议：同时解析双引号和单引号；把 `skills.ts:44-48` 的 Ian 4 条纳入；**断言 id 总数 = 198**（解析不到就报错），并**只按 id 扫描**（名字碰撞太多，可只作为辅助/不参与失败判定）；补一条“故意放一个技能 id 进 fake dist，闸门必须 exit 1”的测试。修好后再决定名字是否要按上下文检查——当前 `dist-player` 的 7 个名字命中说明不能直接查名字。
