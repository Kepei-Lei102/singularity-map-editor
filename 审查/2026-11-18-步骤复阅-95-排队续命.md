## 排队续命语义

- `refreshQueued` 从 `requests.get(requestId)` 拿同批 key 集合；`forget` 在 fail/timeout/end/cancel/chunk-error 时已把 key 移出，所以集合里不会留下已结束的 key。
- 对每个还在 `pending` 且 `!started` 的 key 重 arm `queueTimeoutMs`；已 start 的 key 跳过，不碰它的 inactivity timer。当前 key 先 `armKeyTimeout(start, timeoutMs)` 再 refresh，跳过自己，正确。
- `queueTimeoutMs=0` 时直接 return；初始也没 arm，等于是“不设排队上限”，符合 `timeoutMs=0` 的语义。
- 32 个 key 串行时每次 start 最多扫 31 个 pending，O(32²) ≈1024 次，完全可以接受。
- 首个 key 一直不来时，所有 key 仍按原 120 s 排队失败；已 start 的 key 卡住时，它自己 30 s inactivity 失败，后面 key 最多再等 120 s，合理。
- **P3 边界**：
  - refresh 只认同 requestId；receiver 一次最多 32 key，超过 32 个会拆成多个 requestId；**后一个 batch 的 key 不会被前一批的 start 续命**，多批世界媒体仍可能超时。
  - 续命只保证“最近一次 start 后 queueTimeoutMs”；如果前一把 key 在全局 45 ms 节流下传了超过 120 s 才结束，下一把 key 的 timer 仍会在它 start 前过期。refresh 不能解决“单个 key 自身超过 queueTimeout”的情况。
  - 12 人各一个 key 的广播：每个 binding 的 `serveAssetRequest` 并发启动，start 在全局节流下大约 45 ms 一个，1 s 内全部 start，**不会触发 120 s 排队超时**；138 s 是总吞吐时间，不是排队超时。refresh 对“单 key 广播”没有影响，符合你的判断。
  - 12 人各 32 key 的批量世界图片：前一把 key 可能因与其他玩家共享全局节流而超过 120 s，后一把 key 仍可能超时；refresh 只能延到“上一个 start + 120 s”，不能延到“有字节进度”。
- **恶意/异常**：host 不能靠重复 start 同一个 key 永久续命（`p.started` 后重复 start 直接 return），也不能对不存在的 key 续命。它最多按批内 32 个 key，每个 key 只续一次；如果把每个 key 的 start 拖到接近 120 s，整批最长可被拉到约 32×120 s。这是有界但很长的资源占用，归 P3；不是 P2。

## 未知总大小

- `finish` 改成 `onProgress(key, p.bytes, p.totalBytes)`，不知道总字节时最后一条是 `received, undefined`，不再 `received=total` 假 100%。测试补了 end 后的 `['k',3,undefined]`，与 start/chunk 的 undefined 一致。
- 旧 host 不带 bytes：整个下载过程都是「载入中…」，落盘后 `onReady`/`mediaChanged` 取 URL，开始播放；不会短暂 100%。这个行为对旧协议可接受。
- total=0 的空文件仍因 `!total` 显示「载入中…」，不会显示 100%；`mediaProgressText` 对 undefined/0/负数一致返回载入中。received>total 仍只在 UI clamp。

## 测试

- 新测试 `queueTimeoutMs=100, timeoutMs=0`：request a/b，80 ms 后 start a 把 b 续到约 180 ms，再等 50 ms（总130 ms，已过 b 原100 ms）断言 b 没 fail，然后 start b/chunk/end 收下 b。
- 时间边界在 Node 上连跑 15 次全过；80 ms 定时器先于 b 的100 ms 定时器，start 清掉 b 原 timer，50 ms 等待离新180 ms 还有50 ms 余量。CI 极慢时仍可能抖，建议用 fake timer 或把余量拉到100 ms。
- 去掉 `refreshQueued` 调用或整体 no-op，新测试立刻红；去掉 `if (!queueTimeoutMs) return`、`timeoutMs=0` 默认值、Dock 文案等 0 红。测试确实证明是 refresh 在起作用，不是别的原因。
- **P3 覆盖**：没有 32 key、多个 requestId、首个 key 永不到、恶意逐 key start、Dock 渲染的测试；没有验证“b 的 end 走的正常 finish”，只断言 saved b（不过 saved 已经说明 finish 成功）。

## P3

1. **多批/单 key 长传输**：refresh 只续同 requestId；超过32 key 的批量拆成多个 request 后，后一批不续；单个前序 key 在共享全局节流下超过120 s 时，后 key 仍会在 start 前超时。12人单 key 不会排队超时，但总吞吐仍约138 s。
2. **恶意/异常**：host 可按批内32个 key、每个只续一次，把整批拖到约32×120 s；首个 key 永不到仍按原120 s失败；queueTimeoutMs=0 路径无测试。行为有界，P3。
3. **测试时序/覆盖**：80/50 ms 边界在极慢 CI 可能抖；没有 32 key、多 requestId、首个 key 不 start、Dock 渲染测试。
4. **Dock UI**：单独一行解决了 flex 挤压，但出现/消失时高度跳动；文案仍统计所有 active 素材，不区分当前广播；无渲染测试。
5. **未知 total**：已改为不伪造100%，旧 host 全程「载入中…」属可接受；没有 P2。
6. **调度仍缺**：per-binding sentBytes/totalBytes/queued/rate、按 broadcast key 过滤、每 binding 节流/round-robin、队列/在途上限；12人138s和批量超时仍可能。

## 下一包先做什么

1. **先做 per-binding `sentBytes/totalBytes/queued/rate`（94 的第2项）**：改动小、不碰调度，能给下一包提供基线和 Dock 真实数据；同时把 Dock 文案按 broadcast key 过滤（或改成“正在下载素材”）。
2. **紧接着做每 binding 一条节流钟 + 全局预算/round-robin**（94 的第3项）：这是解决12人138s和“前序 key 占满全局节流导致后 key 超时”的关键；单 key 广播的总时间会从138 s降到接近单玩家时间，批量后 key 也不会被前序长传输拖死。
3. **最后再做队列/在途上限**：在有了 per-binding 速率和队列深度后再定阈值，不要先拍脑袋加 timeout 或大 chunk（大 chunk 会破坏旧 receiver 的256KiB校验）。
4. 若只想先消掉“后 key 假超时”，可在第2项之前加一条**批次级宽松 watchdog**（从最近一次任何 start 起算，而不是单 key），但它不能替代公平调度。
