## 焦点 1：45 ms 是否留够

- 45 ms → 22.2 asset/s；加 world 16.7/s、alive 0.5/s ≈ **39.4/s**，离服务器 60/s 还有 **20.6/s**，move-result/判定/说话放得下。**不需要再降速。**
- `asset-fail` 也进同一个节流钟：32 个 forbidden 约 **1.44 s**，30 s 超时够。
- 单文件 64 MB = 256 块，约 **11.5 s**，30 s 够；单条 350 KB 远低于 8 MB。
- 服务器仍只转发；不做 backpressure 是已知项，归 4-C。
- **但 45 ms 只解决服务器 60/s，不解决请求级 30 s 总时限；见 P2。**

## 焦点 2：cancel

- 正常路径成立：玩家 `reset()` 对 `requests` 里每个 requestId 发 `asset-cancel`，之后可重新请求；host `assetCancels` 记 requestId，`serveAssetRequest` 在每块前查 `isCancelled`，取消后不发后续块也不发 end；`finally` 清 requestId。测试覆盖。
- requestId 由计数器 + 随机生成，正常不会复用；重复 cancel 只是 Set add；`finally` 清；重复 cancel 无影响。
- cancel 在 serve 开始前：如果请求已发出、cancel 后到，host 可能先发一块再在下一块停；这是可接受的竞态，不会写出半文件（end 不发）。
- cancel 在 serve 结束后：`onAssetCancel` 会把 requestId 加进 Set，但没有对应的 serve `finally` 清理；Set 会留下未知 id，直到 64 上限。P3。
- `assetCancels` 上限 64：正常一次 reset 最多 30 个请求（request 配额 30/10 s），批量最多 7 个（200 媒体），远低于 64，**不会误丢正常 cancel**；但恶意/迟到 cancel 可填满 64，之后合法 reset 的 cancel 被丢掉，host 会继续发完。P3。
- `onAssetCancel` 在 players 不存在时 return：此时没有 serve 可取消，serve 的 `send` 也会因 `players.has` false 返回 false，效果可接受。

## 焦点 3：timeout（P2）

- 默认 30 s，`timeoutMs:0` 关；`unref` 仅 Node 测试有效，浏览器无 unref，行为正常。
- **问题：timer 是“每个批次 requestId 一个总时限”，不是每个 key 的 inactivity，也不在每收到一块后刷新。** 一个 requestId 覆盖最多 32 个 key，host 在 `serveAssetRequest` 里按 key 串行发；多批并发又共享全局 45 ms 节流。
- 例：一次 world 200 个媒体 → 7 批，每批 32 个 key，全部请求同时发出、各自 30 s 到点。若 200 个媒体平均 1 MiB，总块数约 800，22/s 约 **36 s**；各批在 30 s 到点会把还在传的 key 判 `read-failed`。
- 多玩家同时拉 64 MB：3 个玩家各 256 块 = 768 块，共享 22/s 约 **34.6 s**；每人的 30 s timer 都会在仍收到数据时先到点。
- 探针：`request(['a','b'])`、`timeoutMs:10`；a 正常 end；b 在 5 ms 收到第一块，10 ms 到点即把 b 判失败，证明 timer 不因收到 chunk 刷新。
- 单文件 64 MB 11.5 s、32 个 forbidden 1.44 s 都在 30 s 内；**问题只在多 key 批次/多并发，不是单文件大小。**
- 部分完成时 timer 仍在：`forget` 每完成一个 key 就从 `set` 删除，只有 `set` 空才 clear timer；所以剩余 key 仍受同一个总 deadline 约束——**“部分完成”不延长，正是 P2 的根源。**
- `asset-fail`/chunk 错误路径调 `forget`，全部 key 清掉时清 timer；不会漏清；但 timeout 只清 pending/requests/timers，**不发 `asset-cancel`**，host 会继续把已超时的请求发完。P3。
- `reset` 清所有 timer，正确。

## 焦点 5：request 配额

- 30 次 / 10 s / binding。200 媒体 = `ceil(200/32)=7` 批，**7 < 30，不误伤**。
- 超过约 960 个媒体（31 批）或短时间反复换图/重连时，超出配额；`onAssetRequest` **静默 return，不发 asset-fail**，玩家 30 s 后 timeout 才失败。P3，应 fail fast。
- `assetRequestLog` 只在 `dropPlayerAssets`/reset/project 清；`registerOnlinePlayer` 不清；旧 log 会压新连接配额。P3。
- 没有“同时最多一个/有限个 active serve”的上限：30 次/10 s × 32 key = 960 个 key 的 serve 可并发启动，host 会同时 `getRaw`/占内存；P3（DoS 面，玩家受邀但仍应限）。

## 焦点 7：P0 / P1 / P2 / P3

### P2（1）

**30 s timeout 是批次总时限，不是每 key inactivity；多 key/多批/多玩家共享 22/s 时会砍掉仍在传输的 key。**

- 200 个 1 MiB 媒体约 36 s；3 人各拉 64 MB 约 34.6 s；都由同一个 30 s deadline 先到点。
- 单文件 64 MB 11.5 s 没问题，所以不是“30 s 太短”这么简单，而是 timer 作用域/刷新方式错了。
- 修法：每 key 独立 timer，收到 chunk/end 时刷新 inactivity；或 per-key deadline 按 size/pace 估算；或把批次拆成小批并串行；timeout 时同时发 `asset-cancel`。
- 4-B 不修这处，正常大世界/多人会缺贴图，不能推。

### P3（9）

1. timeout 只清 pending/requests/timers，不发 `asset-cancel`；host 继续发完，浪费带宽和 22/s 预算。
2. `registerOnlinePlayer` 清 allow/cancels 但不清 `assetRequestLog`；重连继承旧配额，与说明不符。
3. `peer.left` 不清 players/allow/cancels/log；旧 binding 权限/配额残留（重连 register 只清 allow/cancels）。

5. `assetCancels` 上限 64 无时间戳/无“是否在途”校验；迟到/恶意 cancel 会留下未知 id，填满后合法 reset cancel 被丢。
6. allow 在最后一块后、end 前撤掉时仍发 end；旧 key 收走不严格（同 binding 旧 world 不算越权）。
7. `fail()` 对 allow 撤掉后的 missing/too-large/read-failed 返回 false，不发 fail，只能等 timeout。

## 4-C 前必须补

1. **timeout 作用域**：每 key 独立 inactivity timer（收到 chunk 刷新），或按 key 的 size/pace 算 deadline；避免批次总 deadline 砍活动传输。
2. **timeout→cancel**：超时发 `asset-cancel`，host 停止后续块；取消后 `finally` 清干净。
3. **配额失败回 fail**：`onAssetRequest` 配额拒绝时发 `asset-fail`（或专门 reason），不要静默等 30 s。
4. **清理**：`registerOnlinePlayer` 清 log；`peer.left`/stale binding 清 allow/cancels/log；cancel Set 加时间戳/在途校验/清理。
5. **live allow 边界**：end 前再查 live；allow 撤掉后的非 forbidden fail 处理（至少不要静默）。
6. **测试**：多 key/多批 timeout、多玩家并发共享节流、timeout cancel、配额拒绝、cancel 上限、register log、allow-end 竞态、rate/fail 节流；再加 onAssetRequest/PlayerView 集成。
7. 注释改 45 ms/22/s；4-C 的失败/进度 UI 和 server backpressure/播放仍按原计划。
