### P2-2 玩家 opener 为 null 时，`source=null` 的 BroadcastChannel `world` 被当 host 消息

- `src/runtime/transportLocal.ts:114`：
  `if (this.role === 'player' && e.data.type !== 'alive' && e.source !== window.opener) return;`
  `e.source === null` 且 `window.opener === null` 时条件为 false，**不拒**。
- `:117`：`e.source === window.opener` 对 `null === null` 为 true，`from` 被记成 `'host'`。
- `src/runtime/sync.ts:556-560`：`listenAsPlayer` 先按 `meta.from !== 'host'` 过滤，再按
  `m.from !== bound` 过滤；上面两者都过了就会收 `world`，`inst/lastHeard` 也更新。
- 实测（transport 级）：`window.opener=null` 的 player transport 接收
  `{origin:'', source:null, data:{type:'world'...}}`，`onMessage` 得到
  `{type:'world', from:'host', source:null}`；opener 非空时同一消息被拒。
- 改前 `git show HEAD:src/runtime/sync.ts` 的 `listen` 对 player 不做来源过滤，但
  `listenAsPlayer` 的 `if (m.type !== 'alive' && (!source || source !== window.opener)) return;`
  会因 `!source` 拒掉；本刀把来源检查搬进 transport 时写漏了 `!source`，是回归。
- 触发条件：玩家直接打开带 `?view=player&session=...&binding=...` 的 URL（opener 为 null），
  再由同源标签页 BroadcastChannel 发一个知道 session/binding 的 `world`。不改 transport 的话，
  `listenAsPlayer` 的 “双守卫” 只有 `meta.from` 这一道，而它被 transport 误标成 host。
- 建议：`if (this.role === 'player' && e.data.type !== 'alive' && (!e.source || e.source !== window.opener)) return;`
  并把 `from='host'` 改成 `e.source && e.source === window.opener ? 'host' : ...`；
  在 `transport.test.mjs` 加 opener=null + source=null 的 world 必须拒。

## P3（不阻塞）

### P3-1 关窗绑定不再清理；失效绑定留 transport peer

- `sync.ts:275-277`：`if (!transport.hasPeer(binding))` 只在 context/pc 无效时
  `players.delete`；context 有效、只是窗口关掉时直接 `continue`，**不删绑定、不 save**。
- 改前 `HEAD:sync.ts:301-302`：`p.win` 为空走无效判断；`p.win.closed` 则
  `players.delete(binding); saveBindings(); continue;`，无条件删掉关闭窗口的绑定。
- 实测：host 开 `a` 的玩家窗口，取 URL 里 binding；把 `opened.closed=true` 后
  `send({type:'world'})`；`sessionStorage['ts-player-bindings-<SESSION>']` 里 binding 仍然在
  （`{"64...":"a"}`），`playerWindowFor('a')` 为 false。改前这一步会删掉并保存空表。
- 影响：关掉的玩家窗口的 bearer binding 继续留在 `players` 和 sessionStorage；host 刷新后
  这份 stale binding 会被重新加载，旧 URL 仍可 `hello` 抢回绑定（host 当前没刷新时，
  `bindPeer` 因 peer 已关闭仍拒绝，见 P3-2）；每次开关窗口还多一条永不释放的记录。
- `sync.ts:290` 在 invalid 时 `players.delete`，但没 `transport.dropPeer(binding)`；
  `transportLocal.peers` 仍保留那个窗口，`bindingFor(source)` 还能反查到绑定，
  `onProjectReplaced` 又只遍历 `players.keys()`，这份 peer 会一直留到页面卸载。
- 建议：给 Transport 增加“peer 存在但已关”的查询（或 `hasPeer` 返回状态），
  在 `send` 的关闭分支删 players + saveBindings；invalid 分支同时 `dropPeer`。
  不要在 `hasPeer` 为 false 时一律删，否则会把 saved binding（本来就没 peer、用来重连）误删。

### P3-2 Transport API 边界：closed peer、dropPeer、sendToPeer、close/onMessage

- `bindPeer`（`transportLocal.ts:39-44`）只拒绝 `existing && existing !== source`；
  existing 是 closed Window 时同样拒绝。实测：`bindPeer('b', closedWin)` 返回 true，
  再用新窗口 `bindPeer('b', newWin)` 返回 false，`hasPeer('b')` false。
  这与 `Transport` 注释“本地窗口刷新后重新把 binding 绑到新的 window”（`transport.ts:19`）
  不一致；若浏览器真的给出新的 WindowProxy（或上层想把 closed peer 重新接回），这里会卡住。
- `dropPeer`（`:58-60`）只 `peers.delete`，不关窗、不清 players；调用方
  `clearTrialWindows`/`onProjectReplaced` 会另行删 players，但 `send` 的 invalid 分支没有。
- `sendToPeer`（`:62-65`）返回 false 时 sync 的 world/alive 都不删绑定、不提示；
  窗口已关但 context 仍有效时，`hasPeer` 已经先 false，绑定就永久留着（P3-1）。
- `close`（`:91-100`）确实 `channel?.close()` 并清 handlers/peers，但 `sync.ts` 的
  singleton 从不调用；`onMessage` 的 off 在 handlers 空时也不会移除 window/channel 监听，
  `listening` 永远保持 true，`seen` 继续累积。若以后页面需要重建 transport，会留下旧监听。
- `seen` 从“每个 listen 各一份”变成 transport 全局一份；
  `for (const fn of [...handlers])` 里某个 handler 抛异常会中断后续 handler，
  而旧实现里每个 window listener 独立，一个抛异常不影响其他 listener；目前 handler 都较窄，
  但这是 P3 级鲁棒性差异。

### P3-4 守卫/API 空档

- `sync.ts:310-315` 的 `bindingOf`：字符串入口只 `players.has(ref)`，不查 transport peer；
  `onSay/onMove/onJudgeRoll/onCodeSubmit` 都是导出的，测试或未来 WsTransport 若把消息里的
  binding 直接传进来，会绕过“这个连接确实绑了该 binding”的校验。当前 local 路径传的是
  `meta.from ?? meta.source`，`meta.from` 来自 `bindingFor(source)`，本地尚可；Ws 必须由
  服务器/连接状态给 binding，不能拿 payload。
- `listen(fn, _player = isPlayerEntry())`（`sync.ts:504-506`）的 `_player` 完全不用了；
  改前调用方传 `player=false` 会改来源白名单，现在 transport role 在模块加载时定死。
  `consent.ts:14` 的 `false` 仍能工作（host transport），但 API 语义变了；调用方应删参数或
  改成显式角色检查。
- `skill-decision` 目前没有任何绑定校验：`consent.ts:5-10` 只比对 `castOf()` 的 id/step，
  同源任意标签页都能广播同意/不同意；若 P2-1 改成 sendToHost，线上任意玩家也能替
  别人点头。需要把决策绑到 `binding → pcId → cast.casterPcId`。
- `onMove/onCodeSubmit` 的 binding 守卫没有行为测试；onSay/onJudgeRoll 只有源码字符串断言。
  目前代码本身正确（`bindingOf` + entry.pcId + sameContextWindow），但 mutation 保护不足。
