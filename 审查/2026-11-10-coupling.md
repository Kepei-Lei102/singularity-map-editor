# 耦合审阅（2026-11-10）

审阅对象：`src/` 全部 66 个模块、284 条 import 边（脚本按相对路径解析，含 `.ts/.tsx`）。
本报告只谈「模块之间怎么粘在一起」，不谈单文件内的代码质量（那在 rules / scene / runtime / ui 四份里）。

## 一句话结论

**数据层（types.ts）是干净的，但状态层（store.ts）成了唯一的上帝对象**：27 个模块直接 import 它，
连 `src/rules/` 里本该是纯函数的三个文件（judgments / dialogue / skillCast）也在 import。
判定逻辑因此有三套入口、四份常量、两处类型定义——不是谁写错了，是层边界从来没画。

## 1. 依赖方向

```
        被引用 →
core        core  scene  rules  runtime  components
core         X     X      X      X        .
scene        X     X      X      .        .
rules        X     X      X      X        .
runtime      X     X      X      X        .
components   X     X      X      X        X
```

理想应该是单一方向的 `components → runtime → rules/scene → core`。现在的实际违反：

| 违反 | 具体边 | 后果 | 严重度 |
| --- | --- | --- | --- |
| core 反向依赖三层 | `core/store.ts` → `scene/architecture`、`scene/perception`、`scene/memory`、`rules/sense`、`runtime/media` | store 是「世界写入器 + 视野重算器 + 媒体上传器」，任何一层改签名都从 store 发酵；想给 store 写单测必须拉起整个 app | P1 |
| rules 依赖 runtime | `rules/consent.ts` → `runtime/sync`<br>`rules/dialogue.ts` → `runtime/actions`<br>`rules/skillCast.ts` → `runtime/sync` | 规则层不再是纯函数，测试必须 bundle runtime（现有测试就是这么绕的） | P1 |
| rules 依赖 store | `rules/judgments.ts`、`rules/dialogue.ts`、`rules/skillCast.ts` 直接 `getWorld()/setUI()` | 这三个文件无法脱离全局状态复用；判定广播的规则和传输搅在一起 | P1 |
| scene 依赖 rules | `scene/memory.ts` → `rules/flow` | 场景层为了一个流程判断被迫依赖规则层 | P2 |

## 2. 循环依赖（脚本报 2 组，复核后 1 组）

**（复核：运行期只有 1 组真环，另一组是类型导入造成的假阳性）**

1. `runtime/actions.ts` → `runtime/sync.ts` → `rules/dialogue.ts` → `runtime/actions.ts`
   **根因**：dialogue 需要 `findMap`（在 actions 里），actions 需要 `sync` 的 `push*`，sync 又需要 dialogue 的文案/规则。
   破法：把 `findMap` 这类纯查询下沉到 `core`（比如 `core/worldQuery.ts`），dialogue 只剩规则函数，sync 只做运输。
   这一步能同时解掉上面「rules→runtime」的两条边，收益最大。
2. ~~`rules/skills-data.ts` ↔ `rules/skills.ts`~~ **（复核后撤回）**
   这条是脚本把 `import type` 也算成边了。实际 `skills-data.ts:4` 只有 `import type { SkillDef }`，
   编译后整条擦除，**运行期没有环**。真正成环的只有第 1 组。

## 4. 单一事实来源缺失（同一个概念多份定义）

### 4.1 判定引擎：两套并存

| 引擎 | 位置 | 谁在用 | 口径 |
| --- | --- | --- | --- |
| `resolve()` | `rules/interaction.ts` ~L300 | 动作卡（186 条）、技能施放、对抗 | ≥ DC、极值覆盖、对抗 DC、次数劣势、幸运特例 |
| `resolveCheck()` / `resolveChecks()` | `rules/interaction.ts` 新增 | 跳跃、感知 | ≥ DC、极值覆盖（已对齐），但**没有**对抗 DC／次数劣势／幸运特例 |

口径这次对齐了，但结构上仍是两份。将来「跳跃对抗」「感知受次数影响」时必然再分叉。
建议：`resolveCheck()` 只保留「单属性判定」这一层，`resolve()` 调它；或者反过来把 `resolve()` 拆成
`judge(属性值, 骰点, DC)` 和 `compose(多属性合并)` 两个纯函数，所有入口都调这两个。

### 4.2 空间常量：一处概念三处定义

| 概念 | 定义位置 | 值 |
| --- | --- | --- |
| 一格几米 | `rules/jump.ts:30` `CELL_M` | 0.75（注释写「跟 height.ts 保持一致」＝人工同步） |
| | `scene/perception.ts:16` `CELL_METERS` | 0.75 |
| | `scene/height.ts:29` `CELL_METERS` | 0.75 |
| 一层几格 | `rules/jump.ts:408` `FALL_TO_NEXT_FLOOR` | 8 |
| | `scene/height.ts:12` `FLOOR_HEIGHT_CELLS` | 8 |
| 默认身高（**死代码**） | `rules/move.ts:154` `DEFAULT_HEIGHT` | 男 170 / 女 160 / 其他 170 |
| 默认身高（唯一在用的） | `scene/sight.ts:27` `DEFAULT_HEIGHT_CM` | 男 173 / 女 164 / 其他 170 |

**更正**：`move.ts` 那份是死代码——`heightOf()`（`move.ts:157`）没有任何调用点，
移动/跳跃这条链根本不读身体高度。所以这不构成"同一角色两套身高"的运行时 bug，
真正的问题是：**身体高度只有视野在用，移动侧没有默认身高**，两处默认值还互相不一致。
要么把身高接进移动/跳跃，要么删掉 `heightOf` 和 `DEFAULT_HEIGHT`，并把 `sight.ts` 那组数写进文档。

### 4.3 类型：同一结构两份

- `TrialEvent`（攻击/伤害卡片）：`core/types.ts:516` 与 `core/store.ts:260` 各一份。
  加 `dice` 字段时先改前者编译不过、改后者才通过——这次踩到的就是这个。
- `CheckResult`（`resolve()` 的返回）与 `AttributeCheck`（`resolveCheck()` 的返回）字段高度重叠但没有共同基类型。
- `CheckSpec`（动作卡）与 `JudgeSpec`（新判定）名字只差一个字母，职责却是两回事——**这是耦合审阅里最容易误用的命名**。

### 4.4 协议：骰点结果只有一个 `value`

`runtime/sync.ts:27` 的 `judge-roll` 消息只带 `value: number`，`core/store.ts:291` 的 `judgmentResult` 同样只有一个值。
「优势骰/劣势骰」需要两个值，协议层根本表达不出来——所以面板路径上的优劣势是被**结构性地**丢掉的，不是忘了写。

## 5. 隐式契约（跨模块靠「约定」而不是类型）

| 契约 | 现状 | 风险 |
| --- | --- | --- |
| 世界结构 | `core/types.ts` 与 `core/schema.js` 两份定义 | 加字段时 schema 不校验 → 旧工程读到脏数据；反向则新工程被拒 |
| 生成物 ↔ 手写代码 | `rules/actions.json`、`rules/skills-data.ts` 由 `scripts/` 生成 | 生成器的字段名一改，`resolve()` 静默不认（没有编译期保护） |
| 跨窗口消息 | `SyncMsg` 有类型，但 host 侧校验靠手写分支 | 任意窗口能否伪造 `judge-roll` 待 runtime 审阅确认 |
| 视野口径 | `docs/视野统一-v0.1.md` + `sight.ts` 常量 | 本次刚统一，但 `render.ts` / `perception.ts` 仍各有一份「看清」距离表 |

## 6. 每次 update() 都跑一遍分析管道

`core/store.ts:127`：`next = produce(withVision(next, world), syncMemory)`。
也就是说**任何一次世界修改**（包括在 Inspector 里敲一个字）都会跑：

1. `withVision` → 逐张地图判 dirty，脏了就 `partyVisionDetailOf`（全图视野）；
2. `syncMemory`（`scene/memory.ts:83`）→ 逐图逐人 `syncLayer` + `pruneMemory` + `cloneLayer`；
   `cloneLayer` 会把 fog 数组（W×H）和 subFog（可能上万个 key）整层复制一份，
   **每队每人一份**（`memory.ts:89`、`95`）；
3. `bumpStateRevs`。

40×40 地图 + 4 名队员时，单次输入 = 4 份整层复制 + 一次全图视野（若 dirty）。
这不是「耦合」本身，但它是耦合的后果：**分析层被塞进了写入路径**，所以任何编辑都要付分析代价。
建议：把 `syncMemory` 从 `update()` 挪到「批次结束/松手/失焦」时跑一次（`batching` 已经有钩子），
`cloneLayer` 改成结构共享（fog 用 `Uint8Array` 池化或只在变化时复制）。

## 7. 随机源四份，且都不走同一个函数

| 位置 | 用途 |
| --- | --- |
| `rules/jump.ts:33` `rollDie(sides)` | 跳跃判定 |
| `rules/sense.ts:38` `defaultRoll(sides)` | 感知判定（与上一行**完全相同的实现**，抄了一份） |
| `rules/jump.ts:115` 内联 `Math.floor(Math.random()*faces)+1` | 摔伤骰 |
| `runtime/trial.ts:699`、`855`、`909` 三处内联 `1 + Math.floor(Math.random()*100)` | 攻击 / 借机攻击 / 救治 |
| `public/dice`（iframe）+ `components/DiceTray.tsx` | 玩家掷骰（唯一带 seed 可复现的） |

后果：想给主机骰子加可复现 seed、想做「见证者代掷」时留痕，得改五个地方；
而且 `trial.ts` 那三处写死 D100，绕过了「D20 区 / D100 区」的概念——
将来攻击如果进 D20 区（比如心理战），这里会静默按 D100 掷。
建议：`core/dice.ts` 导出 `rollDie(sides)` 和 `rollWith(sides, rng)`，全部改为调它。

## 8. 建议的拆分顺序（按收益/风险比）

1. **把 `findMap` 一类纯查询下沉到 `core/worldQuery.ts`** —— 一次解掉 2 组循环里的 1 组，并消掉两条 rules→runtime 边。风险低。
2. **默认身高只留一份**，`move.ts` 与 `sight.ts` 共用 `core/bodyData.ts`。半小时的事，能消掉一个真实数值 bug。
3. **空间常量收进 `core/units.ts`**（一格 0.75、一层 8、每格 75 点、基础 375）。纯替换，测试可立即验证。
4. **`TrialEvent` 只留 `types.ts` 一份**，`store.ts` 引用它。纯删重复。
5. **协议升级：`judge-roll` 携带 `values: number[]`** —— 解掉优劣势的结构性丢失（见 ui 报告 P0）。
6. 最后才动 `store.ts`：把它按「世界读写」「视野重算」「试玩状态」三段拆开。这是大手术，放最后。

前三步做完，`store` 的扇入会从 27 降到 ~20，且判定层能脱离 app 单测。
