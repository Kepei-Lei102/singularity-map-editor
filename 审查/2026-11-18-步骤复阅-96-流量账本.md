## 账本生命周期

- `beginAssetFlow` 在 `tryAcquire` 成功后、`serveAssetRequest` 前建；`endAssetFlow` 在 serve 的 `finally`；register/unregister/drop/reset/换工程都会 `assetFlows.delete(binding)` 或 `clear()`，并 refresh。
- serve throw、send false、players 删除、cancel：都会走到 `finally`，flow 最终删；send false 只让 serve 提前返回，不会漏 finally。
- 旧 serve 在 flow 被删后 `noteAssetBody` 找不到 flow 直接跳过；旧 finally 的 `endAssetFlow` 找不到 flow 直接返回，不影响新 flow。正常路径没有永久残留。
- 配额拒绝的 `beginAssetServe` 传 `stats:false`，不建 flow；只发 forbidden 的请求不会进 dock；active cap 的 `rejectAssetRequest` 本来就没有 flow。
- **P3 边界**：
  - 玩家可以复用同一个 `requestId` 再发 `asset-request`；`beginAssetFlow` 会直接 `flows.set(requestId, ...)` 覆盖旧 flow，旧 serve 的 `noteAssetBody` 会把旧 key 写进新 flow，旧 finally 又会 `flows.delete(requestId)` 删掉新 flow；`startedFiles` 可能超过 `totalFiles`，bytes/totalBytes 错乱。
  - 如果 `serveAssetRequest` 的 `load`/promise 永不 settle，flow 会一直留到下一次 register/drop/reset；本地 `getRaw` 正常会 settle，但 flow 没有独立 watchdog。
  - `players` 删除后 serve 的 send 返回 false，flow 仍在，直到 finally；这段时间统计会显示“在传”，但实际没发出去，时间很短。

## 数值

- `totalFiles`：`beginAssetFlow` 与 `serveAssetRequest` 都用字符串过滤、去重、`slice(0,32)`；当前 `ASSET_MAX_KEYS=32`，两边一致。`slice(32)` 是硬编码，将来改常量容易和 serve 脱节（P3）。
- `startedFiles`：每次成功 send 的 `asset-start` 加 1；serve 对每个 key 只发一次 start，重复 key 已被去重，正常不会超过 `totalFiles`。requestId 复用/重复 start 才会超出。
- `asset-fail` 不记：失败/forbidden/missing/too-large 的 key 永远不计 started，`queued = totalFiles - startedFiles` 会把它们一直算到 flow 结束。正常世界媒体里缺文件、权限撤掉都会让 dock 的“N 个排队”虚高，直到整批结束。P3。
- `base64Size`：`floor(len*3/4) - padding` 对标准 base64 是精确的，256KiB、0/1/2/3 字节都对；正常 chunk 不会多算 1–2 字节。
- `asset-end`：正常 `actual === file.sent`，`bytes += actual - sent` 是 0，不会减成负数；只有恶意/错误的 end 小于已发或 `Infinity`（`typeof === 'number' && >=0` 没排除 Infinity）才会让 bytes/totalBytes 变负或 Infinity。P3。
- `rate = bytes / max(1, 秒数)`：1 秒下限让 5 字节的测试也得到 5 B/s，`rate>0` 成立但很粗；aggregate 用最早 `startedAt`，长 flow 会把总均速拖低；rate 是累计平均，不是瞬时/窗口速率。P3 口径。

## 统计口径

- `players` 按有 flow 的 binding，`requests` 按 flow 数，不是 `AssetSession.activeCount`；配额 `stats:false` 不会有 flow，正确。
- 广播期间地图图片请求也会计入；文案“正在传素材”比“广播 key”宽，但仍可能让主持人以为当前广播文件在传给 N 人。P3。
- `bindings[]` 顺序是 Map 插入顺序，绑定重建前稳定；snapshot 相等比较逐项按 index 比，顺序变化会触发通知，语义可以。
- snapshot 的相等判断包含 `rate` 浮点；每个 chunk 的 bytes 和 now 都变，rate 几乎每次都不同，所以 22 块/s 会 22 次通知/重建 snapshot；值没变时确实不换对象，正常。
- `listener` 单个抛错被 try/catch 吞掉，避免拖住其他订阅者，但没有日志，掩盖订阅者 bug，P3 可观测性。

## 通知/性能

- 全局 `ASSET_PACE_MS=45` 最多 22 块/s，`noteAssetBody` 每块后 refresh；MediaDock 用 `useSyncExternalStore`，宿主每块重渲染一次。单个广播文件可接受；多 binding 时 aggregate 仍 22/s（全局节流），`bindings.every` 只 O(bindings)，不是问题。
- 但 rate 浮点几乎每块都变，UI 会持续重渲染整块 MediaDock（含 MediaView 的 props 引用变化？MediaView props 只看 mediaId/mime，但父组件重渲染仍会走）；建议 100–200ms 节流或只在整数进度变化时通知。
- `noteAssetBody` 每条 start/chunk/end 都 refresh；end 的 `actual` 校正也 refresh；次数可控。

## P3

1. **queued 口径**：`totalFiles - startedFiles` 把 forbidden/missing/too-large/canceled 的 key 一直算成排队，直到整批 flow 结束；dock 可能显示“3 个排队”但实际是3个失败。
2. **requestId 复用/重复请求**：`beginAssetFlow` 覆盖旧 flow，旧 serve 的 note/end 会污染新 flow；startedFiles 可超过 totalFiles，bytes/totalBytes 可错乱；没有 requestId 唯一性校验。
3. **flow 生命周期**：serve promise 永不 settle 时 flow 永久留存；没有 flow watchdog；players 删除/send false 后 flow 仍短暂显示“在传”。
4. **UI**：长文本在340px会换两行、dock 高度跳；fmtBytes 无 GB/负值/NaN 防御；没有渲染测试。
5. **性能/通知**：rate 浮点每块变化导致22/s通知和整 Dock 重渲染；listener 异常被吞且无日志。
6. **测试缺口**：end 校正、base64 padding、rate下限、配额 stats:false、多 binding/多 flow、requestId 复用、UI 都是0红；5字节不能证明 bytes 精确。
7. **下一包所需字段**：bindings 仍只有不透明的 `binding`，没有 pcId/名字；没有“已启动但未完成”的在途数/队列上限/瞬时速率；也无法按 broadcast key 过滤。做每 binding 节流前，至少要先补 identity（pcId/名字）和 in-flight/queue 口径。
