## 焦点 1：每 key timer 是否真 inactivity

- 是“每 key 一个 timer”，不是整批死线：`timers: Map<key, timeout>`；收到该 key 的 chunk 会 `clearKeyTimer` 后重新 arm 30 s；end/fail/坏块/错误/reset 都清 timer；同批其他 key 不受影响。新测试覆盖 a 到点、b 因 chunk 续期不被同一时刻砍。
- **但 timer 在 `request` 发出时给每个 key arm（assets.ts:250），不是在该 key 收到第一块时才启动。** 于是“inactivity”只对已经开始传的 key 成立；排队等 host 的 key 仍按“请求发出时间”计时。
- 主持端 `serveAssetRequest` 按 key 串行发，多批又共享 45 ms 全局钟：
  - 一批 4 个 64 MB 文件：前 3 个约 3×256 块 = 768 块 /22/s ≈ 34.6 s；第 4 个 key 的 timer 在 30 s 就到点，而它约 34.6 s 才开始，必被砍。
  - 200 个 1 MiB 媒体 → 7 批，总约 800 块 /22/s ≈ 36 s；每批 32 key，后几个 key 的首次 chunk 在 30 s 后才到，timer 早已到点。
  - 探针：`request(['a','b'])`、timeout 10；a 正常 end；b 到 15 ms 才有第一块。结果 `fails=[['b','read-failed']]`，并发出 `asset-cancel {key:'b'}`，b 的 chunk 被忽略。**排队时间被算成 inactivity。**
- 因此“第 30 个 64 MB key”确实是极端批次；但**一批 4 个 64 MB、或 200×1 MiB 的 7 批就已经复现**，不是只极端。**P2 仍在：per-key 只修了传输中的死线，没修排队等待。**
- 单文件 64 MB 11.5 s、3 个 64 MB 的第 3 个约 23 s 开始（首块后续期）都安全；问题阈值是“首块到达 >30 s”。
- `reset` 清全部 timer；`timeoutMs:0` 关；`unref` 仅 Node；重复块不续期（见 P3）。

## 焦点 2：主持端 per-key cancel

- `assetActive` 拦截迟到/木马 cancel：只有该 binding 当前 active requestId 才接收；正常早到/晚到都不会落地。reset 的 `{requestId}` 无 key → `all=true`。
- 每 request 最多 64 key（`entry.keys.size < 64`）；每 binding 最多 64 request entry（`byReq.size >= 64` return）。正常 ASSET_MAX_KEYS=32、200 媒体 7 批远低于。
- `serve` 每 key 开头查 `isCancelled(key)`，每块前再查；取消 key 后 `completed=false; break;`，随后 `if (!completed) continue;` **一定继续下一个 key**；取消 all 时外层逐 key `continue`，不发块不报错；最后 `finally` 清 active/cancels。
- **缺口：**
  - **`assetActive` 本身没有 64 request 上限，也不是 refcount。** 30 请求/10 s、每请求持续 >10 s 时 active 可超过 64；`assetCancels` 只保留 64 个 entry，第 65 个 active 请求的合法 reset cancel 会被丢。重复 requestId 时第一次 `finally` 会删掉 active，第二次仍 active 但 cancel 被拒。P3。
  - **`serve` 在 `asset-end` 前不再查 `isCancelled`**（只查 live allow）。玩家在最后一块后、end 前 cancel，host 仍发 end；P3。
  - **`registerOnlinePlayer` 只清 allow/cancels/log，不清 `assetActive`**。同 binding 重连顶旧连接时，旧 serve 可能在 allow 已清后向新连接发 forbidden fail，直到自己 finally；P3。

## 焦点 3：peer.left

## 焦点 4：配额拒绝回 forbidden

- 30 次 /10 s；200 媒体 7 批，不误伤。超配额走 `serveAssetRequest` + `meta:()=>undefined`，每个 key 发 `asset-fail forbidden`；32 个 fail 约 32×45 ms = **1.44 s**，远小于 30 s；玩家每个 fail 都清 pending，不会留到 timeout。
- **但配额拒绝路径不写 `assetActive`**：玩家此时 reset 的 cancel 会被 active 拦截丢弃，host 仍把 1.44 s 的 forbidden 发完；只是浪费，P3。

## 焦点 5：end 前 live allow

## 焦点 7：P0 / P1 / P2 / P3

### P2（1）

**每 key timer 在请求发出时启动，不是首块到达时；排队超过 30 s 的 key 会在 host 还没开始发它之前被 cancel。**

- 4×64 MB 一批、200×1 MiB 的 7 批都能复现；不是只有 32×64 MB 的极端批次。
- 根源不是“30 s 太短”，而是 timer 起点：`request` 对每个 key 立即 `armKeyTimeout`，host 按 key 串行且多批共享 45 ms；首块未到时没有 chunk 可续期。
- 建议：收到该 key 第一块时才启动 inactivity timer；另设独立的“ waiter/开始超时”（如 host `asset-start` 或 60–120 s 排队 watchdog）；或把批次改为串行发送/逐批等待。这样 200×1 MiB 的 36 s 总时长不会再砍最后几个 key。
- 单文件 64 MB 11.5 s、3×64 MB 23 s 首块都在 30 s 内，不在 P2 范围。

### P3（9）

1. `assetActive` 无 64 request 上限、非 refcount；`assetCancels` 只保 64 entry，active >64 时合法 reset cancel 被丢；重复 requestId 第一次 finally 会清掉仍在跑的第二次。
2. `registerOnlinePlayer` 不清 `assetActive`；同 binding 重连顶旧连接时旧 serve 仍可能向新连接发 forbidden fail。
3. `serve` 不在 `asset-end` 前查 `isCancelled`；最后一块后 cancel 仍发 end。
4. allow 在最后一块后撤掉：host 发 forbidden，玩家已收 bytes 全丢并进入 15 s 冷却；若 allow 只是短暂切换，贴图缺一会。
5. live allow 检查与 end send 之间仍有窗口；allow 恰在检查后撤掉仍会 end。
6. `reset` 只清本地 pending/timer，不 fence 在途 `request`（await load 后仍会发请求）和 `finish`（仍可能 save）；reset 后可能发出新请求。
7. 并发 `request` 同一 key 可覆盖 `pending`/旧 request set；旧请求的 set 残留，旧 chunk 被忽略。
8. 重复 chunk（同 index）不续期；坏 index/count 直接 return 也不续期，只能等原 deadline。正常协议不会重复，属健壮性。
9. 测试空白：外层 cancel 0 红；active 拦截、register log、peer.left 回调、active/cancels 上限、配额、pace/fail、排队 timeout、end 后 cancel 无自动化；2 ms 余量可能抖。

## 4-C 前必须补

1. **排队 timer**：首块到达才 arm inactivity；另设排队/开始 watchdog（host `asset-start` 最干净）或批次串行等待；用 4×64 MB、200×1 MiB 两档回归。
2. **`assetActive`**：每 binding 限制 active 数（≤64 或与 request 配额一致）、refcount 或拒绝重复 requestId；`registerOnlinePlayer` 清 active；`assetCancels` 满时不要丢合法 active cancel。
3. **end/cancel**：`asset-end` 前查 `isCancelled`；明确“最后一块后 allow 撤掉”是否要丢 bytes（若丢，测试 player 侧）；end 检查后到 send 的窗口接受或加锁。
4. **reset fence**：reset 后到达的 load/请求/保存不再发/不再写，或 generation 标记。
5. **并发同 key**：request 前再查 pending/known，或把同 key 请求合并。
6. **测试**：排队 timeout、外层 cancel、active 拦截、register log、peer.left 回调、active/cancels 上限、配额、pace/fail、end 后 cancel；去掉 2 ms 余量。
7. 4-C 的失败/进度 UI、播放、server backpressure 按原计划；`asset-fail` 32 个 1.44 s 可接受。

## 结论

84 把“整批 30 s 死线”改成了真正的每 key timer，正常传输中的 inactivity、chunk 续期、end/fail/reset 清理、reset cancel、per-key host cancel、active 拦截、peer.left 清理、register log、配额 forbidden、end 前 live 检查都已落地；门禁一致，82 的 0 红也保持。**但 timer 从请求发出时启动，排队 key 的首块若 >30 s 到达仍会被砍；4×64 MB 或 200×1 MiB 的 7 批即可复现，所以 P2 仍在，84 不可推。** 其余 9 项 P3 主要是 active 上限/refcount/register 清理、end 前 cancel、allow 撤销丢 bytes、reset fence、并发同 key 和测试空白。
