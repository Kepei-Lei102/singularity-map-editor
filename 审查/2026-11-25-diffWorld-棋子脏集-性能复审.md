# diffWorld 棋子脏集 O(n²) · 独立性能复审

- 复审对象：**当前工作区未提交 diff**——`src/scene/dirty.ts`（+10/−1）与 `scripts/incremental-vision.test.mjs`（+17）。diff 指纹 `sha1 a6cae1ed8e3910c266ed7e1b579133a0ba67a80a`，复审开始时与结束时相同，期间工作区没被改动。
- 基线：当前 HEAD `8bbf70a`（比上一份性能审阅的 `f742ecc` 多了两个提交，但 `git diff f742ecc..HEAD -- src/scene/dirty.ts` 为空，所以旧实现与上一份审阅里测的那份一致）。
- 环境：Node `v24.11.0`，Apple M1 Max（10 核），macOS `27.2.1`；微基准全部串行、无其他负载。
- 方法：esbuild 打包到 `/tmp`——旧副本用 `git show HEAD:src/scene/dirty.ts` 的文本，新副本用工作区文本，另加“插桩副本”（把 `byId` 到 `added` 整段包 `process.hrtime.bigint()`）和两套 store 副本跑端到端 `update()`。仓库零改动，`git status` 只有上面两个 M 和本报告。旧/新同时 require 进一个进程做**交替配对**采样（每轮旧、新各一次，各留样取 p50/p90），抵消 GC 与热机漂移。

## 结论

**可提交。P0 / P1 / P2 = 0。** O(n²) 热点确已消失：300 棋子时脏集这一段从 **1.77ms 降到 0.047ms（−97.3%，约 38×）**，1000 棋子时从 **22.1ms 降到 0.165ms（−99.25%，约 134×）**；端到端 `update()` 300 棋子 2.34 → 0.66ms、1000 棋子 24.2 → 1.99ms。语义对拍 319 组（19 个定向用例 + 300 组随机混合）**全部逐字节相同**，四种要求的情形都对得上。唯一残余是同一段里 O(n) 的 `byId` Map + 逐棋子位置比较（引用没变时也照跑，300 棋子约 47µs），列为 P3 可选，不阻断。

## 实测一：脏集段的真实成本（插桩，`update()` 上下文）

夹具 200×200、`update(d => { d.session += 1 })`（棋子数组引用完全没变，最坏情况），40 次 p50：

| 棋子数 | 旧实现段成本 | 新实现段成本 | 加速 |
|---|---|---|---|
| 100 | 210.8µs | **17.8µs** | 11.8× |
| 300 | **1,770.8µs** | **46.9µs** | **37.7×**（−97.3%） |
| 1000 | **22,067.7µs** | **164.9µs** | **133.8×**（−99.25%） |

“段”= `const byId = …` 到 `added` 算完（`src/scene/dirty.ts:156-171`）。上一份报告里 300 棋子这一段是 1.637ms，这次同上下文复测旧实现 1.77ms，量级一致；新实现 **0.047ms**，即上次那个 1.64ms 的数字本次落到 47µs。

## 实测二：端到端 `update()`

交替配对（旧、新各 30 次，同一进程），200×200、只改 `session`：

| 棋子数 | 旧 p50 / p90 | 新 p50 / p90 | 加速 |
|---|---|---|---|
| 300 | 2.337 / 3.606 ms | **0.656 / 0.755 ms** | 3.6× |
| 1000 | 24.22 / 32.94 ms | **1.99 / 4.93 ms** | 12.2× |

另一组独立进程复跑给 300 棋子新实现 0.580/0.640ms、1000 棋子 1.835/4.83ms，与上表差 10% 以内。`update()` 里除 `diffWorld` 外的固定成本（`produce`、`withVision`、`emit`）没变，所以端到端降幅小于段降幅，这符合预期。

## 实测三：直接调 `diffWorld`（冻结 world，交替配对）

生产里的 world 是 Immer 冻结对象；把夹具深冻结后两边交替调用，30 次：

| 棋子数 | 旧 p50 / p90 | 新 p50 / p90 | 加速 |
|---|---|---|---|
| 300 | 1.399 / 1.679 ms | **0.0387 / 0.114 ms** | 36.1× |
| 1000 | 16.25 / 21.87 ms | **0.0984 / 0.105 ms** | 165× |
| 2000 | 71.74 / 82.00 ms | **0.228 / 0.274 ms** | 315× |

二次方在旧实现上是坐实的：300→1000 涨 11.6 倍、1000→2000 涨 4.4 倍；新实现 300→1000 涨 2.5 倍、1000→2000 涨 2.3 倍，是线性（Map + 循环的固定成本）。

棋子**真的动了一位**时（tokens 新数组、长度与 id 集合都不变），新实现也没退化：300 棋子 1.379 → **0.147ms**（9.4×），1000 棋子 16.99 → **0.179ms**（95×）。这条路径新代码要多建一个 `newIds` Set，成本包含在内。

旁证（非冻结普通对象、独立进程，仅看趋势）：300 棋子 0.161 → 0.026ms（6.1×）、1000 棋子 1.956 → 0.095ms（20.6×）、2000 棋子 5.72 → 0.188ms（30.4×）。注意旧实现成本在**冻结对象**上会放大 3–10 倍（冻结数组上的嵌套 `some` 更慢），所以以后给 `diffWorld` 做基准别用普通对象估，否则会低估生产成本。

## 语义核对：没变

对拍方式：同一份 world 对象分别喂给旧副本和新副本的 `diffWorld`，比**整个 Dirty 数组的 JSON**（含 `moved / structure / visionStructure / viewerScope / full / architectureChanged / terrainOnly / materialOnly` 等全部下游要读的字段）。

| 情形 | 旧 `structure` | 新 `structure` | 对拍 |
|---|---|---|---|
| 引用相同（同一 world；或 `{...w}` 但 maps 同数组） | false | false | 相同，`moved` 都是空 |
| 同长度换 id（首个 / 中间 / 末尾；杀一个再加一个） | true | true | 相同 |
| 删除（pop / splice 中间 / 删到只剩一个 / 删光） | true | true | 相同 |
| 只挪一格（x+1 / y+1） | false，`moved` 1 条 | false，`moved` 1 条 | 相同 |
| 加棋子（push / unshift） | true | true | 相同 |
| 只改名字（tokens 新引用、id 全同） | false | false | 相同 |
| 数组倒序 / 两个棋子互换位置（id 集合不变） | false | false | 相同 |

19 个定向用例全部相同；另外 300 组随机混合操作（挪动 / 换 id / 删 / 加 / 倒序 / 改名）逐组比对 Dirty JSON，**0 处不同**。

正确性前提也成立：旧实现和新实现都只在“长度不同”时直接判 `true`，长度相同时新实现用 `Set(m.tokens ids)` + 旧棋子 `some`；因为棋子 id 在 `checkWorld` 里强制唯一，`Set` 判定与原来的嵌套 `some` 等价。而“引用相同 ⇒ 没动棋子”依赖 Immer 语义：对 draft 里的棋子数组做 `push` / 下标赋值 / 元素改写都会产出新数组——仓内两处原地改（`src/runtime/trial.ts:140`、`src/components/MapCanvas.tsx:394`）都作用在 draft 上，没有绕过 `produce` 的路径。

## P0–P3

- **P0**：无。
- **P1**：无。
- **P2**：无。
- **P3（可选，不阻断）**：同一段里 `byId` Map 和逐棋子 `tokenMoved` 循环在“棋子引用没变”时仍然跑（`src/scene/dirty.ts:156-162`），300 棋子约 **47µs**、1000 棋子约 **165µs**。若要一并收掉，加 `const tokensSame = before.tokens === m.tokens;`，把这两步整段包进 `if (!tokensSame)`，`added` 的判断也用同一个变量；我按这个语义不变的改法在 `/tmp` 里量过：`update()` p50 300 棋子 0.715 → 0.592ms、1000 棋子 1.954 → 1.690ms（配对口径 −17% / −13.5%，p90 有噪声，插桩口径只对应那 47/165µs）。收益不大，**建议不单独再开一包**，下次顺手改这个函数时一起带上即可。

## 复现方法

1. 旧副本：`git show HEAD:src/scene/dirty.ts` 存成文本，esbuild `onLoad({filter:/scene\/dirty\.ts$/})` 返回它；新副本直接用工作区文件。
2. 入口：`export { diffWorld } from './src/scene/dirty'` + `export * from './src/core/defaults'`；`react` / `react/jsx-runtime` 用空桩（同 `scripts/ui.test.mjs`）。
3. 夹具：`emptyWorld()` + `newMap('大图','现实',1,200,200)`，`fog.fill(1)`，队伍 1 PC，棋子 n 个（`id tk{i}`、`pcId` 只有第一个是 PC、`x=i%200`）。
4. 插桩：在 `const byId = …` 前记 `process.hrtime.bigint()`，在 `// 自动迷雾从关到开` 注释前收时写 `globalThis.__diffSegNs`。
5. 配对：同一进程 require 旧、新两套，`for i: t0→旧→t1→新→t2`，两边分别取 p50/p90。
6. 语义对拍：同一 world 喂两套 `diffWorld`，`JSON.stringify` 结果比字符串；随机 300 轮混合操作。
7. 冻结：`deepFreeze` 递归 `Object.freeze`（模拟 Immer 产物）后再测，更贴近生产。

## 局限

- 段口径把“整段 `byId`→`added`”算作一块，没把 Map 构建和嵌套 `some` 拆开分别计时；新版是线性，拆开意义不大。
- 端到端 `update()` 的绝对值受历史栈长度、GC 时机影响，±10% 波动正常；结论用的是同进程配对差。
- 测试总时长受 HEAD 上其他提交影响（1061 项 18.6s），本包本身只多 1 条用例，不构成拖慢。
- 结论只覆盖脏集计算；`playerWorld` 投影、序列化等路径本次未动，未复测。
