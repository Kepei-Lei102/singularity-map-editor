## slice 超时

- 每块先 `blob.slice(...).arrayBuffer()`，再 `Promise.race([reading, timedOut])`；超时 reject，`catch` 走 `asset-fail read-failed`，`completed=false`，`break` 当前 key；外层 `if (!completed) continue`，同批后续 key 还能继续，单 key 不发 end。
- 晚 resolve/reject：`Promise.race` 已给 `reading` 挂 handler，超时后晚 reject 不会 unhandled，晚 resolve 被丢弃；`reading` 本身仍 pending，但不再阻塞 serve。
- timer 在 finally `clearTimeout`，且 `unref`；`sliceTimeoutMs=0` 不设；默认15s。
- 超时按 `read-failed` 而不是 `missing` 合适：文件确实存在、只是读不出来；玩家会按失败冷却/重试，语义比“没这份文件”准确。
- **P3**：15s 是**每块**上限，不是整个 flow 上限；如果每块都接近15s，单个大文件仍可拖很久，只是不会永久卡住。玩家 30s inactivity 会 cancel 该 key，但 host 没有总 flow watchdog。
- **P3**：`sliceTimeoutMs` 负值会被当成0ms立即超时，NaN 会被当 falsy 不设超时；没有参数校验，生产默认15s，只有测试/未来调用者会传异常值。

## 公平测试

- 12 binding ×2 job：24个job约500ms，连跑15次全过；每个 binding 计数2，能证明没有饿死。
- 同 binding 两 job + 另一个 binding：断言 `a1,b,a2`。但这条**并没有咬住“选 last 最小”**：a1 同步发出后，a2 要等45ms；b 是新 binding，`readyAt=0+45` 的绝对值早已过去，所以 t=20 全局 token 一到 b 就 ready，a2 还在等。即使把选择逻辑改成 FIFO（取 `ready[0]`），在 t20 也只有 b ready，t45 只剩 a2，顺序仍是 `a1,b,a2`，**突变 0 红**。要咬住选择逻辑，需要先让 b 发过一次（last 也为 t0），再让 a2/b 在 t45 同时 ready。
- 12×2 计数同样不咬 FIFO：FIFO 也会均分。**P3**：公平性仍只有计数/顺序的弱断言，没有真正测 `last` 最小。
- 测试时长约0.5s，5s timeout 余量够；15次无抖动。

## 剩余

- rate 仍是累计平均，`全场均速` 准确但不会显示瞬时掉速。
- 22块/s 每次 note 都 refresh + 通知整 Dock 重渲染，100–200ms UI 节流仍未做。
- 每 binding inFlight/队列上限未做；一个 binding 的多个 request 仍可在共享预算里占多份。
- flow watchdog：load 30s、slice15s、paced 等待都没有“整条 flow 总超时”；最坏情况由玩家30s inactivity cancel 兜底，但 host 侧没有硬上限。
- 12 binding 实测约45.8块/s（99探针），不是精确50；docs“12人61s”仍偏乐观，实际约67s。

## 下一包先做什么

1. **优先 per-binding inFlight/队列上限**：这是资源/背压，和 rate/UI 无关；先限制一个 binding 同时几个文件、排队多少，超过回 forbidden/排队，避免单个玩家在全局预算里占多份。
2. **再补 flow watchdog 和公平性测试**：slice/load 都只是单步超时，整条 flow 仍无总上限；公平测试让 b 先发一次再和 a2 同时 ready，才能真正咬住 `last` 最小。
3. **rate窗口/瞬时 + 100–200ms UI节流**放下一轮 UI；当前累计“全场均速”不会误导总量，但多人共享时看不出瞬时掉速。
4. **文档补 `sliceTimeoutMs=15s`**，并把12人61s改成“约50块/s理论下限，实测约67s，多人共享全局带宽”。
5. 12 binding 实测≈45.8块/s，建议后续实测 host base64+IDB+relay 后再考虑把全局 token 从20ms调到25–30ms。
