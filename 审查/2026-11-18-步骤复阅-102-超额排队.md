## 101 P2 是否解

- 65 key 世界 = 3 个批次：前2条 active，第3条进 queue；某个 flow 结束，`.finally` 里 `endFlow→release→refresh→drain`，drain 取队首开始传。200 key = 7 批次：2 active + 5 queued，仍 <=8，都被吸收。**101 的 >64 漏图主路径已解**。
- 320 key 以内都能进（2 active + 8 queue = 10 个32-key 批次）；321 key 起第11批 forbidden。docs 目标“200个1MiB”在范围内。
- `ASSET_MAX_QUEUED_KEYS=64` 和 queue8 的交互：flows.size<2 时一条 flow 最多32 + 新32=64，恒真；flows.size>=2 先被 flow cap 拒。**queue64 仍然不可达**，实际限制是“2 active + 8 queued requests”，最多约256个 queued key（不是64）。
- drain 只在一个 flow 结束时释放一个名额，while 实际每次最多启动一条（因为 flows.size 从2降到1只空一个槽）；不会一次启动两条，也不会重复服务同一个 requestId。两个 flow 同时结束由两个 `.finally` 各 drain 一条，顺序由 finally 顺序决定，但不会重复。

## P2：排队请求的单 key cancel 会删整条请求

- `onAssetCancel` 先无条件 `clearQueuedAssetRequest(binding, m.requestId)`，这个函数**不看 `m.key`**：只要 requestId 在队列里，就把整条 `QueuedAssetRequest` 从队列移除并清 timer。
- 玩家端 `cancel(keys)` 是单 key 取消：`assets.ts:478-486` 从 pending 删除指定 key、`forget(requestId,key)`，然后发 `asset-cancel {requestId,key}`，同批其他 key 仍在 pending。
- 场景：大世界（>32 media）的某个批次正在 queue 里，玩家停止/切换播放，`PlayerView.tsx:150/156` 调 `assets.current?.cancel([mediaRef.current.mediaId])`，只取消一个广播媒体 key；host 却把整条32-key 的 queued request 删掉且不发 fail。其余31个 key 在玩家端一直 pending，直到120秒 queue watchdog 才按 `read-failed` 失败，**本轮队列修复的所有权被这个单key cancel打掉**。
- 这也会让“排队请求被 cancel”表现为“只删队列、不发 fail”，与玩家端只取消一个 key 的语义不一致；host 没有把剩余 key 继续服务。
- **修复**：`clearQueuedAssetRequest(binding, requestId, key?)`：无 key 删整条；有 key 时只从 `entry.m.keys` 去掉该 key，key 为空才删整条并清 timer；保留其余 key 继续排队。补一个 queued 多 key + 单 key cancel 的测试。

## 队列生命周期

- 同 requestId 在途先 reject；排队时 duplicate 由 `queue.some` 挡住；queue 满8才 reject。重复 requestId 不会两条都进。
- 120秒 timer 与玩家 queue watchdog 都是120秒：host 先到点会 `clearQueuedAssetRequest` + `rejectAssetRequest`（发 forbidden）；玩家先到点会发 cancel，host 清队列、session.cancel 返回 false、不发 fail，玩家端自己标失败。两者都能收口，没有永久 pending。
- timer 在 drain/cancel/reset/drop/register/换工程都清；`clearAssetRequestQueues` 遍历清 timer；unref 有。队列空时 delete Map。
- `onAssetCancel` 对 active 请求 clearQueued 返回 false，继续 session.cancel + cancelAssetFlow；对 queued 请求删队列后返回，不发 fail；whole cancel 正确，单 key 不正确（见 P2）。
- register/unregister/drop/reset/onProjectReplaced 都清队列；`dropPlayerAssets` 也清。没有发现漏清路径。

## drain 顺序/公平

- FIFO：队首先走；`assetFlowHasRoom` 不够时停止，不会越过后面的条目乱序。
- 两个 flow 同时结束时两个 finally 各 drain 一次；第一次可能启动队首，第二次启动下一条，不会重复 `shift` 同一个 entry，也不会把同一 requestId 服务两次。
- queue 满时第11/12条 forbidden，符合“2 active + 8 queue”。
- **P3**：`while` 改成 `if` 测试0红，因为当前每次释放只有一个槽；将来若允许一次释放多个槽，`if` 会少 drain，测试没有咬住。drain 只在 `.finally` 里触发，cancelActiveFlow 的立即 endFlow 不会立刻 drain，要等 serve finally，最坏等 load/slice 超时；可接受但无测试。
