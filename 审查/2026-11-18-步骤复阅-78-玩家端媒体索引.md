## 焦点 1：放置位置与四个调用点

- `applyMediaIndex` 放在 `runtime/media.ts` 合适：`setMediaIndex`、`storageKey`、`getBlob`、`blobUrl` 都在这里；组件只 import 一个入口，没有把索引细节摊到 `PlayerView`。
- 四个点：
  - `world`：`applyMediaIndex(m.world)` 在 `setWorld(m.world)` 前（`PlayerView.tsx:83-84`）。
  - `clear`：先 `applyMediaIndex(null)` 再清世界和播放（`:105`）。
  - `onOnlinePlayerClosed`：先 `applyMediaIndex(null)` 再清世界（`:74`）。
  - unmount：`off?.()` 后 `applyMediaIndex(null)`（`:118`）。
- 没有遗漏：`play`/`stop` 不需要换索引（播放消息直接带存储名和 blob）；`move-result`、`judge-*`、`code-*` 不涉及贴图；world 的 focus-only 推送也会走同一 handler。
- 当前 `App` 在 `isPlayerEntry()` 时只渲染 `PlayerView`，主持人 `Editor` 不在同一文档；player 页面只有这一个入口，所以全局索引清空没有同页第二个 consumer 被误伤。

## 焦点 2：顺序与每帧重建开销

- `applyMediaIndex` 是同步的，`setWorld` 只是排 React 渲染；handler 返回后首次 render 时全局 `storageKey` 已经是新世界的映射，贴图懒加载和 `useBlobUrl` 都排在它后面。
- `setMediaIndex` 重建 `keyOf` 和 `mimeOf` 两个 Map。开销是 O(media 数)；player world 的 media 已按 `usedTextures` 裁过，通常不大。但每次 world 推送（包括 focus-only、每 60ms 的 coalesce 推送）都会新建两个 Map 和一批元组，属于可接受的 P3 优化点，不是正确性问题。
- 同一 ID 换内容时 `storageKey` 变了，`textureImage` 的缓存键 `${mediaId}@${storageKey}` 跟着变；探针确认换索引后同一 mediaId 会重新走 loader，不会返回旧 key 下的图。

## 焦点 3：clear/unmount 清空是否误伤

- 清空的是本页面全局 `keyOf/mimeOf`；PlayerView 是唯一消费者。
- 本地玩家窗口是独立 document，有自己的模块实例；主持人页面的索引不会被 popup 的 unmount 清掉。
- `clear` 时先清索引再 `setWorld(null)`，同一批更新里不会出现“旧世界配空索引”的中间渲染。
- `onOnlinePlayerClosed` 与 `clear`/unmount 三处重复清空是冗余但无害；没有发现误伤路径。

## 焦点 4：旧数据 key 与缓存

- `setMediaIndex` 仍是 `m.key ?? m.id`（`media.ts:44`），旧数据没有 `key` 时回落 id；新测试也断言了这一点。
- `applyMediaIndex(null)` 走 `world?.media ?? []`，确实清空；但测试只验证“旧媒体 id 仍回落 id”，没有验证“先前 keyed 映射被清掉”——把 `applyMediaIndex(null)` 改成不处理 null，测试仍绿，见 P3。
- `getBlob`/`blobUrl`/`textureImage` 都按当前 `storageKey` 取；索引变化后缓存键变化，不会拿错旧图。旧 key 的图片会留在 `images` 里直到 LRU/清理，属于缓存残留，不是错误图。

## P3

1. **call site 无自动化**：world/clear/close/unmount 四个点全靠审阅；删除任一处，717 仍绿。P3。
2. **`applyMediaIndex(null)` 清空本身没被断言**：现有用例只验证旧数据回落 id；“不处理 null”突变仍绿。P3。
3. **每次 world 推送重建两个 Map**：focus-only 和 coalesce 推送也会重建；大媒体表时有 O(media) 分配。P3。
