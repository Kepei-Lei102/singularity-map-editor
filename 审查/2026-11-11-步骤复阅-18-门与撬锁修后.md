## 5) 旧数据 `openStates: []` 的迁移判断（P2-4）

**结论：新规则本身合理，但当前迁移不可接受（如果项目承诺旧存档/导入可用）。**

探针（旧版合法、当前 schema 拒）：`repairWorld` 后仍空、`migrateWorld` 后仍空、`replaceWorld` 也接受空，随后 `checkWorld` 报错：

```text
repair fixed [] open []
migrate ok []
replaceWorld ok {"wallId":"wall1","offset":0,"width":3,"openStates":[]}
check current err 工程文件有问题：地图「一楼」.objects[1]（门）.opening.openStates 门至少要有一个打开状态
```

代码路径：

- `src/core/store.ts:21-29` `load()` 只 `migrateWorld`，**不 checkWorld**；旧工程还能启动。
- `src/core/store.ts:77` 自动保存直接 `saveSlot`；旧数据继续被写回。
- `src/runtime/actions.ts:885-893` `parseWorld` 先 `repairWorld`、`checkWorld` **再** `migrateWorld`；所以导入旧 `world.json` 在迁移前就被拒。
- `src/runtime/actions.ts:814-819` 导出/保存前 `checkWorld`；旧工程点导出会失败。
- `src/core/schema.js:84-145` `repairWorld` 明确“只动数值范围，不动结构”，不补 `openStates`；`src/scene/memory.ts:110-152` `migrateWorld` 也没有补。

**建议（不要自己改，这里只给结论）**：

1. 若旧存档兼容是承诺：在 `repairWorld` 或一个专门的迁移里处理空 `openStates`，但**不要随便取最后一个状态**。优先找名字明确是“打开/开门/开/open”的状态索引；补上后同步 `blocksWhen`。找不到这种状态时，不要猜，保留错误并给出可操作提示（检查器里加“打开”状态）。
2. 若决定把空 `openStates` 定为不再兼容的非法数据：至少要保证导入/导出错误信息告诉用户怎么修，并接受“旧工程必须手工改门”的代价；这属于产品取舍，不是代码 bug。
3. 不建议只在 `trial`/`schema` 里继续加拒，因为那样旧工程只会得到“打不开/存不了”，没有修复路径。

### P3-3 结算期改 hidden / disabled / 电子锁不复验

`settleDoorAttempt` 只复验 `door.lock` 存在、`door.opening` 存在、`openStates` 非空（`trial.ts:914`）；不查 `hidden`、`enabled`、`lock.kind`。探针：

```text
判定期间改 hidden 仍结算（现状） | {"e":null,"state":1}
判定期间 disabled 仍结算（现状） | {"e":null,"state":1}
判定期间改 electronic 仍结算（现状） | {"e":null,"lock":{"kind":"electronic","locked":false,"keyable":true}}

判定期间删 lock 被拒 | 这扇门已经变了，重开判定
```

门被删/锁被删会拒；hidden/disabled/电子锁不会。P3（主持人在判定挂起期间改门才触发；正常 UI 不会一边挂判定一边改门）。若要求“判定期间任何门改动都拒”，这里要补 `door.hidden`、`objectEnabled`、`lock.kind` 复验。

> 说明：通过 `update` 删除 `opening` 的探针会被 `withVision` 按建筑数据补回，所以“删 opening”在该路径不成立；真正可达的是删门、删锁、改空 `openStates`，这三种上面已分别测过。

### P3-4 单属性 / 坏结算输入：先落地，后被 `publishJudgment` 拒

- `publishJudgment` 要求 `values.length >= 2`（`judgments.ts:24`）；`settlePendingJudgment` 对 `p.check` 只写 `values: input.values ?? [input.value]`（`trial.ts:1114`）。如果 `p.check.attrs` 只有一个属性，会先经 `settleDoorAttempt` 把门/锁改掉，然后 `publishJudgment` 返回“骰子结果无效”，pending 还挂着、judgment 没有。

```text
单属性 onJudgeRoll 接受一颗 | values:[15]
单属性结算返回什么 | "骰子结果无效"
单属性结算后门状态 | 1
单属性结算后 judgment 是否存在 | 不存在
单属性 pending 是否还挂着 | 单属性
```

  当前 `trialPickLock` 永远发两属性，正常 UI 没有单属性门判定；这是未来接口/直调路径的 P3。同类还有：`settlePendingJudgment` 的 `input.value` 不在 `values` 里、`sides` 不合法（如 100）——会先改门，再被 publish 拒，pending 留着；`attrs` 为空时 settle 直接报“骰子数量不对”，门不动（安全）。
- `attrs` 3 颗时 `onJudgeRoll` 接受三颗、settle/publish/schema 都能过；但 `DiceTray` 仍只显示一颗，且 `trialPickLock` 不发三属性。P3 边界。
- `publishJudgment` 的 values 上限是 8（`judgments.ts:24`）；schema 不限制 max；超过 8 的 check 会先落地再拒。P3。

### P3-5 暂停角色仍能操作门（17 号 P3-2 未关）

### P3-6 `publishJudgment` 的校验顺序与 `settleDoorAttempt` 的输入校验

- `publishJudgment` 在 `update` 前校验，没问题；但门状态已经在 `settleDoorAttempt` 里改了，`publishJudgment` 的 `values/attrs` 失败不在同一事务里，导致“门开了、judgment 没有、pending 还在”。
- `settleDoorAttempt` 自己只用 `input.values`/`input.value`，不校验 `input.value ∈ values`、`input.sides`、`values` 长度上限；这些校验在 `onJudgeRoll`/`publishJudgment` 里，隔着一次落地。正常 UI 走 `onJudgeRoll`，所以不触发；直调/旧窗口可触发。P3。

## 8) 推荐结论

- **不修旧数据迁移：需修（P2-4）。** 三条 17 号 P2 已关闭，但旧 `openStates:[]` 的门没有迁移/修复入口，导入和导出/保存会失败；这是唯一 P2。
- **修旧数据迁移后：可推。** P3 不挡本笔：`setObjectStates` 空状态、DiceTray 单颗、结算期 hidden/disabled/电子锁、暂停、单属性/坏输入先落地、`playerWindowFor` 都是边界或已有口径问题；其中 `setObjectStates` 与迁移最好一起清。
- 如果项目明确接受“旧存档里空 openStates 的门必须手工修”，并且确认现有工程没有这种门，那么 P2-4 可降为 P3/产品取舍，本笔可推。
