## 50 P2 复检

### P2.1 skill-decision 分端口：已修，真实链路可用

- `sync.ts:308` 把 `skill-decision` 加进 `judge-roll/say/move/code-submit` 的
  `transport.sendToHost` 分支；`transportLocal.ts:8` 的
  `CROSS_ORIGIN_FROM_PLAYER` 加了 `skill-decision`。
- 实测（host/player 两个 bundle，host 5178、player 5179）：player `send({skill-decision})`
  的目标是 host；把该消息按 `MessageEvent{origin:player, source:playerWindow}` 投给 host
  transport 后，host `listenAsEditor` 的撞车守卫不拦它，独立的

  `confirm`。
- 同 SESSION 场景（模拟同源部署下玩家窗口复制了主持人 sessionStorage）也实测：
  `m.from=hostSession`，`m.inst` 不同；`listenAsEditor` 的
  `m.type !== 'skill-decision'` 例外生效，没触发 `renewSession()`，host SESSION
  保持原值，cast 仍 `confirm`。
- `listenAsEditor` 没有单独的 skill 分支，会落到最后的
  `if (m.type !== 'hello' … ) return;`，但它只是**自己的 handler 返回**；
  `consent.listenPlayerDecisions` 是 transport 的另一个 handler，仍会收到。
  实测已确认不是“被 listenAsEditor 吃掉”。
- 结论：路由和撞车守卫都对；**但测试没有真正测 host 接收**，见 P3-1。

## P3.3 关窗清理 / P3.4 bindPeer closed

### P3.3 关窗清理：方向对，但测试只覆盖一半

- `transport.ts` 新增 `peerClosed(binding)`；`transportLocal.ts:58-61` 只对
  “表里有 window 且 window.closed” 返回 true，saved binding（表里没 window）返回 false。
- `sync.ts:277-280`：`!hasPeer` 时 `peerClosed || context 失效 || pc 不在队伍` 才
  `players.delete + saveBindings + dropPeer`；否则保留 saved binding。
  `:295` invalid 分支在发 clear 后也删 players + dropPeer。
- `deployment.test.mjs:45-47`：host 开窗，把 `opened.closed=true`，发 world 后
  sessionStorage 里的 binding 变成 undefined；实测通过，断言不抖。
- **没有过杀**：saved binding（peers 为空、peerClosed=false）会走 keep；代码上是
  `peerClosed` 与 context/pc 检查的并集，不会把没有 window 的 saved binding 删掉。
  但这条没有行为测试（见 P3-1）。
- `dropPeer` 在 invalid 分支是“删 players 后顺手摘表”，players 已经删掉，
  后续 hello 也过不了 `players.get(binding)`；不会破坏重连。原 50 的 peer 表泄漏
  被收掉，方向正确。

### P3.4 bindPeer closed 替换：可用，但边界扩大，按 P3

- `transportLocal.ts:39-43`：`existing && existing !== source && !existing.closed` 才拒；
  existing 已关时，新的 source 可以接管同一 binding。
  `transport.test.mjs:62-66` 覆盖了 closed 替换。
- **安全风险**：旧窗口已关、新窗口只要知道 binding 且在 player origin，就能在
  `hello` 时接管；`bindPeer` 只做 `'postMessage' in source`，不验证新 source 与旧
  window 的关系。binding 是 URL 里的 bearer capability，所以这更像“同一凭据可换窗口”，
  不是新增身份绕过；但如果产品把“关闭窗口”当成撤销，这会让撤销窗口变短。
- **刷新不需要这条**：浏览器刷新保留同一个 WindowProxy，`existing === source` 本来
  就会通过；closed 替换实际只服务“重新打开一个已关窗口”。建议要么只允许
  `existing.closed` 且由主持端显式重连/换 binding，要么在 docs 里明确这是
  “凭据仍有效”的重连路径。当前按 P3，不阻塞。

  `players.get(binding)`，要求 `entry.pcId === c.actorPcId`；`listenPlayerDecisions`

  WsTransport 用 `meta.from` 的 binding。加三条测试：caster 可过、别的绑定玩家拒、
  未绑定 source 拒。
