6. **`mh` 的 32 位边界**：FNV-1a 32 位对同一 `sourceId + textureKey` 稳定，探针验证了 hash 稳定、与 live id 冲突时 `mh…x1`、同源同版本多份记忆 cells 合并均正确；它**不能直接反推出原文**，但不是密码学 hash，碰撞空间只有 32 位。碰撞后缀判断只看 `key`，若两个不同 `sourceId` 恰好同 hash 且 `textureKey` 相同，会被并进同一个 bucket；另外 `usedIds` 把不可见的 live 组和物件组 id 也算进去，会给记忆组加不必要的 `x1`，这类 id 在增删中会漂移。都是 P3 级边角。

### 对六个问题的简短回答

1. **schema 会误拒吗**：不会。正常工程、旧记忆（无 `sourceId` / 无 bounds）、旧 `views`、`playerWorld`、删媒体后、缩图后都通过；live 组带 `sourceId/textureKey` 是唯一预期拒绝。
2. **deleteMedia 漏了吗**：物件附件、实时组、共享记忆、`views` 记忆都清了；漏的是 `textureKey/sourceId/groupRevs`、`materials`、`nowPlaying`，且测试没覆盖 `views`/物件附件。文件保留给撤销一致；只调用一次 `update`，没有双重同步。
3. **reshape bounds**：按剩余格子重算正确；空组/`groupBounds` 为 null 时旧 bounds 会被删；空组本身不删。对象组引用会 prune；views/memory bounds 没有测试。
4. **seen 清理会不会和 syncLayer 打架**：顺序是先清、再由 `update` 的 `syncMemory` 重算，没有重复/反序；`m.views` undefined 在 `withVision` 更早处就会崩，正常不可达。
5. **mh hash**：同一「原组 + 贴图版本」稳定；与 live id 冲突时加 `x1`；同版本多份记忆按 cells 合并；不能直接反推原文，但 32 位 FNV 不是密码学保证，同 key 不同源的碰撞会合桶（P3）。
6. **测试咬合**：bounds 重算、删共享记忆、live 组显式挑字段、schema live 内部字段/bounds、随机 hash 这些变异都会红；删 `views` 清理、删物件附件、去碰撞后缀、去同版本合并、纯序号 id 这些变异全绿，属于 P3 测试缺口。
