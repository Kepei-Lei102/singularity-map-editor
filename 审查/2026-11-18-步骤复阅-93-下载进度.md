## 协议兼容

- `asset-start` 加 `bytes?: number` 是**向后兼容**的增量字段：旧玩家 receiver 的 `handle` 不认识这个字段会直接忽略；旧主持端不发，新 receiver 的 `totalBytes` 就是 undefined，只是不显示百分比。合成消息不带 `bytes` 仍满足 `AssetBody` 和 `isAssetMessage`。
- 服务器仍不解析 payload，只在 relay 里搬运；`bytes` 只是一次 JSON 数字，不改 8 MB `maxPayload` 或每连接 60 条/s 预算。
- **没有 P2 兼容问题。**

## 进度语义

- `totalBytes` 只在 `asset-start.bytes` 是有限非负数时记；`start` 回调 `0,total`，每块累加后 `received,total`，`finish` 落盘成功后 `received,total ?? bytes`，再 `onReady`。
- 重复 `start` 被 `p.started` 挡住，不会重复报进度；重复 `chunk`（同 index）直接 return，不重复累加；`reset` 用 generation 让旧 finish 的 onProgress/onReady 失效。
- **P3 语义**：
  - 未知 total 时，`finish` 用 `p.totalBytes ?? p.bytes`，最后一次进度会变成 `received=total`，UI 上会短暂显示 100%。传输确实完成了，但“未知总大小时突然 100%”不严谨；测试只覆盖 start/chunk 的 undefined，没覆盖 finish。
  - `totalBytes=0` 的空文件：`mediaProgressText` 把 `!total` 当未知，显示「载入中…」而不是 100%；空文件没有百分比，可接受。
  - `received > total` 只在 UI 里 clamp 到 100%，receiver 不校验 `p.bytes` 与 `totalBytes` 的一致性；可信主持端发 `blob.size` 时不会发生，恶意/旧端才会。
  - 22 块/s 一个文件时 PlayerView 每秒约 22 次 `setMedia`，可接受；但 32 个 key 并发时 `onProgress` 对每个 key 的每块都调用 `setMedia`，非当前 key 也进回调，总量可达约 700 次/s，建议按当前 mediaId 先过滤或 100ms 节流。

## cancel(keys)

- `cancel` 只删 pending、清 timer、`forget`、发带 key 的 `asset-cancel`；不动 `failed/known/retried`，也不标失败。host 侧 `AssetSession.cancel` 只认 active 的 requestId，key 优先；同批其他 key 不受影响。
- 正常路径：Play/Stop 时 key 有 pending，cancel 后晚到的 chunk/end/fail 都因 pending 缺失被忽略，测试覆盖。
- **P3 边界**：
  - **load 途中**：`request()` 先 `requesting.add(key)`，再 `await load`，此时还没有 pending；`cancel(keys)` 找不到 pending，直接 no-op。load 结束后仍会建 pending 并发 `asset-request`。实测：`request(['k'])` 在 load 未完成时 `cancel(['k'])`，之后仍然发出 `asset-request`，没有 `asset-cancel`。Stop 后主持端还会开始传这个文件，直到传完/超时；不显示，但浪费带宽和 active 名额。
  - **finish/save 途中**：`asset-end` 已收、`finish` 已开始 `save` 时，pending 还在；`cancel` 会删 pending，但 `finish` 不会停。save 完成后仍 `known.add`、`pending.delete(key)`、`onProgress`、`onReady`。如果这时已经有**同一 key 的新一次 play 请求**，旧 `finish` 的 `pending.delete(key)` 会删掉**新请求的 pending**，新串的 start/chunk 会被忽略；旧 `onProgress/onReady` 会落到新 media 上。实测新请求的 `asset-request` 照发，但旧 save 完成后新串无法完成；save 成功时 `useBlobUrl` 还能从旧落盘文件自愈，save 失败时会把新 play 标成失败。
  - 这两个都不是数据损坏，且窗口小（load 很快、save 通常很快），归 P3；但“cancel 了还继续”与“晚到进度落到新播放”确实存在。

## PlayerView mediaRef

- `mediaRef` 用 `useEffect([media])` 同步，效果是**渲染提交后**才更新；不是 `setMedia` 当时更新。
- 正常消息是分开的 task，effect 会在下一条消息前跑，所以普通 play→stop 能 cancel 当前 media。**P3**：同一 tick 连续 `play`、或 `play` 后立刻 `stop`，`mediaRef.current` 可能还是上一条 media；第二条消息 cancel 的是旧 mediaId，刚到的当前请求没被 cancel。用户看不到错，但下载会继续。
- `play` 里先 cancel 再 `setMedia` 不会把同一 key 的新请求提前取消，因为新请求在 `requestPlayMedia` 之后才创建；但若旧 media 正在 `finish/save`，就是上面的 P3 竞态。
- `onRetry` 清 progress 后 `retry`：若还有 pending，`retry` 被 pending dedupe，不会重复发；failed 状态来自 onFail 时 pending 已删，所以正常 retry 能发。`retried` 仍不重置，哈希失败后重试仍可能直接失败（旧 P3）。

## UI

- `MediaView` 只在没有 URL 时用 `mediaProgressText`；成功拿到 URL 后不显示进度，行为不变。`MediaDock` 不传 progress，仍是「载入中…」。
- `mediaProgressText`：total 未知/0/负数返回「载入中…」；received/total clamp 0–100%；`PlayerMediaOverlay` 的 failed 分支优先于进度，失败时只显示错误+重试。
- **P3**：没有总字节数格式化（只显示百分比），没有“已收/总共 MB”；这轮只有玩家自己的进度，没有主持人侧聚合。

## 多玩家诊断/背压

- 这轮**不满足**主持人侧「几个人在传/总吞吐」：现在只有每个玩家窗口自己的 `onProgress`，host 没有 per-binding 的已发字节、队列深度、速率视图。
- 12 人 64 MB、全局 `nextAssetAt` 45 ms/块仍是约 138 s，超过 receiver 120 s queue timeout；最后几个玩家会排队超时失败。这不是这轮引入的，但**未解决**。
- 下一包建议：
  1. host 侧 per-binding 账本加 `sentBytes/totalBytes/queued/rate`，主持人 UI 显示总吞吐和每个玩家进度。
  2. `paced` 从全局一把钟改成**每 binding 一条钟 + 全局 CPU/连接预算**，round-robin 公平出块；同一玩家的 64 MB 不应阻塞另一个玩家。
  3. 每 binding 设队列上限/在途上限，超过就回 forbidden 或让玩家显示“排队中”，不要静默等 120 s。
  4. 大文件降低 queue timeout 风险：按文件大小给 queue timeout，或先发 start 再让 queue watchdog 停止。

## P3

1. **cancel during finish/save**：旧 finish 不认 cancel，仍会落盘并删掉同 key 新请求的 pending，晚到 onProgress/onReady 落到新一次 play；save 成功时通常靠本地文件自愈，save 失败时新播放会被标失败。
2. **cancel during load**：requesting 阶段没有 pending，cancel no-op；stop 后 load 结束仍会发 asset-request，主持端继续传。
3. **mediaRef 同一 tick 滞后**：连续 play/play、play/stop 可能 cancel 到上一 mediaId，当前请求漏取消；无 UI 错误，但继续下载。
4. **未知 total 的 finish 报 100%**：`totalBytes ?? p.bytes` 让 final progress 变成 100%；空文件 total=0 不显示百分比；received>total 只靠 UI clamp。
5. **进度 UI/性能**：只有百分比，没有总大小；PlayerView 对每个 key 的每块都 setMedia，22/s 单文件可以，32 key 并发偏多，建议过滤/节流。
6. **测试缺口**：没有 cancel 在 load/ finish、同 tick mediaRef、未知 total final、PlayerView onProgress 接线的测试；`cancel_skips_finishing`、`finish_total_fallback`、`pv_progress_callback`、`media_ref_effect` 均 0 红。
7. **多玩家诊断/背压**：host 无聚合进度；全局 45ms 节流 12×64MB≈138s 超 120s queue；公平/按 binding 分速未做。
