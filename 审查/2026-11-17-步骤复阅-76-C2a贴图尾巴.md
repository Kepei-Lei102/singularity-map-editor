## P2：ghost 物件的实时组还在玩家载荷里，但媒体已经被滤掉，`playerWorld` 过不了 `checkWorld`

`playerMap` 仍把 ghost 物件的物件组放进 `groups`（`sync.ts:313-324`）：可见物件只要有任何一格 fog1，就带这一组，`objectId` 和 `texture`（例如 texA）都在。`usedTextures` 又把这一组的媒体按 `liveGhost` 滤掉（`sync.ts:217-221`），所以 `playerWorld(w, mapId, pcId)` 的结果同时有：

- `map.groups` 里一个 `objectId:'o1'`、`texture.mediaId:'texA'` 的组；
- `world.media` 里没有 `texA`。

`checkWorld` 对实时组的媒体存在性仍是硬的（`schema.js:830-833`），探针直接报：

```
工程文件有问题：地图「一楼」的贴图组「贴图」 找不到媒体 texA
```

新加的 ghost 媒体测试（`objectappearance.test.mjs:161-177`）只断言 `live.media` 不含 texA，没有断言 `pm.groups` 是否还带这个组，也没有 `checkWorld(pw)`；所以 716 全绿。

实际影响：

- `PlayerView` 收到 world 后直接 `setWorld(m.world)`，不跑 schema；ghost 渲染分支不画图，所以眼下不会崩。
- 但玩家载荷已经违反“每个组贴图都能在 media 里找到”的既有契约；任何以后在接收端做校验/转存的路径都会拒绝这份 world。
- 修法要么在 `playerMap` 里把 ghost 物件的实时组一并去掉（对应 `visibleObjects`/`liveGhost` 过滤），要么保留组就不要滤它的媒体。当前“只滤媒体、留着组”是半套。

**这是 P2，不是 P3：它是实际存在的载荷结构矛盾，不是测试缺口。**

## 焦点 1：上传守卫

顺序是对的：工程 context → 编辑模式/试玩 → 物件存在 → 选中仍是这个物件（`Inspector.tsx:26-32`）。

- `ctxBefore !== ctxNow` 用 `worldContext()`，`replaceWorld`、试玩 begin/end 都会改 epoch，能拦住换工程和进出试玩。
- `exists` 用 `findObj(getWorld(), mapId, o.id)`；`mapId` 和 selection 的 `mapId/id` 都单独比，所以“同 id 但换了图”被选中检查拦住，不是只靠 id。
- 试玩结束：如果上传是在编辑里发起、途中进出试玩，epoch 变了会拒绝；如果是在试玩中发起，按钮本身不可用。
- `unlock`：`canEditMap` 是 `mode==='edit' || unlock`，所以在 play/prep/run 里开解锁时守卫会放行。这和“解锁就能编辑”的既有口径一致；如果产品定义是“只 edit”，这里需要收紧。
- `getUI()` 即使还指着旧 selection，也还要过 `mapId/id/exists` 和 context，没看到“旧 UI 对象直接硬挂”的漏。
- 实际异步上传（`storeBlobStatus` → guard → `setObjectTexture`/`offerDeleteOrphanBlob`）没有自动化测试，只有纯守卫；已知无 bug，算 P3。
- 一个消息精度问题：试玩开始/结束也会让 `ctxBefore !== ctxNow`，于是返回“工程已经换了”，而不是“离开编辑模式”。拒绝结果对，文案不准；P3。
- `undo/redo` 不改 epoch；上传途中撤销、或同 id 物件被重建，可能仍挂到当前物件。P3。

## 焦点 2：空物件组 UI

- 外观区仍是 `canTexture = edit && !ui.trial && !architecture && o.kind === 'object'` 才显示；非编辑/试玩/建筑/触发区都没有这个入口。
- `textureGroup` 存在就显示「清除贴图」；`objectTexture` 为空时只是不显示预览/fit/opacity，不隐藏清除按钮（`Inspector.tsx:530-542`）。测试 `objectappearance-ui.test.mjs:82-101` 用 `{id:'g-empty', cells:[0], objectId:'o1'}` 验证按钮存在、点击后组消失。
- 不会误删正常组：`clearObjectTexture` 只找 `groups.find(g => g.objectId === objectId)`，普通组没有 `objectId`。删的是这个物件组本身，符合“回退彩色方块”。
- 还有两条到不了的路径：物件已被删、只剩 `objectId` 指向空对象的孤儿组时，检查器没有入口；同一物件若被手改成两个物件组，`clearObjectTexture` 一次只清第一个。P3。

## 焦点 3：host ghost

- `drawObject` 只有玩家分支读 `o.ghost`，host 分支每次都从 `blocksWhen/state` 推（`render.ts:231`）。
- 所有 `drawObject` 调用都带 `player`：`drawObjects`（`render.ts:674`）和标签重画（`:743`）；host 的 `labelOnly` 也走同一分支。灰区记忆层只会在 `mode==='player'` 时构建（`:683-691`），不会进 host。
- 持久化 `MapObject.ghost` 现在 host 不信；测试 `objectappearance.test.mjs:179-191` 用 `ghost:true`、当前 `state:0` 验证 host 仍画实心图。
- 别处也没有 host 信任：`sync.ts:369` 的 `ghost` 是玩家实时载荷派生；`memory.ts:45` 的 snapshot 从 `blocksWhen` 推；`fromMemory` 用的是 SeenObject 的 ghost。`schema.js` 仍接受 `MapObject.ghost`、不剥离，导出/备份里仍能带，但 host 渲染桥已经不看它；P3 残留（原 P3-8）。

## 焦点 4：玩家媒体过滤

- `liveGhost` 只看 `pm.objects`（当前可见物件），`memoryGhost` 看 `pm.seen.objects` 和 `pm.views[*].seen.objects`（`sync.ts:212-216`）。
- 探针“旧记忆 ghost、当前已开但不在这张图”：灰区 `seen.objects` 仍是 ghost true，`liveGhost` 空；媒体跳过 texA，渲染灰区虚线无图，正确——旧记忆就是当时的开态，当前已开不该改变灰区记忆。
- 探针“旧记忆开着、当前 ghost 但不在图里”：`memoryGhost` 空，记忆贴图照发，灰区画旧图，正确。
- `seen.objects` 用 `!memoryGhost.has(r.id)` 在 id 唯一时等价于 `!r.ghost`；重复 id 会一起滤掉，但 schema 是唯一 id，P3。
- `views` 两行是死代码：`playerMap` 固定返回 `views: {}`（`sync.ts:358`），所以 `memoryGhost` 的 views 分支和 `usedTextures` 的 views 分支都不会命中。删掉 views 那行 716 仍全绿；P3。
- 真正的 P2 是：live 组只滤媒体、不滤组，见上。

## 焦点 5：`objectTexturesOf`

正常数据下等价：

- 一个 objectId 一个 texture → 同。
- 组有 objectId 无 texture → 旧 `find` 返回 undefined，新表没有这个 key，同。
- objectId 没有对应 object → 旧函数只会被已知 object 调用；新表多一个无用 key，行为无差。
- 无 `groups` → 空表，同。

不等价的情况：

- 同一 objectId 两个组：旧 `find` 取第一个，新 `Map.set` 取最后一个；如果第一组有 texture A、第二组 B，新表返回 B。schema 明确禁止一个物件多个组，正常数据不存在；但这是一条真实的行为差异，且没有测试。P3。
- `objectTextureOf` 原来导出，现在被收成私有；仓库内已无引用，`tsc` 通过；外部脚本若 import 会坏。P3。

“纯性能改动”这个说法要修正：空了表之后 8 个 `objectmemory` 用例会红，所以正常查询行为是被间接覆盖的；缺的是重复组/无 texture 组的直接等价测试。
