## 3) 没有全局 memo；原地改 subCells 立刻生效

- 读码：`sightCacheFor`（`sight.ts:322`）每次调用都新建 `{cost, block}`，`sight.ts` 里没有模块级缓存；`visiblePoint` 的 cache 只是调用方传入的快照。
- 实测（6×6，主格 (1,1) 细分，中心子格）：
  - 初始 = **true**
  - `map.subCells[k] = 'wall'`（**原地改，不换 map 引用、不换 subdivisions 数组**）→ 下一次 `visiblePoint` = **false**；用新 `sightCacheFor` 也是 **false**
  - 改回 `'floor'` → 下一次 = **true**
  - 旧 cache（改之前建的）仍按旧表判 —— 快照语义，符合设计；`autoReveal` 每次调用都重建，所以不受影响。
- 测试里确实有原地改的路径：`scripts/sight.test.mjs:116` `delete map.subCells[...]` 后立刻 `visiblePoint`，全量测试通过。
- 「nearestPc 每次重绘、每 token 一次建表」的绝对耗时：100×100 **全细分**、4 token = **5.25ms/次重绘**（4 × 1.33ms 建表）；原版 5.6ms，`e025e95` 389ms。另有优化余地：cost 表只依赖 `eyeHeight`，按眼高去重 + 共享 block 后可降到 **2.12ms**（实测），但这不是阻塞项。

## 4) 边界收紧到 `>=` 之后：7 个调用点复核

随机差分：250 张随机地图 × 3 眼 × 全图目标（格中心 + 格内随机点 + 子格中心，全部落在 `[0,W)×[0,H)` 内）共 **172,059 次**：`e025e95^` vs `e9bf367` **0 差异**，带 cache vs 不带 cache **0 差异**。

越界点专项（6×6，eye=(2,2)，15 个边界/越界点）：base true=4、new true=3，唯一不同是 **`target=(6,2)`** 这类「`x==width` 且 `y1<height-1`」的别名读点：base 读到下一行首格（此处 floor）→ true，new → false。`target.y==height` 的 NaN 类点两边都是 false。属有意收紧（correct fix），不是回归。

7 个调用点逐个看参数来源：
1. `actions.ts:1365` 门中点 `mid = rect.x + rect.w/2`：墙端点校验到 `width*3` 且矩形宽度 >0，中点 < width，安全。
2. `trial.ts:731` `tokenPosition(target)` = `x+0.5`，正常棋子 `x ≤ width-1`，安全。
3. `trial.ts:939` `attackTargets` 同上，安全。
4. `scene/perception.ts:50/59`、`scene/sliding.ts:15`：格中心/子格中心，`≤ width-1/6`，安全。
5. `sync.ts:205` `{x: j.place.x, y: j.place.y}`：**有风险**——`rules/judgments.ts:14` 的校验是 `input.place.x > m.width`（允许 `==`），所以一条手填/导入的判定可以锚在 `x==width`（或 `y==height`）；现在 `visiblePoint` 判它不可见，队友就看不到这条判定。建议把校验收成 `>=`（或夹取），与 `visiblePoint` 一致。正常路径（`trial.ts:422/456/501` 生成 place 都是 `+0.5`）不会踩。
6. 另：`core/schema.js:501` 对 token 的 `x/y` 只校验整数、没校验范围；编辑器路径不会产生 `x==width`，但坏存档会出现——现在这种棋子视野全 false（比以前读到别处更安全），可不必处理。

## 新问题（都 P3，不影响常规单人单棋子的路径）

### 新-1（P3）`autoReveal` 的 cache 以 `pcId` 为键、取自「第一个棋子」：同一 PC 绑多个棋子且姿态不同时会错判
位置：`src/runtime/actions.ts:387-399`（`eyes`/`caches` 都按 `p.id` 存一次；`pcWithin` 里会对该 pc 的**所有** token 复用这一份 cache）。
触发：同一 `pcId` 绑 ≥2 个棋子、且第一个棋子的 `stance` 与后面某个棋子不同（`eyeHeight` 不同 → cost 表不同）。
实测（10×6，中间放 height 1.0 的矮墙，眼在 (2,2)，目标 (6.5,2.5)；第一个 token 趴、第二个 token 站）：**无 cache = true（站姿看得见），共享趴姿 cache = false**；单独判站姿 token = true。即同一 pc 的第二个棋子会按第一个棋子的眼高判。若第一个是站姿、第二个是趴姿，就会反向「看得见本来看不见的」，并可能把隐藏线索 reveal 给该玩家。
建议：`caches` 按 **tokenId** 建（`eyes` 也按 tokenId），`pcWithin` 传 `{...m, tokens:[t]}` 与对应 token 的 cache；或把 cache 键改成 `${pcId}:${stance}:${heightCm}`。改动 2–4 行。
（原版 `e025e95^` 每个 token 各自建表所以没这个问题；这是本轮「提 cache」顺手带来的边角。）

### 新-2（P3）`autoReveal` 现在无论有没有 auto 秘密都先给每个队员建表
位置：`actions.ts:392-393` 在物件循环之前就建。实测 100×100 **全细分**、无 auto 秘密的地图：**7.0ms/步** 的固定开销（40×40 全细分 0.97ms；100×100 细分 1 格 ~0.8ms）。原版为 0。绝对量可接受，但可以把建表挪到「遇到第一条待判定的 auto 秘密」时惰性建（或先扫一眼 objects 有没有 auto 秘密）。

### 新-3（P3）判定位置校验与 `visiblePoint` 的边界口径不一致
`src/rules/judgments.ts:14` 用 `> m.width`，允许 `x==width`；`visiblePoint` 现在是 `>=` → 这种判定锚点对别人永远不可见（`sync.ts:205`）。建议改 `>=` 或夹到 `width-1e-9`。正常流程不会产生这种 place（都是 `+0.5`），只在手填/导入/以后接别的 UI 时出现。

### 新-4（P3）`declareText` 对可选 `dc` 没有兜底
`src/rules/events.ts:47`：`attrs` 非空时无条件拼 `，DC ${c.dc}`；`dc` 现在是可选的，若以后有事件是 `kind:'check'` 但忘了填 `dc`，会渲染出 **「要过 敏捷，DC undefined」**（实测确认）。建议 `c.dc != null ? \`，DC ${c.dc}\` : ''`。攻击事件因为 `attrs: []` 走「掷 D100」分支，现状不触发。

### 新-5（P3）文档例句没跟上「命中」
`docs/物理互动-范式-v0.1.md:250` 还写着 `… → 【攻击（钝器）】成功：…`；`e9bf367` 用 `outcome = ATTACK_BAND_LABEL[band]` 后，命中档渲染是 **「命中」**（实测四个档位：落空/命中/大成功/特大成功）。建议例句改「命中」；否则文档和日志又不一致了。`docs:242` 的 check 字段说明已更新（kind/band、无 DC），这一条没问题。
