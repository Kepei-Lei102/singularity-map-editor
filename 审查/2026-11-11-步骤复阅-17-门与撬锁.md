### P2-1 已卡死的锁，暴力大失败仍写假 delta

- 代码：`src/runtime/trial.ts:939-942`

```ts
} else if (fumble) {
  o.lock = { ...o.lock!, keyable: false };
  deltas.push({ kind: 'object', id: o.id, name: o.name, path: '锁具', from: '锁着', to: '卡死' });
  msg = `${o.name} 的锁芯卡死了，只能强行打开`;
}
```

  这里没有先看 `o.lock.keyable` 原本是否已经是 `false`。卡死后 UI 只给「强行打开」；强行打开再掷出大失败（例如 1/8）时，`keyable` 从 `false` 改为 `false`，实际没变化，但事件仍多出一条 delta。

- 复现（探针，卡死锁 + `force` + `values [1,8]`）：

```text
【疑点】已卡死再加卡死仍写假 delta | [{"kind":"object","id":"door1","name":"门","path":"锁具","from":"锁着","to":"卡死"}]
```

  事件 `check.tier='fumble'`、门仍 `locked:true,keyable:false`、门仍关着；`deltas` 却有一条。`eventText` 会因这个假 delta 渲染出「锁具从锁着改为卡死」，与“只记真变化”冲突。
- 文档原文：`docs/物理互动-范式-v0.1.md:253`「撬锁/暴力开锁（锁具＋门状态、失败不写假 delta）」；`:257`「只记真变了的状态……真没变化时用 note 说明原因」。
- 修法：`if (o.lock!.keyable) { o.lock = {...}; deltas.push(...) }`，否则只写 `note`（例如「锁芯已经卡死了」）。

### P2-2 `openStates` 为空时，撬锁成功解锁，但门仍关着且事件报成功

- 代码：`src/runtime/trial.ts:928-938`

```ts
if (success) {
  if (o.lock!.locked) { ...锁具 delta... }
  const openIdx = o.states.findIndex((_, i) => o.opening!.openStates.includes(i));
  if (openIdx >= 0 && o.state !== openIdx) { ...状态 delta...; o.state = openIdx; }
  msg = `${pc.name} ... 撬开了 ${o.name}`;
}
```

  `openIdx < 0` 时只解了锁，没有开门，但 `success` 仍为真，`msg` 仍说「撬开了」。`trialOpenDoor` 对同一扇门有明确的 `if (openIdx < 0) return '门缺少打开状态'`（`trial.ts:850-851`），`trialPickLock`/`settleDoorAttempt` 没有这条守卫。
- schema 也接受空数组：`src/core/schema.js:391-395` 只校验 `openStates` 是数组、每个索引在 `states` 范围内，不校验非空。
- 复现：

```text
门没有打开状态时撬锁仍成功？ | null
没有打开状态：锁解了但门还关着（现状） | {"lock":{"kind":"physical","locked":false,"keyable":true},"state":0}
没有打开状态：事件仍报 success | true
schema 接受 openStates 为空的门（现状） | OK
```

  Inspector 的门状态编辑允许把“打开状态”取消勾选（`openStates` 变空），所以不是只能靠手改存档构造的状态。
- 修法：在 `trialPickLock` 开判定前或 `settleDoorAttempt` 成功分支里要求 `openStates.length > 0`；否则拒绝开判定/把成功改判为失败并只写 `note`，不要先解锁再报“撬开了”。

### 3-8 非 opening 物件带 lock：pending 能开，settle 会崩


  `openJudgment` 接受这种 door，schema 也允许 `lock` 在非门物件上；正常 UI 的 `trialPickLock` 只找带 `opening` 的门，所以不是正常路径。但主持人在判定挂起时改门/删 opening，或以后别的入口直接开判定，就会炸；建议 `settleDoorAttempt` 在更新前确认 `door.opening`，没有就返回错误。

### 3-9 成功但两个状态都没变：空 deltas 且无 note

- 如果判定挂起期间锁已经被解开、门也已经开着，`settleDoorAttempt` 的 success 分支既不写锁 delta、也不写状态 delta，`note` 仍可能是 `undefined`（`trial.ts:928-938` 与 `:920-922`），事件就是一条 `success` + 空 `deltas` 的假事件。
- 这是很窄的并发窗口；按文档 `:257`，没变化至少要用 `note` 说明。修 P2-1/P2-2 时可以顺手把 success 的空 delta 分支补 `note`。

### 3-10 `playerWindowFor` 仍不按上下文过滤（上一笔 P3，本笔门路径也会碰到）

- `sync.ts:322-325` 只看 `pcId + win open`。如果同 pc 的真实窗口还开着、试玩窗口关了，`trialPickLock` 会以为玩家在，开 pending 但不推请求（`pushJudgmentRequest` 的 `sameContextWindow` 挡住真实窗口），主持人只能代掷。

## 8) 剩余风险 / 建议

1. **P2-1/P2-2 先修**；P2-3 若验收只要求事件账本，可改为 P3 并在文档里写清楚“正式判定只显示采信值”。
2. `settleDoorAttempt` 手写 `every + crit`，没有走 `resolveChecks`；当前 `merge:'all'` 行为对，但以后多属性/优劣势/`any` 会漂移。建议把“大成功顶整条”做成公共函数，别两处各写一份。
3. `onJudgeRoll` 的 `values.length > 2` 是两属性门的硬上限；三属性检定要同步改协议。
4. `playerWindowFor` 不按 trialContext 过滤（上一笔 P3），本笔门路径也会“以为玩家在”；正常 UI 有试玩窗口时不触发。
5. 同上下文 `publishJudgment` 失败不是原子的（事件/状态已落地、pending 还在），这是上一笔遗留 P3；门结算复用了同一条发布路径，失败重试会重复写 delta/事件。
6. `events` 200 / 日志不截断是设计中的已知行为（P3 记录向）；被挤掉的事件只剩日志文本，`eventId` 指向已不在 `events` 里的 id。
7. 没有 UI 自动化测试：`JudgmentPanel` 代掷逐颗累加、`PlayerView` FIFO/两颗显示都只做了源码审查和烟测；`TrialHud` 电子锁/暂停也没有测试。
8. 提交本身还带了 `docs/物理互动-范式-v0.1.md` 的改动和 15 条测试；如果仓库要求“只改代码+测试”，文档改动要按项目惯例处理，行为上没有影响。

## 结论

**核心功能能跑，但不是“完全无阻断”：P2-1（假 delta）和 P2-2（空 openStates 仍解锁/报撬开了）直接违反本笔文档原话，P2-3（正式判定只记第一颗）按“落账”的原文也不完整。因此建议先修 P2-1/P2-2，按口径决定 P2-3，再推。** P3 里隐藏/暂停守卫、电子锁 HUD、`onJudgeRoll` 缺颗、`forPlayer.door`、schema per-attr total、非 opening 崩溃都建议随后清掉；这些不影响主路径，但都已有独立复现。
