## §1 判定口径：公式只剩一套，但"判定"没有只剩一套

### 1.0 现在是 5 条路径，不是 1 条

| 路径 | 位置 | 谁在用 | 口径 |
| --- | --- | --- | --- |
| `resolveCheck()` / `resolveChecks()` | `interaction.ts:124` / `:196` | `jump.judgeValue`、`sense.rollSense`、`trial.settleJump` | 骰点＋属性 ≥ DC；极值覆盖；优势取高 |
| `resolve()` | `interaction.ts:298` | **只有** `skillCast.ts:104`（试点 stub） | 多模式 or/and/sum/contest/gm、次数劣势、对抗 DC、幸运特例、000 补投链 |
| `attackBand()` + `rollAttack()` | `combat.ts:38` / `:62` | `trial.ts:700`、`:856`（攻击、借机攻击） | 000 特大、1–5 落空、95–99 大成功 |
| `rollRescue()` | `combat.ts:286` | `trial.ts:910`（救治） | 只有 1 失败，00 特大 |
| `resolveLuck()` | `interaction.ts:85` | **无人调用**（只有测试） | 纯骰 11+/51+ 成功 |

属性检定的**公式**确实只剩 `resolveCheck` 一处（`zoneOf` 也只是它的薄包装，见 §2）。但"判定"整体仍是 5 条路，其中第 3、4 条是生产在用的独立口径，第 5 条是写了没接。下面是不重复耦合报告的具体分叉。

### 1.1 P1 — D100 掷 00 的补投链只活在测试里

`interaction.ts:313`：`const critRoll = input.d20s?.[0]?.[1];`

- **问题**：`resolve()` 的 000 补投 D20 不是"补投"，而是偷用**第一项属性的第二颗骰**。只有调用方恰好传了两颗（优势/劣势）才有补投；传一颗就没有补投。
- **后果**：全项目唯一的 `resolve()` 生产调用方 `skillCast.ts:107` 传的是 `d20s: [[d20]]`（一颗）→ 00 在真实技能判定里既不特大成功也不大失败，纯按总数算。测试 `interaction.test.mjs:55` 传 `[[100,20]]` 才让它跑起来，所以这条规则**只被测试覆盖**。实测：`resolve()` 传 `[[100,5]]` → `pass:false`（补投 5 判大失败），传 `[[100]]` → `pass:true`（当普通点数）。
- **建议**：补投 D20 由 `resolve()` 自己掷（内部 `rollDie(20)`），不要复用优势骰；或者干脆删掉 `resolve()` 的这条链，统一交给 `resolveCheck`（见 1.2 要先补 critRoll）。

### 1.2 P1 — 统一引擎的 D100 极值整个失效，与自己的注释矛盾

`interaction.ts:145`：`tierOfRoll(scale, used, undefined, ...)`，而 `tierOfRoll` 的 000 分支要求 `critRoll !== undefined`（`:245-252`）。

- **问题**：注释 `:100`、`:224` 都写着"D100 区走 000 补投链"，但 `resolveCheck` 永远传 `undefined`。实测 `resolveCheck({scale:'d100', rolls:[100]})` → `{tier:null, level:null, success:true}`。
- **后果**：`jump.ts:47-49` 已经写明"物理这条线走 D20 区，等做恐怖／心理那条线再切 D100 区"。一旦切过去，00 既不会特大成功也不会大失败——切尺那天会静默丢规则。
- **建议**：`resolveCheck` 加 `critRoll?: number`，并在 `used === 100 && scale === 'd100'` 时内部补投；`resolveChecks` 透传。补一条测试："D100 区 resolveCheck 掷 100 → tier 不是 null"。

### 1.3 P1 — 空骰数组会被悄悄变成"必定大失败"

`interaction.ts:138`：`const rolls = opts.rolls.length ? opts.rolls.map(clamp) : [1];`

- **问题**：调用方漏传骰（或 UI 没拿到结果）时，不报错，而是把点数当成 1。实测 `resolveCheck({attributes:{敏捷:100}, attr:'敏捷', rolls:[]})` → `used:1, tier:'fumble', success:false`。
- **后果**：一个属性 100 的角色在"漏传一个参数"时会必定失败；这种 bug 在日志里看起来像正常的运气差，评审和测试都抓不到。
- **建议**：`rolls` 为空时抛错/返回 error（`success:false` + `error:'没有骰点'`），由调用方决定怎么显示；`Math.max(1, Math.min(sides, …))` 的夹取也建议只夹类型，别把 0/越界静默改成合法骰面。

### 1.4 P1 — 攻击命中不归引擎管，两处阈值逐字重复

`combat.ts:38-43` `attackBand` 与 `interaction.ts:234-238` `tierOfRoll(…, {attack:true})`：

- **问题**：两边都是"100→特大、≤5→落空、≥95→大成功、其余命中"，一份返回 `'miss'|'hit'|'great'|'super'`，一份返回 `{tier, level}`。生产走 `combat` 那份（`trial.ts:700`、`:856`）；引擎那份只有死掉的 `resolve()` 会用（且 `resolve()` 从没被传过 `attack:true`）。
- **后果**：改一处漏一处；将来攻击要接属性对抗（作者口径里"命中要过属性"）时，两条路必然分叉。
- **建议**：`attackBand(roll)` 改成 `tierOfRoll('d100', roll, undefined, {attack:true})` 的薄包装（band 由 tier/level 映射），只留一份阈值。

### 1.5 P1 — 借机攻击的注释和代码是两条规则

`trial.ts:854-856`：注释「没有技能就是纯幸运骰 D100」，代码 `const r = rollAttack(roll, 8)`。

- **问题**：`rollAttack` 是攻击口径（只有 1–5 落空 → 95% 命中）；规则书/战斗模式文档的"纯幸运骰"是 51+ 成功（`resolveLuck`，`interaction.ts:85-87`）。注释写的是后者，代码做的是前者。
- **后果**：借机攻击的实际命中率是 95%，不是 50%；文档、注释、代码三方不一致，而 `resolveLuck` 这条正确实现只有测试在用。
- **建议**：二选一写死。若按文档走纯幸运骰 → `trial.ts:856` 改 `resolveLuck(roll)` 并按结果施加伤害；若按攻击走 → 改注释并删掉"纯幸运骰"这句。

### 1.6 P1 — 技能发动判定完全不读角色卡（六维已在编辑器里）

`skillCast.ts:101-109`：

```ts
// 试点：角色卡上的六维还没进编辑器，先按 0 走，判定只反映骰面
const attrs = Object.fromEntries(ATTRS.map((a) => [a, 0])) …;
const result = resolve({ check: skill.check ?? {attributes:['智慧'], mode:'single'}, actor: attrs, d20s: [[d20]], scale:'d20' });
```

- **问题**：`attrs` 全 0，兜底属性是智慧、DC 20 → 骰 + 0 ≥ 20 只有掷 20 才过（极值覆盖）。`skill.check` 也永远 undefined（194 条技能数据里 0 条带 `check`，见 §5.5）。注释说"六维还没进编辑器"已过期：`PartyPanel.tsx:97` 早在 0–100 夹取并显示区值。
- **后果**：技能面板（`App.tsx:216` 正式入口）里每个技能的成功率恒为 5%，与角色智慧高低无关，且被判成"失败"时见证者会照实播报。UI 里有一句「这一步只是试点链路」缓解了误导，但数值上就是错的。
- **建议**：`attrs` 改成从 `pc.attributes` 取（`getWorld().party.find(...)`），兜底判定也读 `skill.check` 或按技能表映射；注释同步删掉。这件事依赖 §5.5（数据没有 check），但"读角色六维"这一半现在就能修。

### 1.7 P2 — 两个引擎的档位聚合不同

`resolveChecks:213-215`（**全部** crit 才 crit）；`resolve:356-360`（**任一** crit 就算 crit）。实测同一组骰 `[[20],[10]]`：`resolveChecks` → `tier:'success'`，`resolve()` → `tier:'crit'`。

- **后果**：多属性判定（如搜索＝敏捷+观察）在两条路上会给出不同档位，而档位决定 secrets 的 crit 文案。单属性时两者一致，所以现在没暴露。
- **建议**：把"单项档位 → 整次档位"抽成一个函数，两个引擎共用；或者明确写死"多属性时 crit 只算自己那一项"（现在 `resolveCheck` 的注释就是这个意思，只是 `resolve()` 不遵守）。

### 1.8 P2 — 引擎外还有一份"骰几面、对多少 DC"的知识

`jump.ts:61-64 jumpScale()` 自己算 `sides` / `dc`（0 调用点，见 §4）。

- **后果**：将来 jump 切 D100 或 DC 改动时，`jumpScale` 和引擎各说一套；UI 若拿它显示"DC 20"会和实际判定不一致。
- **建议**：删掉 `jumpScale`，让调用方从 `AttributeCheck`（`dc`/`scale` 字段）读。

### 1.9 P2 — 引擎入口的属性名是 `string`，不是 `Attr`

`interaction.ts:126`（`attr: string`）、`:159`（`AttrSpec.attr: string`）。

- **问题**：属性名写错不会报错，按 0 走 DC 公式。另外 `Attr` 里包含【幸运】（`:16`），但 `resolveCheck` 没有幸运分支（`resolve()` 里有，`:319-322`）。实测 `attr:'幸运', rolls:[15]` → 失败（0+15<20），而 `resolveLuck(15)` → 成功。
- **后果**：`sense.ts:29-35` 的 `SENSE_SPECS` 用的是裸字符串，写错一个"观察"就静默变成 0 值；将来谁敢在 JudgeSpec 里用幸运，拿到的是错的规则。
- **建议**：`attr` 改成 `Attr`；`幸运` 在 `resolveCheck` 里显式走 `resolveLuck`（或禁止它出现在 JudgeSpec 里）。

### 2.1 P1 — `DEFAULT_HEIGHT` / `heightOf` 是死代码，移动这条链根本没有默认身高

`move.ts:154-159`（`DEFAULT_HEIGHT`、`heightOf`）0 生产调用；`move.ts:80-86` 用的是 `heightBonus(pc.heightCm)`。

- **问题**：耦合报告只说"两套默认值不同"。实际更糟：`heightOf` 是唯一会用默认值的地方，而它没人调。没填 `heightCm` 的角色，`heightBonus` 返回 0 → 身高加成恒 0，`DEFAULT_HEIGHT` 里的 170/160 **永远不生效**。
- **后果**：`types.ts:295` 写着"不填按性别默认"，但移动（`moveBudget`）根本不认；同一角色在移动侧按 150cm 算、在视野侧（sight.ts）按 173/164cm 算。两套数都不生效于移动的"默认"。
- **建议**：`moveBudget` 改用 `heightOf(pc)`（或让 `heightMoney` 收 pc 而不是 cm），然后把 `sight.ts` 的 `DEFAULT_HEIGHT_CM` 并过来，只留一份表。

### 2.2 P1 — 移动 HUD 还在用步数时代的分母

`trial.ts:29 MOVE_PER_TURN = 5` → `TrialHud.tsx:89` 显示 `已走 {used}/{MOVE_PER_TURN * 3} 子步（15）`。

- **问题**：现役模型是点数池（`movePool` + `stepPrice` + `canAffordStep`），一个 375–475+ 点的角色、慢跑单价 50 时一回合能走 8–10 格 = 24–30 子步。HUD 上限 15 对不上，会出现"已走 24/15"。
- **后果**：见证者按 HUD 判断"还能走多少"会判错；`MOVE_PER_TURN*3` 和 `move.ts:201` 注释、`terrain.ts:14 SUB` 三处各写 3，改一个漏两个。
- **建议**：HUD 改成读 `t.movePoints[tokenId]`（剩多少点）和 `stepPrice(mode, prone)`（一格多少点），显示"还能走 N 格"；删掉 `MOVE_PER_TURN`。

### 2.3 P2 — `zoneOf` 两份同名导出

`jump.ts:55`（带 scale 参数）与 `combat.ts:89`（固定 D20）都在包装 `attrValue`。

- **后果**：两个函数同名不同签名，import 时很容易拿错；`combat.zoneOf` 固定 D20，将来有人用它算 D100 区会静默按 ÷5。
- **建议**：只留 `combat.ts:89` 一份（或并回 `attrValue`），`jump.ts` 删掉自己的。

### 2.4 P2 — `CHARGE_POINTS` 定义了却没人用，公式还被抄了一遍

`move.ts:142` 定义 `MAX_CHARGE_CELLS * POINTS_PER_CELL`；`move.ts:149` 又写 `Math.min(storedCells, MAX_CHARGE_CELLS) * POINTS_PER_CELL`。

- **后果**：改上限时只改一处，另一处就漂。现在两处一致纯属手快。
- **建议**：`:149` 改用 `CHARGE_POINTS`；如果不需要导出就删掉导出。

### 2.5 P2 — 伤害骰常数被调用点硬编码覆盖

`combat.ts:15 DEFAULT_DAMAGE_DIE = 8`；`trial.ts:700`、`:856` 都写 `rollAttack(roll, 8)`。

- **后果**：作者哪天把"默认伤害 = 1D10"，改 `DEFAULT_DAMAGE_DIE` 对生产毫无影响，只有测试会跟着变。
- **建议**：调用点去掉第二个参数，走默认值。

### 2.6 P2 — 随机源是 7 份，其中 2 份是 crypto（耦合报告漏了）

已报：`jump.ts:33`、`sense.ts:38`（两行实现完全相同）、`jump.ts:115`、`trial.ts:699/855/909`、DiceTray。
**补充**：`combat.ts:72-76 randomDie`（`crypto.getRandomValues` + `buf[0] % sides`）与 `SkillPanel.tsx:8-12 d20()`（crypto + `%20`）。后者是技能面板现掷的那颗，前者是伤害骰。

- **后果**：主机侧有 `Math.random` 和 `crypto` 两套随机源；`%` 取模在 4/6/8/10/12/20/100 面上有极轻微偏差（可忽略，但两套源会让"可复现 seed"永远做不成）。另外技能面板自己掷 D20，绕过了 `resolveCheck` 的骰面定义。
- **建议**：与耦合报告 §7 同解：`core/dice.ts` 一处；技能面板改成调它；crypto 那两份统一成一种（要么全 crypto，要么全 Math.random + 可注入 roller）。

### 2.7 P2 — 优势/劣势语义这次是一致的，但同名字在不同文件里指不同东西

`interaction.ts:40 Advantage`（normal/advantage/disadvantage）与 `:152 DiceMode`（single/advantage/disadvantage）是同一概念的两个类型；`height.ts:86 FearTier` 也用 `advantage/disadvantage`，指的是"恐惧档"而不是"骰数"，靠 `fearRollMode`（`:102-104`）转换。

- **结论**：`pickRoll`（取高/取低，掷高好）在 jump/sense/height 全链路一致，历史上"优势反而变差"的错已消。**这不是 bug**，但三个同名枚举容易误读，建议把 `FearTier` 改成 `fear-advantage` 之类，或在类型注释里写明"档位 ≠ 骰数"。

## §3 层违反与循环（只补耦合报告没说的）

### 3.1 P2 — 文档只豁免了 skillCast，consent 是第二条未申报的边

`docs/代码结构-v0.1.md:23` 明确写「rules 不 import runtime（`runtime/sync.ts` 是个例外…`rules/skillCast.ts` 会调它的 `pushFocus()`）」——只点名了 skillCast。`consent.ts:2` 也 import 了 `runtime/sync`，属于文档没覆盖的第 2 条边。

- **后果**：下次有人按文档审依赖，会漏掉 consent；文档与实际不一致比"违反"本身更难发现。

### 3.2 P2 — `skills-data.ts ↔ skills.ts` 不是运行期循环，耦合报告判重了
