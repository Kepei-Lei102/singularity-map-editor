## 2) repairWorld 对越界 place — 报错不修，没有静默接收；老存档兼容

- **只报错不修**：给 `judgments.place = {x:24}`（或 x=-1），`repairWorld(w)` 返回 `fixed: []`，place 原样还在；随后 `checkWorld` 抛「判定位置超出地图」。导入路径 `parseWorld` 是 `repairWorld(w) → checkWorld(w)`（`src/runtime/actions.ts:888-890`），所以导入会**大声拒绝**，不会静默接收。
- **导出/存档也把关**：`buildProjectZip` 里 `checkWorld(w)`（`actions.ts:819`）；导出前还有一次 try/catch（`actions.ts:853`）。没有发现任何路径能把坏 place 写进 save/import。
- **老存档仍过**：
  - 无 `judgments` 字段 → PASS
  - `judgments: []` → PASS
  - `place: null` → PASS
  - `place` 字段缺失 → PASS
  - 合法 place（含合法边缘 `(23.5, 15.5)`）→ PASS
- **观察 P3-a（repair 不修 place）**：`repairWorld` 完全没处理 judgments（`schema.js` 里 judgments 只有 checkWorld 的块，repair 里没有），与 events 的「repair 丢弃面与 check 对齐」不是一套。历史上 `c7e1b17` 的发布口是 `>`，因此**旧版本真的能产生 x==width 的锚点**；这类老工程/localStorage 现在导入会被硬拒，而 repair 不提供修法（不能夹回、不能置 null）。建议在 `repairWorld` 里把越界 `place` 置 `null`（或夹到 `width-0.5`），并记一条 `fixed` 消息。
- **观察 P3-b（加载路径不校验）**：`load()`（`src/core/store.ts:25`）用 `migrateWorld` 恢复 localStorage，`replaceWorld`（`store.ts:213`）也用 `migrateWorld`，都**不调 checkWorld**；而 `migrateWorld` 不碰 judgments（`src/scene/memory.ts` grep 无 judgments）。所以 localStorage/桥接世界里若有坏 place，会静默进内存，直到导出时才在 `buildProjectZip` 的 checkWorld 处失败（toast）。不影响导入/导出正确性，但体验是「静默加载、导出才炸」。同一修法（repair 处理 place）能一并解决。
- 结论：任务要求的「没有路径把 bad place 静默留下」在**写入/导入**方向成立（都会拒）；**加载**方向有静默残留（P3-b），但因为本版本发布口是 `>=`，只有历史数据会碰到。
