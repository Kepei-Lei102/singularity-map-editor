# UI 与数据契约审阅（2026-11-10）

范围：`src/components/`（Inspector 660、MapCanvas 553、FlowPanel 492、Sidebar 368、TrialHud 293、PlayerView 279、JudgmentPanel、DiceTray、TrialEventCard 等）、`src/core/types.ts`、`src/core/store.ts`、`src/core/schema.js`。

## 结论

有一个 **P0**：优劣势骰在"玩家掷骰"这条链路上是**结构性丢掉的**——协议只传一个点数，
所以「往下 3–5 格 = 劣势敏捷」在玩家自己掷的时候被当成单颗，等于白送。这不是忘了写，是消息格式不支持。
其余是契约重复与组件职责过载。

## P0

### P0-1 优势骰／劣势骰在玩家掷骰链路上丢失

链路：`planJump` 产出 `check.dice`（`jump.ts:243-244`，往下 3–5 格是 `disadvantage`）
→ `JumpRequest.dice`（`types.ts:481`，本次已加）
→ `openJudgment({ jump })` 存进 `pendingJudgment.jump`（`judgments.ts:39,53`）
→ 推给玩家窗口（`sync.ts:89 pendingFor` 返回整个 PendingJudgment，所以**玩家窗口拿得到 dice**）
→ 玩家掷骰（`PlayerView.tsx:225-237`）→ `reportJudgmentRoll({ type:'judge-roll', value: r.value })`
→ `sync.ts:27` 消息体只有 `value: number`
→ `store.ts:291` `judgmentResult.value` 只有一个值
→ `JudgmentPanel.tsx:88` `settleJump(p.jump, [result.value])`
→ `trial.ts:535` `judgeValue(check, pc, [一个值])` → `resolveCheck` 的 `pickRoll` 拿到只有 1 个元素的数组 → 优势/劣势退化成单颗

**后果**：所有需要优劣势的跳跃（往下 3–5 格劣势敏捷、往下 12 格以上、恐惧检定将来也用）
在玩家掷骰路径上都按单颗算，难度被静默降低。测试测不到，因为测试直接调 `rollJumpCheck` 走的是另一条路。

**最小修法**（不动引擎）：

1. `sync.ts:27` 的 `judge-roll` 消息加 `values?: number[]`（`value` 保留为采信值，兼容旧窗口）。
2. `store.ts:291` 的 `judgmentResult` 同样加 `values?: number[]`。
3. `PlayerView.tsx`：`pending.jump?.dice !== 'single'` 时要求掷两次（`DiceTray` 连掷两颗，先显示第一颗再显示第二颗），
   两颗都拿到才 `reportJudgmentRoll({ values:[a,b], value: 采信值 })`；掷的颗数按 dice 决定。
4. `JudgmentPanel.tsx:87-95`：显示「掷出 5 / 17，采信 17」，`settleJump(p.jump, result.values ?? [result.value])`。
5. `trial.ts:535` **不用改**——它已经读 `req.dice`（本次已加），拿到两个值就会正确取高/取低。

顺带：`JudgmentPanel.tsx:79` 宣告面板也要显示这次判定是「优势骰 / 劣势骰 / 一颗」，
否则见证者开出劣势判定时自己都不知道要玩家掷两次。

## P1

### P1-1 同一个结构两份定义：`CombatNotice` 与 `Trial.event`

- `core/types.ts:516` `CombatNotice`（带 `id`、`role`、`at`）
- `core/store.ts:259` 内联在 TrialState 里的 `event`

本次加 `dice` 字段时先改 types.ts **编译不过**，必须再改 store.ts 才通过——说明两处是各算各的。
**建议**：store.ts 改成 `event?: Omit<CombatNotice, 'id' | 'role'> | null`，删掉内联定义。

> **已修（2026-11-10）**：已按上面这条改掉，`store.ts` 不再自己写一遍。

### P1-2 判定面板不传递"这次要掷几次"

见 P0-1 第 5 条。`PendingJudgment` 有 `jump.dice`，但面板完全没读它，宣告时也不显示。
见证者开出一个劣势判定，玩家收到的界面和普通判定一模一样。

### P1-3 玩家窗口"掷了不能取消"与两次掷骰冲突

`PlayerView.tsx:227` 文案写「掷了不能取消」，`rolled` 是单值且一旦设置就固定。
改成两颗后，要明确「第一颗已掷，第二颗继续」的状态，不能让人以为要重掷第一颗。

## P2

1. **`000` 格式化散落 5 处**：`PlayerView.tsx:230`、`PlayerView.tsx:244`、`JudgmentPanel.tsx:87`、
   `JudgmentPanel.tsx:155`、`rules/judgments.ts:25` 都是 `value === 100 ? '000' : value`。
   抽一个 `formatRoll(sides, value)`（D20 不会出现 100，D100 才显示 000）。将来 D20/D100 混排时会不一致。
2. **`types.ts` 与 `schema.js` 是两份契约**（`schema.js:1-6` 自己写了这是有意的设计）。

   将来会越来越难对齐。建议加一条测试：从 `types.ts` 的关键实体字段里抽名字，断言 schema.js 里出现。

   - `Inspector.tsx` 660 行：属性编辑 + 秘密/线索编辑 + 媒体挂载 + NPC 关联混在一个文件。

   - `MapCanvas.tsx` 553 行：命中测试 + 拖拽状态机 + 画笔 + 渲染入口 + 视口管理。

   - `FlowPanel.tsx` 492 行：流程树编辑 + 条件编辑 + 预览。
4. **组件里的 `getUI()` 直读不算 bug**：抽查 MapCanvas（8 处 getUI）全部在事件处理器和 effect 里，
   顶部有 `useUI()` 订阅（`MapCanvas.tsx:64`），没有脏读。这条不报。
