## requestId 守卫

- 守卫在 `tryAcquire` 前：`session.get(m.requestId) > 0` 时直接 `rejectAssetRequest`，不占 active、不建 flow、不发 start；正常 receiver 每个 batch 新 requestId，不会被误杀；`asset-request` 重发/同 requestId 分批在 receiver 不会出现。
- 配额 `stats:false` 路径也在守卫之后，同 requestId 在途时同样被拒；active cap 的 reject 仍走原路径。
- `AssetSession.get` 在 `release` 归零后删 cancel，requestId 结束后可复用；cancel whole 后到 finally 前 `get>0`，同 requestId 重发会被拒，符合“旧 serve 未归还前不重入”。
- **P3**：守卫只有 deployment 源码断言，没有行为测试；重复请求会走 `rejectAssetRequest` 发最多32条 forbidden，恶意高频重复会占节流/带宽；迟到重复请求在 receiver 没有 pending，会被忽略。

## cancel 账本

- 不带 key：`cancelAssetFlow` 直接 `endAssetFlow`，flow 立刻删除；serve 继续跑，但 `noteAssetBody` 找不到 flow，所有后续块不计；finally 再 end 无 flow，安全。
- 带 key：只认 `plannedKeys`、未 failed、未 ended；已 start 的删 `files`、`failedStartedFiles++`；未 start 的 `failedFiles++`；`failedKeys` 防重复；refresh。之后 serve 的 chunk/end 找不到 file，不计；`endedFiles` 不会对未 start key 加。
- 已 ended/failed 的 key 再 cancel 直接 return；未知 key 不占账；重复 cancel 因 `failedKeys` 无效。
- **P3 边界**：
  - cancel after start 会把已发部分留在 `bytes`，`totalBytes` 仍是整文件；dock 的“已发/总量”包含被取消文件的部分字节，之后 inFlight 减掉，但字节数不会回退。显示口径问题。
  - cancel 后 serve 仍可能发一块（如果已过 `isCancelled` 检查）；note 找不到 file/flow 不计，不会重复计数，但这一块仍占带宽。
  - 单 key cancel 的 `failedStartedFiles/files.delete` 没有行为测试；online 只测 whole cancel，且测试可能在 serve 自然结束后才看到 players0，无法证明账本“立刻”收起。

## load 超时

- `loading = opts.load(key)` 后 `Promise.race([loading, timedOut])`；超时 resolve `undefined`，走 `missing`；timer `unref` 且 finally `clearTimeout`。`loadTimeoutMs=0` 不设超时；默认30s。
- 超时不会 abort `loading`，只是不再等；`Promise.race` 已挂 rejection handler，不会因晚 reject 产生 unhandled；晚 resolve 被丢弃。
- **P3**：`load` 卡住按 `missing` 而不是 `read-failed`，玩家看到“没传过来”并重试；重试会再发新 requestId，host 再起一条 load，如果底层仍卡，会重复挂起多个 load promise。30s 对本地 `getRaw` 足够，但慢磁盘/大文件若真超过30s，会被误报 missing。
- **P3**：只覆盖 `opts.load`；后续 `blob.slice(...).arrayBuffer()` 仍可能卡住整条 serve，flow 没有 watchdog，`ASSET_LOAD_TIMEOUT_MS` 不覆盖它。

## 下一包先做什么

1. **可以直接上调度**，不必再单独插一轮 rate/UI：rate 窗口和100–200ms节流可以跟调度一起做。
2. 调度形态建议：**每 binding 一条 45ms 钟 + 全局 token bucket（约50块/s） + round-robin**。保留45ms作为单连接基线，全局预算防止12个 binding 同时把 host/base64/relay 打满；不建议直接把全局 pace 降到20–30ms 作为唯一改动，那会让所有玩家一起抢，缺少公平性和 CPU 预算。
3. **12人138s**：单 key 广播的 start 是并发快速发出的，120s 排队超时不会触发；138s 是总吞吐时间，是否接受取决于媒体大小。若把全局 budget 提到50块/s，理论总时长可降到约61s；30块/s 约92s；45ms 单钟不变则仍138s。建议先测量 host base64/IndexedDB 吞吐，再定全局 budget，不要拍脑袋只改45ms。
4. **队列/在途上限**：每 binding 同时 inFlight 上限（例如1–2个文件）+ 排队上限；超过回 forbidden/排队中，避免一个大文件占满全局预算。
5. **flow watchdog** 补 `arrayBuffer` 阶段；cancel 行为测试补 whole + single key + after-start；requestId 守卫补重复请求用例。这些可以和调度包并行，不阻塞调度。
