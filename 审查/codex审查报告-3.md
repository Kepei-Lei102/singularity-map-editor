## 第二部分：新发现

以下包含本轮确认的残留缺陷和修复引入的回归。P1 为数据破坏、泄露或卡死，P2 为功能和状态错误。

1. **P1 — `scripts/open.mjs:45`：Host 检查与实际路由匹配规则不同，可以绕过读取接口的保护。**  
   **触发：** 使用非本机 Host 请求 `/__LOAD`、`/__load.json` 或 `/__SAVE-TARGET`。前置正则不匹配这些路径，但当前 Vite 的 Connect 路由忽略大小写，并接受点号后缀。  
   **后果：** 内存请求验证返回了工程内容或保存口令；这些自定义处理器还位于 Vite 自带 Host 检查之前，后者无法补救。这不等于已绕过保存 POST 的来源检查，但工程读取边界已经失效。  
   **建议：** 在每个敏感处理器内部检查 Host，或对所有请求先统一检查；不要使用比路由器更窄的路径正则保护接口。

2. **P1 — `scripts/tsmap.mjs:73`：逐个改名不是整体提交，失败仍会破坏旧工程的一致性。**  
   **触发：** 新包依次更新媒体 `a、b`，磁盘上的 `b` 是符号链接；暂存全部成功，`a` 已替换后，第 74 行才拒绝 `b`。普通的后续 `renameSync` 失败也有同样结果。  
   **后果：** 已复现“旧 world.json＋新 a”，且 `finally` 删除暂存目录，没有恢复旧媒体。  
   **建议：** 提交前检查全部目标，并为提交阶段保留可回滚的旧版本；更稳妥的是版本化媒体、最后原子切换清单。

3. **P1 — `src/actions.ts:536`、`:570`、`:657`：读取失败被当作不存在，恢复缺备份媒体时也继续成功。**  
   **触发：** 覆盖同 ID 媒体前，读取旧 Blob 报错；或者恢复时 `__backup__/m` 缺失／读取失败。

   **建议：** 区分“成功读取但不存在”和“读取失败”；备份声明的媒体必须全部取得，否则在任何修改前中止恢复。

4. **P1 — `src/actions.ts:550`：回滚失败被吞掉，仍声称“已经还原”。**  
   **触发：** 更新 `m` 成功、更新 `n` 失败，随后恢复 `m` 的写入也失败。

   **建议：** 一批 Blob 更新及备份交换使用同一个 IndexedDB 事务；若保留补偿回滚，必须检查每一步结果并保留恢复材料。

5. **P1 — `src/actions.ts:565`：导入和恢复没有互斥，会互相覆盖备份记录和备份媒体。**
