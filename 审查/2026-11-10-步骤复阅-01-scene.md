## 问题清单

### P1-1 有细分格的地图上，`sightToObject` 每次调用都建全图挡死表 → `autoReveal` 每步慢 4–12.8×

位置：
- `src/scene/perception.ts:43`（`const cache = sightCacheFor(...)`，在 `sightToObject` 里、每次调用都建）
- `src/scene/sight.ts:174-186`（`sightSubcellBlockers`：只要 `subdivisions.length > 0` 就扫整图 `w3×h3` 个子格；且每个子格走 `terrainAtSubcell`，里面又是 `subdivisions.includes()` 线性扫描）
- `src/runtime/actions.ts:382-396`（`autoReveal` 对每个物件 × 每个 secret × 每个队员调 `pcWithin`）
- `src/runtime/trial.ts:381`（试玩每走一步调 `autoReveal`）；`src/runtime/actions.ts:374`（跑团模式每步也调）

触发与证据（探针实测，旧实现按 `e025e95^:src/scene/sight.ts` 逐行还原）：
- 建表成本（现状）：40×40 细分 1 格 **0.29ms**／全细分 **2.74ms**；100×100 细分 1 格 **1.14ms**／细分 625 格 **13.1ms**／全细分 **97.7ms**（表内存 14KB / 88KB）。
- 旧路径：`visiblePoint` 逐点算，预算/锥形/墙任一不过就提前 `return`，挡死表 **根本不会建**；单个远处物件 40×40 旧 **0.036ms**、100×100 旧 **0.234ms**。
- 新路径：一次 `sightCacheFor` 建两张表 → 每个（物件 × 队员）一次；同一个远处物件 40×40 新 **0.721ms**（19×）、100×100 新 **4.568ms**（19.5×）。
- 端到端（`pcWithin` 全扫，判定结果旧/新命中数一致）：
  - 40×40、细分 1 格、36 物件 × 4 队员：旧 **6.5ms** → 新 **25.9ms**（慢 4.0×）
  - 100×100、细分 1 格、256 物件 × 4 队员：旧 **89.9ms** → 新 **1147.6ms**（慢 12.8×）
  - 40×40 无细分：旧 1.9ms → 新 1.6ms（反而快 1.2×，说明问题只在细分地图）
- 影响面：`autoReveal` 是每步都跑的；`nearestPc`（`Inspector.tsx:322` 每次重绘）与 `pcWithin`（揭示/互动校验）也同构变慢（100×100 稀疏细分下 `nearestPc` 约 5ms/次 vs 旧 0.2ms，绝对量小）。

建议修法（两条，可叠加）：
1. **重写 `sightSubcellBlockers`（推荐，byte 等价）**：按主格循环，用 `Set` 判细分，只给「主格本身挡死」和「细分格」写那 9 个子格；不要对每个子格调 `terrainAtSubcell`/`includes`。我按此写了候选版，与现状表在 100 张随机图上逐字节对比 **0 差异**；耗时：40×40 1 格 0.29→**0.03ms**、40×40 全 2.74→**0.26ms**、100×100 1 格 1.14→**0.13ms**、625 格 13.1→**0.28ms**、全细分 97.7→**1.33ms**。
2. **别在每个调用点急建表**：`block` 做成惰性（`visiblePoint` 过了 budget+墙判定才建），或把 cache 提到调用方——`pcWithin`/`nearestPc` 每个 token 建一次，`autoReveal` 每个队员建一次传下去。`SightCache` 只依赖眼高（cost）+ map/world（block），**不依赖站位/朝向/子格**，同一眼高可跨棋子复用；`autoReveal` 里现在实际跑了 物件×队员 次建表（100×100 稀疏细分 1024 次 × 1.14ms ≈ 1.1s，正是上面实测值）。

顺手：`terrainAtSubcell`（`src/scene/terrain.ts:21-30`）每个子格也做一次 `includes`，`syncLayer` 也在用；不是本轮引入，但同一张表的问题建议一起换 `Set`。

### P2-1 边界外一点：索引越界 → `NaN`，旧实现「看不见」，新实现「看得见」

位置：`src/scene/sight.ts:321-322`。

触发条件（实测）：`sum` 变成 `NaN` 时，旧 `canSee` 是 `sum <= budget`（false → 返回 false），新是 `sum > VISION_BUDGET`（false → 继续往下走），于是后面锥形/墙/子格都放行时返回 **true**。`NaN` 只在索引越界时出现：
- `floor(target.y) == map.height`（任意 x），或
- `floor(target.x) == map.width` 且 `floor(target.y) == map.height-1`。

实测：6×6 平地、eye=(2,2)，target=(3,6)/(6,6)/(6,5)/(5.5,6) 旧 `false`、新 `true`；15 个边界点里 4 个不一致。另外 `target.x == map.width && y1 < height-1` 不产生 NaN，但会读到**下一行第一个格子**（旧实现也这样）。

现状安全性：7 个 `visiblePoint` 调用点全都传格内点（格中心/子格中心/夹取过的门几何中点/棋子位置），实测均不触发；但 `visiblePoint` 是导出 API，以后接 AI 或别的模块按「格子坐标」传参就会踩。

建议：bounds 从 `> map.width` 收紧到 `>= map.width`（顺手修掉别名读；这会让 `x==width`/`y==height` 这类退化点从「可能可见」变「不可见」，属有意收紧），或 `floor` 后加 `if (x1 >= map.width || y1 >= map.height) return false;`；`canSee`（`sight.ts:142`）现在生产代码已无人调用（只剩测试），可以标 deprecated 或删掉，避免以后有人拿它和新写法混用。

### P2-2 攻击事件把通用 `check` 编成 `dc:0 + attrs:[]`，与文档契约不一致

位置：`src/runtime/trial.ts:774-783`（`check: { scale:'d100', attrs:[], merge:'single', dc:0, … }`）；类型 `src/core/types.ts:585-597`（`dc: number` 必填）；文档 `docs/物理互动-范式-v0.1.md:242`（「尺、每个属性各掷了什么、合并方式、**DC**、总数、档位」）。

触发与证据：每次攻击都这样。实测事件 `check = {scale:'d100', attrs:[], merge:'single', dc:0, total:roll, success, tier, level}`；渲染侧因为 `attrs` 空走 `掷 D100` 分支（`events.ts:46-47`），**人读没问题**，但结构化账本里 `dc:0` 会被未来的判定记录/AI 读成「DC 0 的检定」，而且 `attrs:[]` 与文档「每个属性各掷了什么」对不上。攻击本来就没有 DC 和属性对抗，这是硬塞。

建议：把 `check.dc` 改成可选（`dc?: number`），或给 `check` 加 `kind: 'check' | 'attack'`（攻击额外带 `band: AttackBand`）；攻击事件只填 `scale/total/success/tier(/band)`，不要借 `dc:0` 当哨兵。类型放宽后 `declareText` 的 `attrs` 空分支就不需要兜 `dc` 了。

### P3-1 日志没有上限，事件有 200；`appendEvent` 每条又写一条日志

位置：`src/rules/events.ts:22-26`（`appendEvent` push events 并截到 `EVENT_CAP`，同时 `d.log.push(...)`）；文档 `docs/物理互动-范式-v0.1.md:255`（「存档只留最近 200 条（EVENT_CAP）」）。

证据：连发 205 条 → `events.length = 200`（最旧 `e5`），`log.length = 205`（最旧 `e0-log`）；全仓没有日志截断（`log.length/splice/LOG_CAP` 无命中），日志会一直长、且被挤出 200 的事件只剩日志里那句渲染文本（`ev.id-log` 的 event 已不在数组，无法回查结构）。

建议：`appendEvent` 给 log 也设上限（或 log 条目存 `eventId` 并在保存时清孤儿），文档写清「200 只针对 events，日志另算」。

### P3-2 渲染器对未来 delta 的兜底

位置：`src/rules/events.ts:58-66`（`deltaText`；`moved` 在 `:62` 直接打印小数格坐标）、`:63`（`status` 的 `from ?? '无'` / `to ?? '无'`）。

证据（实测）：`deltaText` 会输出「甲 从 (2.5, 3.5) 挪到 (3.5, 3.5)」「乙 的状态从 无 改为 无」。当前攻击不会产生这两种（`deltas` 不判真变是 runtime 报告 P1-1，同源），但 `appendEvent` 是通用入口，接移动/跳跃/状态时就会撞上。

建议：`deltaText` 里 `from === to` 直接跳过；`moved` 打印格坐标或写明「格坐标（可带小数）」，避免和子格坐标混淆。

### P3-3 渲染缓存的失效键：现状够用；少 `party`，多 `heights`

位置：`src/scene/render.ts:367-383`。

结论：**对当前所有写入路径是够的**。
- 所有 token 写入都走 `update()` 的 draft：`trial.ts:228/359/556/594/612` 的 `dt.facing`、`setTokenPosition`（`architecture.ts:88-89`，调用点 `actions.ts:1374`、`trial.ts:358/555/593/611`）、`sliding.ts:72`（注释明写「同一次 store update 中调用」）→ token 引用必变 → 缓存正确失效。
- 地图任何编辑（包括没进键的 `d100`/`subCells`）都会换新的 map 对象 → `m.map === map` 已兜住；`world.terrains` 在键里（`cellSightCost` 要读 `visionCoef`）。
- 缺的键：`world.party`。`viewerOf(st, { sex, heightCm })` 的眼睛高度从 party 来（`render.ts:379`）；现在全仓**没有写 `heightCm`/`sex` 的 UI 入口**（只有读），所以现状不触发；一旦加「改身高/性别」，选中棋子的看清范围就会不更新。建议把 `party` 引用加进键，或干脆把 `eyeHeight` 值存进缓存键。
- 多：`heights` 在键里但 `visionOf` 不读 heights（`sight.ts` 里没有 heights），属于多余失效，可删。
- 使用范围提醒：这个缓存只省「没有 update 的重绘」（平移/缩放/悬停）。每次 update 后（party 非空时）`withVision` 都会重写 `m.views[p.id]`（`perception.ts:105` shared / `:112` individual），**所有 map 对象引用都换新** → 缓存必然失效；所以「改一步后的重绘」仍要付一次 `visionOf`（40×40 全细分约 3.4ms、100×100 全细分 97ms，大头是 P1-1 那张表）。P1-1 修好后这两个数才一起下来。

## 七个关注点逐条

1) **等价性（含 Infinity 墙角斜穿、边界外、同格）**：随机差分 171,524 次（300 张随机地图 × 4 眼 × 全图目标，地形/物件/细分/子格覆盖/建筑薄墙几何/朝向/姿态/身高/D100 区全随机）→ **旧 vs 新 0 差异**；显式 7 场景 2,106 次（平地/一堵墙/草丛/物件+薄墙/斜穿墙角/60°锥/细分）→ 除边界外 0 差异；专项子格挡死：挡死时旧 false/新 false，去掉挡死时旧 true/新 true（两版一致，挡死表真的在起作用）。**唯一不等价是 P2-1 的越界 NaN**。
