## 1. `buildSkillTree`：levelUp 开合、当前途径、计数

`src/rules/skills.ts:100-116` 在 `groupSkills(SKILL_LIBRARY, unlocked, {levelUp})` 上派生，`currentPathwayOf(pc)` 只用于标记。

- `levelUp:false` 时 `groupSkills:61` 过滤成 `unlocked.has(id)`，只留已解锁的途径/组；空技能返回 `[]`。探针：`[] -> []`；`['037-9-101'] -> 金手指/医疗·调养，1/1`。
- `levelUp:true` 探针：17 条途径、合计 198 个节点；`['037-9-101']` 时金手指 `current:true`、`unlockedCount:1`、`totalCount:4`。
- 显式路径优先：`{skills:['037-9-101','不存在'], pathway:'控场途径'}` 下控场 `current:true`，金手指 `current:false`；未知技能 id 不计入 `unlockedCount`（仍为 1）。无显式路径时从第一个可识别技能回退，未知 id 跳过。
- 计数：`unlockedCount` 按节点 `skill.id` 过滤，`totalCount` 是当前可见节点数；`levelUp:false` 下两者相等（只算已解锁），`levelUp:true` 下合计 198。测试 `scripts/skill-tree.test.mjs:30-59` 已覆盖 17/198、开合、显式路径和未知 id。

**P3（不阻断）**：显式 `pc.pathway` 若写成库外的值（旧角色卡可能沿用「游戏鉴赏家」这类职业名），`currentPathwayOf()` 仍把它当权威值（`skills.ts:31`），树上不会有「当前」标记，但不会崩、计数也不受影响。`SkillPanel` 的合法路径选择来自 `SKILL_LIBRARY`，正常 UI 不会产生这种值。

## 2. 发动入口守卫：顺序和副作用

`src/rules/skillCast.ts:51-58` 的顺序是：技能存在 → 无进行中 cast → 角色存在 → **`pc.skills.includes(skillId)`** → ME 已填 → 费用/强行 → 建 cast。解锁判断在 `:57`，在任何 `setCast`、`charge`、focus 之前。

- 探针：未解锁时三种入口（`player`、`gm`、`player+force`）都返回「没有解锁【游戏解题】」，`castOf()` 仍是 `null`、`ui.focus` 仍是 `null`、ME 完全不变。
- `pc.skills` 缺失时守卫也不崩（按空列表拒绝）；未知技能 id 先报「没有这个技能」；已有 cast 时尝试未解锁技能只报「已经有技能在发动中」，原 cast 和 ME 不变。
- 跨途径仍正常：`skills.test.mjs:171-181` 通过；探针里当前途径「游戏鉴赏家」+ 金手指技能，`meCost:2`、ME 10→8、途径在发动时切到金手指；同途径仍是 `meCost:1`。守卫不参与费用计算，没有把 +1 改掉。
- 失败路径全部在 `setCast` 之前返回，因此不会立 focus/建 cast，符合本轮边界。

**P3（不阻断）**：守卫只发生在 `beginSkillCast()`。若一个已解锁技能已进入 `approval`/`confirm`，期间把该 id 从 `pc.skills` 移除，`approveSkillCast()`（`:75-84`）不会复检，点头后仍会扣 ME 并继续结算。它不是入口漏洞（入口已拒绝），但若以后要求“撤销即作废”，应在 approve/resolve 再查一次。
