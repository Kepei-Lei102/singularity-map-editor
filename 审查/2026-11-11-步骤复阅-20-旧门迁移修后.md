### 3.2 残留 P2-A：`blocksWhen` 缺失/空时仍静默把状态标成打开

探针：

```text
门: states=['关闭','打开','备用'], state=0, blocksWhen=undefined, openStates=[1]
setObjectStates(mapId,'door1',['关闭','锁着'])
=> 接受，无 toast
=> states=['关闭','锁着'], openStates=[1]（打开的 name = '锁着'）, blocksWhen 仍 undefined
=> checkWorld 过
```

`blocksWhen=[]` 时同样：提交 `['关闭','锁着']` 后 `openStates=[1]`，无提示，`checkWorld` 过。

机制（`actions.ts:481-491`）：

```ts
const mapped = [...new Set(o.opening.openStates.map(to).filter(i => i >= 0))];
if (!mapped.length) {
  const named = nextStates.findIndex(s => /.../i.test(s.trim()));
  if (named >= 0) mapped.push(named);
  else {
    const cur = Math.max(0, to(o.state));
    const candidates = nextStates.map((_, i) => i)
      .filter(i => !(nextBlocks ?? []).includes(i) && i !== cur);
    if (candidates.length) mapped.push(candidates[0]); // ← blocksWhen 缺失被当成“没有挡路状态”
    else { toast('门至少要留一个「打开」状态…'); return; }
  }
}
```

`nextBlocks` 只在 `o.blocksWhen` 为真时计算（`actions.ts` 上方），缺失即 `undefined`，`(nextBlocks ?? [])` 变成空数组 → 除了当前状态外所有状态都算“能开的”，于是静默选第一个。**这不是“用 blocksWhen 反推”，而是“没有 blocksWhen 时把未知当没有挡路”**，正是本轮要禁止的静默猜。`blocksWhen` 因改名/变长度导致映射后为空数组时同理。

建议修法：

- 只有在 `Array.isArray(o.blocksWhen) && o.blocksWhen.length` 时才用 `nextBlocks` 反推；否则（缺失/空/映射后为空）与“名字读不出”一样，`toast('门至少要留一个「打开」状态…')` 后整次拒绝，不要挑任意状态。
- 补一条回归：门 `blocksWhen=undefined`（以及 `[]`）删打开态 → 拒绝、世界不变。
- 若希望 `blocksWhen=[]`（检查器把两个状态都勾成打开）也能改名，至少要求新名字是打开名；不要用“排除当前状态后取第一个”兜底。

### 3.4 同长度改名：不拒绝（P3 观察）

探针：门 `states=['关闭','打开']`、`openStates=[1]`、`blocksWhen=[0]`，提交 `['关闭','锁死']` → 接受，`openStates=[1]`（打开的 name 变成「锁死」），`checkWorld` 过，无 toast。

这来自既有映射规则“行数不变时按位置对（改了某一行的字）”（`setObjectStates` 注释/`actions.ts:465-471`）：同一行改名被视为同一状态，不是“删掉打开 + 新增关闭”，因此不算本轮禁止的“关闭态偷偷标成打开”；但如果用户把打开那一行改成「锁死」，这行仍算打开态，语义上容易误解。**P3**，不是本轮 P2。

## 5) P3 清单（不阻塞，但建议排期）

1. **confirm 的“最后一个状态”不总是最后一个**（`schema.js:172-175`）：`i = states.length > 1 ? (o.state === states.length - 1 ? 0 : states.length - 1) : 0`。探针 `states=['关着','锁着']`, `state=1` 时确认后得到 `openStates=[0]`（「关着」），提示文案却说「按确认把『关着』当作打开」；当前 state 是「锁着」→ `openingIsOpen=false`，门仍是关的，与 confirm 文案「把最后一个状态当打开」不符。影响面窄（只在当前状态正好是最后一个时），列 P3；若把 confirm 文案视为硬契约可升 P2。
2. **guess 路径提示重复**：先 push「按确认把…当作打开」，后面通用分支又 push「没有打开状态，补成…」；成功时 toast 两条（无功能影响）。
3. **成功迁移提示会被覆盖/丢弃**：`buildProjectZip`/`exportWorldJson` 先 `toast(hints)`，随后成功 toast 覆盖；导入里 `repairWorld` 的 hints 未被接收（第二次显式 repair 返回空），所以按名字/挡路反推成功的导入是静默的。未解决错误仍会显示（P3）。
4. **blocksWhen 反推不保留当前非挡路态**：`states=['关闭','锁着','备用'], blocksWhen=[0], state=1` → 反推 `openIndexes=[1,2]`，代码 `pick = open.find(k => k !== o.state) ?? open[0]` 选 2（备用），当前 state 1（锁着，按 blocksWhen 非挡路）不再是打开态，门从“本来算开着”变回关着；建议若当前状态在非挡路集合里优先选当前（P3）。
5. **`openStates` 缺失/为 null 仍不迁移**：`repairDoorOpenStates` 的 `!Array.isArray` 直接 `continue`；随后 `checkWorld` 里 `openingIsOpen` 调 `.includes` 抛裸 TypeError（非「工程文件有问题：…」）。旧编辑器门都写过该字段，概率低（P3，承上轮）。
6. **同长度改名不拒绝**：见 §3.4；语义观察，非 P2（P3）。
7. **入口接线无回归测试**：`doors.test.mjs` 26 条覆盖 `repairDoorOpenStates`/`repairWorld`/`checkWorld`/`setObjectStates`，**没有**覆盖 `parseWorldWithConfirm`、`buildProjectZip`、`exportWorldJson`、`restoreBackup` 的接线；三条变异都在函数级。删掉 actions 里的调用，现有测试不会红（源码核对，未实际跑该变异）。P3。
8. **不变量只覆盖 blocksWhen 是数组时**：缺失字段的门可以通过 `checkWorld`，而 `setObjectStates` 又把它当“无挡路”使用（与 P2-A 同源）；建议 schema 至少要求门有 `blocksWhen` 数组（或迁移补空/补全），否则“打开状态不能挡路”对缺失字段没有约束（P3）。
