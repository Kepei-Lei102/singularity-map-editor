- 审阅范围：启动/构建、React 渲染、地图绘制、同步/序列化、内存/资源；只读审阅，未改代码、未提交。

## 结论一句话

**日常小图可接受，首屏和 198 技能搜索也不是瓶颈；但 200×200 上限图目前不适合连续画笔：单格地形改动会触发整图视野/记忆重算（`store.update` 实测 186–214ms），加上全量画布重绘，单次端到端约 0.23–0.27s。这是最痛的点，应先修 P1；其余是局部慢和资源风险。**

### P1（1 条）

#### P1-1 200×200 上限图上，单格地形/小格画笔触发整图视野+记忆重算，单次约 0.23–0.27s

证据（实测）：

- 在 200×200 地图、4 个角色、队伍页打开、画布 806×557、DPR 1 的 dev 页上，连续改同一格地形：
  - `store.update` 同步段 **186–214ms**；
  - 端到端（含一次画布重绘到下一帧）**233–265ms**；
  - 每次重绘 **77,640 次 `fillRect`**，画布自身 span **33.7–38.4ms**。
- 这是“单格”而不是整片刷；画笔拖动时每个 pointermove 落一个 `update`，按这个量级会把拖动变成逐格卡顿。
- 对照：小图 24×16 画布仅 **0.6–0.7ms/次**；所以问题集中在大图，不是所有地图都慢。

原因（当前代码）：

- 改地形会让 `mapStructureChanged` 为真（`src/scene/dirty.ts:79-91`），随后 `structure/visionStructure` 为真（`:113-114`）。
- `planVision` 只要看到 `visionStructure` 就返回整图 full（`src/scene/visionPlan.ts:36-39`）。
- `update` 每次都走 `withVision` + `syncMemory`（`src/core/store.ts:156-160`）。
- `syncMemory` 对整张图执行 `syncLayer`，全量路径会扫 `width*height*9` 个子格（`src/scene/memory.ts:131`、`:223-260`）；200×200 即 **360,000 个子格**。
- 画布又在这个 update 后再全量重绘（`src/components/MapCanvas.tsx:112-128`）。

推荐修法（按性价比排序）：

1. **画笔拖动期间先只改地形和画布，把视野/记忆重算延后到 `endBatch()` 或空闲帧。** 单次点击仍在松手后算一次；连续拖动从“每格 190ms”变成“整笔一次”。风险：拖动中玩家端看到的雾/记忆会短暂滞后；需要确认是否接受，或只在没有玩家绑定/试玩时延后。工作量约 **1–2 天**，风险中等。
2. **给 `syncMemory` 增加按脏格收窄的路径**：地形编辑只同步被改的大格/小格及其 3×3 邻域，而不是整图 360,000 子格；建筑/物件高度变化仍走全图。工作量 **3–5 天**，风险较高（容易漏同步记忆）。
3. 先用 **rAF 合并 pointermove**，一个帧最多一次 `update`；这能把连续拖动的事件数降下来，但不能把单次 190ms 降下去，属于辅助措施。
4. 在上述两点完成前，不建议用“加大画笔节流”掩盖：单次点击仍会卡 0.2s。

### P2（4 条）

#### P2-1 任意世界/UI 变化都会重渲染整个 Editor，并全量重绘画布

证据（实测，dev 页，200×200 + 4 角色 + 队伍页）：

- 只改世界名（与画面无关）：编辑模式 **40,204 次 `fillRect`，画布 span 24.1ms，到下一帧 29.4ms**；队伍页模式下 **77,640 次，span 34.4ms，到下一帧 51.7ms**。
- 只改 UI 的画笔值（与世界无关）：编辑模式 **span 22.5ms / 27.9ms**；队伍页 **34.5ms / 48.1ms**——照样整张画布重画。
- 打开队伍页时：**155,280 次 `fillRect`（两次重绘）**，到下一帧 **110.3ms**，DOM 从 353 个节点涨到 **3,773 个**。
- 画布独立基准：200×200 适配缩放下，编辑 median **16.9ms**、准备/带团 median **24.1ms**；24×16 仅 **0.6–0.7ms**。

原因：

- `Editor` 直接订阅整个 `world` 和整个 `ui`（`src/App.tsx:57-58`），任何字段变化都重渲染整棵树；`MapCanvas` 在树里（`:184`），没有 `React.memo`。
- `MapCanvas` 的绘制 `useEffect` **没有依赖数组**（`src/components/MapCanvas.tsx:112-128`），组件每重渲染一次就重画一次；`useUI()` 也在 `MapCanvas` 内（`:53`），UI 变化同样触发。
- `render` 每帧都按可见大格重画地形（`src/scene/render.ts:530-566`），准备/带团模式还会再画一层迷雾覆盖（`:828-837`）；适配缩放下 200×200 全图可见，40,000 个格子就是 40k 次地形 `fillRect`，加迷雾约 77k 次。
- `terrains`/`materials` 的 Map 和低缩放下的 9 子格聚合也在每次绘制重算（`src/scene/render.ts:522-523`、`:530-566`），没有缓存。

推荐修法：

- **先把 `MapCanvas` 拆成只接收绘制输入的组件并 `React.memo`**；绘制 effect 的依赖收敛到 `map`（Immer 下世界改名不会换 `map` 引用）、`view`、尺寸和真正影响绘制的 UI 字段（selection/tool/brush/showFog 等）。世界名、toast、面板开关等不再触发画布重画。工作量 **0.5–1 天**，风险低。
- 对 pointermove/绘制做 **rAF 合并**：同一帧最多一次 render；不要在事件里同步画。工作量 **0.5 天**，风险低。
- 对 200×200 适配缩放，**缓存地形底图到离屏 canvas**（按 map/cells/fineCells/terrains/view 做键），每帧只 `drawImage` 底图并叠加物件、token、雾、标记。工作量 **2–3 天**，风险中等；这是把 16.9/24.1ms 降到个位数的关键。
- 面板层再做 `React.memo`（PartyPanel、Inspector 等）和按需订阅；不要先重写所有组件。

#### P2-2 队伍页把每个角色的 198 个技能复选框全部挂到 DOM，`<details>` 收起也照挂

证据（实测）：

- 4 个角色时：`.skill-tree-editor` 内 **792 个 checkbox**，整页 **3,773 个 DOM 节点**；每个角色单独一棵树是 **198 个 checkbox / 755 个节点**。
- 浏览器打开队伍页（200×200 + 4 角色）到下一帧 **110.3ms**（含画布两次重绘；React dev 下偏保守）。
- jsdom/React 基准：
  - 单角色 198 项首次挂载 median **15.7ms**；
  - 4 角色首次挂载 median **73.7ms**；
  - 无关世界更新 median **14.5ms**；勾选一项 median **14.9ms**；搜索 median **3.25ms**。
- 浏览器里勾选一项同时触发整页重渲染和画布重绘：**同步 47.6ms / 到下一帧 48.8ms**，其中 77,640 次 `fillRect`。勾选本身不是瓶颈，画布和整树才是。

原因：

- `SkillTreeEditor` 用 `<details>` 收起内容，但内部 `tree.map(...)` / `row(...)` 无条件渲染（`src/components/SkillTreeEditor.tsx:34-56`）；`PartyPanel` 对每个角色都挂一棵（`src/components/PartyPanel.tsx:117`）。
- 每个 `SkillTreeEditor` 都 `useWorld()`（`SkillTreeEditor.tsx:8`），世界任一变化都会重算 `buildSkillTree`、`all`、`unlocked`、`hits`（`:11-17`）。

推荐修法：

- **只在 `<details>` 打开时渲染 rows**：用 `open` state 控制 `tree.map` 是否执行；收起时只渲染 summary 和搜索框。工作量 **0.5 天**，风险低；4 角色首屏 DOM 从 792 checkbox 降到 0。
- 把单行抽成 `React.memo(SkillRow)`，勾选时仅被点行和计数更新；搜索用 `useDeferredValue` 或保持现在（搜索实测 3ms，不需要复杂虚拟列表）。工作量 **0.5–1 天**，风险低。
- 不要为此上虚拟滚动：198 行本身不贵，贵的是“无条件挂载 + 整页重渲染 + 画布重绘”。

#### P2-3 host→player 每次全量投影 + 结构化克隆；4 个玩家时一次广播约 80ms

证据（200×200、4 角色、世界含 200 个物件）：

- `playerWorld(w, mapId, pcId)` 单次 median **12.2ms**（11.4–16.4ms）。
- 投影后 JSON **1,745,283 字符**；原世界 JSON **7,212,188 字符**。
- `structuredClone`：原世界 median **51ms**；投影 median **8.3ms**。
- 当前广播是 **60ms 防抖**（`src/runtime/sync.ts:845-847`），`send` 对每个已绑定玩家各做一次投影（`:372`）并 `postMessage`（`:379`）。按 4 个玩家相乘估算：**约 4×12.2 + 4×8.3 ≈ 82ms** 的主线程同步工作，超过 60ms 的发送间隔。
- 玩家端收到 `world` 后 `setWorld` 整份替换（`src/components/PlayerView.tsx:124-132`），`MapCanvas` 再全量重绘；玩家端在 200×200、全雾不可见时画布约 **8.7ms**。
- `pushFocus` 会绕过防抖立即 `send(world)`（`src/runtime/sync.ts:840-842`），频繁 focus 变化会重复做同样的全量投影。

推荐修法：

- 短期：把广播间隔从 60ms 调到 **100–200ms**，并只在世界结构真的变化时发送；focus/cast 消息拆成轻量消息而不是整份世界。工作量 **0.5 天**，风险低。
- 中期：给 `playerWorld` 做**增量投影**（只发变动的地图格/物件/token）或至少按地图版本缓存投影；玩家端维护旧 world 做合并。工作量 **3–5 天**，风险高（最容易出可见性/身份漏发）。
- 在线上房间下还要考虑带宽：投影 1.75MB/次 × 4 人 × 最高约 16 次/秒，名义上可达 100MB/s 级；本地窗口尚可，线上必须先做增量或降低频率。这是“同步”而不是首屏问题。

#### P2-4 200×200 世界自动保存：7.2MB JSON 主线程 stringify 39ms，且 localStorage 配额直接失败

证据（实测，200×200 + 4 角色 + 200 物件）：

- `JSON.stringify(world)` median **39.4ms**（38.8–41ms），字符串 **7,212,188** 字符。
- 对该字符串执行 `localStorage.setItem` 实测抛 **`QuotaExceededError`**；同一页面控制台随后出现 **4 次 `自动保存失败：浏览器存储空间不够`** 警告。
- 自动保存链路：`emit()` 400ms 防抖（`src/core/store.ts:72-74`），`saveNow()` 在**主线程** `JSON.stringify` 后写 localStorage（`:78-81`）；`saveSlot` 还会做索引和淘汰（`src/core/persist.ts:27-44`）。
- 结果是：大图不只是“保存慢 39ms”，还会**保存失败**；刷新/关页可能丢自动存档。这属于资源/可靠性问题，但由性能路径暴露。

推荐修法：

- 把世界存档从 localStorage 换到 **IndexedDB**（项目已有 `ts-map-media` 的 IndexedDB 封装，`src/runtime/media.ts:11-33`），异步写、不会在主线程做配额失败；JSON.stringify 仍可放 `requestIdleCallback` 或 Worker。工作量 **1–2 天**，风险中等（迁移旧存档/备份时必须兼容）。
- 如果暂不改存储：至少在大世界保存失败时给可见提示，并把 `fineCells` 这种重复度高的 360k 数组改为紧凑编码/压缩，避免 7.2MB 字符量。工作量 **1 天**，风险中等。
- 不要只把 400ms 防抖加大：只能降低频率，不能解决配额和 39ms 主线程成本。

### P3（可优化，不阻断）

1. **撤销历史 200 步在大图上的内存风险（静态推断）**：`past` 上限 200（`src/core/store.ts:113-116`），每次地形编辑至少复制一张 40k 的 `cells` 数组；小格编辑还可能复制 360k 的 `fineCells`。Immer 结构共享会让未变数组共享，但连续 200 步仍可能保留很多大数组。未做堆测量，建议按地图面积限制历史步数或按内存预算裁剪；工作量 **0.5 天**，风险低。
2. **头像上传的 object URL 没有 revoke**：`src/components/PartyPanel.tsx:85` 创建 URL，`img.onload` 只写入 dataURL，未 `URL.revokeObjectURL`；每次上传泄漏一个图片 Blob 的 URL，直到页面关闭。加 `onload/onerror` 后的 revoke 即可；工作量 **10 分钟**，风险低。
3. **`SkillPanel` 在桌面抽屉关闭时仍然挂载**：`src/App.tsx:214-218` 用 `hidden` 隐藏，但子组件仍渲染；`SkillPanel` 仍 `useWorld/useUI` 并每次 update 重算树（`src/components/SkillPanel.tsx:15-17`）。单次成本小，但和 P2-1 叠加；改成条件挂载或 `React.memo` 即可。工作量 **10 分钟**，风险低。
4. **`render` 每次重画都重建 `terrains`/`materials` Map，并在低缩放做 9 子格聚合**：`src/scene/render.ts:522-523`、`:530-566`。这是 P1/P2 的组成部分；等底图缓存/重绘收敛后自然消失，不建议单独改。
5. **host 主包 853KB（gzip 约 287KB）触发 Vite 500KB 警告**：首屏实测 FCP 116ms（本地 preview），JSZip 97.6KB 是动态块、首屏没有请求；玩家包 304KB（gzip 104KB）。目前没有重复打包证据，不建议为了消警告拆包（会引入 waterfall 和配置复杂度）。
6. **`playerWorld` 里按 id 的 `m.objects.find` 在 seen object 上可能是 O(n²)**（`src/runtime/hostSession.ts:227`）。200 个物件时影响很小；只有物件数继续上升才值得改成 Map 索引。静态推断，不建议现在动。
7. **`MapCanvas` 有标记时每 10 秒整图重绘一次**（`src/components/MapCanvas.tsx:103-110`）。这是有意让标记淡出，10 秒一次可接受；不要改成每帧。

| `filterSkills` × 2000 | 39.1ms（约 0.020ms/次） |

jsdom 数字明显高于浏览器；但相对关系明确：**搜索/建树函数很便宜，贵的是 792 个 checkbox 无条件挂载 + 整页重渲染 + 画布重绘**。

## 同步/序列化

- 世界（200×200，含 200 物件）：JSON 7,212,188 字符；`structuredClone` median 51ms。
- 单个玩家投影：`playerWorld` median 12.2ms；投影 JSON 1,745,283 字符；`structuredClone` median 8.3ms。
- 广播：60ms 防抖（`sync.ts:845-847`）；每个已绑定玩家复制一次投影并 `postMessage`（`:372`、`:379`）。4 人时约 82ms 的主线程投影+克隆，已经超过 60ms 的间隔；如果玩家端还在收/画，会形成积压。
- focus 推送：`pushFocus` 立即 `send(world)`（`:840-842`），绕过防抖；focus 不常变时没事，频繁切人/暂停会重复全量投影。
- 玩家端：`setWorld(m.world)` 整份替换并重渲染（`PlayerView.tsx:124-132`）；没有增量合并。

## 内存/资源

- **好的部分**：贴图缓存上限 256（`src/scene/texture.ts:12`），pending object URL 会 revoke（`:34-72`）；媒体 URL 缓存在媒体变更时统一 revoke（`src/runtime/media.ts:124-129`）；`MapCanvas`/TrialHud/NpcPanel 等定时器和监听都有 cleanup；没有发现无上限增长的监听器。
- **需要处理的**：头像上传 URL 未 revoke（P3-2）；撤销历史 200 步在大图上的内存风险（P3-1）；大图自动保存的 7.2MB/配额问题（P2-4）；`SkillPanel` 关闭时仍挂载（P3-3）。
- **未做**：浏览器堆快照、长时间试玩 30 分钟以上的 heap 曲线、线上房间带宽实测。以上内存结论中标了“静态推断”的都不是实测值。

## 明确“不要动”的过早优化

1. **不要为 198 技能搜索上虚拟滚动/复杂索引**：`filterSkills` 约 0.02ms/次，浏览器搜索输入到下一帧 8.3ms；真正贵的是树全部挂载和画布重绘。先做 P2-2 的条件渲染即可。
2. **不要拆 host 主包或改 manualChunks 来消 500KB 警告**：host 首屏 JS gzip 约 287KB、FCP 116ms；JSZip 已经是动态块且首屏没请求。拆包只会增加请求 waterfall，收益不明。
3. **不要动 24×16 这类普通地图的画布**：0.6–0.7ms/次，已经在预算内；优化应针对 200×200 适配缩放的整图路径。
4. **不要先上 WebGL/Worker 重写 `render`**：先做 P2-1 的依赖收敛、rAF 合并和底图缓存；这三步风险低、收益直接。WebGL 会带来字体、命中测试、截图和可访问性回归，不是当前性价比最高的方案。
5. **不要全局下调撤销步数**：小图 200 步没有明显问题；按地图面积/内存预算裁剪，不要影响正常创作体验。
6. **不要为了“统一”把玩家端也换成整份世界增量协议之外的重型状态库**：玩家端当前只收一份投影，先做 host 端投影增量和广播节流。
7. **不要给 `build:single` 再做额外压缩实验**：单文件 985KB / gzip 327KB，离线便携场景可接受；没有首屏阻塞证据。

## 优先级排序

1. **P1-1**：画笔/地形编辑把视野+记忆重算延后或增量（否则 200×200 图不可连续画）。
2. **P2-1**：`MapCanvas` 依赖收敛 + `React.memo` + rAF 合并 + 底图缓存（把 24–34ms 的无效重绘降下来）。
3. **P2-2**：队伍技能树收起时不挂 792 个 checkbox，并 memo 单行（把打开队伍页 110ms 降下来）。
4. **P2-4**：大图自动保存改 IndexedDB/空闲写，至少先让 7.2MB 不直接 quota 失败。
5. **P2-3**：广播节流/轻量 focus 消息先做，增量投影视线上房间需求再排。
6. **P3**：撤销内存预算、头像 URL、SkillPanel 条件挂载。

### 审阅边界

- 本文的“P1 0.23–0.27s”是 dev 页实测；生产构建会降低 React 开销，但 `store.update` 的视野/记忆扫描和 `render` 的绘制逻辑不变，量级不会消失。
- 未测：生产构建下的真实大图交互、30 分钟以上 heap 曲线、线上房间实际带宽、4 个真实窗口同时打开时的端到端延迟。建议在修 P1/P2-1 后用同一套探针复测。
