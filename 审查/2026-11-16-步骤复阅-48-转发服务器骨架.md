## P2（阻塞）

### P2-1 关房/过期后房间仍留在 RoomService，sweep 不自动跑，坏 token 还能刷新 TTL

- 位置：`server/rooms.ts:71-76` `close()` 只 `closeRoom(state)`，**不 `rooms.delete`**；
  `:99-110` `sweep()` 只有手动调用；`server/index.ts` 全文没有 `sweep` 调用；
  `:37-42` `get()` 在鉴权之前就 `entry.touchedAt = this.now()`。
- 实测：
  - `create('R','H')` → `close('R','H')` 后 `size()` 仍为 **1**；`get('R')` 仍返回
    `closed: true` 的房间。
  - 用注入时钟：`create` 在 t=0；t=90 用**错误邀请 token** 调 `join('R','bad',...)`，
    `get` 把 `touchedAt` 刷到 90；t=190 调 `sweep()` 返回 `[]`，房间还在；
    t=191 才被清掉。即未认证的坏 token 可以一直把房间续到 TTL 外。
- 影响：
  - 每次建房→关房都在 `rooms` 里留一个 tombstone；sweep 不自动跑，长驻进程会
    无限增长（`room.create` 每秒可建 60 个，见 P2-4）。
  - 关房后 `rooms.size()`/`get()` 仍非空；文档 `docs:106` “房间关闭时内存清空”
    与实现不符。
  - 坏 token 的 `join`/`relay` 可把已关房间的 `touchedAt` 刷新，sweep 更不会清。
- 是否阻塞：**阻塞**。修法：服务器在通知完 `room.closed` 后 `rooms.delete`；
  `get` 拆成“只读 peek”和“成功操作后 touch”；server 加定时 `sweep`（或关房即删）；
  对未认证请求不要刷新 TTL。

### P2-2 玩家重连时给主持端的 `peer.joined` 把 `inviteId` 发成空串

- 位置：`server/index.ts:174-180`：
  `inviteId: result.room.invites[result.binding]?.inviteId ?? ''`。
  `RoomState.invites` 的键是 **inviteId**，不是 binding；binding 对应的 inviteId
  在 `players[binding].inviteId`。
- 实测（真实 WS）：
  - 首次 join：host 收到
    `{"inviteId":"ce0-ST2D","binding":"op0NZfMv6jJe"}`；
  - 重连后 host 收到
    `{"inviteId":"","binding":"op0NZfMv6jJe"}`。
- 影响：主持端用 `inviteId → pcId` 映射找回角色卡；重连后收到空 inviteId，映射丢失。
  `isPeerJoinedPayload()` 要求 inviteId 非空，服务器下行本身就是无效握手 payload；
  后续接 host UI 会直接踩。
- 是否阻塞：**阻塞**。改为 `result.room.players[result.binding]?.inviteId`，测试断言
  reconnect 的 `peer.joined.inviteId` 等于首次 inviteId。

### P2-3 重连替换旧连接后，旧连接仍活着，仍可 relay

- 位置：`server/index.ts:109-113` `bindRoom` 直接覆盖 `entry.players[binding]`；
  `:168-180` reconnect 分支只用新 conn 绑定，**没有关闭/失效旧 conn**。
- 实测：旧 player 连接在 `room.reconnect` 成功后继续
  `room.relay { token: playerToken, payload: {type:'move'...} }`，host 仍收到
  `from: binding` 的 relay。
- 影响：同一 binding 有两个活连接；旧连接可继续用同一 playerToken 发输入，
  产生重复/落后动作；这也违背测试标题“重连替换旧连接”的语义（测试只把旧连接
  手动 `close()`，没有验证服务器主动替换）。
- 是否阻塞：**阻塞**。reconnect 成功时找到当前 `entry.players.get(binding)` 并
  `close()` 或标记 superseded；旧 conn 后续消息应 `not-allowed`/丢弃；测试断言
  旧连接发 relay 不再到达 host。

### P2-4 默认 origin 全开，速率只按连接，无全局房间/连接上限

- 位置：`server/index.ts:81-85`：`allowedOrigins` 为空时 `done(true)`；`:65`
  默认从 `ALLOWED_ORIGINS` 取，空则 `[]`；`:84` 即使配了白名单也允许
  `origin` 缺失。`:47-48` 速率是每连接 60/s；`:66` `maxMessageBytes` 默认 8MB。
- 影响：
  - 生产/演示若忘了设 `ALLOWED_ORIGINS`，任意网页都能连；`room.create` 不需要
    认证，可批量建房；没有每 IP/全局连接数/房间数上限，配合 P2-1 的房间不删，
    内存可被持续占用。
  - `maxPayload` 只限单条消息；60 条/s × 8MB 也没有总量限制；对公网默认值偏高。
  - 文档 `:156` 写“生产必须 origin 白名单”，代码默认不是安全默认。
- 是否阻塞：**阻塞**（至少作为上线前必须修的 P2）。建议：生产无
  `ALLOWED_ORIGINS` 时拒绝启动/拒绝带 origin 的连接；加全局/每 IP 连接与房间上限；
  速率和 `maxPayload` 在 `/health` 或启动日志可观察；补测试。

## 已核的安全点

- **角色/token**：server 用连接上的 `conn.role`/`conn.token` 判定，不拿 `msg.token`
  当角色；主机/玩家 token 校验在 invite/relay/close 上都存在。
- **`from`**：`server/index.ts:124-125` 任何客户端上行带 `from` 一律
  `bad-envelope`；server 下行 `room.relay` 自己填 `from: 'host'` 或 `conn.binding`。
- **relay 路由**：host 必须带 `to`（`relayShapeOk`），player 不得带 `to`；host→在线
  binding，player→host 且 host 在线；离线/错房/错 token 回 `relay-failed`。
- **关房**：host `room.close` 校验 hostToken；给 host/players 发 `room.closed`，
  `roomConns.delete`；玩家后续 relay 因 `closed` 被拒。
- **玩家断线**：`stillBound` 检查 `entry.players.get(binding)===conn`；旧连接关闭
  不会踢新连接（测试 3 通过），但新连接没有主动踢旧连接（P2-3）。
- **握手 guard**：`RoomInvitePayload`/`RoomClosedPayload` 已在 `src/protocol.ts`
  补齐，`isErrorPayload` 校验 message 为 string（47 P3 已修）。
- **maxPayload**：`ws` maxPayload 8MB；rate 60/s 每连接；存在但不够（P2-4）。
