## 1）`applyStandInRoll` 与旧组件等价性

新增 `src/components/judgmentStandIn.ts:36-67`：

- **attrs 模式**（多属性，N>1）：
  - 未齐：`rolls=[...prev, roll]`；message 为 `已掷 ${attrs[rolls.length-1]}：D${roll.sides}=${fmt(roll.value)}；再掷 ${next}`；
  - 齐：`chosen=rolls[0]`、`value=rolls[0].value`、`values=rolls.map(x=>x.value)`。
  - 旧 `JudgmentPanel.tsx` 对应分支：同样取 `rolls[0]`、同样 values、同样 message；`rollId/sides/tens/units/material/seed` 都走 `chosen`（即 `rolls[0]`），**等价**。
- **two 模式**（优/劣势）：
  - 第一颗：`done:false`，message `已掷 D${roll.sides}=${fmt(roll.value)}；再掷一颗，取${advantage?'高':'低'}`；
  - 第二颗：`taken=max/min`，`chosen=find(value===taken)`，`value=taken`、`values=all`。
  - 旧分支同样 max/min、同样 find；`rollId/sides/tens/units/material/seed` 从 `chosen` 取，**等价**；ties 时同样取第一个匹配。
- **普通单颗**：`mode=null`，`onStandInRoll` 直接 `finish({rollId: roll.id, sides:roll.sides, value:roll.value, ...})`，与旧组件单颗分支一致。
- **模式选择**：`isCheck && checkAttrs.length>1` → attrs；否则 `needTwo` → two；否则单颗。旧组件顺序同样是先多属性，再 needTwo，再单颗。`p.attack`/`p.fall`/`p.door` 无 `jump`，`dice='single'`，不会误走 two；`p.check` 单属性仍单颗（既有 P3）。
- **一处有意的行为差异**：旧组件在多属性/优劣势“最后一颗”不会先 `setStandInRolls` 再 finish；新组件统一 `setStandInRolls(step.rolls)` 后 finish。这正是失败清空需要的；成功时 pending 关闭、组件卸载，没有可见差异。

后端链路：`settlePendingJudgment` 收到的 `values` 进 `publishPendingRoll`（jump 非单骰时 values+重复 attr），`settleJump` 用 `diceValues`；代掷劣势后端实测 `used=5`、正式判定 `values=[20,5]`、`persona='witness'`；优势探针 `values=[5,20]` → `used=20`。新增测试「代掷劣势」覆盖低值；优势高值本轮用探针验证。

## 2）`afterStandInSettle` 与 React 状态顺序

源码：`judgmentStandIn.ts:69-75`：

```ts
return error ? { rolls: [], message: error } : { rolls, message: null };
```

`JudgmentPanel.tsx:56-62`：

```ts
const after = afterStandInSettle(err, standInRolls);
setStandInRolls(after.rolls);
if (after.message) setMessage(after.message);
```

- **成功**：`after.rolls` 是当前 `standInRolls`（可能不含最后 added 的数组引用），`after.message=null`，不 setMessage；`settlePendingJudgment` 成功会关闭 pending，组件卸载。没有可见的旧状态；没有清 message 的问题（组件已卸载）。
- **失败**：`after.rolls=[]`，`after.message=err`；`setStandInRolls` 和 `setMessage` 在同一个 handler 中，React 18 自动批处理，最终一次渲染是空 rolls + 新错误 message；**不会出现中间态“清空后仍显示旧 message”**。
- 若失败后 pending 仍在（例如重复 rollId、上下文错误），下一次点击从第一颗开始，不会拼成三颗；UI 状态清空，runtime 的 pending 未被 UI 改写，仍可重试。若失败是预检失败（target 不存在），runtime 已经关闭 pending，组件卸载，也不留死状态。
- **实际变异验证**：把 `afterStandInSettle` 改成永远不清空后，新增的失败清空测试变红；还原后 508 通过。说明这条测试确实覆盖失败清空，而不是只靠注释。
