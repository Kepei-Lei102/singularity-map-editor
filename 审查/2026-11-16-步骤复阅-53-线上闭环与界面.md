## P0 / P1 / P2 / P3

### P1 线上广播媒体：Blob 过 JSON 变成 `{}`

- 主持端 `playMedia(..., broadcast=true)` 在 `src/runtime/actions.ts:337` 把
  `blob` 放进 `send({ type: 'play', blob })`。
- 线上 `send` 的 world/play/stop 分支走 `transport.sendToPeer()`
  （`src/runtime/sync.ts:293-316`），`WsTransport` 再调
  `socket.send()`；`src/runtime/wsSocket.ts:51-55` 最终 `JSON.stringify(envelope)`。
- `Blob` 没有可枚举字段，实测：

  ```js
  JSON.stringify({ type: 'play', blob: new Blob(['x'], { type: 'image/png' }) })
  // {"type":"play","blob":{}}
  URL.createObjectURL({}) // TypeError: ... must be an instance of Blob
  ```

- 玩家端 `src/components/PlayerView.tsx:104` 原样 `setMedia({ blob: m.blob })`，
  `src/components/MediaPanel.tsx:57` 的 `MediaView` 调
  `src/runtime/media.ts:134-141` 的 `useBlobUrl()`；`blob` 为 `{}` 时
  effect 里 `URL.createObjectURL(blob)` 抛 TypeError，至少导致媒体显示失败/
  React 报错。线上播放因此不可用；`stop` 正常。
- 现有 `online.test` 只测 world/say，没有 play；`docs/三端分离-v0.1.md:103-105`
  的闭环示例也没有媒体。若本轮明确“线上不支持播放”，必须在 UI 侧禁用广播或在
  `send` 里显式拒绝，不能静默把 `{}` 发出去。
- 另外 `server/index.ts:80` 单条 8MB；大媒体会 1009 断开（docs:115 已写），
  属于同一路径的边界。

### P3-1 `SwitchTransport.use()` 不关闭旧传输；`close()` 可被重新订阅复活

- `src/runtime/transport.ts:63-69`：`use(next)` 只 `detachActive()`，没有
  `this.active.close()`；实测 fake transport：`aClosed: false`，旧
  `LocalTransport` 的 window/BroadcastChannel 监听还在（`transportLocal.ts:84-106`）。
- `src/runtime/transport.ts:81-88`：`onMessage()` 只把 `listening` 置 true；
  `close()` 后（`:90-95`）再次 `onMessage()` 会对已 close 的 active 重新
  `attachActive()`；实测 close 后再订阅，fake active 仍能把 seq=4 送到新回调。
  `LocalTransport.close()` 后 `onMessage()` 会重新挂 window 监听
  （`transportLocal.ts:84-89`），即“复活”。
- 当前 `src/` 里没有 `transport.close()` 调用点（grep 只在实现里），所以这是
  未触发的 API 边界；一旦线上/关房走 close 就会暴露。

### P3-2 `wsSocket.close()` 后 `open` 仍为 true，pending 靠超时收

- `src/runtime/wsSocket.ts:75-78` 的 `close()` 只置 `closed = true`，未置
  `open = false`、未清 pending。
- close 事件进 `fail()`，`src/runtime/wsSocket.ts:102-111` 先
  `if (closed && settled) return;`；显式 `close()` 后 `closed=true,
  settled=true`，直接 return，既不置 `open=false`，也不 reject/clear pending。
- 后果：显式关房/关 socket 后 `socket.open` 仍为 true，
  `WsTransport.sendToPeer/sendToHost`（`transportWs.ts:49,55`）仍会尝试发送；
  pending request 要等 10s timeout 才 reject。`online.test` 与 mutation G
  （删掉该 early return）都不咬，覆盖为空。
- 未请求回包的错误（如服务器 `relay-failed`）只进 `onEnvelope`
  （`wsSocket.ts:100`），`WsTransport.handle` 只认 `room.relay`
  （`transportWs.ts:93`），UI 收不到；玩家房间已关后仍可静默发 move/say。

### P3-3 来源校验偏“服务器可信”，测试甚至把不拒绝写成了期望

- `src/runtime/transportWs.ts:94`：主持端侧 `from` 直接取服务器给的
  `e.from`，不检查 `e.from` 是否在 `this.peers`；玩家端侧一律把任意
  `room.relay` 的 `from` 改写成 `'host'`。
- `scripts/transportWs.test.mjs:75-76` 发了一条 `from: 'b1'` 的 relay，断言
  `meta.from === 'host'`；测试标题写“只认 host 来源”，实际行为是“不拒绝，改标签”。
  服务器是唯一 relay 权威（`server/index.ts:112-115,231-248`），当前没有直接利用；
  但这是客户端边界，和文档“服务器下行 from 只信服务器”不等价。
- mutation D/C（把 host/player 的 `from` 分别改 null）能咬住，说明这条路径有
  基础覆盖；缺的是“非 host 来源应拒绝”的断言。

### P3-4 `peer.joined` 晚于首份 hello：首个 hello 被丢，最坏等 5 秒

- 玩家 `joinOnlinePlayer()` 成功后，`PlayerView.tsx:108-113` 立刻
  `listenAsPlayer()`；`sync.ts:603` 立即发第一份 hello。
- 主持端 `listenAsEditor` 的 hello 分支要求 `players.get(m.binding)` 存在
  （`sync.ts:561-565`）；`players` 由 `peer.joined` 的
  `registerOnlinePlayer()` 填充（`onlineRoom.ts:65-68`）。
- 服务器先发 `room.joined` 给玩家，再发 `peer.joined` 给主持端
  （`server/index.ts:183-184`）；跨 socket 后到达顺序不保证。若 hello 先到，
  主持端直接 return；玩家只能等 `listenAsPlayer` 的 5 秒心跳重发
  （`sync.ts:604-607`），首屏最多空白 5 秒。
- `online.test.mjs:69-73` 先 `waitFor(host.pcIdForBinding === 'pc')` 再注册
  host listener/player listener，正好避开了这个顺序，属于自证式覆盖。

### P3-5 关房/断线的 UI 收尾不足；错误文案与实际原因不符

- `PlayerView.tsx:144` 无差别拼 `加入线上房间失败：${joinError}`；
  实测关房后显示“加入线上房间失败：房间已关闭：host-closed”，语义自相矛盾。
- 玩家 `onClosed` 只清 world/media/pending、设错误（`PlayerView.tsx:72-75`），
  不关 transport、不清 `sessionStorage` 的 `ts-online-player`
  （`onlineRoom.ts:163-165` 刷新仍会重连）。实测关房后刷新显示
  “加入线上房间失败：重连失败”，没有回本地的路径，只能手动清 sessionStorage。
- 主持端 `createWsTransport` 没传 `onClosed`（`onlineRoom.ts:63-69`）；
  `WsTransport` 的 `room.closed` 只回调 `onClosed`（`transportWs.ts:89-91`），
  主持端 socket 掉线/房间过期时 UI 仍显示“已开”，邀请/关房会失败；
  `peer.left` 只删 peer（`transportWs.ts:84-87`），主持端不提示玩家掉线。
- `onOnlinePlayerClosed` 本身单 handler、无重复触发（PlayerView 一个 effect，
  非 StrictMode）；问题是覆盖“room.closed”而不覆盖 socket close。

### P3-6 本地窗口 bindings 切换时被清空，但没有通知旧窗口；旧 transport 也不 close

- `onlineRoom.ts:70-72` 开房前 `resetPlayerBindings()`，之后 `setTransport(ws)`；
  `resetPlayerBindings()`（`sync.ts:45-50`）只 `dropPeer/clear`，不向已打开的
  本地玩家窗口发 `clear`。开房后旧本地窗口停在旧 world，输入也被 host 忽略。
- `closeOnlineHostRoom()` 的 `useLocalTransport()`（`onlineRoom.ts:101`）新建一条
  local transport，旧 `WsTransport` 只被 `current.socket.close()` 关 socket，
  `offEnvelope`/handlers 没有 `close()`；与 P3-1 同源。
- 线上点“打开玩家窗口…”会 toast（`sync.ts:128`），但已开着的本地窗口不在提示里。

### P3-7 测试覆盖有空洞，且部分断言是自证式

## 八个关注点（简）

1. `Transport`/`SwitchTransport`：懒挂载、`use()` 后重挂、role 不变实测通过；

   `room.closed` 不进业务实测通过；`from` 边界见 P3-3，close/error 见 P3-2，
   peer.joined 见 P3-4。

   invite URL 的 `view=player&room&invite`、URL 清理、`playerToken` 重连、
   binding 不变均实测；关房/本地窗口收尾见 P3-5/P3-6。
4. `sync.ts`：本地默认路径未改（613 tests，本地窗口行为对照旧测试）；线上
   world/hello/say/重连走通；`play` 是 P1；广播 no-op、reset/close 见 P3-6。
5. `PlayerView`/`OnlinePanel`：实测开房 UI、邀请链接、玩家加入后地图显示、
   invite 从地址栏消失、关房后玩家收到关闭；错误文案/stale token 见 P3-5；
   无重复订阅（PlayerView 一个 effect，未用 StrictMode）。
6. `server/index.ts` + `deployment.ts`：joinUrl 带 `?view=player&room=`，邀请
   链接同源/分端口都识别为 player；`server.test` 6/6、`deployment.test` 通过。
7. CSS：见 P3-8；1728×940 与 1024×768 无横向溢出，900 顶栏挤压。
8. 测试：4 条新测试（transportWs 3 + online 1）通过；但 Switch/wsSocket/play/
