# 代码结构 v0.1

`src/` 按“谁负责什么”分四层，不按技术类型分。

## 目录

| 目录 | 放什么 | 规矩 |
|---|---|---|
| `core/` | 类型、状态仓库、工具、校验、持久化、部署、会话 | 最底层，不依赖上面三层 |
| `scene/` | 视野、感知、记忆、建筑、地形（`terrain.ts` 是地形读取唯一入口）、滑块、身份、渲染 | 只读 world，不写业务状态 |
| `rules/` | 互动结算、技能、发动、玩家同意、判定、流程 | 尽量纯函数，副作用交给 runtime |
| `runtime/` | 动作分发、窗口同步、试玩、AI、NPC、媒体、导入 | 唯一允许“干活”（写状态、开窗口）的地方 |
| `components/` | React 界面 | 只调 runtime/rules 暴露的函数 |

入口和样式留在 `src/` 根：`App.tsx`、`main.tsx`、`styles.css`。

## 依赖方向

```
components → runtime → rules → scene → core
```

反过来不许：`core` 不 import 上层，`scene` 不 import `rules`，`rules` 不 import `runtime`（`runtime/sync.ts` 是个例外，它是窗口通讯的出口，`rules/skillCast.ts` 会调它的 `pushFocus()`）。

## 测试

`scripts/*.test.mjs` 一一对应模块，名字跟目录对得上：`scripts/interaction.test.mjs` 测 `src/rules/interaction.ts`。测试用 esbuild 把入口打成一个包再 require，入口字符串写的是新路径。

## 为什么这么分

之前是平铺四十多个文件，找“技能在哪、视野在哪”要靠 grep。分成四层后：
- 想改规则结算，只看 `rules/`；
- 想加一个物件类型或渲染效果，只看 `scene/`；
- 想改窗口同步或试玩，只看 `runtime/`；
- 类型和 store 在 `core/`，谁都看得见但不该乱改。
