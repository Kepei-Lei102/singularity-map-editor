# 视野与计算增量化 v0.1

把「每次世界改动都整张图重算」改成「只重算这次改动可能影响的格」。行为不变，只改算多少、怎么复用。

涉及：`src/scene/sight.ts`、`scene/perception.ts`、`scene/memory.ts`、`scene/vision.ts`、`core/store.ts`；新增 `scene/sightIndex.ts`、`scene/dirty.ts`、`scene/visionPlan.ts`。
测试：`scripts/sight-index.test.mjs`、`scripts/incremental-vision.test.mjs`、`scripts/incremental-memory.test.mjs`。

## 一、问题

一次改动（走一格、开一扇门）在主持端要跑：

1. `withVision`：对每张图、每个玩家层，算一遍自动视野；
2. `syncMemory`：扫 `宽×高×9` 个子格，把看得见的部分同步进记忆；
3. 逐玩家投影（`playerWorld`）。

成本是**乘法**，不是加法：每张图有个固定底价（扫全图），每个玩家再叠一份（记忆层克隆/合并）。9 人 3 图就是 27 份全量工作，全落在主持人一个标签页的主线程上。

再往里看，视野本身还重复两件事：

- `visionOf` 每次调用都现建三张表：每格衰减、建筑几何、子格挡死表；
- 每格算视线时遍历**全部**建筑段（`wallSightSum`），不区分这条线到底碰不碰得到。

## 二、思路

三句话：

1. **受影响集只要包含「可能变化的格」，不需要精确。** 多算几格是浪费，漏一格是规则错误，所以一律取保守上界。
2. **全量 = 全图范围的增量。** 只保留一条实现，避免增量与全量两套逻辑漂移。
3. **只有「纯棋子移动」才收窄，其余退回全图。** 改地形、开关门、增删棋子、换队员、换图，都会改变任意一条视线的结果，不值得为它们做精细判断。

移动能收窄的依据：视野半径由预算决定（1.56 ÷ 每格最低 0.1 ≈ 16 格），`visionOf` 本来就以这个半径剪枝。所以眼睛从 A 到 B，能看见的范围变化只可能发生在「以 A 为心、以 B 为心」的两个圆盘里。

## 三、四块改动

### 1. 视野表按引用缓存、按眼高分组

三张表只和「地图内容」和「眼高」有关：几何、子格挡死表与眼高无关，建一次；衰减表按眼高各建一份（一队通常只有站/蹲两三种）。

缓存键用引用相等：immer 每次改动会换掉被改到的数组/对象，没改的保持同一引用，所以「引用变了就重算」是准确的失效条件。地图对象作 `WeakMap` 键，换图/导入后旧表自然回收。

调用点（`withVision`、交互判定里的 `sightCacheFor`）都改成传入共享表。

### 2. 墙段按格分桶

地图切 8 格一块，每段墙按它的包围盒登记进相交的桶。查一条视线时只取线段包围盒覆盖的桶，再用 `stamp` 去重（同一段墙跨多个桶只累加一次）。

判定顺序与逐段全扫完全一致，只是候选集变小。

### 3. 移动脏区

`diffWorld(prev, next)` 给出这次改了哪些棋子（带 from/to）、有没有结构变化、要不要整份重算。只用稳定 id，不记对象引用（试玩沙盒、撤销、导入都会整对象替换）。

`planVision` 把脏集翻译成「每张图要重算哪些格」：纯移动 → 两个圆盘；结构变化或世界级变化 → 整图。`withVision` 只对这些格写 fog。

脏集还收三类容易漏的变化：

- 棋子换 `pcId` 也算脏，按「原地变化」重算该棋子为心的圆盘；只看坐标/朝向/姿态会漏掉换人后的视野。
- 改 `d100` 区会改这一格的视野锥（60°/120°），算结构变化；视野和记忆都要重算。
- 自动迷雾开着时，手动改 `fog`/`views` 先保留本次手动结果；下一次有视野脏动的 update 再按自动视野整图覆盖，和整图重算的旧行为一致。要保留手动雾，必须先关掉这张图的自动迷雾。这样不会留下「手动擦掉一格，但只有这一格没按自动视野重算」的实时格。
  实现上，标记跟的是**最终落盘**的 fog 数组：`store.update` 在 `syncMemory`（独立/分组会 clone 视野层）之后重打标记；自动覆盖不删除历史数组的标记，所以 undo 恢复手动雾后仍会在下一次视野脏动时被覆盖。

### 4. 记忆按脏格同步、共享层共用一份

`syncLayer` 只处理脏区的 9 个子格、整格与材质，物件按脏区外接矩形过滤，贴图组只处理与脏区相交的；`pruneMemory` 同理，脏区外的记忆条目原样保留。

另外，共享视野模式下每个玩家层的内容与地图那份完全相同，改成共用同一份 `fog`/`seen` 数组，不再逐个 `cloneLayer`。切到「各自独立」时原有路径会给每人补一份真副本。

## 四、正确性

- **差分测试**：随机操作序列（走位、转身、蹲下、搬家具、改地形、加贴图格），每步断言「增量重算」与「整图重算」逐格一致；三种视野模式（共享/独立/分组）各跑一遍。记忆侧同样比对整份 `seen`。
- **保守上界**：只有纯移动收窄；其余一律全图。`memoryDirty` 也要认 `d100`，否则改 D100 区时视野重算了、记忆没同步。
- **时间戳字段的口径**：`observed`/`cellRevs`/`objectRevs`/`groupRevs` 是「第几次观察」，全量口径每次给所有可见格盖新 rev，增量只盖脏区。两者先后关系一致、数值会漂，所以差分测试把它们归一成「有没有值」再比，内容字段（地形/物件/贴图组）严格比。
- **无行为变化的两个提交**（表缓存、分桶）跑原有测试即可，新增测试只补充「缓存与现建表逐格一致」「分桶与全扫逐项等价（400 条随机线）」。

## 五、实测

环境：100×80 工程（454 段建筑、9 个角色、3 张图），Node 跑浏览器模块，2 核 VPS，无渲染。

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 一次改动的整条链路 | ~770 ms | ~230 ms |
| 视野重算（脏区） | ~373 ms | ~17 ms |
| 记忆同步（脏格） | ~480 ms | ~100 ms |
| 队伍 9 人视野（整图口径） | ~190 ms | ~5–40 ms |

口径说明：这是 Node 里量的 CPU，不是浏览器帧时间；浏览器侧只做了手测（操作体感可接受），没有量化数据。剩下的大头是逐玩家投影与整包序列化，不在本次范围。

## 六、没做的

- **增量传输**（只发变化的格）与**增量投影**：需要给世界加版本号、保存每玩家基线，是另一件事。
- **权威服务器**：不省计算量，只换执行位置，且与「服务器不保存地图」的现有约束冲突。
