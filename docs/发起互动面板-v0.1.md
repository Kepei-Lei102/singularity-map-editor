# 发起互动面板 v0.1（2026-11-14）

把「动作 → 检定 → 物件状态 → 账本」接成主持人能点的一条路。公共动作库仍然只给判定口径，效果留在模组自己的物件档案里。

## 一条链路

1. **编辑地图**：选中物件 → 检查器里的「互动（模组）」。
2. 先建档案，再加「动作 × 本物件」，给大成功／成功／失败／大失败各选一个本物件状态；留空＝这一档没有预置效果。
3. **备团／带团／试玩**：同一个物件 → 「发起互动」。
4. 选角色、选动作，按动作库的口径填骰点，点「看结果」。
5. 预览只显示档位、逐项骰点和状态从哪到哪；改骰点/角色/动作/骰势/物件状态、切地图、改角色属性、改互动映射或状态名都会让旧预览失效。点「确认，落账」前还会核对预览时的输入快照，不一致就要求重新看结果；预览旁有「取消预览」，取消不动世界。只有确认才真的改状态并写一条 `PhysicalEvent`。

## 数据放在哪

`MapObject.interaction?: ObjectInteraction`：

```ts
interface ObjectInteraction {
  material?: string;   // 作者备注；v0.1 的效果查找按物件 + 动作 id
  tags?: string[];
  overrides: {
    actionId: string;                        // src/rules/actions.json 的 id
    outcomes: Partial<Record<Tier, number>>; // 档位 → 目标 state 下标
  }[];
}
```

- **不补进 `actions.json`**：动作库是跨模组的公共资产，物件是每个模组自己的东西；把“砸橡皮泥”写进公共库会让公共资产背所有模组的知识。
- 一个物件一个动作一份四档表，物件本身已经决定了材质／上下文；`material/tags` 先留字段，留给以后按材质/标签复用的映射，不参与 v0.1 查找。
- 旧存档没有这个字段就是“没有互动档案”，不解包、不猜默认。旧档里坏掉的动作/未知档位/越界状态/重复动作由 `repairWorld()` 清掉：`actionId` 去首尾空格，重复动作以第一条为主、后一条只补空档、同档冲突保留第一条，一条可用档位都没有的映射也删掉；材质备注不是文字或标签里有非文字项也清掉。清完没有可用动作就整份档案删掉，不把效果硬塞到第一个状态。
- `states` 为空是物件本身非法，`repairWorld()` 不会替作者编状态；这时 `checkWorld()` 会直接报错，需要作者补状态。

## 动作库怎么接

`src/rules/actionLibrary.ts` 把公开动作库的原始列转成 `CheckSpec`：

| 动作库「判定口径」 | 面板行为 |
|---|---|
| 单属性 | 一个属性掷一次 |
| 并集（或） | 每个属性各掷，任一过就算过 |
| 交集（与） | 每个属性各掷，全部都过才过 |
| 交集（三检定叠加） | 每个属性各掷，每一项都要过 DC（作者对【涉水】的口径：分别过 20，失败一个就算失败；走 `and`，不是 `sum` 的合计过 DC） |
| 多来源不同（视环境） | **v0.1 不接**：要按角色解锁来源取口径 |
| 双方对照检定 | **v0.1 不接**：要拿对方属性拼点 |
| 仅见证者裁决 | **v0.1 不接**：不掷骰，先由见证者定档 |
| 待补 | **v0.1 不接**：动作库本身没有判定属性 |

能直接掷的有 148 条（186 条总数 − 13 条多来源 − 17 条仅见证者裁决 − 4 条待补 − 1 条拼点 − 3 条单属性但没填属性 = 148）。面板动作下拉只列这些；动作库里的其余条目仍然可以在编辑模式挂效果，等口径接上再用。

## 骰点与预览

- v0.1 固定 **D20 区**：属性 ÷5 取区值，DC 20。D100 招式等技能层再接，不在这一版混进来。
- 正常一颗骰；优势／劣势每个属性填两颗，逗号隔开，走 `resolve()` 的取高／取低。
- 动作库的「判定依据」是散文，里面常有情境条件（比如【舞蹈】有经验才是优势）；v0.1 不解析这些散文，由主持人用「骰势」下拉决定。
- 极值按 `tierOfRoll()`：D20 掷 20 大成功、掷 1 大失败；预览直接显示档位。
- 预览不落账；只有「确认，落账」调用 `commitObjectInteraction()`，而且确认的必须是当前这组输入（地图/角色/六维/动作/骰点/骰势/物件状态/互动映射/状态名都没变）。
- 预览的输入快照比对是纯函数 `interactionPreviewValid()`，不依赖 React；改骰点、换角色、换物件、改映射、改状态都能在 node 测试里咬住。面板 UI 另用 jsdom + react-dom 做最小接线测试（取消、改骰点失效、外部改状态失效、成功落账提示），不是视觉测试。

## 落账

一条事件，动作来源「动作库」，目标是物件：

- `check.attrs` 逐项记属性、真实骰势（`dice: single|advantage|disadvantage`）、采用骰点、两颗骰的 `rolls`、区值、总数、成败、极值（`crit|fumble|null`）；日志会写 `敏捷 15+区值10✓`，优势/劣势写 `15/10→取15+区值10`。
- 账本里的 `rolls` 跟骰势对得上：单骰必须 1 颗，优势/劣势必须 2 颗，`roll`/`used` 必须在 `rolls` 里；`checkWorld()` 拒绝不一致，`repairWorld()` 丢弃坏事件。
- `deltas` 只有物件状态这一条：`状态` 从旧状态名到新状态名；状态没变就是空数组，不造差值。
- 目标状态**真的变了**才 `stateRev` 加一，供流程图撤销判断“之后有没有别人改过”；目标状态和当前状态相同就只落一条空 delta 事件，不涨版本号。
- 只进主持人账本；玩家窗口仍然不拿 `events`。

## v0.1 边界

不做：

- 玩家窗口推送、玩家自己掷骰；
- NPC／角色作为目标的互动（心理层）；
- 信息效果（`KnowledgeEffect`）和 `applyKnowledge()`；
- ME／行动点扣除、技能来源、动作前置条件；
- 一次改多个物件或多个状态；
- 临场 AI 生成效果。

这些要么在后面的层里，要么等作者把口径拍死。v0.1 只保证一条：**主持人确认后，物件状态和账本一致。**
