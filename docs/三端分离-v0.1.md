# 三端分离 v0.1：服务器 / 主持 / 玩家

先把线上带团需要的三个角色分清楚：**服务器**、**主持端**、**玩家端**。编辑/备团不在这三端里，仍然是本地功能；开始带团时，主持端把这一场要用的世界交给房间。

这一版是**转发型**：主持端仍然是规则权威，服务器只做房间、鉴权、路由和连接生命周期。协议按以后能换成权威服务器的方向设计，但这一版不把 `store` / `trial` 搬到服务器。

## 角色和边界

| 角色 | 拿什么 | 干什么 | 不干什么 |
| --- | --- | --- | --- |
| 主持端 | 完整 world、主持 UI、玩家绑定表 | 跑规则、算玩家的投影、把每个玩家的 `world` 定向发给服务器 | 不把完整 world 广播给玩家；不把绑定凭据交给玩家 |
| 玩家端 | 一份裁剪后的 `playerWorld`、自己的判定/密码/聊天 | 显示、掷骰、移动、说话、回传输入 | 不拿主持人数据；不直接连主持端；不改别人绑定 |
| 服务器 | 房间元数据、连接、邀请/绑定 token | 建房、邀请、加入、重连、按绑定转发 | 不解析 world、不算规则、不落盘聊天/地图载荷 |

编辑端仍然是本地编辑器；它不加入房间，也不把工程上传。主持端开始带团时，把当前 `world` 作为本场快照放进内存，结束带团后再把结果/账本收回本地工程。

## 数据所有权

- **完整 world**：在主持端进程里。服务器只经手“某个玩家该看的那份 `playerWorld`”，不保存完整世界。
- **玩家投影**：仍由主持端 `playerWorld()` 计算；服务器只按 `binding` 路由，不重新裁剪。以后若换权威服务器，投影函数搬到服务器，协议不变。
- **房间**：服务器内存里的 `roomId`、`hostToken`、`inviteToken`、`binding`、连接表；不写数据库，不进日志正文。
- **断线**：玩家掉线后凭 `playerToken` 重连，拿回同一个 `binding`；主持端掉线，房间保留一段宽限时间，玩家看到“主持人离线”。

## 传输模型

业务层只认一个 `Transport`：

```ts
interface Transport {
  connect(): Promise<void>;
  send(msg: Envelope): void;
  onMessage(fn: (msg: Envelope) => void): () => void;
  close(): void;
}
```

目标有两个实现（本轮都还没接）：

- `LocalTransport`：现在的同源窗口 / `BroadcastChannel` / `postMessage`，开发和线下继续用；行为不变。
- `WsTransport`：浏览器 WebSocket，连转发服务器；线上用。

目标形态是 `sync.ts` 不再直接 `window.opener` / `BroadcastChannel`，而是调 `Transport`。**本轮还没改 `sync.ts`**：它现在仍直接用 `BroadcastChannel` 和 `window.opener`，第 2 步才拆；本地模式拆完后不经过服务器也能完整跑。

## 协议 v1

所有消息统一信封；服务器只校验信封和角色权限。`payload` 分两类：**握手字段**用下面列出的固定结构，**业务消息**仍是现有的 `SyncBody`，由主持端/玩家端自己校验。

```ts
interface Envelope {
  v: 1;
  type:
    | 'room.create' | 'room.created'
    | 'room.invite' | 'room.invited'
    | 'room.join' | 'room.joined'
    | 'room.relay'
    | 'room.reconnect' | 'room.reconnected'
    | 'peer.joined' | 'peer.left'
    | 'room.close' | 'room.closed'
    | 'error';
  requestId: string;
  roomId?: string;
  token?: string;      // hostToken / playerToken / inviteToken，按 type 定
  to?: string;         // binding；只允许主持端定向发
  from?: string;       // 只由服务器下行 relay 填来源 binding；客户端不许填
  payload?: unknown;   // 握手字段或现有 SyncBody；服务器不解析业务正文
}
```

握手 `payload` 字段：

| type | payload |
| --- | --- |
| `room.create` | 无 |
| `room.created` | `{ roomId, hostToken }` |
| `room.invite` | `{ pcId?: string }` |
| `room.invited` | `{ inviteId, inviteToken, joinUrl }` |
| `room.join` | 无（`token` 放 inviteToken） |
| `room.joined` | `{ binding, playerToken }` |
| `room.reconnect` | 无（`token` 放 playerToken） |
| `room.reconnected` | `{ binding }` |
| `peer.joined` | `{ inviteId, binding }` |
| `peer.left` | `{ binding }` |
| `room.relay` | 业务 `SyncBody` |
| `room.close` | 无 |
| `room.closed` | `{ reason? }` |
| `error` | `{ code, message? }` |

### 房间与邀请

1. 主持端连上服务器，发 `room.create`；服务器回 `room.created { roomId, hostToken }`。
2. 主持端为每个玩家发 `room.invite { pcId? }`；服务器回 `room.invited { inviteId, inviteToken, joinUrl }`。主持端把 `inviteId → pcId` 映射留在自己这边，服务器不需要知道角色卡。
3. 玩家打开 `joinUrl`，发 `room.join { roomId, inviteToken }`；服务器回 `room.joined { binding, playerToken }`，同时给主持端 `peer.joined { inviteId, binding }`。
4. 主持端用 `binding` 给这个玩家发投影：`room.relay { roomId, token: hostToken, to: binding, payload: { type: 'world', world: ... } }`。
5. 玩家输入回主持端：`room.relay { roomId, token: playerToken, payload: { type: 'move', dx, dy } }`；服务器转给主持端并带 `from: binding`。
6. 玩家刷新：用 `room.reconnect { roomId, playerToken }` 拿回同一个 `binding`，主持端重发一份 `world`。

`inviteToken` 一次性使用，绑定成功后作废；丢了就由主持端重新生成邀请。`hostToken` / `playerToken` 只存在内存或 `sessionStorage`，不写进 URL、不写日志。

### 服务器路由规则

- 连接建立时先不定角色；第一条 `room.create` / `room.join` / `room.reconnect` 才把角色钉死。消息里的 `from` 一律不信，客户端上行带 `from` 直接拒。
- `room.relay` 只允许：
  - 主持端 → 本房间某个 `binding`；
  - 玩家端 → 本房间主持端。
- 主持端不能发给别的房间；玩家不能发给别的玩家；未知 `type`、超大 `payload`、未知/失效 token 一律 `error`。
- 服务器不打印 `payload` 正文，不把 `playerWorld` 落盘；关房/过期会删掉房间状态和 `roomConns`。
- 房间 TTL 12 小时，服务器每 60 秒扫一次；`peek` 不刷新 TTL，坏 token 不能续房。
- 默认只允许 `localhost:5178/5179` 和 `127.0.0.1:5178/5179`；生产必须显式配 `ALLOWED_ORIGINS`，非浏览器客户端要 `allowNoOrigin`。
- 默认上限：1000 个房间、2000 条连接、单条 8MB、每连接 60 条/秒。

## 目标结构（分步落地）

不复制整个 `src/`，只加边界。

**本轮已落地**：`src/protocol.ts`、`server/rooms.ts`、`server/index.ts`、`scripts/protocol.test.mjs`、`scripts/server.test.mjs`、`scripts/serve.mjs`。

**还没落地**：`src/runtime/transport*.ts`、`hostSession.ts`、`host.html`/`player.html`/`editor.html` 入口。下面列出的是目标结构，没建的文件不要当成已有。

```
src/protocol.ts            信封、type、角色权限、房间/邀请状态机（纯函数）
src/runtime/transport.ts   Transport 接口
src/runtime/transportLocal.ts  现有窗口的本地实现
src/runtime/transportWs.ts     浏览器 WebSocket 实现
src/runtime/hostSession.ts 玩家绑定、投影、主持端会话（从 sync.ts 抽）
server/                    Node WebSocket 转发服务器（不 import React）
  index.ts                 连接、角色、邀请/加入/relay/close
  rooms.ts                 内存房间表（RoomService）
```

`sync.ts` 最终只当门面：业务消息 ↔ `Envelope` ↔ `Transport`。主持/玩家 UI 先共用同一个 Vite 应用，后面再拆 `host.html` / `player.html` / `editor.html` 入口。

服务器现在这样跑：

```bash
npm run server
# 默认 ws://localhost:8787；PORT / HOST / PLAYER_ORIGIN / ALLOWED_ORIGINS / MAX_ROOMS / MAX_CONNECTIONS / MAX_MESSAGE_BYTES 可覆盖
```

服务器只做了转发骨架：建房、邀请、加入、玩家重连、双向 relay、关房。主持掉线时这一版直接关房并把 `room.closed { reason: 'host-disconnected' }` 推给玩家，还没有宽限重连。

## 迁移顺序

1. **边界文档 + 协议纯函数**：信封校验、角色权限、房间/邀请状态机，先不接真 socket。
2. **抽 Transport**：`LocalTransport` 包住现有窗口行为，`sync.ts` 改用接口；先给现在的本地窗口行为补适配测试，不能只靠现有测试全绿。
3. **抽 hostSession**：绑定、投影、消息分发从 `sync.ts` 挪出，行为不变。
4. **Server MVP**：WS 建房/邀请/加入/玩家重连/双向 relay/关房；先用内存房间，不做持久化。**已落骨架**，还差把主持端/玩家端接上去。
5. **接 UI**：主持端带团时选“线上房间”；玩家端用邀请链接加入；开发默认仍走本地。
6. **拆入口/部署**：`host.html` / `player.html` / `editor.html`，共用 `src/protocol.ts` 与 `src/runtime`；最后才拆三个 app/repo（如果真需要）。

战斗 v0.2（流血/中毒/眩晕）放在第 2 步之后：规则落 `rules/`，命令走新传输，不再往 `trial.ts` 里堆。

## 安全不变量

- 玩家端永远拿不到完整 `world`；投影只由主持端（以后是服务器）生成。
- 服务器不信任消息里的 `from`、`roomId`、`binding`；以连接和 token 为准。
- 邀请 token 一次性；主持/玩家 token 不落 URL、不落日志。
- 服务器只保存房间元数据，不保存地图、聊天、判定正文。
- 本地模式不开 socket；线上模式不把 `hostToken` 发给玩家端。
- WS 生产必须 `wss://`，有 origin 白名单、payload 大小上限、基本速率限制。

## 还没定/以后再说

- 房间码长度、邀请有效期、主持掉线宽限时长（这一版主持掉线直接关房；房间默认 12 小时过期）。
- 玩家账号/官网登录：先房间码 + token，账号以后接。
- 服务器权威化：等转发型跑顺，再把 `playerWorld()`、规则结算和状态搬进服务器。
- 房间持久化/回放：先不做，主持端本地账本仍是最终记录。
- `requestId` 幂等/重放：转发型 MVP 先不做，后续按 E 组口径补；服务器先只做基本速率限制和 payload 大小上限。
