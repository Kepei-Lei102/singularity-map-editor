# 三端分离 v0.1：服务器 / 主持 / 玩家

先把线上带团需要的三个角色分清楚：**服务器**、**主持端**、**玩家端**。编辑/备团不在这三端里，仍然是本地功能；开始带团时，主持端把这一场要用的世界交给房间。

这一版是**转发型**：主持端仍然是规则权威，服务器只做房间、鉴权、路由和连接生命周期。协议按以后能换成权威服务器的方向设计，但这一版不把 `store` / `trial` 搬到服务器。

## 角色和边界

| 角色 | 拿什么 | 干什么 | 不干什么 |
| --- | --- | --- | --- |
| 主持端 | 完整 world、主持 UI、玩家绑定表 | 跑规则、算玩家的投影、把每个玩家的 `world` 定向发给服务器 | 不把完整 world 广播给玩家；只把玩家自己的邀请/绑定发给本人 |
| 玩家端 | 一份裁剪后的 `playerWorld`、自己的判定/密码/聊天 | 显示、掷骰、移动、说话、回传输入 | 不拿主持人数据；不直接连主持端；不改别人绑定 |
| 服务器 | 房间元数据、连接、邀请/绑定 token | 建房、邀请、加入、重连、按绑定转发 | 不解析 world、不算规则、不落盘聊天/地图载荷 |

编辑端仍然是本地编辑器；它不加入房间，也不把工程上传。主持端开始带团时，把当前 `world` 作为本场快照放进内存，结束带团后再把结果/账本收回本地工程。

## 数据所有权

- **完整 world**：在主持端进程里。服务器只经手“某个玩家该看的那份 `playerWorld`”，不保存完整世界。
- **玩家投影**：仍由主持端 `playerWorld()` 计算；服务器只按 `binding` 路由，不重新裁剪。以后若换权威服务器，投影函数搬到服务器，协议不变。
- **媒体索引**：玩家窗口收到 `world` 后要把自己的媒体索引换成这份世界的 `media`（`mediaId → 内容存储名`）；本地窗口同源能直接读 IndexedDB，但不换索引会按 `mediaId` 找错文件。
- **房间**：服务器内存里的 `roomId`、`hostToken`、`inviteToken`、`binding`、连接表；不写数据库，不进日志正文。
- **断线**：玩家掉线后凭 `playerToken` 重连，拿回同一个 `binding`；这一版主持端掉线直接关房，宽限重连还没做。

## 传输模型

业务层只认一个 `Transport`；`Envelope` 只活在 `wsSocket.ts` / `protocol.ts`，不渗进规则和 UI。

```ts
interface Transport {
  role: 'host' | 'player';
  kind: 'local' | 'ws';
  hasBroadcast: boolean;
  openPeer(binding: string, url: string): boolean;
  bindPeer(binding: string, source: MessageEventSource | null): boolean;
  bindingFor(source: MessageEventSource | null): string | null;
  hasPeer(binding: string): boolean;
  peerClosed(binding: string): boolean;
  dropPeer(binding: string): void;
  sendToPeer(binding: string, msg: SyncMsg): boolean;
  sendToHost(msg: SyncMsg): boolean;
  broadcast(msg: SyncMsg): void;
  onMessage(fn: (msg: SyncMsg, meta: TransportMessageMeta) => void): () => void;
  close(): void;
}
```

两个实现：

- `LocalTransport`：同源窗口 / `BroadcastChannel` / `postMessage`，开发和线下默认走这条；行为保持改造前不变。
- `WsTransport`：浏览器 WebSocket，房间内按 `binding` 定向 relay；线上用。

`sync.ts` 已经通过 `SwitchTransport` 只认 `Transport`：本地窗口先起，点「线上房间」后把收发切到 `WsTransport`，`listenAsEditor` / `listenAsPlayer` 的订阅不用重挂。建房、邀请、加入、重连这些**房间生命周期**在 `onlineRoom.ts`，不塞进 `Transport.openPeer`（本地是同步开窗，线上是异步出邀请链接，语义不同）。

## 协议 v1

所有消息统一信封；服务器只校验信封和角色权限。`payload` 分两类：**握手字段**用下面列出的固定结构，**业务消息**仍是现有的 `SyncBody`，由主持端/玩家端自己校验。

```ts
interface Envelope {
  v: 1;
  type:
    | 'room.create' | 'room.created'
    | 'room.invite' | 'room.invited'
    | 'room.join' | 'room.joined'
    | 'room.relay'
    | 'room.reconnect' | 'room.reconnected'
    | 'peer.joined' | 'peer.left'
    | 'room.close' | 'room.closed'
    | 'error';
  requestId: string;
  roomId?: string;
  token?: string;      // hostToken / playerToken / inviteToken，按 type 定
  to?: string;         // binding；只允许主持端定向发
  from?: string;       // 只由服务器下行 relay 填来源 binding；客户端不许填
  payload?: unknown;   // 握手字段或现有 SyncBody；服务器不解析业务正文
}
```

握手 `payload` 字段：

| type | payload |
| --- | --- |
| `room.create` | 无 |
| `room.created` | `{ roomId, hostToken }` |
| `room.invite` | `{ pcId?: string }` |
| `room.invited` | `{ inviteId, inviteToken, joinUrl }` |
| `room.join` | 无（`token` 放 inviteToken） |
| `room.joined` | `{ binding, playerToken }` |
| `room.reconnect` | 无（`token` 放 playerToken） |
| `room.reconnected` | `{ binding }` |
| `peer.joined` | `{ inviteId, binding }` |
| `peer.left` | `{ binding }` |
| `room.relay` | 业务 `SyncBody` |
| `room.close` | 无 |
| `room.closed` | `{ reason? }` |
| `error` | `{ code, message? }` |

### 房间与邀请

1. 主持端连上服务器，发 `room.create`；服务器回 `room.created { roomId, hostToken }`。
2. 主持端为每个玩家发 `room.invite { pcId? }`；服务器回 `room.invited { inviteId, inviteToken, joinUrl }`。主持端把 `inviteId → pcId` 映射留在自己这边，服务器不需要知道角色卡。
3. 玩家打开 `joinUrl`（`?view=player&room=…&invite=…`），发 `room.join { roomId, inviteToken }`；服务器回 `room.joined { binding, playerToken }`，同时给主持端 `peer.joined { inviteId, binding }`。主持端用自己留着的 `inviteId → pcId` 把 binding 对到角色。
4. 主持端用 `binding` 给这个玩家发投影：`room.relay { roomId, token: hostToken, to: binding, payload: { type: 'world', world: ... } }`。
5. 玩家输入回主持端：`room.relay { roomId, token: playerToken, payload: { type: 'move', dx, dy } }`；服务器转给主持端并带 `from: binding`。
6. 玩家刷新：用 `room.reconnect { roomId, playerToken }` 拿回同一个 `binding`，主持端重发一份 `world`。

`inviteToken` 一次性使用，绑定成功后作废；丢了就由主持端重新生成邀请。`hostToken` / `playerToken` 只存在内存或 `sessionStorage`，不写进 URL、不写日志。

### 服务器路由规则

- 连接建立时先不定角色；第一条 `room.create` / `room.join` / `room.reconnect` 才把角色钉死。消息里的 `from` 一律不信，客户端上行带 `from` 直接拒。
- `room.relay` 只允许：
  - 主持端 → 本房间某个 `binding`；
  - 玩家端 → 本房间主持端。
- 主持端不能发给别的房间；玩家不能发给别的玩家；未知 `type`、未知/失效 token 回 `error`；超大 `payload` 由 `ws` 直接按 1009 断开，不会先回一条 `error`。
- 服务器不打印 `payload` 正文，不把 `playerWorld` 落盘；关房/过期会删掉房间状态和 `roomConns`。
- 房间 TTL 12 小时，服务器每 60 秒扫一次；`peek` 不刷新 TTL，坏 token 不能续房。
- 默认只允许 `localhost:5178/5179` 和 `127.0.0.1:5178/5179`；生产必须显式配 `ALLOWED_ORIGINS`，非浏览器客户端要 `ALLOW_NO_ORIGIN=1`。
- 默认上限：1000 个房间、2000 条连接、单条 8MB、每连接 60 条/秒。

## 目标结构（分步落地）

不复制整个 `src/`，只加边界。

**本轮已落地**：协议与服务器（`src/protocol.ts`、`server/rooms.ts`、`server/index.ts`、`scripts/serve.mjs`）、本地传输（`transport.ts` / `transportLocal.ts` / `messages.ts`）、线上传输与房间（`wsSocket.ts` / `transportWs.ts` / `onlineRoom.ts`）、最小线上入口（`OnlinePanel.tsx` + `PlayerView` 的加入/重连）、以及 `protocol/transport/transportWs/online/server/rooms/consent` 这些测试。本地窗口仍是默认，点「线上房间」才切 WebSocket。

**还没落地**：`src/runtime/hostSession.ts`、`host.html`/`player.html`/`editor.html` 入口。下面列出的是目标结构，没建的文件不要当成已有。

```
src/protocol.ts            信封、type、角色权限、房间/邀请状态机（纯函数）
src/runtime/messages.ts     业务消息形状（SyncBody / SyncMsg）
src/runtime/transport.ts   Transport 接口
src/runtime/transportLocal.ts  现有窗口的本地实现（已落地）
src/runtime/transportWs.ts     浏览器 WebSocket 实现（已落地）
src/runtime/wsSocket.ts        WebSocket + request/response（已落地）
src/runtime/onlineRoom.ts      建房/邀请/加入/重连/关房（已落地）
src/runtime/hostSession.ts 玩家绑定、投影、主持端会话（还没抽）
server/                    Node WebSocket 转发服务器（不 import React）
  index.ts                 连接、角色、邀请/加入/relay/close
  rooms.ts                 内存房间表（RoomService）
```

`sync.ts` 现在是业务门面：消息形状已经挪到 `messages.ts`，低层收发走 `Transport`；绑定、投影、判定分发还留在 `sync.ts`，下一步再抽 `hostSession.ts`。线上最小闭环先共用同一个 Vite 应用：主持端点「线上房间」开房、每个角色生成邀请；玩家打开邀请链接进 `?view=player&room=…&invite=…`。后面再拆 `host.html` / `player.html` / `editor.html` 入口。

服务器现在这样跑：

```bash
npm run server
# 默认 ws://localhost:8787；PORT / HOST / PLAYER_ORIGIN / ALLOWED_ORIGINS / MAX_ROOMS / MAX_CONNECTIONS / MAX_MESSAGE_BYTES / ALLOW_NO_ORIGIN 可覆盖
```

线上联调：

```bash
npm run server          # 8787
npm run dev:host        # 5178，带团 → 右上角「线上房间」→ 开房 → 生成邀请
npm run dev:player      # 5179；玩家打开 5178 生成的邀请链接
```

主持端连服务器地址默认是 `ws://当前主机:8787`，部署时用 `VITE_SERVER_URL` 钉死；服务器拼邀请链接用 `PLAYER_ORIGIN`。

这一版线上只同步 `world`、判定、输入和说话；媒体「同步给玩家」在线上禁用（`Blob` 过不了 JSON relay），主持人仍可用「▶ 仅主持人」在本机播放。主持端 socket 掉线或房间过期会切回本地窗口并提示；玩家收到 `room.closed` 后会清掉 `playerToken`，刷新回本地入口。

服务器只做了转发骨架：建房、邀请、加入、玩家重连、双向 relay、关房。主持掉线时这一版直接关房并把 `room.closed { reason: 'host-disconnected' }` 推给玩家，还没有宽限重连。

## 迁移顺序

1. **边界文档 + 协议纯函数**：信封校验、角色权限、房间/邀请状态机，先不接真 socket。
2. **抽 Transport**：`LocalTransport` 包住现有窗口行为，`sync.ts` 改用 `SwitchTransport`；本地窗口行为补了 `transport.test.mjs`，原有 `deployment.test.mjs` 也改成认新边界。**已落**；`WsTransport` 也已接上，线上入口见第 4/5 步。
3. **抽 hostSession**：绑定、投影、消息分发从 `sync.ts` 挪出，行为不变。
4. **Server MVP**：WS 建房/邀请/加入/玩家重连/双向 relay/关房；先用内存房间，不做持久化。**已落骨架 + 最小线上闭环**。
5. **接 UI**：主持端带团时选「线上房间」，按角色发邀请链接；玩家端打开链接加入；本地窗口仍是默认。**已落最小版**，还没做房间列表/更细的在线状态。
6. **拆入口/部署**：`host.html` / `player.html` / `editor.html`，共用 `src/protocol.ts` 与 `src/runtime`；最后才拆三个 app/repo（如果真需要）。

战斗 v0.2（流血/中毒/眩晕）放在第 2 步之后：规则落 `rules/`，命令走新传输，不再往 `trial.ts` 里堆。

## 安全不变量

- 玩家端永远拿不到完整 `world`；投影只由主持端（以后是服务器）生成。
- 服务器不信任消息里的 `from`、`roomId`、`binding`；以连接和 token 为准。
- 邀请 token 一次性；主持/玩家 token 不落 URL、不落日志。
- 服务器只保存房间元数据，不保存地图、聊天、判定正文。
- 本地模式不开 socket；线上模式不把 `hostToken` 发给玩家端。
- WS 生产必须 `wss://`，有 origin 白名单、payload 大小上限、基本速率限制。

## 还没定/以后再说

- 房间码长度、邀请有效期、主持掉线宽限时长（这一版主持掉线直接关房；房间默认 12 小时过期）。
- 玩家账号/官网登录：先房间码 + token，账号以后接。
- 服务器权威化：等转发型跑顺，再把 `playerWorld()`、规则结算和状态搬进服务器。
- 房间持久化/回放：先不做，主持端本地账本仍是最终记录。
- `requestId` 幂等/重放：转发型 MVP 先不做，后续按 E 组口径补；服务器先只做基本速率限制和 payload 大小上限。
