# 贴图组 v0.1

状态：编辑器可画、可保存在工程里；主持人本地窗口和玩家窗口都已能画出来，物件自带贴图也能替换物件外观。线上房间已能把玩家 `world` 里用到的图片按需分块拉过去；广播播放的媒体同步仍等下一步。

## 是什么

`CellGroup` 是「任意一组 1/3 小格 + 一张图」。它只改外观，不是地形、不是材质、不是物件：

- 不影响移动、通行、视线、迷雾、高度、D100 和任何判定；
- 不占用大格位置，也没有矩形/十字之类的限制；
- 一个组可以铺任意形状，格子是 `GameMap.fineCells` 的 key；
- 组有 `z`：地面 0–9，贴花 10–19；同一处后画的组按 `z` 覆盖；
- `objectId` 表示物件自带贴图：替换物件外观，不占地面；一个物件最多一个组，格子固定等于物件脚印，地面绘制会跳过这些组。

## 编辑

左侧「工具 → 贴图」，选「分组贴图」；右侧「贴图组」：

1. 点「＋ 新建」建一个空组，默认 `z = 0`；
2. 在地图上拖动，往组里涂 1/3 小格；Shift 拖动擦掉；
3. 可以改名、改层、选已有图片或上传一张图；
4. 「铺法」：`fill` 把整张图铺满整组的包围盒；`contain` 保持比例完整放进去；
5. 一次拖动只算一步撤销；新建、删除、改贴图也各自是一步。

同一个组换了图不会改动画在地图上的格子；删图只解掉贴图，格子还在。媒体库删除一张图时，会顺手把它在实时组、记忆组和各视野记忆里的贴图引用清掉（文件本身留给撤销）。

普通物件（不含墙/门和触发区）在右侧「物件」检查器里有「外观（物件贴图）」：

1. 从已有图片里选一张，或上传一张；
2. 可以改「铺满物件 / 完整放进物件」和不透明度；
3. 「清除贴图」删掉物件组，物件回退到原来的颜色方块；删媒体后留下的空物件组也能用这个按钮清掉；
4. 上传的图片和贴图在同一个事务里，撤销一次回到上传前。

## 渲染

画布顺序：地形底色 → 材质色 → 贴图组（按 `z`）→ 高度暖色 → 网格 → 物件。地面/贴花贴图用 `Path2D` 只裁出组里的小格，所以组可以任意形状，图按整组包围盒铺，不会被单格切开。

物件贴图不做小格裁剪：一张图铺进物件脚印矩形。有贴图时不再画原来的彩色方块，透明像素直接露地形，所以透明 PNG 可以做出异形家具；`fill` 拉伸，`contain` 等比留白；投影保留，选中框和浮签照旧。可开合的物件在“不挡路”状态仍只画虚线轮廓，不画贴图。文字标签保留名字、状态和高度，有贴图时不叠图标，并加暗描边。

玩家窗口里，实时组只画 `fog === 1` 的格子；灰区（`fog === 2`）再画一遍 `seen.groups` 里记得的组，地形也按记忆判断，所以贴图不会在“看见 → 转灰”时突然消失。

物件贴图在灰区走 `SeenObject.texture`：整件物件按最后一次看见时的那一版画，不按小格分版本；物件只要还有一部分看得见，整件快照就更新成当前贴图/ghost，完全转灰后保持旧版，重新看见才换新版。灰区的 `ghost` 也一起记：开着的门继续画虚线，不画贴图。

图片按媒体 ID 懒加载：`world.media` 只有元数据，真正的文件在浏览器 IndexedDB；同一媒体 ID 换了内容会换存储名，缓存不会拿旧图。图片加载完会通知画布重画。

## 玩家载荷

- 实时层（`fog === 1`）只发看得见的组格子；一个组只要有一格可见就发；
- 整组都看见时才带整组 `bounds`。只看见一角时不带整组 `bounds`，渲染按可见格子的包围盒铺图，会在可见区域里局部拉伸；这样不会把看不见部分的形状/范围带给玩家；
- 灰区（`fog === 2`）从 `seen.groups` 发记得的格子和它被看见时的那一版贴图，带记得格子的 `bounds`；记得的格子玩家本来见过，不会再泄露新范围；
- 同一组在灰区会按贴图版本分开记：换图只影响当前看得见的格子，灰区格子留在它上次被看见时的旧图里；等这些格子再次看见，才换成当前版本；
- 组名和媒体文件名对玩家统一改成「贴图」，只留 `id`、贴图媒体 `id` 和存储名；
- 只带实时组和记忆组用到的 `world.media` 元数据，没用的图片不出现；
- 物件组（`objectId`）只发非 ghost 的当前可见物件那一组，带 `objectId`、可见小格和贴图媒体；ghost 物件不发组，玩家标签靠 `objects.textured` 维持；隐藏或看不见的物件不发；
- 灰区物件的贴图和当时是否 ghost 跟着 `seen.objects` 走，不跟当前物件组；ghost 物件不画外观图，所以它的贴图媒体也不发给玩家；
- 物件贴图和地面/贴花贴图共用媒体表，玩家只收当前用得上的图片元数据；
- 本地玩家窗口和主持人同源，能直接读同一份 IndexedDB；玩家窗口收到 `world` 后会用自己的 `media` 表把 `mediaId` 换成内容存储名，本地才真正读得到；线上房间按下面的「线上按需传输」拉文件，不再靠同源。

## 存档与校验

- 旧 v2 工程导入时补 `groups: []`、`seen.groups: []` 和 `seen.groupRevs: {}`，不升 `world.version`；
- 记忆组内部用 `sourceId` 指回原组、`textureKey` 标贴图版本；旧工程里没有 `sourceId` 的记忆组会在同步时归一成「原组~版本」，同版本并回一组；玩家包里这两个字段会剥掉，记忆组 `id` 换成不透明的 `mh` 短哈希，名字仍然只暴露「贴图」；
- schema 校验：组 ID 唯一、`cells` 是指定地图范围内的小格 key 且不重复、实时组的 `texture.mediaId` 是合法 ID 且在 `world.media` 里、`fit` 只能是 `fill` / `contain`、`opacity` 在 0–1、`objectId` 必须指向本图物件；记忆里的旧贴图允许不在当前媒体表（旧工程还能读），删媒体时会清引用；`bounds` 必须是非空矩形且在新图范围内；`sourceId` / `textureKey` 只允许出现在记忆组，`groupRevs` 的值必须是非负整数；
- 记忆物件存 `texture` 和 `ghost`；旧工程缺这两个字段按“没有贴图 / 不是 ghost”处理，不升 version；
- 扩图/改尺寸时组格子跟着平移，越界格子丢掉；`bounds` 按剩下的格子重算，不照搬旧图矩形；物件被裁掉时它的物件组和记忆里的物件组引用一起删掉；
- 复制地图时组跟着复制，物件组的 `objectId` 重映射到副本物件，玩家记忆不带过去。
- 物件组是物件外观的派生数据：一个物件最多一个组，格子始终按物件脚印重算（移动、改尺寸、房间复位、滑块移动、扩缩图、复制地图、导入都会跟着校正）；通用「贴图组」列表不显示物件组，也不允许当普通组涂。
- `ghost` 是玩家载荷里的派生字段，host 渲染不信任工程里持久化的 `MapObject.ghost`，一律按当前 `blocksWhen` 推。

## 线上按需传输（v0.1）

线上房间的 `world` JSON 里只有媒体的 `id / key / mime / size`，没有文件。玩家收到 `world` 后按存储名请求，主持端按 binding 发字节：

- 玩家 → 主持：`asset-request { requestId, keys }`。一次最多 32 个 key，多了分批。
- 主持 → 玩家：`asset-start { requestId, key }`，表示文件确实存在、马上开始发这个 key；玩家收到后把 120 秒排队 watchdog 换成 30 秒 inactivity timer。
- 主持 → 玩家：`asset-chunk { requestId, key, mime, index, count, data }`，每块 256 KiB 原文、base64 后约 350 KB；单个文件上限 64 MB。
- 发完发 `asset-end { requestId, key, bytes }`；失败发 `asset-fail { reason: missing | forbidden | too-large | read-failed }`。
- 主持端只发这个 binding 当前 `world.media` 里有的 key；玩家要别的 key 一律 `forbidden`。世界一推就换允许集合，换图/换视角后旧 key 收走。
- 全场共用一个节流钟：一块约 45 ms，约 22 块/秒，给 world/判定/说话留出服务器每连接 60 条/秒的余量；分块走现有 ws relay，服务器不解析 payload。
- 玩家 clear/unmount 会给在途请求发不带 key 的 `asset-cancel`（整批停）；从请求发出到收到 `asset-start` 最多等 120 秒，之后某个 key 30 秒没有新块会发带 key 的 `asset-cancel`，只停那一个文件，并按 `read-failed` 处理，避免 pending 永久卡住。同一 binding 10 秒内最多 30 次请求。reset 不撤销已经开始的 IndexedDB 写入：文件可能已落盘，但不会再进贴图缓存或 `onReady`。
- 120 秒是 v0.1 的单请求排队上限：4 个 64 MB（约 46 秒）和 200 个 1 MiB（单人约 54 秒）都在内；32 个 64 MB（约 371 秒）会超。多人同时拉大世界时，上限按同一连接 22 条/秒估算；4-C 若要承诺更大的量，再改成按全局队列动态算或批次串行，不把这个数当无限。
- allow 在最后一块之后、`asset-end` 之前被撤掉时，主持端不发 end，玩家丢掉刚收的 bytes 并按 `forbidden` 处理；短暂换图/换视角会缺一会儿图，下次 world 再请求。
- 玩家收到 `v:` 内容哈希的 key 会校验 SHA-256；不符最多重试一次，第二次仍不符才报 `read-failed`。拼好的文件写进同一个 IndexedDB，`mediaChanged()` 会让贴图缓存重新取图。
- 本地窗口不走这套：同源直接读 IndexedDB，行为不变。

## 贴图缓存与上传孤儿

- 画布的图片缓存最多留 256 张，超过时丢最旧的一张；命中会把它挪到最新，避免频繁重读。
- 图片加载成功或失败后立刻 `revoke` 临时地址；`clearTextureCache()` 会清掉图片、加载中、失败记录和临时地址。
- 切工程、媒体文件变化（导入/恢复/清理）都会清空缓存；还在加载的旧图回来不会再落进新缓存。
- 加载失败不会无限重试；缓存清空后允许重试；图片解码失败也算失败。
- 删除正在播放的媒体会先停掉播放，广播中的会同步给玩家停。
- 上传途中换了工程、退出编辑/进试玩、选中换了或物件已经没了时，媒体不会硬挂到物件上。如果这份文件是这次上传**新写进浏览器**的，会问用户要不要删掉；删之前会检查同一标签页的工程、撤销和备份是否还在引用，有引用就不删。如果同内容文件原来就有，不动它。用户不删的话，文件留给「清理用不到的文件」统一处理。
