# 物理互动：统一范式 v0.1

> 配套代码：`src/rules/interaction.ts`（结算与施加），测试：`scripts/interaction.test.mjs`（10 条）。
> 数据来源：《奇点之后》动作库 V2.1.1（186 个动作）、规则书 V1 的【判定难度】【检定规则】【大成功】。

## 一句话

**动作是数据，检定是纯函数，效果只写状态，连带影响由派生层现算。**
门关了不能通过，不需要写代码——因为"挡不挡路"本来就从状态现算。

## 编辑器现在有什么（接入点）

| 已有 | 在哪 | 这次怎么用 |
|---|---|---|
| `MapObject.state` / `states[]` | `types.ts` | 状态就是效果唯一的落点 |
| `blocksWhen` / `opening.openStates` | `types.ts` | 状态 → 挡路，声明式 |
| `physical.blocksMove/blocksSight`、`pushable/heavy` | `types.ts` | 特例属性的挂点 |
| `blocksMovement(o)` | `src/scene/perception.ts` | **纯函数**，读 `state`，不缓存 |
| `architectureBlocksSight` | `architecture.ts` | 同上，视线 |
| `setObjectState` / `stateRev` | `actions.ts` | 施加层，已带撤销用的版本号 |
| `publishJudgment` | `judgments.ts` | 骰子公布，已有 |
| `Effect {mapId,objectId,toState}` | `types.ts` | 流程图里的旧效果，可复用为转移记录 |

缺的只有中间一层：**把"谁对谁做了什么动作、掷了什么、改了什么状态"绑成一条记录**。

## 四层

```
声明层  ActionDef      动作卡：属性、模式、消耗、四档效果表
   ↓
结算层  resolve()      纯函数：骰点 + 属性 → 档位（不碰世界）
   ↓
施加层  applyTransitions()  只写 object.state 与 stateRev
   ↓
派生层  blocksMovement()    纯函数：state → 能不能过、看不看得见
```

一次互动就是一条 `Interaction`：动作编号、发起者、目标、每个属性的骰点、档位、转移列表、时间。

## 为什么"门的连带影响"不用插代码

链条是这样闭合的：

1. 门是 `MapObject`，`states = ['关闭','打开']`，`blocksWhen = [0]`。
2. `blocksMovement(o)` 的实现是 `o.blocksWhen.includes(o.state)`——**现读，不是缓存**。
3. 通行、视线、寻路、`reachable` 全部走这个函数。
4. 所以只要 `o.state` 从 0 变成 1，**下一帧所有查询自动变**。

结论：**状态本身只写数字；"状态→后果"必须是声明式字段（`blocksWhen`、`openStates`、`physical`），不能是 if。**
新增一类后果，加一个字段 + 一个纯函数，不加一处散落的条件判断。

## 什么时候才真的需要写代码

三类，别的都别写：

1. **状态表达不了的物理**：推（`pushable/heavy`）、攀（高度+助跑空间）、拖、抛。这些挂 `executor` 字段，交给专门执行器，默认路径不走它们。
2. **跨对象不变量**：两人合力才推得动、门被卡住后打不开、机关要两个都按下。这类写成"前置条件"函数，不在效果里写。
3. **时间性**：持续几回合、冷却、每回合掉落。挂在 `cost` 或独立的 `duration`，由会话时钟推进。

## 动作卡字段（从动作库映射）

| 动作库的列 | 卡里的字段 | 说明 |
|---|---|---|
| 编号 / 动作名称 / 动作分类 | `id` / `name` / `category` | 直接照搬，编号就是主键 |
| 检定属性 | `check.attributes` | `【敏捷】/【观察】` → 两项 |
| 判定口径 | `check.mode` | 单属性→`single`；并集（或）→`or`；交集（且）→`and`；「和」→`sum` |
| 判定依据 | `evidence` | 原文照抄，给主持人看的，不进代码 |
| 动作释义 | `intent` | 边界说明，用来判"这个动作能不能这么用" |
| — | `outcomes` | **动作库现在没有这一列**，要补：四档各一组状态转移 |
| — | `cost.me` | 原始动作那页有 ME 消耗，技能增强版另算 |

**最大的缺口**：动作库有 186 条属性与口径，但**没有结构化的效果**（「动作释义」是散文）。
补法是在动作库加一列「效果（四档）」，格式：`成功→目标状态+1；失败→不变；大失败→目标状态−1`。
没有这一列，卡就只能停在"能掷骰"，不能"掷完改变世界"。

### 智慧个体：两条路，不能混

动作库对这类互动只给了一个名字——「双方对照检定」（全文只有 1 条：【决斗】）。规则书另有一条 DC 修正。
**两条都实现，各有各的用途：**

| 情形 | 用哪条 | 算法 |
|---|---|---|
| 动作库标了「双方对照检定」 | 拼点 | 两边各掷 D20 ＋ 属性区值，高者赢；平手算没做成 |
| 其它与智慧个体互动的动作 | 规则书 DC 修正 | 最终 DC ＝ 20 −（A 区值 − B 区值） |
| 与物件、环境互动 | 固定 DC | 20（D100 区 100） |

规则书的例子照抄进测试了：A 魅力 13、B 魅力 12 → DC 19，A 骰点 ≥6 即过。

**优势／劣势的来处**（规则书同一条的后半句）：D20 区属性差 ≥4、D100 区 ≥20 时，
**优势方拿【优势检定】，劣势方拿【劣势检定】**；差不到阈值就都掷一颗。代码里 `sideAdvantage()` 自动分，
不靠见证者手动勾。

### 一次检定就四个槽（术语定版）

原来「双重检定」这个词跟「优势／劣势」撞在一起，会出现「优势的双重检定劣势」这种没法读的表达。
拆成两个互不相干的槽，词也分开：

| 槽 | 取值 | 说明 |
| --- | --- | --- |
| 尺 | D20 区 / D100 区 | D20 区：属性值 = 属性 ÷ 5，骰 D20，DC 20；D100 区：属性值 = 属性，骰 D100，DC 100 |
| 属性 | 1 项 / 2 项 / 3 项… | 每项各掷自己的骰 |
| 合并 | **或** = 过一个就好 / **与**（＝和）= 都要过 | 动作库里的「双重检定」说的就是「与」 |
| 骰 | 一颗 / **优势骰** = 两次取高 / **劣势骰** = 两次取低 | ←—— 只有这一槽用「优势／劣势」这两个字 |

**优势骰是按属性挂的，不是整组挂的。** 作者口径：一个人一段时间内魅力检定有优势，
这时要过魅力＋智慧，那就是魅力掷两次取高、智慧只掷一次。代码里 `AttrSpec.dice` 就是干这个的。

于是：

- 搜索 = 「与 2 项」（敏捷、观察各一颗，都要过）
- 带优势的搜索 = 「优势骰 · 与 2 项」（敏捷掷两次取高、观察掷两次取高，各自加自己的区值，都要过）

### 其它检定

- 单属性／或／与／和：属性值 ＋ 骰点 ＋ 主动调整值，**达到** DC 20（D100 区 100）就算过。
- **主动调整值＝临时加值**，默认 0。见证者慎用，只在当场有明确理由时给。
- **优势骰／劣势骰**：掷两次取高／取低，**只**指骰面。动作库【舞蹈】的依据已经把这事写死了：
  「玩家有舞蹈经验，骰点为优势。否则为劣势判定」——所以优势来源常常是具身表演，不是技能。
- **极值覆盖总数**：D20 区掷 20 直接算过、掷 1 直接算不过，不看属性高低（区值 0 的人掷 20 也能过）。
  D100 区走 000 补投链。
- **大成功顶替**：多项属性（或／与）里，任一属性掷出大成功，**整次判定就算完全成功**，
  哪怕另一项没过。作者原话：「一个大成功可以顶俩。力量+敏捷，敏捷大成功直接完全成功」。
  大失败没有这个效力：只判死它自己那一项。
- **极值只作用于它自己那一项**：一个「或」检定里，敏捷掷出 1 只判死敏捷，观察过了照样算过。

### 特大成功只有 D100 区有

| 尺 | 极值 | 规则 |
|---|---|---|
| D20 | 20 | 大成功。没有补投 |
| D20 | 1 | 大失败 |
| D100 | 000 | 补投 D20：1 特大失败、2–10 大失败、11–19 大成功、20 特大成功 |
| D100 | 其它 | 照常数比 |

代码里 `tierOfRoll(scale, roll, critRoll)` 就这一条分支：D20 区即使传了补投也不出特大。

### 要不要过检定，可以交给见证者

17 条动作是「仅见证者裁决」（【偷窃】【嘴炮】【伪造】这类）。这类动作**不掷骰**，`resolve()` 返回 `success: null`，
由见证者在面板上直接定。代码里不留默认值，避免"没掷骰就默认失败"这种自动判定。

### 多重检定的真实例子（动作库原文）

- **并集（或）·【教授】**：属性【魅力】/【智慧】，依据「讲得动人取魅力，讲得清楚取智慧」——两项任一过就算过。
- **交集（与）·【读心】**：属性【观察】/【智慧】，动作库原话是「【观察】+【智慧】双重检定」——
  按上面那张表，「双重检定」就是「与 2 项」，两项都得过。代码里不要再叫双重检定。
- **交集（三检定叠加）·【涉水】**：属性【意志】/【力量】/【敏捷】，依据「存在纯走水下步行过水的解，这种情况三个检定叠加，见证者具体负责呼出多少个检定」。
- **双方对照检定·【决斗】**：属性【魅力】→对方【意志】，依据「魅力拼点对方意志，成功则进行决斗」。
- **多来源不同·【双持】**：属性【敏捷】/【观察】，依据「【敏捷】/【敏捷】；【敏捷】；【观察】/【敏捷】」——同一个动作在不同来源技能下用不同属性，所以要按角色已解锁的来源取，不能取并集。

## 效果表：四档各给一组转移

同一个目标，不同动作给不同的表——这是这个范式最省事的地方：

| 动作 | 检定 | 大成功 | 成功 | 失败 | 大失败 |
|---|---|---|---|---|---|
| 撬锁（巧力） | 智慧＋敏捷（与） | 打开，且锁无痕 | 打开 | 不动 | 锁芯卡死（锁着＋配不出钥匙） |
| 撬锁（暴力） | 力量＋敏捷（与） | 打开 | 打开 | 不动 | 锁芯卡死＋动静传出去 |
| 撞门 | 力量 | 打开，门轴断 | 打开 | 不动且响（触发事件） | 门卡死＋自己受 1 点伤 |
| 开锁（电子） | 智慧 | 打开且留后门 | 打开 | 不动 | 触发警报 |

表里只有 `toState`，没有代码。**通行后果哪一档都不写**——它在派生层。

## 效果分两级：动作卡默认表 ＋ 物件档案覆盖

同一条【砸】，落在橡皮泥和非牛顿流体上不是一回事。所以：

```
动作卡 outcomes（动作库给的默认四档表）
   ↓ 物件档案有覆盖就整档替换
ObjectProfile { material, tags } ＋ OutcomeOverride[]
```

- 覆盖是**整档替换**，不是合并：换就换清楚，别指望叠加。
- 匹配键：材质（`material`）或自定义标签（`tags`：可破坏、可点燃、精密）。
- 没匹配上就走动作卡默认表。
- 代码：`resolveOutcomes(def, tier, profile, overrides)`。

**为什么不把效果补进动作库本身**：动作库是跨模组的公共资产，物件是每个模组自己的东西。
把"砸橡皮泥"写进公共动作库，等于让公共资产背所有模组的知识。分开之后，模组只写自己那几条覆盖。

## 现挂：见证者当场加的效果，但不是代码

预置表覆盖不到的情况（大失败罚多重、正确决策撞上大失败该轻罚），由见证者当场定。
走 AI 对话框时，模型返回的**不是代码，是受限效果**：

| 允许的 kind | 作用 | 字段 |
|---|---|---|
| `object-state` | 改物件状态（走 blocksWhen 派生） | mapId / objectId / toState / reason |
| `object-move` | 挪位置 | mapId / objectId / x / y / reason |
| `object-enable` | 开关物件 | mapId / objectId / enabled / reason |
| `token-status` | 给角色挂状态（被注意／流血／昏迷） | mapId / tokenId / label / reason |

四条规矩，缺一条就不许现挂：

1. **白名单**：只认上表四种，多一个字段就整条拒绝（`parseAdHoc`）。
2. **可撤销**：状态改动带 from/to，`stateRev` 自增，沿用现有 undo。
3. **可回放**：落成一条 log，带 reason（"大失败：门被撞变形"）。
4. **见证者审过才生效**：走编辑器已有的审核通道（`AdvisorChange` 那套），AI 只是提议。

为什么不直接执行生成的代码：模型输出不可信、无法撤销、无法回放、玩家窗口拿不到同样的结果。
真需要新规则的，走"物件档案覆盖"，不走运行时造代码。

## 派生约束层

| 约束 | 输入 | 消费者 |
|---|---|---|
| 通行 | `blocksMovement(o)` | 棋子移动、`reachable`、推车、滑块 |
| 视线 | `architectureBlocksSight` + 高度 + 地形衰减 | 视野、秘密范围、媒体触发 |
| 承载 | 物件高度与 `blocksWhen` | 攀爬、翻越、落点 |

状态变更后不需要"传播"，因为没人缓存结果；`reachable` 这类短期缓存按 `stateRev` 作废即可。

## 日志与回放

`【撬锁】A → 门（关闭→打开），D20+13=22 ≥ 17，成功`。

## 事件账本（2026-11-10 落地一部分）

上面这套范式已经有代码形状了，在 `src/core/types.ts` 的 `PhysicalEvent`：

| 字段 | 含义 |
|---|---|
| `actor` / `target` | 谁对谁（`pc` / `npc` / `object` / `terrain`），`target` 可以没有（移动、感知） |
| `action` | 动作名 + 来源（动作库 / 技能 / 临场） |
| `check` | 尺（D20/D100）、每个属性**各掷了什么**（单骰/优势/劣势）、合并方式、总数、档位。属性判定带 `dc`；攻击用 `kind:'attack'` + `band`（落空/命中/大成功/特大成功），没有 DC，也不拿 0 当哨兵 |
| `deltas` | 每一处状态变化：谁、什么、从 X 到 Y（HP / ME / 位置 / 状态 / 移动点 / 物件字段） |
| `knowledge` | A 得到的信息：只改认知，不改世界 |
| `ruling` | 见证者当场写的裁定 |

**句子是事件的渲染结果，不是输入。** `declareText()` / `resultText()` / `eventText()`
在 `src/rules/events.ts`，日志、判定记录、事件卡片以后都读同一份事件。现在长这样：

`攻击者 对 目标 发起了【攻击（钝器）】，掷 D100 → 【攻击（钝器）】命中：目标 的 HP 从 6 改为 3`

- 已接：**攻击**（HP、倒地/濒死、目标没血条的情况）、**开门**（物件状态）、**撬锁/暴力开锁**（锁具＋门状态、失败不写假 delta）。
- 未接：移动、跳跃、感知、推、治伤、撞门、电子开锁。它们现在还是各自拼一句中文；接的时候只补 `deltas`，句子不用重写。
- 玩家窗口不拿事件账本（`playerWorld` 里清空）：那是主持人侧的记录，别让人顺着历史反推隐藏物件的状态。
- 存档里 `events` 只留最近 200 条（`EVENT_CAP`）；**日志不截断**，每条日志带 `eventId` 指回事件，超出 200 条被挤掉的事件只剩日志里那句渲染文本。
- 只记真变了的状态：落空不写「HP 从 6 改为 6」；打已经倒地的人不写「状态从 昏厥 改为 昏厥」；真没变化时用 `note` 说明原因。

### 门锁的记法（2026-11-11）

门锁是门上的第二位状态，不另起物件、不存钥匙：

```ts
lock?: { kind: 'physical' | 'electronic'; locked: boolean; keyable: boolean }
```

- 没有 `lock` ＝ 没锁；`locked:true` ＝ 锁着。撬开后 `locked:false`。
- **卡死＝`locked:true, keyable:false`**：门照旧关着挡路，但「配一把对应的钥匙」这条路没了，界面只剩「只能强行打开」。不是第三种开合状态。
- 不存钥匙、不存每次尝试的历史，所以反复撬不会让存档长大。以后真要做随身钥匙，钥匙物件上存 `doorId` 指回门即可。
- 门不单独带 DC：用标准 DC（D20 区 20／D100 区 100）。巧力要【开锁副手】，暴力谁都能试；两颗骰都过才算成功（`merge:'all'`），**任何一颗大成功都算整条过**（「一个大成功顶俩」）。
- 门至少要有一个「打开」状态；schema 会拒空 `openStates`，检查器也不让取消最后一个。否则会出现“锁解了但门还关着”这种假成功。
- 骰子进玩家窗口：智慧、敏捷各掷一颗，见证者确认后落账；玩家不在电脑前就见证者现掷，同样落成正式判定。两颗都进正式判定记录和日志（`roll.values` / `roll.attrs`），玩家确认后也看到两颗，不只记第一颗。
- 卡死之后再失败（比如强行打开又掷出 1）：只写 `note`，不再重复写「锁着→卡死」这条假 delta。

为什么要它：以后临场生成意料之外的分支，读的是这份结构化状态，而不是拿自然语言反推。

## 心理互动层（预留）

同一个 `Interaction`，目标从 `object` 换成 `token`，状态从"门的开关"换成"角色的心理状态档"。
`resolve()` 一行都不用改：属性、模式、DC 修正都一样。
差别只在效果表多一列"谁能看见这个变化"，以及**不能自动生效**——心理状态要主持人确认，物理状态不要。

## 前置条件与范围（补完）

动作库没有前置条件栏，但条文里带前提：【点火】要“目标满足易燃物属性”，且默认拥有者身上带安全打火机；
【撬锁】要物理锁具、【开锁】要电子锁具。所以卡上单列，不让见证者临场记。

| 字段 | 作用 |
|---|---|
| `preconditions[]` | `targetHasProp`（易燃物／物理锁具…）、`targetStateIn`、`targetEnabled`、`withinRange`、`actorHas`（打火机…） |
| `range` | `{ cells, shape, targetLimit }`；动作库只在「怪物招式库」有范围，玩家动作多数到接卡时再定 |
| `checkPreconditions()` | 纯校验，只报哪些没满足，不改世界、不掷骰 |
| `describeUnmet()` | 一句话给见证者看：“目标不是「易燃物」；发起者没有「打火机」” |

## 【幸运】单列一条规则

幸运不是第七个属性：动作库【教唆】【隐匿】的判定依据用了它，但六维表里没有，
所以它走**纯骰**，不套 DC、不加属性、不吃主动调整值。

| 尺 | 失败 | 成功 |
|---|---|---|
| D20 | 1–10 | 11–20 |
| D100 | 1–50 | 51–000 |

**幸运骰不触发 000 特殊链**：掷 20／000 不算大成功，掷 1 也不算大失败。
代码里 `resolveLuck()`／`luckThreshold()`，且极值判定会跳过幸运那一项。

## 计数绑角色，不绑动作

带计数的动作（【恐吓】【测谎】：前 3 次劣势、7 次后 +2/+10）里，次数记在**角色**身上。
同一个动作，A 用得多不影响 B。调用方传的是“这个角色用过几次”的 `uses`。
